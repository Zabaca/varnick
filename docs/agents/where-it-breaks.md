# Where Launchy breaks

Failure modes that come from how Launchy is built: what a change can break even when it follows `CODING_STANDARDS.md`. `launchy-reviewer` checks every diff against this list (its Correctness axis); `launchy-planner` names the items a plan touches.

**Saved state** (`SessionStore.swift`, `Settings.swift`)
- `sessions.json` decodes as one `State`; a decode failure falls back to `State()` and silently drops every open tab and recent session. A renamed or retyped field breaks old files the same way a new non-optional one does.
- `Settings.storeSkipPermissionsIfAbsent` tells an existing install by `sessions.json` existing, so it must run first in `applicationDidFinishLaunching`, before `makeModel` (its first `SessionStore.save` creates the file) and before anything reads `Settings.shared`; the relay and the command-line modes never call it. Skip permissions is stored once because a value worked out on each read would turn on at the second launch.

**The claude command line** (`ClaudeSession.startClaude` and the headless relay's `launch` in `HeadlessLaunch.swift`; the script, shell arguments and argument list are `ClaudeCommand`, in `Packages/LaunchyPeer`)
- claude runs via the account's login shell (zsh, bash or sh from the account record, else `/bin/zsh`; the relay uses the account's own shell) as `-l -i -c 'exec claude "$@"'`, with its arguments passed positionally: user text (prompt, agent name, paths) goes in as its own argument, outside the script string.
- New sessions use `--session-id <id>`, resumes `--resume <id>`. The prompt follows `--` and has a trailing space when it has no whitespace (`ClaudeCommand.arguments`, `operand`), so a prompt that starts with a dash is a prompt, and one that is a command's name (`doctor`) isn't that command.
- The environment is deliberately minimal; claude gets only what is set for it, nothing inherited from the launcher.
- The folder of `LAUNCHY_SESSION_FILE` (`PaneFolder`) must exist before claude starts: the hook's `cat >` fails into a missing one, and the pane silently stops following `/clear` and `/resume`. Claude panes still running in zmx from before the `scratch` folder was renamed `panes` write through a link at the old name (`PaneFolder.migrateOldScratchFolder`), so that link stays until none of them runs.
- The turn hooks (ADR 0010, `ClaudeCommand.hookSettings`) are in the same `--settings` as the SessionStart hook, so a value claude rejects would cost the session file too. Each must print nothing and exit 0 (`UserPromptSubmit`'s output goes to Claude, `PermissionRequest`'s is a decision) and write only when the word changes, since the turn file's date is when that turn began, except `UserPromptSubmit`, which always writes working: a prompt begins a working period, and after Esc or a Deny the file still says working, so a write only on a change would leave the age counting from before it; they find the file from `LAUNCHY_SESSION_FILE`'s folder, so that variable stays beside it. Their SessionStart entries are only `clear` and `resume`: a compaction can come mid-turn, and the pane that starts claude writes the first word. `clear` writes working instead of waiting over a `plan` turn: approving a plan with "clear context" denies it, so no `PostToolUse` follows (untested whether that `clear` runs the hook). The permission entry's regular expression must keep matching every tool but `AskUserQuestion` and `ExitPlanMode`, which have entries of their own, or a dialog marks twice or not at all. `PostToolBatch` is only for a session that can show a dialog (Skip permissions off), so a pane started again with another setting gets other hooks. The transcript correction (`PaneFolder.corrected`, shared by the app and both relays) is why `ClaudeSession.checkTurn` must watch the transcript's date too, and why `UserPromptSubmit` rewrites the file after an Esc. It matches Claude Code's undocumented interrupt text (`TranscriptReader.stoppedAt`), so a Claude Code that words it differently stops the correction with no error. `TranscriptReader.pendingBackground` reads the `turn_duration` field names (workflows only) and the English start of the notifications' `<summary>`: a renamed one, or a last `turn_duration` before the 64 KB tail, shows the card as Stopped with no error. Background shells, agents and teammates come from `.launchy-stop` (option 01, Background work): `PaneFolder.runningTasks` reads `background_tasks`' `type` strings (`shell`, `subagent`, `teammate`), `status`, `id` and `description`, so a renamed field or type, or a Claude Code that stops listing them, shows none with no error; they are subtracted by the notification's `<task-id>` (a shell's at any time, a subagent's only after the stop file's date) and a stop by the user by the English plain text that names the agents' descriptions. A teammate is busy or idle from the lead's transcript (`TranscriptReader.busyTeammates`, read incrementally in the app, whole on every ask in a relay, which is a new process each time): the `idle_notification` JSON (`from`, `timestamp`) in the `<teammate-message teammate_id=…>` wrapper of a user entry, the `Agent` tool call's `input.name` and `input.description` (the description is how a task is matched to a name), and the `SendMessage` call's `input.to`; a change to any shows an idle teammate as busy (a card stuck in Running) or a busy one as idle, with no error. An end in mid-turn arrives as an `attachment` entry, which `TranscriptReader.pendingBackground` must keep reading beside the user entries, or a shell that ended while a later turn ran shows as running. The `Stop` entry must write by rename and run in the same event as the turn word (the freshness window `PaneFolder.staleWindow` assumes it), and `StopFailure`'s entry must keep re-dating the file, or an API error drops the shells.
- `/rename` names are read from Claude Code's undocumented transcript format (`TranscriptReader.customTitle`, `TranscriptSession.customTitle`: `custom-title` entries with a `customTitle` field), whole-file once and then from the last 64 KB each time the transcript changes, whenever the pane has a title record (whatever the switch says). A renamed entry type stops it with no error: the pane shows the generated title, or Claude's own, instead of the user's name.

**App panes** (`ClaudeSession.startApp`; the contract is in the `custom-apps` skill)
- An app server's zmx session must end with its pane: `finish` kills it, but a server that exits on its own goes through `appEnded`, not `finish`, so the pane stays open to show its output.
- An app pane owns its zmx session whatever Keep sessions running says (`ownsZmxSession`): a restored pane's session must be in the launch sweep's keep set, and `finish` must kill a never-shown one's. Quit ends app servers only with the setting off (`stopAppServers`).
- The server's port is `record.appPort`, never `record.url`: the address follows navigation. A pane reconnecting to a running session must not pick a port (the server holds the old one); only a pane running the app picks, and then moves `url` to the new root. A record saved before `appPort` existed has the port only in its `url`: `settlePort` falls back to it and stores it, so never reconnect on port 0.

**Panel size** (`LauncherModel.panelHeight`, `LauncherView`)
- The panel is fixed-size, so `panelHeight` must add exactly the rows `searchContent` shows, in every branch: settings, board (fixed, like settings), tab, prompt (the prompt line, then the suggestions or the sessions listed under it), search (`?`), `?` alone (the empty state's height), command, empty field (the session list). A mismatch clips content or leaves a gap. What a query does is its `LauncherModel.Mode`, read from its first character; every branch and key handler switches over it, so none can disagree.

**Focus and keys**
- After a session ends, focusing search has to wait a tick (see `focusSearch`); focus set synchronously is dropped.
- A key handler that returns `.handled` for a key it didn't act on swallows it (Tab, arrows).
- While the session board shows (`showingBoard`), no terminal is on screen (`showsTerminal` is off, so the tab shortcuts don't act), and `SessionBoard.key` takes esc, the arrows, ↩, D and the End session key before the shortcuts: ⌘W must never reach the hidden tab's pane. Anything that shows a tab goes through `activate`, which closes the board; only the exit of the tab underneath keeps it open. The board stats each pane's turn file once a second on the main actor (cheap, like `checkConversation`) and asks zmx once, off the main actor, when it opens; nothing in its view reads a file or publishes. A paired Mac's board cards come from `peerOpenRows` less the sessions marked done (by pane id, never by conversation, or two board cards share an id), refreshed through `refreshPeersForBoard` every 5 s with a 4 s timeout so one silent Mac can't hold the others up; a pane here on a peer takes its turn from `ClaudeSession.follow`. A board card's id is the pane's, or for a paired Mac's session the id its pane would get, and a paired Mac's session is found, marked and replaced in Completed by pane id, never by conversation, which /clear moves on (`peerOpenRow`, `rebuildRecent`, `put`). A tab under the board or Settings is activated without focusing it (`activate`): a frozen card's container would take ⇧↩ as Take over.
- Done on the board ends the pane through `ClaudeSession.end`, so a session goes into Completed only in `sessionExited`, once the pane has closed; a close that doesn't happen clears the mark through `onKept`, and a conversation open in a pane drops out of Completed in `rebuildRecent`, before the save.
- Only Done takes a session off the board. A Claude pane that closes any other way leaves an ended card (`LauncherModel.ended`, saved as `State.ended`) in `sessionExited` beside Recent, once the pane is out of its tab, and never with Done (`markedDone` goes to Completed alone). The one close Recent leaves out that does leave a card is a frozen view of a session another Mac controls whose own check found it gone: `ClaudeSession.endedByUser` (read-only outside) tells the user's close, which leaves none, from that. A card on a peer that its own check found gone (not the user's close, and only `isViewOfSessionControlledElsewhere` or `opensOnCard`, `addClosed`) may only have lost a Mac that restarted and restores the session, so it goes into `remembered` and becomes a card only when that Mac's Recent names its pane id; every other close, `/exit` and claude exiting in a pane in control included, adds the card at once. Every reader of a cached listing that could clear or hide a card (`openConversations`, `peerOpenRows`, `rebuildRecent`, `remember`) goes through `listedSessions`, which leaves out a session closed here after the listing's ask was sent. Ended cards are found, replaced and dropped by pane id (`put`) or, when a conversation is open here or on a paired Mac, by conversation, in `rebuildRecent` before every save (Recent's rule, not Completed's); a paired Mac's listing of a session whose pane just closed is dropped from the cache in `noteClosed`, and a listing whose ask was sent before the close is ignored for that pane id (`closedHereAt`, `listedPaneIDs`, and in `remember`), or that rule would clear the card at once. `addCompleted` removes the ended card with the same id, so a session is never in both. Nothing else removes one, and there is no cap, so the relay decodes a longer `sessions.json`.

**Search store** (`KnowledgeBase.swift`, `HistorySync.swift`, `Embedder.swift`, `LocalReranker.swift`, `RelevanceSearch.swift`, `ModelServer.swift`)
- One WAL database (`db/launchy.sqlite`): `HistorySync` updates the search tables in place in one transaction while `FavoritesStore` reads, and the store reloads its vectors when `PRAGMA data_version` changes. Rows keep their id across syncs so ids held in the in-memory vectors stay valid; renumbering rows breaks that.
- Claude sessions (`session:` rows, built from `~/.claude/projects` transcripts, and the paired Macs' rows in `peer_sessions`) never go to any reranker: its candidates are a ranking's pages (`RelevanceSearch.filtered`), and a spoken request that reads sessions only skips the filter. A session holds the user's prompts. They stay on the user's paired Macs: a peer's prompts are copied here for Recent and search (`PeerOp.rows`), this Mac's go to a paired Mac the same way, and nowhere else, never to a reranker, TypeSafe or any other service. With Search embeddings on a server, see the model server bullet. Keep every peer row `source == FavoritesStore.sessionSource`. A prompt (anything typed without a leading `?` or `!`) never reaches a reranker, TypeSafe or a log either: it runs only the store's session queries and the chosen embedder (`listPromptSessions`), cut to 1,000 characters, and the "no results" log lines print the query, so they stay in search mode. A filter on those sessions (`SessionFilter`) goes inside the store's queries, before the cut to a count.
- MLX is shared by the whole process (the embedder, the local reranker and the text generator). Check `MLXRuntime.hasMetalLibrary` before any MLX call: without the metallib MLX aborts the app, and that ends every session in it. The first model to load sets the 64 MB cache cap (`MLXRuntime.capCache()`). Wrap loading, scoring and generating in `withError`; touch no MLX in an `init` (they run on the main thread at launch), since MLX's default error handler exits the app too.
- A model server (an OpenAI-compatible address on the tailnet; `ModelServer`, `ServerEmbedder`, `ServerGenerator`) is reached only through `ModelServer.post`. It accepts only `http` or `https` addresses whose name resolves only to tailnet (100.64.0.0/10, fd7a:115c:a1e0::/48) or loopback addresses, checked before anything is sent, and follows no redirect and no system proxy (`connectionProxyDictionary` is empty: a proxy would get the prompts and the key in the clear). The name is resolved again when the connection is made, so an answer that changes in between is a known gap; there is no IP pinning. It logs the kind of failure and the status code, never the request, the reply's body or the key (`MODEL_SERVER_KEY`, in the Keychain).
- What goes to a model server, and to nothing else (never a reranker, TypeSafe or a log; the exceptions go to TypeSafe alone and are never logged: the spoken request's text, and, with the relevance filter on TypeSafe, a spoken request's search words and the title, site and own description of its first 20 pages, as a typed search sends them; see below): with Search embeddings on a server, the searches typed (`?` ones too), the search words of a spoken request (`RelevanceSearch.withMeaning` embeds them through `embedQuery`, as the panel does), the prompts typed in the panel (cut to 1,000 characters), and every page's and session's embed text, the paired Macs' included; with Text generation on a server, a conversation's first prompt cut to 1,500 characters, and with Hey Launchy on, what the user says after the wake phrase and the kind, title, site or folder, date and description (cut to 300 characters) of the few rows read to answer it: for a page its own summary only (`Reranker.metaDescription`: never the history title, search terms or address), for a session its prompts, the paired Macs' too. Vectors from a server are stored only after a Check that passed within 10 minutes in this launch, under the one model key (`toEmbed`, `refreshSearch` and the stored `embedding_model` are unchanged, so switching either way embeds only new and changed entries).
- The fallback rule lives in `ModelServerState.place` and nowhere else: work the user waits on (a search, the sessions under the prompt line, a spoken request through `TextGeneration.generateNow`) uses a server not known to have failed and otherwise falls back to this Mac's installed model; background work (the sync, titles) needs a server that passed a Check and otherwise waits, and never loads this Mac's model; On this Mac never contacts the server. A change of the choice, or a Check that found another model, stops a sync under way (`HistorySync.SyncEmbedder.stillChosen`) and is re-read before a title's prompt is sent. A failure rests the server only for the request's own address and model (`failed(_:for:)`), and a local failure never does.
- The server embedder's vectors are compared with `EmbeddingReferences` (made-up sentences, three vectors from this Mac's model). An mlx-swift or mlx-swift-lm bump, or a change to `Embedder`'s method or prefix, can move them: rerun `Launchy --embed-reference` (it prints each fresh vector's cosine to the shipped one, 1.0 to 1e-6) and `Launchy --embed-check <address>`.
- The local reranker's row format is a contract with the checkpoint (`LayaScorer`, `LayaModel`): the question prefix, the state (query, host, title cut to 60 Unicode scalars), [MASK] replaced, right padding with [PAD], and the weights' PyTorch names. Drift lowers ranking with no error, so rerun `Launchy --rerank-eval` after touching them or bumping mlx-swift or swift-transformers. Run it on the long-row set kept locally, outside the repository, too (23 searches, rows of 28 to 512 tokens counting the prefix and [SEP], 220 of 460 past 129, with their Python MLX scores, same eval file layout) as `Launchy --rerank-eval <checkpoint> <eval file> <reference file> --max-diff 1e-3`. The eval's rows are too short for the sliding band, so a wrong band only fails there, and only at that bar: an off-by-one band moves these rows by 9.6e-3 and passes the default 0.01, where a correct build is off by 2.3e-4. The MRR bar is relative to the reference file's own MRR, so any set with its reference scores works. `tokenizer.json` is pinned by SHA-256 and checked before swift-transformers reads it, which `fatalError`s on files it doesn't support.
- The TypeSafe request carries each page's title, site and own description (`Reranker.metaDescription`: the first blank-line-separated part of the description field, unless it is the history title, the search terms or the URL). The rest of that field, the URL and the tags never go: URLs can carry private ids and login tokens.
- On this Mac never sends anything to TypeSafe for the filter, including after a failure: a failed local check shows unfiltered results with the warning, and a failed load turns the filter off until Retry.
- The checkpoint and the eval data encode the user's browsing history: never commit, upload or log them (no titles, queries, scores or file contents), and import only the five files in `LayaCheckpoint.files`.
- `refreshSearch` deletes every row it didn't write and `toEmbed` deletes every embedding key it doesn't know, so session rows and session embeddings must be written and counted as current in those same passes, or the next sync removes them. Both, and `sessionsDigest`, take their sessions from `sessionEntries`, which adds the peers' rows without the folder check (the host made it); a new source of session rows goes through it.
- A page row can carry a host too (`favorites.host`): the paired Mac that alone visited it, when none of the entry's URLs is a page or bookmark of this Mac's own. A paired Mac's pages (`peer_pages`, `peer_search_terms`, `peer_page_meta`) are built into search rows through `entries`, merged by URL with this Mac's before grouping, so `refreshSearch`, `toEmbed` and `archiveSignature` count them current and nothing deletes them. Pulled rows never go into `pages`, `search_terms` or `page_meta`: the relay passes on only this Mac's own, and removing a Mac removes exactly its rows. A request for a page's description (`toFetch`) goes only to a URL this Mac holds (`Entry.fetchURL`), never to one only a paired Mac visited.
- `pages`, `search_terms` and `page_meta` carry `changed` (real unix milliseconds, never whole seconds times 1000: a stamp below a cursor already handed out is skipped), which the relay's cursor orders by. The hot upsert (`upsertSQL`, `upsertTermSQL`) runs for every Chrome row each minute and must move `changed` only when a value `pages` sends changes; `store` stamps every description it writes.
- SQL built from user text uses bound parameters; FTS queries quote or escape user input so stray quotes or operators don't throw.

**Sessions and tabs**
- Ending a session keeps the tab model consistent: removing the last pane removes the tab, and `activeTab`, `sessionSelection` and `renamingTab` never point at a removed tab.
- Nothing inside a SwiftUI view update (`body`, `makeNSView`, `updateNSView`) may block on a subprocess, spin the main run loop (`Process.waitUntilExit`, `RunLoop.run`) or publish model state: a spun run loop re-enters SwiftUI mid-update (a restored split kept the search-size height and stranded a web view). Start panes after the update, as `TerminalHost` does.
- Session titles (`SessionTitles.swift`, `ClaudeSession.checkTitle`): a result for a conversation the pane has left, or for a pane that ended, must be dropped, or the conversation is titled twice; /clear and /resume hand the record to the conversation left behind (`checkConversation`). The prompt and the title are never logged, and neither is an error's body. With Text generation on a server (see "What goes to a model server"), a failure that isn't the model's (no answer, a timeout, a status other than 200, a reply that can't be read, one that ran out of tokens before any text) never sets the failed mark, which is permanent for the conversation; only a reply that cleans up to nothing does. A pane on a peer (`isOnPeer`) reads no transcript here: its host titles it.
- Whether a session can be resumed is computed from its directory path (non-alphanumerics become `-`), so changing how `directory` is set changes which sessions resume.

**Peers** (`SSHRunner.swift`, `MacPeerHost.swift`, `Peers.swift`, `Packages/LaunchyPeer`; ADR 0007)
- `Packages/LaunchyPeer` is built by both the app and the Linux relay (`launchy-peer`), so a change there must compile on Linux too: `swift build` in the package on a Linux machine with Swift (swiftly puts it at `~/.local/share/swiftly/bin/swift`), with anything Darwin-only under `#if os(Linux)` or `#if canImport(Darwin)`, and no AppKit, SwiftUI, CryptoKit or app type. The app reaches it through `public`, since `package` access stops at the path dependency: a new declaration the app uses needs `public`, and a struct it builds field by field a public initialiser. The Mac's own answers are `MacPeerHost` (the `PeerHost` seam); the support folder is `SupportFolder`, and on a Mac its path never moves.
- Every call to another Mac goes through `SSHRunner`, which builds the `ssh` command for three kinds: `run` for a request (off the main actor, with a deadline), `terminalCommand` for a pane's terminal and `stream` for a command that runs until cancelled (a card's `watch`). Never a bare `Process` for `ssh`, never `waitUntilExit`, never from `body`. A Mac that isn't in the peer list is contacted only by Find Macs and Add.
- A change to a request or reply shape bumps `PeerProtocol.version`, or two builds misread each other with no error. The relay parses a request's version before anything else, so keep `PeerRequestHead` to `v`, `op` and `by`. The exception is `upgrade` and `restart` (`PeerProtocol.answersAnyVersion`): the frozen shapes and envelope are in the doc comments of `PeerMaintenanceAsk`, `PeerUpgradeReport`, `PeerRestartReport`, `PeerReply` and `PeerRequestHead`. A reply to them sets nothing but the envelope keys and its own report, since an older asker decodes the whole `PeerReply`, and is `ok` even for a refusal, since `PeerClient.verdict` drops the body of a failed one.
- A socket or control path over 103 bytes fails to bind with no useful error, and a long `ControlPath` also needs ssh's 17-character temporary suffix (`PeerSocket.path`, `SSHRunner.controlPath` check both). A path with a space goes into an ssh `-o` value in double quotes.
- On a Mac the relay never writes UserDefaults, since the app may be running. Only a hello with `pair` set adds a peer, so a refresh doesn't undo a removal.
- A headless host (`Sources/launchy-peer` in the package; its install root, state rule and installer are in ADR 0009, which also says to reinstall it at every protocol bump, now its row's Upgrade button; see the upgrade bullets below) answers everything but a hello only to a Mac in `peers.json` (or a device, below), checked first, and never calls a Mac back. A `peers.json` that isn't a list, or can't be read, fails a pairing instead of being replaced. Point a check at a copy of the binary, never at `~/.launchy`.
- A Mac's SSH command (`PeerLink.remoteCommand`) tries the macOS link, then `$HOME/.launchy/launchy-peer`, and `exec`s it so the relay is the ssh's own process. Keep it one POSIX literal that a request is appended to: `scripts/install-peer.sh` reads it from `PeerSocket.swift` at HEAD to verify with the very command a Mac sends.
- A peer's request runs the launch snapshot, not the build folder (`LaunchSnapshot`, `PeerLink.refresh`): at each launch Launchy clones its binary, zmx, build stamp and Phone page files into `.build/snapshots/` (the first 12 characters of the commit, or `unstamped`, then the launch time) and points the link at that binary, so a `make build` changes nothing a peer reaches until Launchy restarts. The relay finds zmx beside itself, so a file the relay needs at run time must be copied there too, or it is the build folder's, which a build rewrites. Only the app takes a snapshot (the relay exits before anything of the app starts). The earlier snapshots are removed only once the link is seen pointing at the new one; a request that arrives mid-swap can fail once, and a running `watch` or `attach` keeps its open files. Where Launchy isn't running from a checkout's `.build`, or the copy fails, the link points at the binary in place. `make build` writes the stamp (`BuildStamp`) as its last step, only when everything before succeeded, so it names the last good build, not the running one; a stamp older than the binary is ignored (a plain `swift build`, or a build that failed after linking), and compare stamps with `isSameBuild(as:)`, never with the time.
- A Mac answers `upgrade` and `restart` in its running Launchy (`PeerManager.handle` before the version check, then `BuildUpgrade`), and its relay (`MacPeerHost.upgrade`, `restart`) forwards them and, with Launchy not running, answers the build fields from the stamps and git with `running: false` and a refused state. The relay must never read `LaunchSnapshot.current` (it would snapshot the snapshot): its stamp is `LaunchSnapshot.relayStamp()`. Everything in `answer(upgrade:)` has to end inside 10 s, since the relay waits that long for the socket and a longer one reads as "Launchy isn't running": a fetch is waited for 8 s, a `begin` 6.5 s, and the report's git reads 1 s in all (the report then has the running commit alone; it takes about 0.1 s even with every core busy). The relay's own fallback, with Launchy not running, gives the same reads 2 s each and 3 s in all. `CheckoutGit` and `BuildProcesses` go through `Subprocess`, and the relay, which is synchronous, waits on them with `MacPeerHost.blocking`.
- The target is origin/main alone (`CheckoutGit`): fetch is `+refs/heads/main:refs/remotes/origin/main` with `gc.auto` and `maintenance.auto` off (a detached gc after a fetch is what XProtect dislikes), read-only commands run with `GIT_OPTIONAL_LOCKS=0` so they never write the user's index, and the only change to the checkout is `merge --ff-only`, which acts on HEAD whatever it names: so `CheckoutGit.settle` reads the branch and the changes again right before it (the fetch before it can take 60 s, and a branch switched or a file edited meanwhile would be moved or built). Never `pull`, `checkout` or `reset`. A fetch runs once at a time (`OriginWatch`): a report with `fetch` and Settings › Peers opening join one under way or start one, and a report without it starts one only when the last try is over 10 minutes old, a failed try counting (`FetchRecord.attempted`), so a failing remote isn't hit at every report.
- The build runs only in the zmx session `launchy-upgrade` (`UpgradeRunner`), never in process: XProtect once killed a Claude process that ran installs, launchctl and a downloaded binary together. Its log is emptied before the upgrade is marked building, and nothing resolves that state while the session is still being started (`BuildUpgrade.pipeline`): the log's last line, `launchy-build-exit=<n>`, is the only record of how `make` ended (a zmx session's exit status says nothing), and an old one or a session not there yet would read as an end. A zmx session with no such line that is gone is a failure. The result is kept in `upgrade/state.json` in Application Support, so a relaunch picks a build up; a built state ends once the running commit is the built one. It runs with Launchy's environment less `ZMX_*` and `GIT_*` and the system tools first on `PATH` (no login shell), so a build step that needs another tool must find it there.
- A restart (`BuildUpgrade.answer(restart:)`) is refused while an upgrade runs, while a `make` or SwiftPM process has the checkout as its working folder (`BuildProcesses`, `ps` then `lsof`), and when no stamp newer than the running build waits, or the one that waits was made with uncommitted changes or off main. It starts after the reply is sent (a second later) as `make run` does, `scripts/restart.sh` under `perl`'s `setsid`, and only Launchy restarts. The panes it says would end (`LauncherModel.restartImpact`) must follow what the next launch does: a Claude or terminal pane survives only with Keep sessions running on now (the sweep kills the session of a restored pane otherwise), and an app's server always does, since Launchy has no SIGTERM handler and `stopAppServers` never runs at a restart. Handling SIGTERM would change that list.
- The relay's process arguments must stay unlike `make run`'s kill pattern (anchored to the bare binary path), or a restart kills a peer's request.
- A zmx run (the build, a headless install; `ZmxRun`) whose `zmx ls --short` can't be answered is still `running` and never `lost`: only a listing that came back may say a session is gone (`zmx ls --short` exits 0 with no output when none exist, and 1 on an unusable socket folder, so empty is a success). But a run no listing has answered for 30 minutes is failed ("Couldn't ask zmx about the build"), or `building` would stay for ever and keep Upgrade and Restart refused.
- A headless host is upgraded from a Mac, never by itself and never with `begin` (its relay answers "upgraded from a Mac, with the installer"): `HeadlessUpgrade` runs `scripts/install-peer.sh <host> --commit <origin/main>` in the zmx session `launchy-install-<slug>` (the slug carries a hash of the address, so two addresses never share a session or a log), judged by its `VERIFY=ok` and `BUILD` markers and never by an exit status. What the installer ships is `RelayFiles.pathspecs` in `RelayComparison.swift`, which also decides "relay unchanged": change both together. The installer ships and reads what is committed at the commit, its far half included; the far half says what it supports in its `# supports: RUN LOCK` line (add a word for a feature the near half adapts to, never remove one), installs on one host queue on `~/.launchy/install.lock`, and takes per-run tarballs (`incoming-<run>.tar.gz`) that other runs' far halves remove once a day old (uninstall removes only its own and the day-old ones, since a newer one may belong to an install queued on the lock). A comparison fetches only past the 10-minute rule. Known limit: `RelayFiles.pathspecs` always counts `PhonePage`, since a headless host's report doesn't say whether it has a page, so a page-only change offers Upgrade on a host with none. A headless row's states (`HeadlessUpgradeState`) are told apart (not compared yet, couldn't compare, ahead of origin/main, up to date), and `offersUpgrade` (behind, or a failed install to retry) is the one rule the row and Upgrade all share.
- Upgrade all and Restart all (`PeerBulk`; the lines are `BulkPlanner`'s, from each machine's last report): Upgrade all begins the other machines together and this Mac after their begin replies, then waits by asking for reports itself, since Settings' poll may not be running; nothing restarts. Restart all lists only Macs with a build waiting, never a headless host, and each Mac is asked again before its confirm (`PeerBuilds.sendRestart`, the same path as one row's Restart Launchy): a list that changed, or a refusal, skips that Mac. This Mac restarts last, once the others have answered or 15 s have passed, and its report is written to `upgrade/restart-all.json` before the restart so the next Launchy shows it once (only a launch other than the one that saved it does, and a file over 10 minutes old is dropped). A confirmation is dropped when Settings stops showing; a run goes on.
- The Tailscale CLI in the app bundle starts the GUI instead unless `TERM` is set.
- A pane with `record.host` (a session on a peer) is that `ssh` client (`startOnHost`), never inside this Mac's zmx and never given `Zmx.kill` (`ownsZmxSession` is false for it). Only the host kills the session, when the Mac in control sends `end` for a session it started for that Mac; the host accepts `end` only from a listed peer or device the session's `launchy-control` label names, and releases instead of killing when the session didn't originate from the asker (the bullet on closing in control, below).
- A Claude client exiting isn't the pane ending: `finish` asks the host's zmx (`clientExited`) and a session still running and labelled for another Mac leaves the pane open on a card. Keep the label, not timing, as the test, and keep a takeover relabelling before it detaches. A card for a lost link or an unreachable host asks again every few seconds (`Away.isLink`), so it can't stick; one that needs the user or a start under way doesn't (`Away.skipsAutomaticCheck`).
- A pane on the host never attaches to a session another Mac controls (`startClaude` checks the label before a restored pane attaches); a second client would make two keyboards type into it. The card on the host asks before closing, since it is the only pane the session has here.
- The launch sweep is unchanged except for one exception: it never kills a session whose `launchy-control` label names a listed peer or a listed device (`Zmx.sessionsToKill(sparing:)`; `cleanUpAfterLastRun` passes both lists' ids), since that Mac or device may be typing into one whose pane here was closed.
- The relay's `attach` checks that the session exists and, without take, that its label names the caller (an unlabelled session is its host's). `zmx attach` creates a session for a missing name and has no flag to refuse, so the relay gives it `/usr/bin/false` as the command: one that lost a race ends at once instead of running a login shell. `attach` needs only zmx, and `status` zmx and the saved tabs, so keep both working with Launchy not running.
- Take over relabels, then detaches, then attaches (`ClaudeSession.takeOver`; the relay's `attach` with take on a peer): the Mac that sees its client exit tells a taken session from an ended one by the label, so the label comes first. On the host the pane's client restarts in zmx whatever Keep sessions running says now (`launchClaude` passes `alwaysInZmx`), and a session this Mac started for a peer stops being given that peer's labels (`startedFor`), since attaching with it would hand the session straight back. Only its control label is handed back that way: `launchy-origin` is set when the session is created and stays.
- A client for a pane coming back from a card (take over, Reconnect, going live after a release) starts only once the terminal view is on screen at its real size (`resumeClient`, `startWhenHosted`). While the card shows, the view is in no window and keeps its first grid, so a client started at once is told that size: zmx draws the saved screen and Claude repaints for it, the real size arrives after, and the transcript above the prompt box ends up missing (seen on opening a peer's session a second time). A fresh pane is safe because it starts after `TerminalHost` hosts it; keep every start that follows `away = nil` behind the same wait.
- Closing a pane in control of a session on a peer sends `end`, and the host decides (`LauncherModel.hostEnd`): if the session's `launchy-origin` zmx label names the asker it is killed and its pane closed; otherwise (the host started it itself, so there is no label, or for another Mac) it is released: `Zmx.release` clears `launchy-control` and then detaches every client, in that order like a take over, and the host's card goes live (`goLiveAfterRelease`, also done by the card's own check when it finds the label no longer names a peer). The label is the live source. It is written with the control label as the session is created for a peer, from `SessionRecord.origin`, which `hostStart` and `hostResumeConversation` save and `hostResume` reuses, so a session the host starts again after zmx lost it (a reboot) keeps its real origin; the label is only given at creation (`startedFor` set), never re-applied from the record by a later attach. Sessions from before the label existed have none and are released. A session with no pane on the host ends, since nothing would own it once released. The peer's closed pane never asks to be started again: it is over (`endedByUser`), and a `released` reply only takes its conversation out of the peer's Recent (`onReleased`). Keep the decision on the host; the peer can't tell where a session came from.
- On a headless host (`HeadlessHosting.swift`) every session carries a control label naming a Mac or a device, and release keeps it: it detaches the clients and never clears the label (`Zmx.release`, which clears it, is the Mac host's). A Mac reads a missing label as the host in control, and nothing there types. `end` is the same rule as `hostEnd`: the label must name the asker, then origin kills and anything else releases.
- A headless host's `start` runs in this order: the record (saved with `starting`), the pane folder, the pty client (`PtyClient`: `openpty`, `posix_spawn` with SETSID, signals reset), the wait for `launchy=1` and the control label (`zmx get` succeeds before `attach --labels` has set them), then the detach of the relay's own client. The folder before claude starts is the hook's, and the first turn is written where the session file is cleared (ADR 0010). The labels are written in the one attach, so a start never creates a session in two steps. Claude's environment is built fresh there (`claudeEnvironment`), `DISABLE_AUTO_UPDATE=true` included, since oh-my-zsh's update prompt blocks `zsh -l -i`.
- The state lock (`StateFolder.locked`) is held for a read or a write of a file and never across a wait, whether for zmx, the pty or a sleep: the other Mac's polls would stall behind it. A start takes it for each record write on its own.
- A headless host reconciles its records with zmx before any request reads them (`StateFolder.reconcile`; `HeadlessLifecycle` is these rules' code, and this is where they are written): a session gone in this boot is ended, one gone from an earlier boot (the record's `bootID` differs) is lost and left with `ended` unset, and a start that never handed over, with no session, is ended once it is 30 s old. A listing that failed (`Zmx.listedSessions` nil), or a host whose boot id can't be read (for any record but a stuck start), changes nothing, since only a listing that came back may say a session is gone; the hand listing and `recent` say so instead of showing sessions as gone. The records are read before zmx is asked and written only if still unchanged, so a start finishing meanwhile is never ended. Nothing ends a session by itself, and orphans stay in the list.
- Only a lost record is ever started again, and only for a Mac's `start` with `resume`, which `claimResume` decides and marks `starting` under the lock, so two panes can't both start it (the other gets `running` or `closing`). A record that ended in this boot answers `ended`: starting it would be unasked. With no boot id for the host a record isn't called lost, so a Reconnect answers `ended` without marking it, and the hand listing says "unknown". A restart that fails puts the record back as lost with the conversation it claimed (`launch` has already cleared the hook's file), and neither that nor the hand-over writes over a record ended meanwhile by a hand `end`. Resuming an ended conversation is the `resume` request, which refuses one a running or starting record has open (`isHeld`, checked in the same lock as the record's save). `LAUNCHY_BOOT_ID` replaces the boot id for a check, and a Mac's ssh command never sets it.
- Two Macs taking a session at once can leave both attached (a take landing between the other's detach and attach), so a second or two after any client attaches the pane reads the label once and lets go of its client if another Mac is named (`checkControlAfterAttach`). A client for a session expected to exist is started with `/usr/bin/false` as its command (`attachToLocalSession`, like the relay's attach), never with the claude command line, which would start a second session if the first ended meanwhile.
- The frozen screen is `zmx history --vt` read from the host (sent to a card by `watch`; the `screen` request, served by the relay from zmx alone, is no card's path now and is kept for checks), and it is never fed to a live terminal: it replays the private modes the session had set (mouse, focus, paste, alternate screen), and a shell that received them printed the reports as text. `FrozenScreen.prepare` strips them and cuts to a tail before it is sent, and the view (`FrozenTerminalView`) has no process, drops what the terminal would send, and never becomes first responder. Keep both when changing either. The screen carries the grid it was drawn on, read before and after the history, and the view keeps that grid and fits it by font size. A font change on a laid-out view makes SwiftTerm resize the terminal to the frame and lose its buffer, so `fittingFontSize` measures with the frame at zero; keep that. No grid falls back to the pane's size.
- `watch` is the live screen of a card (ADR 0008, which has the timings and counts), answered by the relay alone like `attach` and `status`, so it works with Launchy not running. It prints one reply line, then frames (`WatchFrames`), with blank keep-alive lines, until its input ends, a write fails or the session's socket closes (Take over, Release and the session ending all close it). `ZmxReader` is the one reader, run by the relay and, in process, by the host's own card; a card for a session on a peer reads the peer's relay through `PeerManager.watch` (`ClaudeSession.startWatching` picks). It sends only history requests (`ZmxWire.historyRequest`), never input, Init or Resize: any of those makes it a terminal, the leader or a sender of focus reports. It never stops reading the socket, or zmx queues output for it without limit, and its socket never raises SIGPIPE (`SO_NOSIGPIPE`; the relay also ignores the signal), since a signal would end every session in the app. A pending frame is replaced by a newer one, never queued. The keep-alive is what ends the relay after the viewer's ssh is killed on a shared connection, which sshd alone doesn't notice. A zmx pin bump rechecks the socket header, the tags and the history request in `ZmxWire`.
- A reader counts as a zmx client, so every client count that says "Controlled on" or "Last controlled on" goes through `Zmx.statuses`, which subtracts the live readers in `ReaderRegistry` (one empty file per reader, written on its first history reply and removed before it disconnects; a file whose pid is gone is skipped and removed). Reading `zmx ls` directly for a count would show "Controlled on" for a Mac that quit. Take over and Release detach every client, so they end readers; a card still showing another Mac in control starts one again after a backoff. A card runs a reader only while a view of it is on screen in a visible window (`FrozenScreenContainer.onShownChange`, counted per container, since a new one can join before the old leaves) and for a short while after, and never takes the reader's ending for the session's: the card's own check decides that.
- A peer's card holds one `watch` channel to its host while a view of it is shown, on the same shared connection as the panes (ADR 0008 has the count the spike ran). `SSHRunner.stream` keeps the ssh's input a pipe open for its whole life, never `/dev/null`: that is how the relay learns its viewer is gone (Launchy quitting or crashing closes it; cancelling closes it, then terminates the ssh after 1 s and kills it after 2 s, a command that reads its input ending sooner than a killed ssh does). The parent's pipe ends are close-on-exec, or a pane started meanwhile (`forkpty`) would hold the input's write end open after cancel and orphan the ssh and relay on quit. A stream's ending is never a timeout, so it never asks the shared connection to exit, and a channel ending is never the session ending: the card's own check decides that, as for the host's card. `PeerManager.watch` skips lines before the reply, checks its version and `ok`, and refuses a peer known to speak another version before sending anything. A refusal (another version, or this Mac unlisted) updates the peer's status like `send` and stops the card until it is shown again, never a retry loop. No reply in time is a failed attempt. A card's frames hop to the main actor and check the generation, like the host's.
- A peer's open sessions in the session list (`sessions`, read by the relay from `sessions.json` and zmx, so it works with Launchy not running) are rows of `panelHeight`'s session-list branch (a header per Mac and a row each) and sit between this Mac's tabs and Recent in `move`, `openSelected` and `sessionSelection`. A session this Mac has a pane for is left out of them. Opening one (↩, or ↩ on a Recent or search row whose session is open there) is `openPeerSession`: the pane opens on the card, never attached, whoever is in control and with or without a client there (`opensOnCard`, asked of the host through `settle`, like a restored pane, and starting nothing). Control moves only when the user presses Take over; the one case that attaches is a label that already names this Mac. The pane keeps `opensOnCard` for its life, so a session found gone later (the card's check, Retry) closes it (`sessionGone`) instead of starting it again. Explicitly resuming an ended session is a different path and starts and attaches.
- A peer's pane never follows /clear and /resume through its own hook file (it is written on the host, so `checkConversation` is off for `isOnPeer`). It takes the conversation from `status` (`PeerFollow.fill`: the hook's last report, else the saved record), polled by `LauncherModel.followPeerSessions` while any pane is on a peer and when the panel opens, never on the main actor. The record changes without `onConversationChange`: the host's own pane puts the conversation left behind in the host's Recent. The title is the host pane's, sent only while the host is in control and applied only where this pane has no client.
- A session gone on its host is started again only into the pane the host restored for it and hasn't started (`start` with `resume`, `hostResume`), labelled for the Mac that asked, which then attaches with take. A host with no such pane answers `ended` and the peer's pane closes: that session was ended there on purpose, and nothing is ever started behind the user's back. Resuming an ended session is an explicit action (Recent, search), a different request (`resume`). A restored pane, Reconnect and Retry, and the pane's own check of a lost or unreachable card all resume a session found gone; a card showing another Mac in control closes instead. `running` and `closing` answers are looked at again, never taken as success: take control only if the label names this Mac.
- Tailscale SSH (a Mac's own Tailscale serving SSH) reports every remote command as exit 0, so an ssh exit status says nothing about a peer's answer. Read the reply JSON (`PeerClient.exchange` does, whatever the status), and never take `status == 0` from `SSHRunner` for success; `Tailscale.status`'s check is of the local CLI, which is fine. A check made by hand echoes `$?` on the remote side, inside the command.
- A session's turn travels as text (`PeerSessionStatus.turnWord`, key `turn`) and `Turn` is read from it, so a word this build doesn't know is nil and the card shows "Turn not known" instead of the reply failing; a strict decode would fail every `status` ask to that host. The rest is in ADR 0010. A new optional field in `PeerSessionStatus` or `PeerOpenSession` must also be added to its explicit `CodingKeys`, or it never reaches the wire (the compiler doesn't say).
- A peer's session rows (`rows`) and Recent (`recent`) are served by the relay alone, `rows` from the search database read-only (the path is `LAUNCHY_DB`, else the file the running Launchy writes at launch, `PeerSearchDatabase`; the relay isn't started like Launchy) and `recent` from `sessions.json`. `rows` limits itself to those changed since a stamp and always lists every id, which is how a session that is gone leaves the other Mac. `HistorySync.pullPeers` writes them to `peer_sessions` in the sync, reading each Mac in full once per launch, and again when the ids it lists have no rows here (a session whose folder came back, which no stamp of changes shows); a Mac that doesn't answer keeps its rows (the failure is logged), and the rows of a Mac no longer paired are deleted in the same pass, which removing it starts at once. The sync waits for the pull, so keep its timeout short (`peerPullTimeout`). A search row carries its Mac in `favorites.host`, written by `refreshSearch` from the entry that won, so nothing decides it a second time.
- A peer's pages (`pages`) are served by the relay alone, from the Mac's own archive tables read-only (never the `peer_*` ones), in pages of about 2 MB ordered by (`changed`, key), with a cursor of both, since rows written in one sync share `changed`. The cursor's key is a digest, which the relay finds again among the rows of that stamp (not found: the stamp repeats, never skips), so no URL, which can carry sign-in parameters, is saved in `meta` or sent in a request. A reply also says whether more remain and how many pages and search terms the archive holds. `HistorySync.pullPeers` sends it in the same pass as `rows`, one reply per Mac per sync, from the cursor kept for that Mac (`PagesRead`, in `meta` under `peer_pages_read:<id>`, written in the transaction that stores the rows, so a relaunch reads nothing again). A full read, from zero, happens only when this Mac holds no rows from that Mac, or when an ask that says nothing more remains finds fewer pages or search terms kept here than the reply's counts say the Mac holds (a database replaced there, which no cursor shows); the cursor is then reset and the read comes at the next sync. The counts stand in for `rows`' list of ids, since a large archive's URL list is about 1.8 MB per ask. Pulled rows are only inserted or updated, as sent and none skipped (or the counts could never match), and the relay answers its rows and counts from one read transaction. A Mac's pulled rows are never swept: a page gone from its archive stays here, as history is never deleted, so more rows here than its counts say is not a reason to read again. A Mac that doesn't answer keeps its rows and cursor. A Mac that is no longer paired loses its pages and its cursor in the same transaction as its sessions.
- The peers' Recent (`LauncherModel.allRecent`, rebuilt by `rebuildRecent` when its inputs change, and in `saveSessions`) is merged from the last answer of each Mac and this Mac's own: one entry per conversation, records with a host aren't checked for a local transcript (`addRecent`, the restore filter), and a peer's entry takes the conversation's own id as its record id so a row keeps its identity between fetches.
- Resuming an ended session on a peer (Recent or search, `resumeOnPeer`) is the `resume` request, never `start` with `resume`: it starts `claude --resume` under a new session id the asking pane chose, labelled for the asker, in a background tab (`hostResumeConversation`). The pane asks for it only with `resumesOnPeer`, which the model sets for that click and Retry on a failed one sets again, and which is cleared as soon as the host answers; nothing restored or retried by itself sets it, so the automatic path above keeps its guarantee. A frozen view of a session another Mac controls that closes isn't put in Recent (`isViewOfSessionControlledElsewhere`). The host refuses a conversation it has open in a running session; the asker takes that one over instead, from the open sessions it already lists.
- The relay answers every request but hello only to a Mac this one lists (`PeerList.lists(by)`, the saved list read without writing it, checked before anything else), or to a listed device (`PeerHost.listsDevice`, ADR 0011), since anyone who can ssh in could otherwise read prompts, screens and sessions or attach. A device is refused `rows` and `pages`, the search sync's, which hold the user's prompts and pages for the paired Macs alone; it gets the same `unlisted` reply. The running Launchy takes a device's `start`, `resume` and `end` as a peer's, reading the device file fresh (`PeerManager.handle`), and puts its id in the labels as a peer's. `PeerManager.send` and `attachCommand` fill in `by`. The answer to an unlisted Mac says so (`PeerReply.unlisted`), and a Mac that gets it is `.removedThisMac`: it is read no more, its `peer_sessions` rows and Recent entries go, and only a hello from it (it added this Mac again) brings it back.
- A host pane whose client exits while the session runs and is labelled for the host (or nobody) attaches again (`ClientExit.dropped`, with the reattach limit), never ends the session: a take-over that raced another could otherwise kill work. A pane started for a peer runs `checkControlAfterAttach` too, so its starting client lets go once the label names the peer, and a failed first attach by the peer can't leave two keyboards.
- The device file (ADR 0011) is `devices.json` in the support folder: `DeviceList` in `Devices.swift` is its one reader and writer, and holds its rules. On a Mac only the running Launchy writes it (`PeerManager.addDevice`, `removeDevice`; never the relay); on a headless host `launchy-peer device add` and `device remove` do, under the exclusive state lock. Only the user's own untagged nodes may be listed (`PeerDevice.mayBeListed`, used by both add paths). Ids compare through `Zmx.sameID`, never with `==`. A device is never contacted and never sends a hello.
- `status` and `sessions` replies carry `controlName`, filled in by the shared relay (`PeerControllerNames` says how it names a controller). A device is never told another controller's id: the relay leaves out `control` unless it names the asking device (`PeerRelay.hiding`), so the page tells who is in control from `controlName`. A Mac or card names its controller from its own peers and devices first and the reply's name second (`PeerManager.name(of:reported:)`), saying "another Mac" only when nobody does. A change to a reply shape bumps the protocol: both Macs and the headless host run one commit.
- Any request but hello to a peer goes through `PeerManager.send` or `attachCommand`, which refuse a peer found to speak another protocol version, except `upgrade` and `restart`, which `PeerClient.exchange` sends and `verdict` reads across versions.
- A paired Mac's session becomes an ended card (`LauncherModel.endRememberedSessions`) only when all of these hold: this Mac listed it open and remembered it (`remembered`, saved as `State.remembered`, by pane id), that Mac's latest `sessions` answer succeeded without it, and its Recent, asked after the session was last listed (`peerRecentSentAt`: the time the ask was sent, an unchanged reply counts), has an entry whose `session` is the pane's name (`PeerRecentSession.session`, protocol 16: the relay fills it from the record's id, and a conversation /clear left behind has a fresh id that matches nothing). A session merely missing ends nothing, since a restarted Mac restores its panes and closes none, and a Mac that doesn't answer ends nothing. Never match by conversation (a /clear moves it), and never read an end from a Recent asked before the last listing, or an old entry of a pane id resumed since would end it. Recent is asked of a Mac that just stopped listing a session, alone, while that session was last listed within a minute (`recentWatchWindow`), and of every Mac at most every 5 s when the board opens, never of every Mac every 5 s: the headless host's Recent reads each ended session's whole transcript for its title. The remembered list is forgotten when a pane here takes the id, when marked done, when the Mac is unpaired and 30 days after the last listing, in `rebuildRecent`; and a session started and ended there between two listings is never on the board.

**Phone page** (`PhonePage/`; ADR 0011)
- Bun is for the page only, never the relay. `PhonePage/` takes no npm package, and `bun test` in it checks the pure decisions (`checks.ts`, `home.ts`, `hosts.ts`, `relay.ts`, `terminal.ts`, `launch.ts`, `watch.ts`, `page/rules.js`, `page/newrules.js`, `page/liverules.js`).
- Every list and action is a relay request with the device's id as `by`, spawned with an argument list (`relay.ts`), never through a shell. `by` comes from the server alone (whois on `X-Forwarded-For`, then the node, then `devices.json`) and `buildRequest` writes it last, so nothing a client sends can replace it.
- whois's `Node` has no `ShareeNode` (`status --json`'s peers do): a node shared in shows as `Sharer` non-zero or `Hostinfo.ShareeNode` (`parseWhois`, with a fixture from a real answer). The rule is `PeerDevice.mayBeListed` in `checks.ts` too, so change both together.
- User ids stay text (`parseTailnetJSON`): a 17-digit id isn't exact in a double.
- On a socket serve sends `Host: localhost` and the browser's host only in `X-Forwarded-Host`, so the Host check reads that there and `Host` on loopback.
- `/api/*` answers only the page itself (`checkFetchSite`), because another site open on the phone can send a `no-cors` read with the phone's identity, and a read runs a relay. Relay runs and whois spawns are capped, per device too. Mutations and websocket upgrades need the page's `Origin` (`gateMutation`, `gateUpgrade`). Send no `Access-Control-*` header, ever.
- Bun can't set a socket's mode: the socket's folder must be the user's and 0700, and the socket is chmodded 0600 once bound.
- Which hosts can serve a socket, and why Macs whose Tailscale can't serve a socket listen on loopback: the option's Spike › Results (one app's mount looks right in `serve status` and still answers 502).
- `PROTOCOL_VERSION` in `server.ts` must equal `PeerProtocol.version`: a protocol bump changes both, or the server refuses to start.
- A Mac's server runs in a zmx session named `launchy-phone-page`, never a pane's name (`Zmx.attachCommand(named:)` refuses one): the launch sweep and the relay's `sessions` read a pane id from a name, so a pane's name would get the server killed at the next launch.
- It is started through `PtyClient`, never `zmx run`, which crashes 0.8.1's daemon, and waited for and detached as a headless `start` is.
- Only the setting ends it: not Quit, not Keep sessions running (`stopAppServers` looks at panes), not the sweep. A server that exits by itself (Tailscale not up at login, a protocol mismatch) stays down, and Settings offers Start again with the log's last lines.
- Its files are the launch snapshot's clone of the copy `make build` puts at `.build/release/PhonePage`, in `.build/snapshots/page-<digest>` (`LaunchSnapshot.serverInstall`), so an edit in a checkout reaches a running server only through a build and a restart. The folder is named by the digest, not by the launch, and the session's labels name it (`launchy-page-place`): the server outlives Launchy, and a launch that finds the same digest in the same place leaves it running, so its files must stay. A server without that label (started before snapshots, from the build folder) isn't current and is replaced once. A page folder is removed only after a reconcile, and never the one the running session's label names, so a server that isn't replaced (Bun missing, `stop()` failing, no page in the build) keeps its files.
- Launchy publishes the page's port itself (`PhonePagePublisher`), by the rules in ADR 0011's note: one mount, no funnel, fail closed, the user's own mount left alone. The app's CLI needs `TERM`, and is always loopback whatever its `--help` says, since the Tailscale app's mount answered 502 for every socket when tested (1.102.3). The target follows the running session's `launchy-page-mode` label, not what the CLI can do now. Never run `serve` as root anywhere but the Use a socket button, and keep every read as the user (the rest of the refused-socket rules are in ADR 0011's note). `PhonePagePublisher.swift` takes the CLI as a closure and the port as an argument, and imports nothing of the app's, like `PhonePage.swift`, so a check can run it on a throwaway port (the kit's `ticket11-check.sh`).
- Home's "Other hosts" are the relay's `hosts` reply (name and address of each listed peer, never an id: `PeerHostEntry` has none; from the saved list on a Mac and `state/peers.json` on a headless host, read and never written) read by `hosts.ts` against `tailscale status --json`'s nodes. An address that isn't a node of the tailnet (`alex@check`, an IP, one with a port) gets no link, and a link only says where a host's page would be: the page can't know whether it is published, and the browser's own error is the answer. `hosts` is a request like the rest, so adding it moved the protocol to 14.
- On a headless host the server is the systemd user unit `launchy-phone-page.service`, written only by `scripts/install-peer.sh <host> --page`, which is also the only thing that enables, restarts or stops it by hand (systemd starts it at boot and restarts it on failure). It needs `KillMode=process`: a session the page starts is created by the relay the server spawned, so its zmx daemon is in the unit's cgroup, and systemd's default mode would end every session at a stop or restart. Linger must be on for the user, or the unit stops with the last login (the installer warns). Like Settings above, the installer follows ADR 0011's note (`page_publish` once the page answers, `page_unpublish` for `--no-page` and `--uninstall`). Funnel that is anything but off, unreadable included, also disables and stops the unit (a stop alone would let a reboot bring it back), and a clean run enables it again.
- `PhonePage.swift` and `PhonePageRunner.swift` import nothing of the app's: a scratch package that links `Packages/LaunchyPeer` compiles them for a check against real zmx and Bun.

**The terminal** (`PhonePage/`: `bridge.ts`, `terminal.ts`, `page/session.js`; ADR 0011)
- One websocket per open terminal, at `/ws/terminal`, carrying bytes to the relay's `attach` run in Bun's pseudo-terminal. Its upgrade is checked before anything is spawned (`gateUpgrade`), and a device has at most three terminals open (429 past that).
- `take` is sent only right after a press (Take over, or the Start or Resume that made the session), and never on a reconnect: the first message's `take` counts only as the literal `true`, and the relay refuses an attach without it for a session the device doesn't control.
- Every client re-checks control, as the Mac clients do (`checkControlAfterAttach`, above): about a second after the attach goes live the server asks `status` once, and if the label isn't the device's it closes the pty and sends 4001 with the controller (`recheckControl`). Two takes landing between the relay's label check and its `execve` would otherwise leave two keyboards live. Input is dropped until the screen is live.
- Closing the websocket closes the pty, which ends only the phone's zmx client: the session keeps its label, and the phone stays in control. Never release on close: Android drops a backgrounded tab all the time.
- Every reconnect asks `status` first (`/api/session`): labelled for the device attaches without take, anyone else shows the session view, gone says "Session ended". A client that exits by itself is told from "taken" and "ended" by `status`, never by its exit code (4001 taken, with the controller as a JSON field of the reason; 4002 ended; 4003 dropped; 4004 refused, with the relay's error as the reason). The tries start over only after a connection that lived 10 s.
- A refused attach prints one reply line and exits instead of becoming zmx. Output that starts with `{` is held for up to a second; a child that exits meanwhile with a reply line closes the websocket with its error, and the line never reaches the terminal. Anything else is released at once.
- What was typed or shown stays out of the logs: opens, closes, codes and grids only. The page's CSP allows inline styles, because xterm.js's renderer writes `<style>` elements; scripts stay `'self'`, and `connect-src` names the page's `wss://` address.
- xterm.js is vendored in `PhonePage/vendor/` at pinned versions, with `VERSIONS` holding each file's SHA-256 and the packages' registry integrity (`bun test` checks the digests). Fetch new versions on a headless host, never on a Mac inside a Claude session, and serve them from `vendor/`, not `node_modules`.

**Starting and resuming on the phone** (`PhonePage/`: `launch.ts`, `page/new.js`, `page/newrules.js`, `page/dom.js`; ADR 0011)
- The browser sends only `{folder, agent, prompt}` to `/api/start` and `{conversation}` to `/api/resume`; `parseStartBody` and `parseResumeBody` read nothing else. The server picks the session id (`crypto.randomUUID()`), sets `by`, and never sends `skipPermissions`, so the host's own setting applies. The prompt, folder, agent and conversation reach the relay only as JSON fields of its one base64 argument.
- A folder must be one of the host's `projects` (for `/api/agents` too) and an agent one of that folder's `agents`, asked fresh each time. A conversation must be one the host's `recent` offers, and its folder and agent are the Recent row's, never the body's. A conversation a running session has open (its `conversation`, else its own id, as `conversation(of:)` does on a Mac) is answered with 409 and that session's row, and `resume` isn't sent; when the host refuses all the same, in a race, `sessions` is read again and the row returned the same way. The page offers Take over on that row.
- A start or resume that fails or times out asks `status` for the session it named before it answers: a running session is a success, or a second tap would make a duplicate.
- The prompt is never logged and never echoed in a reply, a refusal included, and never in `document.title` (browser history, Chrome Sync).
- The prompt is limited as `JSON.stringify` writes it (`promptLimitBytes`), since a newline or a quote costs two bytes in the request, which then goes base64 into one argument. Linux takes 131,072 bytes for one argument; `Relay.ask` refuses a request over `argumentLimit` before it spawns anything.
- Claude's parser reads the first operand as a subcommand even after `--`, so a prompt that is exactly `doctor`, `update`, `mcp` and so on would run that command. `ClaudeCommand.operand` gives a prompt with no whitespace a trailing space, which no command name equals. Keep both (`--` and the space) when changing `arguments`.
- `parseStartBody` still refuses a prompt that starts with a dash, for a host that doesn't put `--` before the prompt yet (before `ClaudeCommand.operand`). Remove the check once every host has that change.
- A Mac host takes up to 25 s to answer `start` and `resume`: the relay is given `launchTimeoutMs` for them, and the request `server.timeout`, past Bun's 30 s idle limit.
- `projects`' `lastUsed` is Foundation's `Date`: seconds since 2001-01-01. `shapeProjects` converts it, and sorts newest first itself.
- The page sets `take` for the terminal only after Start or Resume succeeded (`enterSession` names the one session to take, once) or after a Take over press, including the one on a refused resume's row. A reload, a revisit and every reconnect attach without it. A resume under way is kept per conversation, not per row, since the home reloads while the host answers. New session's last project and agent, and the last lists, are in localStorage per origin (so per host), and the page works without it.

**The live screen on the phone** (`PhonePage/`: `watcher.ts`, `watch.ts`, `page/live.js`, `page/liverules.js`, `page/session.js`; ADR 0008, ADR 0011)
- The server runs the relay's `watch` on pipes, never a pseudo-terminal: a reader never sends input, Init or a size, and a pty would make the relay's client a terminal. Nothing is ever written to the relay's input, the first message names the session and nothing else (`take`, `by` and a grid in it are ignored), and any later message from the page closes the socket with 4400. A watch needs the same caller, Host and Origin checks as the terminal (`gateUpgrade`, before anything is spawned) and is sent only to a listed device.
- The relay's input is a pipe held open for the websocket's whole life: closing it is how the relay learns its viewer has gone, which is also what removes its `readers/` file and keeps the Macs' client counts right. When the websocket closes the server closes that input, terminates the relay after 1 s and kills it after 2 s (as `SSHRunner.stream`'s cancel does). The slot (3 a device, 8 in all; `Admission` in `relay.ts`, shared with the terminal) comes back when the relay is gone, not when the socket closes. Never give the relay `stdin: "ignore"`: it would see its viewer gone at once.
- The channel ending never means the session ended. Take over, a release, the session ending and the relay failing all close it the same way, so the page asks `status` after every close (the terminal's rule) and shows whatever that says: this view again with the new controller, the terminal, or "Session ended". A channel that ran for 10 s asks at once; one that failed at once backs off 1, 2, 5, 10, then 30 s.
- A slow phone mustn't grow the server: only the newest frame not yet sent waits (`Outbox`), and a frame goes only while the socket holds under 256 KB unsent, so a stalled connection gets the latest screen when it drains and the rest are dropped (the close line in the log counts them). `Bun.serve` has one `backpressureLimit` (4 MB) for every websocket and closes a socket whose unsent bytes pass it, and JSON writes each escape character as six bytes: so a screen over `longestScreen` (1 MB of text) is skipped as it arrives, a message over `longestMessage` (3 MB) is replaced by `{tooLarge: true}`, and the page says "Screen too large to show" in the bar and goes on. Keep `longestMessage` plus `sendHighWater` under the limit (`watch.test.ts` checks it against a real server). The relay's pipe is read at all times, whatever the socket does. Keep the logs to opens, closes, codes and counts: never a screen.
- The channel is open only while the page is visible. A hidden page closes it (and the host's reader goes with it), a visible one opens it again, and the first frame is then a fresh snapshot. A page that is hidden still shows its last frame, but returning says "Loading screen…" until a fresh one arrives, since the old one is old.
- Each frame is drawn from scratch (`ESC c` through xterm's parser, which `term.reset()` isn't: it would run before a frame still waiting to be parsed) at the grid it came with, in a read-only xterm.js with no scrollback and `pointer-events: none`, never focused. A grid of `0 0`, or past 400 columns or 200 rows, is fitted to the phone instead (`pageGrid` on the server reads the page's own `gridLimits`, so there is one set of limits). The scale is `fitScale` of the width measured from `.xterm-screen`, never above 1. Pinch to zoom is the browser's own: don't put `user-scalable=no` or `maximum-scale` in the viewport meta.
- `Bun.serve` takes one websocket handler for both channels: each socket's `data.kind` says which one it is (`socketHandlers` in `server.ts`), so a third channel adds a kind there.

**Listening and spoken requests** (`Listening.swift`, `Speaking.swift`, `SpokenText.swift`, `SpokenRequests.swift`; ADR 0015)
- The system audio tap must keep excluding Launchy's own process (`ownProcessObject`); without it the wake sound and the answer come back as `[system]` lines. It is looked up when each capture starts, and a failed lookup only logs.
- Launchy's speech must come from this process, so `Speaker` renders it with the synthesizer and plays the buffers on its own engine. Moving it back to `AVSpeechSynthesizer.speak` alone (which only the no-audio fallback does) may play it from a system process the tap does not exclude.
- `SpeechSpans` must be open from before the first sound to after the last, plus its tail: Listening drops a mic result whose audio began inside it, by audio time (`AudioClock`: time zero is re-anchored at every buffer, so mic drift and gaps don't move recent audio), never by when the result arrives, since finals come 1 to 2 s late. A path that speaks without `Speaker.speak`, or ends the span early, lets Launchy wake itself.
- Only final mic results wake it, only while Listening is on and Hey Launchy is on. Mic results while a request is decided, read or spoken never wake it or join a request. Turning either off, or stopping Listening, cancels the request and the voice.
- The panel's search and the spoken search share one ranking, `RelevanceSearch` (ADR 0017): `keyword`, `withMeaning`, `judge(for:)`, `filtered` and `fuse`, with the constants. The module sets no UI state, waits for nothing and logs nothing; the panel keeps its debounce, the judge's `pause`, the statuses, the selection and its log lines, and a spoken request calls the passes back to back. The panel's statuses are set synchronously in `runSearch` (`--search` waits on them), so a pass moved behind an `await` there changes what `--search` and `--search-eval` see. The "no results for" log lines print the query and stay in the panel: a spoken request never reaches them. A change to a pass, the fusion, the threshold or the choice of judge is one change in the module and reaches both; check the panel with `--search-eval` and `--search` before and after (off and On this Mac must match exactly, TypeSafe within its run-to-run noise).
- A spoken request runs the relevance filter wherever Settings › Search says, unless it reads sessions only (sessions are never judged): `SpokenPipeline.prepare` calls `judge(for:)` on the search words, so the rule "TypeSafe only with the filter on TypeSafe and a key; On this Mac never falls back to TypeSafe" has one home. On TypeSafe that sends the search words and the title, site and own description of the first 20 pages (`Reranker`), new since ADR 0016; the README, SECURITY.md and the Settings text say so, and anything more in that body is a privacy change needing the same. When the filter judged any page of the chosen kind relevant, only those are read (`SpokenText.rows`, `relevant:`), so a page wrongly judged irrelevant is not heard; a failed or unavailable judge leaves the fused order. The timing line and `--ask` name who filtered.
- The decide step asks TypeSafe's Jev (`SpokenRouter`, ADR 0016) only when `activeRelevanceFilter == .typesafe` and a key is saved: a key alone, the filter On this Mac or off sends nothing, and Text generation decides, as on any failure, no source in the reply or after 1.5 s. The body carries the request text and the two fixed questions, never a title, folder or project name, search word or row. The session folder names (`sessionFolderNames`) are compared with the request in `SpokenText.plan` and stay in this process. Jev's "other" (0.5 or more) is answered with a fixed line and no search or Text generation. That body is the decide step's alone; the filter's call is separate (above). Anything added to the request body is a privacy change: it needs the ADR, the README and SECURITY.md amended and the Settings text changed. The model is pinned (`jev-latest` moves); changing it or the questions changes the thresholds' meaning (`SpokenRouter.offTopicFrom`, `alsoSessionsFrom`), which were measured on made-up requests.
- `SpokenPipeline.prepare` (decide, search, filter) runs while a request is still being collected, and `respond` and the speech wait for the hold to end (ADR 0017 has what a discarded partial request sends). `SpokenRequests.speculate` keys the run by the exact request text and cancels it on any change; `cancel()` must cancel the run as well as `working`, which does not cancel the task it awaits. After an `await` that catches errors, `prepare` calls `try Task.checkCancellation()`: a cancelled local generation returns what it had instead of throwing, and a failure while cancelled must not rest a server. What `prepare` can still write is harmless: a server Check recorded in `ModelServerState`, `store.refreshIfChanged()`, and resting a server on a real failure. The timing line's decide, search and filter now overlap the hold; `waited` is what the end of the hold still waited for. `--ask --restart-after <seconds>` exercises the cancel.
- The request, the search words, the rows and the answer are never logged (the answer is in the transcript by design). A failure logs its step and the error's kind (`Error.logKind`, never `localizedDescription` or the error itself), and the timing line logs durations, places and kinds: who decided (Jev, or where Text generation ran and why Jev was not used), where the meaning pass ran, who filtered (or off, sessions only, or the failure's kind), the render and the first sound.

**Checking by hand**
- `NSLog` lines (the spoken request timing, failures) go to stderr, which `make run` and the LaunchAgent append to `~/Library/Logs/Launchy.log`; they are not in `log show`. Read that file after a spoken request. A Launchy started any other way (from a terminal, or by a build that predates this) writes them to its own stderr.
- Measure search with `Launchy --search-eval <terms> <output>` on a copy of the database (`LAUNCHY_DB`), with `LAUNCHY_EVAL_FILTER` (typesafe, local, off) to pick the filter and, for typesafe, `TYPESAFE_API_KEY` in the environment: it runs the app's own fused search and filter and prints MRR and top-k for the target pages. The terms and output are personal like the checkpoint; keep them out of the repo.
- Foundation finds the home folder and Application Support without `$HOME`, so a check run with only a temporary `HOME` still reads and writes the user's real `~/Library/Application Support/Launchy`. Set `CFFIXED_USER_HOME` to the temporary folder too (it moves Application Support but not UserDefaults: those writes reach the real preferences, so `defaults read com.zabaca.launchy` afterwards and delete the keys a check added), or pass the folder in, as `PaneFolder.migrateOldScratchFolder(in:)` takes it.
- Test zmx with a throwaway absolute `ZMX_DIR` (0.8.1 panics on a relative one, and refuses a long path: a scratch folder's is too long, so use a short one such as `/tmp/xyz`), never the user's `/tmp/zmx-<uid>`, and make sessions the way Launchy does, `zmx attach` through a pty (`script -q /dev/null zmx attach …`): sessions `zmx run` creates crash 0.8.1's daemon on the child side of fork and leave crash reports. Set `LAUNCHY_ZMX_DIR` too (Launchy and its relay read it), and unset `ZMX_SESSION` if the shell is itself in a zmx session, or `zmx attach` switches sessions and fails.

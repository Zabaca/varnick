# Where Varnick breaks

Failure modes that come from how Varnick is built: what a change can break even when it follows `CODING_STANDARDS.md`. `varnick-reviewer` checks every diff against this list (its Correctness axis); `varnick-planner` names the items a plan touches.

**Saved state** (`SessionStore.swift`, `Settings.swift`)
- `sessions.json` decodes as one `State`; a decode failure falls back to `State()` and silently drops every open tab and recent session. A renamed or retyped field breaks old files the same way a new non-optional one does.
- A tab's id is saved with it (`SavedTab.id`) and a tab saved without one takes its first pane's id in layout order, so `State.openTabs` is the one way to read the open tabs: the app and the relay both go through it, which also splits a tab with panes on two machines (the first piece keeps the id, each other takes its first pane's) and moves a mark on its panes to the tab only if all its Claude panes here are marked. Completed, the ended cards and the remembered tabs are `completedTabs`, `endedTabs` and `rememberedTabs`; the old keys `completed`, `ended` and `remembered` keep their type, are read once as one-pane tabs under the record's id (`completedList` and the others) and are saved absent, since a changed type under an old key would make the whole file unreadable. Never read `State.completed` and the others directly. Recent is `recentTabs`, the newest 20 closed tabs. The old `recent` key keeps its non-optional type, since a build without `recentTabs` needs it present to decode the file, and is still written: Recent's tabs flattened to a session per pane and per past conversation, each naming its tab in `SessionRecord.tab` (`State.flatRecent`: every tab's panes first, then the past conversations, so an older build's cap of 20 never cuts a tab for another's history; a past conversation keeps its own folder, `HeldConversation.folder`, since the older build checks the transcript there, and an id of its own that no pane's has), so a build before this one lists them and drops `recentTabs` and the histories, and a later build migrates them again. Recent is read through `recentList`, which migrates that key's sessions (a paired Mac's left out): those that ended in one tab are one closed tab, the newest the one pane and the rest its history, since they never ran together, and the tabs in `recentTabs` win by id. `restoreSessions` folds a migrated tab whose id is open into that open tab's history, or `rebuildRecent` would drop it at once, leaving out conversations another open tab holds and taking the rest out of the closed tabs' histories (`claim`). A tab's history is `SavedTab.history` and `TabRecord.history`, optional; Another machine's tabs are saved apart from this Mac's own, as `State.hostTabs` with `State.tabOrder` for the order of all of them (and `SavedTab.inControl`), so a build that doesn't know them ignores them, where it would restore their file, page and Transcript panes as its own: `State.openTabs` is still the one way to read the open tabs. `ClaudeTab.id` is that id (it can change, `take`); `ClaudeTab.viewID` is the views' own.
- `Settings.storeSkipPermissionsIfAbsent` tells an existing install by `sessions.json` existing, so it must run first in `applicationDidFinishLaunching`, before `makeModel` (its first `SessionStore.save` creates the file) and before anything reads `Settings.shared`; the relay and the command-line modes never call it. Skip permissions is stored once because a value worked out on each read would turn on at the second launch.
- `Settings.storeTextGenerationIfAbsent` runs right after it, for the same reason: `textGenerationRunOn` absent reads as Claude Code (`claude`, ADR 0029), so an install that never chose but already answers with this Mac's model (Hey Varnick on, or Gemma installed) gets `local` stored once at the first launch of the build; a default worked out on each read would move under it later. `TextRunOn` is Text generation's own three-way type; Search embeddings keeps `ModelRunOn`, since Claude Code can't embed. A build that predates `claude` reads it as unknown, which gives `local`, so going back a version is safe.

**The claude command line** (`ClaudeSession.startClaude` and the headless relay's `launch` in `HeadlessLaunch.swift`; the script, shell arguments and argument list are `ClaudeCommand`, in `Packages/VarnickPeer`)
- claude runs via the account's login shell (zsh, bash or sh from the account record, else `/bin/zsh`; the relay uses the account's own shell) as `-l -i -c 'exec claude "$@"'`, with its arguments passed positionally: user text (prompt, agent name, paths) goes in as its own argument, outside the script string.
- New sessions use `--session-id <id>`, resumes `--resume <id>`. The prompt follows `--` and has a trailing space when it has no whitespace (`ClaudeCommand.arguments`, `operand`), so a prompt that starts with a dash is a prompt, and one that is a command's name (`doctor`) isn't that command.
- The environment is deliberately minimal; claude gets only what is set for it, nothing inherited from the launcher.
- Screen access's `--mcp-config <json>` is `ClaudeCommand.arguments`'s optional `mcpConfig`, first of all; it is the one argument not stored on the record (see Screen access below).
- Restart (`ClaudeSession.restart`, the Restart button, ⌘⌥R, R on a board card) starts claude again in the same pane through `launchClaude(restarting: true)`, so it reads the current hook settings and gets the first turn word, the cleared subagent work records and a cleared stop file like any start (a stop file saved within `PaneFolder.staleWindow` of the restart would otherwise show the last run's background tasks). It resumes the conversation if its transcript exists (the hook's `transcript_path` when that is this conversation's file, else the computed path) and otherwise starts it again under its own id, with the prompt only while the pane has never moved off its first conversation (`record.conversation == nil`), since after /clear or /resume the prompt isn't that conversation's. The new zmx session is labelled with `record.origin` whatever `startedFor` is, or `hostEnd` would release a taken-over peer session instead of ending it. `restarting` makes `finish` ignore the old client's exit, so nothing may call `conclude` on its own while it is set; a pane closed meanwhile is concluded when the restart reaches its end. Only a pane that runs here with its client attached restarts (`canRestart`): never a card, a session on a peer (the host would have to start it, and the relay has no restart request), a pane not started yet, or one started for a peer (`startedFor`: the label would hand the session back to that peer). A pane in zmx has its zmx session killed and confirmed gone from a listing that came back (`Zmx.endConfirmed`, every call time-limited) before anything starts; zmx missing, silent, or still listing it makes the restart stop with `restartFailure` shown in the pane, never a launch, since a bare claude beside a live session would be a second one. The old client's exit is waited for too, and a restart's quick death (`launchedAt`, not `startedAt`) says it ended right after restarting.
- The folder of `VARNICK_SESSION_FILE` (`PaneFolder`) must exist before claude starts: the hook's `cat >` fails into a missing one, and the pane silently stops following `/clear` and `/resume`. Claude panes still running in zmx from before the `scratch` folder was renamed `panes` write through a link at the old name (`PaneFolder.migrateOldScratchFolder`), so that link stays until none of them runs.
- The turn hooks (ADR 0010, `ClaudeCommand.hookSettings`) are in the same `--settings` as the SessionStart hook, so a value claude rejects would cost the session file too. Each must print nothing and exit 0 (`UserPromptSubmit`'s output goes to Claude, `PermissionRequest`'s is a decision) and write only when the word changes, since the turn file's date is when that turn began, except `UserPromptSubmit`, which always writes working: a prompt begins a working period, and after Esc or a Deny the file still says working, so a write only on a change would leave the age counting from before it; they find the file from `VARNICK_SESSION_FILE`'s folder, so that variable stays beside it. Their SessionStart entries are only `clear` and `resume`: a compaction can come mid-turn, and the pane that starts claude writes the first word. `clear` writes working instead of waiting over a `plan` turn: approving a plan with "clear context" denies it, so no `PostToolUse` follows (untested whether that `clear` runs the hook). The permission entry's regular expression must keep matching every tool but `AskUserQuestion` and `ExitPlanMode`, which have entries of their own, or a dialog marks twice or not at all. Subagents and teammates run the lead's hooks and write the lead's turn file, so any of them can mark the pane, and an idle lead must go back to waiting, not working (`ClaudeCommand.askedCommand`, `answeredCommand`, `leadEndedCommand`). A `PermissionRequest` adds one file per asker to `.varnick-turn.askers/` (the input's `agent_id`, else `lead`; searched only before `hook_event_name`, since `tool_input` can hold any key) and, for the first asker, copies the turn file to `.varnick-turn.before` with `cp -p`: the date must stay, since the stop file counts as the turn's only within `PaneFolder.staleWindow` of it. `PostToolBatch` and `SubagentStop` remove that agent's file, and the one that empties the directory (`rmdir`) moves `.before` back, or writes working without it, only while the word is still permission. `Stop`, `StopFailure` and `UserPromptSubmit` drop the lead's file, since a Deny of the lead's own request fires no hook, and with other askers left they set `.before` to the word they wrote. What's left: a lead Deny followed by a subagent's request before the next prompt keeps the mark after that answer until the next prompt or stop; a request racing the answer that empties the directory, within milliseconds, can leave the restored word on the card while its dialog is open until its asker's next hook; there is no hook between Allow and the tool's end, so the mark stays while an allowed tool runs. `agent_id` is on a subagent's and a named agent's `PermissionRequest`, `PostToolBatch` and `SubagentStop` (2.1.295; after an Esc on the dialog too); a team's teammate is untested, and a Claude Code that drops it makes every asker `lead`, so any batch answers it. `PostToolBatch` is in every pane's settings, Skip permissions on or off: a pane with Skip permissions has shown a dialog (a teammate's Bash call, 2026-10-09). Hooks reach only panes started after the build is installed and Varnick restarted. The transcript correction (`PaneFolder.corrected`, shared by the app and both relays) is why `ClaudeSession.checkTurn` must watch the transcript's date too, and why `UserPromptSubmit` rewrites the file after an Esc. It matches Claude Code's undocumented interrupt text (`TranscriptReader.stoppedAt`), so a Claude Code that words it differently stops the correction with no error. `TranscriptReader.pendingBackground` reads the `turn_duration` field names (workflows only) and the English start of the notifications' `<summary>`: a renamed one, or a last `turn_duration` before the 64 KB tail, shows the card as Stopped with no error. Background shells, agents and teammates come from `.varnick-stop` (option 01, Background work): `PaneFolder.runningTasks` reads `background_tasks`' `type` strings (`shell`, `subagent`, `teammate`), `status`, `id` and `description`, so a renamed field or type, or a Claude Code that stops listing them, shows none with no error; they are subtracted by the notification's `<task-id>` (a shell's at any time, a subagent's only after the stop file's date) and a stop by the user by the English plain text that names the agents' descriptions. A teammate is busy or idle from the lead's transcript (`TranscriptReader.busyTeammates`, read incrementally in the app, whole on every ask in a relay, which is a new process each time): the `idle_notification` JSON (`from`, `timestamp`) in the `<teammate-message teammate_id=…>` wrapper of a user entry, the `Agent` tool call's `input.name` and `input.description` (the description is how a task is matched to a name), and the `SendMessage` call's `input.to`; a change to any shows an idle teammate as busy (a card stuck in Running) or a busy one as idle, with no error. An end in mid-turn arrives as an `attachment` entry, which `TranscriptReader.pendingBackground` must keep reading beside the user entries, or a shell that ended while a later turn ran shows as running. The `Stop` entry must write by rename and run in the same event as the turn word (the freshness window `PaneFolder.staleWindow` assumes it), and `StopFailure`'s entry must keep re-dating the file, or an API error drops the shells.
- The Problems board is behind a switch, off by default (Settings › Experimental, `Settings.problemsBoard`; on a headless host the file `~/.varnick/problems`, written by `install-peer.sh --problems` and removed by `--no-problems` or `--uninstall`, read by `HeadlessPeerHost.problemsBoard`). The host that runs a session decides, from its own switch, whoever asked for it, and reads it at each start or restart: `ClaudeCommand.arguments(problems:)` passes it to `hookSettings(problems:)`, which leaves the `WorkHooks` entries out when off and is otherwise byte-identical (a new caller must say which, there is no default; `Varnick --hook-settings` says true). A running session keeps the hooks it started with. Only the hooks and the display are gated: pane folders, `work-log`, `work_history`, `SessionRecord.workLinks`, `PeerWork` and `Varnick --problems` are not, so recorded links are kept; the Problems tab is the only place that shows them, so they are hidden while the switch is off and back when it is on. Everything that shows the Problems tab or reaches it needs the switch: `SessionBoard.hasProblems` gates the tab button, Tab and `show(.problems)`, and `LauncherCommand.available` gates `!problems`; a new way to open the tab must go through `show`.
- The Outline is behind a switch, off by default (Settings › Experimental, `Settings.outlineOn`, default false for every install: an existing user sees it vanish after upgrading until they turn it on). Off, nothing may load, write, move or delete `outline.json` (ADR 0030): the file is read only when the Outline first shows or a session's tool asks (`Outline.appear`, `loadForSession`), so every way in is gated before that: `showOutline` and `toggleOutline` (guard), the shortcut (`perform` leaves the key for the pane), `LauncherCommand.available` (so `!outline`/`!wf` are neither listed nor run), the Shortcuts row (filtered), and in Panel access `show` (`view: outline`, `command: outline`) and `OutlinePanelView.ready()`, which both `outline_read` and `outline_act` go through before anything else (`PanelRefusal.outlineOff`). The tools stay in the MCP server's list (`PanelMCP.tools`, `make check-mcp`): that process is separate from the app and cannot read the switch, so they refuse at the call, as the Problems tab does. Turning it off while it shows closes it (`LauncherModel.outlineSwitch`, which reads the value it is sent: the publisher sends before it is stored); `Outline.close()` flushes a change still pending, which is the user's own edit. The switch is checked again after the file loads (`ready()`) and in `outline_act`'s `allowed:` closure, right before the edit, so a call already under way when it turns off writes nothing. The hidden shortcut keeps its binding (`ShortcutAction.isHidden`): `Settings.set` ignores it in conflicts and `action(for:)` skips it, so binding ⌘⇧Y to another action neither unbinds it nor lets it shadow the new action. A new way to reach the Outline must check the switch before touching the file.
- The work-link hooks (ADR 0020, `WorkHooks`, in the same `--settings`) follow the turn hooks' rules: POSIX sh with grep, cut, tail, awk and git, no jq, working in bash, zsh and dash and on the headless Linux host; print nothing and exit 0 whatever happens, never block a tool (`PreToolUse` exit 2 would), write by rename, and find the pane folder from `VARNICK_SESSION_FILE`'s folder. `SessionStart`'s work entry is the one that prints, and to Claude: one line and the open problems, only where `$VARNICK_PROJECT` has `.claude/skills/work/SKILL.md` and `docs/problems`. Its `awk` runs under `LC_ALL=C` and cuts titles by bytes: in a UTF-8 locale macOS awk aborts on a cut inside a character, which drops the problem from the list. A JSON key is matched only after `{` or `,` with its quote raw (`field`), so a path quoted inside the content being written, whose quotes are escaped, can't pass for `file_path`; a value with a backslash escape is not matched, so such a path makes no link. A subagent's `agent_id` goes into a file name only if it is letters, digits, dashes and underscores. The `/work` marker is `VARNICK-WORK|<pane id>|<nonce>|<kind>|<value>|<repo>|` with the pane folder's own name, built by `work.sh` when it runs together with the file `.work-mark.<nonce>` in the pane folder (printing the script links nothing, and a marker for another pane is ignored); the hook after Bash reads every marker in its whole input, accepts one only if its nonce's file exists and deletes the file, and the last accepted wins, so a marker replayed in output (a transcript read back) changes nothing; `work.sh` sweeps nonce files over an hour old, and it refuses a repo or slug with `|`, a quote or a backslash. The hooks read their JSON keys with one `grep -E` and no filter language, so a new key they need goes into that pattern and the `case` after it. Every hook that changes a record appends a line to `work-log`, whose date is how the app learns to read the records again (`ClaudeSession.checkWork`), so `SubagentStop` logs an `end` line too, and a new hook that writes a record without logging leaves the app stale. An option record is never replaced by the path hook, only by `/work` (and `none`); a subagent with no record inherits the session's option only for the problem that option belongs to, so for another problem the path hook gives it a record of its own. The log line's seven tab-separated fields (`PaneWork.logged`) are read by the app and by the relay (`PeerWork.read`, which sends them to a paired Mac). The repo in a record is the main checkout (`git rev-parse --git-common-dir`), compared with a project's folder by `WorkRepo.key` (symlinks resolved), so a project listed through a symlink matches. A pane that starts claude removes the subagents' records (`PaneFolder.clearSubagentWork`, also in the relay's launch) and appends an `end` line to the log when it removed any, because a removal the log doesn't show leaves the app's cached record, and the dead subagent's link, live. `SessionRecord.workLinks` is optional, set once in `sessionExited` from the log (on a record with a `host`, from the host's last `status` answer), and `sessionExited` also writes it to `work_history` (below).
- A teammate outlives its lead's conversation across /clear, a continuation ("clear context") and /resume, so the teammate ledger (`TeamLedgers`, `TranscriptReader.busyTeammates`) reads the pane's earlier conversations too (`PaneFolder.earlierTranscripts`: the pane id's own, then those `.varnick-conversations` lists), or a teammate whose spawn is in one counts busy forever and the card stays in Running. A description is matched against the newest conversation with a spawn carrying it, so an old spawn of a finished teammate doesn't inflate the count; a name's busy and idle times come from all of them. The hook's file holds only the latest conversation and Claude Code's transcripts don't name the one before, so `PaneFolder.recordConversation` appends to that list as `corrected` reads a waiting turn: a conversation that never had a waiting read is missing from it. Pairing unspawned teammates by number was dropped because it could match the wrong one; don't bring it back.
- `/rename` names are read from Claude Code's undocumented transcript format (`TranscriptReader.customTitle`, `TranscriptSession.customTitle`: `custom-title` entries with a `customTitle` field), read whole by the history sync (the `custom_title` column) and, in a pane, from the last 64 KB each time the transcript changes (`ClaudeSession.checkRename`, kept in the pane's `TitleRecord`). A renamed entry type stops it with no error: the pane and search show Claude's own title (`ai-title`, also undocumented), or the first prompt's first line, instead of the user's name.

**Notices and the failed word** (`SessionNotifier.swift`, `NoticeRule` and `TurnFailure` in `Packages/VarnickPeer`, `TranscriptReader.apiFailure`, `PaneFolder.corrected`; `sessions-finish-unnoticed`, option 01; ADR 0010, amendment of 2026-10-14)
- The `failed` turn rests on Claude Code's undocumented API-error transcript entry (`TranscriptReader.apiFailure`): an `assistant` entry with `isApiErrorMessage: true` and the kind in `error` (`rate_limit`, `server_error`, `authentication_failed`; `overloaded` is expected, unseen), the last conversation entry of the 64 KB tail and dated no more than `PaneFolder.staleWindow` before the waiting turn began (`StopFailure` writes the turn file just after the entry). A renamed field or entry type reads the turn as an ordinary waiting and raises Done instead of an error, with no error of its own. Only a waiting turn with no background work is read for it, and an Esc-made waiting never is; it shares the tail read of `pendingBackground` (`endOfWaitingTurn`), so a change to one reader's tail handling is a change to the other's. Like `background` it is never written to the turn file and travels to peers as text, with its kind (`PeerSessionStatus.failure`, `PeerPane.failure`, `TurnFailure.wire`, protocol 27): a paired Mac on an older build is refused by the protocol check, and the headless relay raises Done for a failed turn until it is reinstalled. A kind this build doesn't know reads "API error", as a missing one does.
- The `Notification` hook must keep matching only `idle_prompt` (`ClaudeCommand.hookSettings`). A finished subagent's `agent_completed` notification would otherwise write waiting over a working lead, and Done would be raised while Claude goes on.
- `ClaudeSession.turn` reports a change of the turn's word, and only that, to `SessionNotifier` (`onTurnWordChange`): not a new date (a peer's moves with each reply every 5 s) and not a change of background counts. The first word read for a pane, and the first after the host stopped answering (`clearHostTurn` sets the turn to nil), is a starting point and raises nothing; clearing the turn to nil must stay that way or a host that comes back would raise Done. A pane raises nothing while it shows a card (`ClaudeSession.away`), and the tick drops a standing notice once its pane shows one, so a session raises a notice on one Mac at most: whoever shows no card.
- Done and an error are not raised on the read that sees them: the turn file is written just before `turn_duration`, so a read in that gap sees waiting with no background work yet, and the error entry can arrive a read after the waiting. They wait (`SessionNotifier.settle`) and are raised only if the same rule, run a second or more later on the turn as it is then, still raises them (for a pane on a peer, on its host's next reply). Waiting then failed in the same turn (dates within 2 s) is a raise, not a clear (`NoticeRule`'s same-turn row). Needs you is raised at once. A change that shortens the wait, or reads the turn only on a change of date, brings the false Done back.
- `NoticeRule.decide` is the one rule, and `phone-page-is-only-a-browser-tab` option 02 keeps a copy of its table for the phone's push in the page server's language (`PhonePage/pushrule.ts`, `decide`; the words and the kinds' wording are in `failureWord` and the worker's `sw.js`). A change to the table, the failed word, the `Turn` words or the wording of a kind is a change to both; `pushrule.test.ts` reads the Swift table and the `Turn` cases and fails when they differ from its own.
- A paired Mac's `status` reply carries the Esc mark (`PeerSessionStatus.esc`, protocol 27) with the word, and `ClaudeSession.follow` passes it as `PaneTurn.interrupted`, so Esc raises no Done for a session hosted on a peer either. A host's reader sets the mark only for a waiting made from the transcript's interrupt entry (Esc or Deny), so a peer on an older build isn't a case: the protocol check refuses it.
- Dormant panes (restored since the launch, never opened) have no watch of their own: `SessionNotifier`'s once-a-second tick calls `checkTurn` on each one whose zmx session exists (`LauncherModel.turnIsLive`), as the board does. That is on the main thread, with the panel hidden, for as long as Varnick runs: a stat of the turn, session and transcript files per pane, and the parse of the transcript's 64 KB tail when the transcript's date changed (as the board's). A dormant pane may belong to a peer that controls its zmx session, so before it notifies `SessionNotifier.raise` asks zmx for its control label, off the main thread, and raises only if no peer holds it; it never assumes the session is this Mac's.
- "On screen" (`LauncherModel.isOnScreen`) is the panel being the key window and showing the board's Sessions tab (the Problems tab shows no pane), or a tab with this pane focused, and not Settings. Any new full-panel view that covers the tabs must not count as showing a pane: it goes into `coversTabs`, which `showsTerminal` reads.
- The menu bar icon keeps its two template images; the dot is a subview of the status button (`NoticeDot`), and the notices are menu items tagged `AppDelegate.noticeItemTag` that `menuNeedsUpdate` replaces each time the menu opens. Nothing that finds a menu item by position (the Show Varnick title) may use `items.first`, since a notice stands there.
- A notice names a session by its title, so nothing about a notice may be logged. The sound is a system sound by name (`NoticeKind.soundName`): a Mac without it plays none.

**Messages** (`NotifyTool.swift`, `MCPServer.swift`, `PaneMessage.swift`, `ClaudeCommand.messageInputCommand`, `NoticeRule.decide(message:)` and `merge`, `SessionNotifier.messageChanged`, `PhonePage/pushwatch.ts` and `pushrule.ts`; `phone-page-is-only-a-browser-tab`, option 04; ADR 0038)
- **The hook is the only writer of the message file, and `--mcp` still never acts.** `notify` is answered by `NotifyTool.call` (a check of the arguments, nothing sent, nothing written); `ClaudeCommand.hookSettings` gives `PostToolUse` an entry for `^(mcp__varnick__notify|PushNotification)$` that saves its input raw to `.varnick-message` beside the turn file, by rename, in POSIX sh with no jq (the turn hooks' rules). The server's key in the pane's MCP config must stay `varnick` (`NotifyTool.server`): the tool's name in Claude Code, and so the hook's matcher and the `permissions.allow` entry, are `mcp__varnick__notify`. The prompt hook and the `/clear` hook remove the file, and every start of claude in a pane does (`PaneFolder.clearMessage`, in `launchClaude` and the headless `launch`).
- **Claude Code's side was checked on 2.1.300 with a throwaway `claude -p`** (hook dumps kept in the problem's scratch folder). PostToolUse fires for an MCP tool with `tool_name`, `tool_input` and `tool_response`; an MCP tool that answers `isError` fires `PostToolUseFailure` instead, so a refused `notify` (only an empty title is) is never recorded; `--settings` permissions add to the user's own, so `notify` is allowed with no dialog. **PushNotification was never seen to run:** it is behind a server-side flag of Claude Code's (`tengu_kairos_push_notifications`) plus `agentPushNotifEnabled`, and was not offered in a print-mode run on the user's account. Its input, read from the 2.1.300 binary, is `message` (non-empty, under 200 characters) and `status: "proactive"`, with no title; its result is `message`, `pushSent`, `localSent`, `disabledReason` (`config_off`, `user_present`, `no_transport`) and `sentAt`. `PaneMessage.parse` maps `message` to the title (one line, 80) and, when it is longer or has more lines, the body (300), reads a `title` and `body` too in case a release renames the fields, and says "Claude sent a notification" when it can place none. A `config_off` result is not a message: the user turned Claude's own pushes off (`PaneMessage.refusedByConfig` searches the result whole, as an object, a string or content blocks, for `config_off` or "disabled in /config", since the shape the hook sees is unverified). Whether the hook fires for PushNotification, and its real fields, are **unverified until a hand test with it on**; a rename of either costs the message's words, not the message.
- **The reader strips what a title must not carry** (`PaneMessage`: control and formatting characters, so a bidi override can't reorder the menu; white space made single spaces; a file over 64 KB or an unreadable one is none). The page server cuts again (`shapeSaid`) and so does the worker (`sw.js`), because the words end up on a lock screen.
- **One rule in two languages.** `NoticeRule.decide(message:)` and `merge` have a copy in `pushrule.ts` (`decideMessage`, `merge`): the first message read for a pane is a starting point (or, with none, a clear of a standing Message), a message whose id isn't the last one's raises a Message, a message gone clears a standing Message and nothing else, a Done folds into a standing Message, Needs you and an error replace it. Two readings are the same message exactly when their ids are equal, the message file's date on the host's clock in ms (`PaneMessage.id`, on the wire `PeerMessage.id`): no time tolerance, so an old message is never read as new on a poll and a second message close behind the first is another. `pushrule.test.ts` reads the Swift table's rows. A change to one is a change to both.
- **A message is read before the turn it comes with, on both sides,** or the Done is raised first and the fold fails: `ClaudeSession.checkTurn` calls `checkMessage` first and `follow` takes `said` before the turn; the page server's `observe` takes a pane's message before its turn. The fold has no time limit, so a message that stands unseen through a long turn swallows its Done.
- **A Done folded into a message is kept for the subscriptions that take no messages** (`Standing.folded`, `PushWatcher.effective`): the fold is a decision about the message, so a subscription with Messages off still gets the Done, and gets it from the Done's own settle. A subscription gets the message or the Done, never both. The Mac's `decide(message:)` raises nothing with its switch off, so a Done is its own notice there.
- **Alerts are bounded in two places.** The Mac sounds once a minute a pane (`SessionNotifier.lastMessageAlert`); a newer message within the minute only changes the menu line. The page server pushes a message at most once a minute a pane (`messageGapMs`, `lastMessagePush`), the newest standing message at the minute's end, on top of the 60 pushes an hour a device.
- **The words are in `message`, never in a push** (protocol 28): `PeerSessionStatus.message` and `PeerPane.message` carry title, body and id; the relay hides it from a device's `status` and keeps it in `tabs`, and the shaped pane (`shapePane`) carries it for the worker. A bump of `PeerProtocol.version` changes `server.ts`'s `PROTOCOL_VERSION` too. Every Mac and the headless host run one commit.
- **The presence marker must not exist when nothing will push.** `CLAUDE_CLIENT_PRESENCE_FILE` is set in every pane's environment (`ClaudeCommand.presenceEntry`, to `claude-client-present` in the page server's folder), and while that file exists Claude Code skips its own Remote Control mobile pushes (checked once per push event; its desktop notification is a separate check). The server makes it while a subscription exists and removes it when none does, at its start (a server killed hard leaves it, also when no push is set up at all), when push is off and when it stops (`presenceMarker`, `setupPush`, `server.ts`). Varnick ends the page with `zmx kill`, which sends the child SIGHUP and then SIGKILL, so the server stops on SIGHUP as on SIGTERM, and `PhonePageRunner` deletes the marker itself when it stops the server or the Phone page is turned off. A folder moved, or a server killed by anything else, leaves the user without Claude's own pushes; delete the file. A pane started before this build has neither the variable nor `notify` until it restarts.
- **Every Claude pane has an MCP server now,** about 19 MB each by the memory snapshot of 2026-10-13, and a headless host's too. A pane with Screen and Panel access off lists `notify` alone.
- **Checking:** `make check-mcp` covers the notify set (alone, with the others, absent with none named, the arguments); the rest is `bun test` and a hand test (the option's list).

**App panes** (`ClaudeSession.startApp`; the contract is in the `custom-apps` skill)

**Panel size** (`LauncherModel.panelHeight`, `LauncherView`)
- The panel is fixed-size, so `panelHeight` must add exactly the rows `searchContent` shows, in every branch: settings, board, outline and Resources (fixed, like settings), tab, prompt (the prompt line, then the suggestions or the sessions listed under it, each group of matches under a row for its tab that is shorter than a session's: `resultRowsHeight`, `tabRowHeight`), search (`?`), `?` alone (the empty state's height), command, empty field (the session list: this Mac's tabs, a row per tab of each paired Mac under its name, then Recent's closed tabs). - `refreshSearch` deletes every row it didn't write and `toEmbed` deletes every embedding key it doesn't know, so session rows and session embeddings must be written and counted as current in those same passes, or the next sync removes them. A session has no vector of its own once embedded: its exchanges are keyed `session:<id>#<n>` in `entries` (`SessionExchanges`), `toEmbed` counts every exchange key of every session it lists as current (the paired Macs' too, built from their prompts and replies with this Mac's embedder), and a session's old single vector, `session:<id>`, is counted as current as stored until one of its exchanges has a vector, then dropped; `refreshSearch` writes the row's own embedding as nil from then on. The relay opens the database read-only beside a Varnick that may not have restarted, so `sessionEntries` checks that the table and the column exist and `peerRows` skips the NULL check without the column. A peer's sessions keep the title the host sent.

A request for a page's description (`toFetch`) goes only to a URL this Mac holds (`Entry.fetchURL`), never to one only a paired Mac visited.

The hot upsert (`upsertSQL`, `upsertTermSQL`) runs for every Chrome row each minute and must move `changed` only when a value `pages` sends changes; `store` stamps every description it writes.
- `session_tabs` (host '' for this Mac, a paired Mac's peer id otherwise) is in the archive half, made if it isn't there (`CREATE TABLE IF NOT EXISTS`) and changed by no migration, so a database from before it has no table until its Varnick restarts: the reads check that it exists (`rowTabs`) or find nothing (`FavoritesStore.tabs(ofSessions:)`). This Mac's rows are written from the saved state at each sync (`SessionTabs.read`: open tabs, then Recent, Stopped and Completed, a conversation under the first that holds it) and at once when a tab is named or closes (`HistorySync.keepTabs`, off the main thread), and deleted only with their session, never because a tab left the state. A paired Mac's are replaced whole by each `rows` answer (`PeerRowTab`, sent whole whatever `since` says, since a conversation moves to another tab with no change to its transcript) and deleted when the Mac is no longer paired. A match's tab is worked out live first (`tabHolding`: this Mac's tabs, Recent, Stopped and Completed, a paired Mac's listing and Recent) and from the table only when nothing live holds it (`groupedByTab`). `SearchResult.tab` is set there only; a tab's row is a `SearchResult` of source `tab` and a negative id that no database row has, so the footer's count, the preview, ⌘↩ and the relevance filter's offsets (`sessionCount` includes the tab rows) must each skip or allow for it.

**Sessions and tabs**
- The strip's +N chip is orange while a hidden tab has a session waiting on the user, and the projects column's and list's rows carry an orange count of their tabs that wait (`LauncherModel.tabMarks`, the board's `Turn.mark`: a permission dialog, a question, a plan, an MCP request; waiting for the next prompt is not one). A pane closed in a tab that stays open, and a conversation /clear left, are history only and never reach Recent, which holds closed tabs (`addRecent`, from `sessionExited`, for a tab that ran on this Mac). A tab that shows a paired Mac's sessions keeps no history here: its host does. A tab open here, or listed open by its host, or whose Claude conversations are all open, is dropped from Recent as from the ended cards (`rebuildRecent`), so reopening one, or a peer's `reopen` of its id, takes it out.
- A Claude pane nothing was ever sent in (no prompt and no transcript: `SessionRecord.isUntouched`, `HeadlessSession.isUntouched`) comes back like a terminal does, fresh in its folder and in its place, on a relaunch, a reopen from Recent, Completed or a stopped card, a host's `reopen` and a lost session started again (`hostResume`, `resumeDecision`). It never sends a prompt: a pane that had one and lost its transcript (Claude deletes old ones) is dropped, or ended, as before. "Has a conversation" is a transcript with something in it (`TranscriptReader.hasConversation`): Claude Code can leave an empty file for a session with no message, and then `--resume` says "No conversation found" while `--session-id` refuses the id as in use, so a fresh start removes the empty file first (`removeEmpty`). A tab is listed in Recent, Completed and Stopped when a Claude pane of it has a conversation, or when it has an untouched one beside another pane (`TabRecord.resumable`); one untouched Claude pane alone is not listed. A peer's Recent lists only Claude sessions with a conversation (`PeerRecentTabs`), so a tab with none is offered to no other machine.
- Ending a session keeps the tab model consistent: removing the last pane removes the tab, and `activeTab`, `sessionSelection` and `renamingTab` never point at a removed tab.
- `PaneView` keys each leaf's whole view by `session.id`, never by its place or only its terminal container; the frozen screen, the address bar and the container all depend on it (the comment there). A move changes the tree in one main-actor step, so no session is made, ended or started again.
- The pane drag (`PaneDrag`): panes' frames are reported through a preference into `PaneDrag.frames`, which must stay unpublished. `PaneDropZones.read` decides what takes a drop and what the overlay draws, and the drop uses the target of the last move, so a change to the rules belongs there alone. The grip stays on screen for the whole of its own drag (`drag.dragged`), or SwiftUI cancels the gesture without an end. The veil over the dragged pane is drawn, not an opacity, which isn't known to reach a hosted AppKit view.

Start panes after the update, as `TerminalHost` does.

Every frame change of a terminal is sent to its pty, and Claude with `"tui": "fullscreen"` draws on the alternate screen, which has no scrollback, so a shrink and a grow in one turn (the panel at the board's size, then `placePanel`'s) clips the screen for good: Claude sees its old size again and doesn't repaint. Deferred, the two collapse into no change. A client starts through `launchProcess`, which fits first; a container out of a window fits nothing, so a hidden pane's pty keeps its size.
- A session is named, on the board and in search, by the ⌘⇧R name of its one-pane tab, else its /rename name, else Claude's latest title, else (search) the first prompt's first line or (a pane) its prompt. Varnick no longer writes titles; its text generation is for spoken requests, loaded on the first one. A `sessions.json` that doesn't decode means the names are unknown, never that there are none: the step writes and deletes nothing. A name outlives its tab, and is deleted when a one-pane tab holds the conversation with no name; a tab with several panes writes and deletes nothing. So every way of opening a conversation in a new tab on this Mac must give that tab the name back (`LauncherModel.resume` and `hostResumeConversation` do, from `FavoritesStore.tabName(ofSession:)`), or the next sync finds the new tab unnamed and deletes the row. Naming a one-pane tab writes the row at once (`HistorySync.keepName`), so a tab closed before the next sync keeps it. Names are bound as parameters and never logged. A pane on a peer reads no transcript here: its host's label is what shows.
- Whether a session can be resumed is computed from its directory path (non-alphanumerics become `-`), so changing how `directory` is set changes which sessions resume.

**Peers** (`SSHRunner.swift`, `MacPeerHost.swift`, `Peers.swift`, `Packages/VarnickPeer`; ADR 0007)
- `Packages/VarnickPeer` is built by both the app and the Linux relay (`varnick-peer`), so a change there must compile on Linux too: `swift build` in the package on a Linux machine with Swift (swiftly puts it at `~/.local/share/swiftly/bin/swift`), with anything Darwin-only under `#if os(Linux)` or `#if canImport(Darwin)`, and no AppKit, SwiftUI, CryptoKit or app type. The app reaches it through `public`, since `package` access stops at the path dependency: a new declaration the app uses needs `public`, and a struct it builds field by field a public initialiser. The Mac's own answers are `MacPeerHost` (the `PeerHost` seam); the support folder is `SupportFolder`, and on a Mac its path never moves.
- Every call to another Mac goes through `SSHRunner`, which builds the `ssh` command for three kinds: `run` for a request (off the main actor, with a deadline), `terminalCommand` for a pane's terminal and `stream` for a command that runs until cancelled (a card's `watch`). Never a bare `Process` for `ssh`, never `waitUntilExit`, never from `body`. A Mac that isn't in the peer list is contacted only by Find Macs and Add.
- A change to a request or reply shape bumps `PeerProtocol.version`, or two builds misread each other with no error. The relay parses a request's version before anything else, so keep `PeerRequestHead` to `v`, `op` and `by`. The exception is `upgrade` and `restart` (`PeerProtocol.answersAnyVersion`): the frozen shapes and envelope are in the doc comments of `PeerMaintenanceAsk`, `PeerUpgradeReport`, `PeerRestartReport`, `PeerReply` and `PeerRequestHead`. A reply to them sets nothing but the envelope keys and its own report, since an older asker decodes the whole `PeerReply`, and is `ok` even for a refusal, since `PeerClient.verdict` drops the body of a failed one.
- A socket or control path over 103 bytes fails to bind with no useful error, and a long `ControlPath` also needs ssh's 17-character temporary suffix (`PeerSocket.path`, `SSHRunner.controlPath` check both). A path with a space goes into an ssh `-o` value in double quotes.
- On a Mac the relay never writes UserDefaults, since the app may be running. Only a hello with `pair` set adds a peer, so a refresh doesn't undo a removal.
- A headless host (`Sources/varnick-peer` in the package; its install root, state rule and installer are in ADR 0009, which also says to reinstall it at every protocol bump, now its row's Upgrade button; see the upgrade bullets below) answers everything but a hello only to a Mac in `peers.json` (or a device, below), checked first, and never calls a Mac back. A `peers.json` that isn't a list, or can't be read, fails a pairing instead of being replaced. Point a check at a copy of the binary, never at `~/.varnick`.
- A Mac's SSH command (`PeerLink.remoteCommand`) tries the macOS link, then `$HOME/.varnick/varnick-peer`, and `exec`s it so the relay is the ssh's own process. Keep it one POSIX literal that a request is appended to: `scripts/install-peer.sh` reads it from `PeerSocket.swift` at HEAD to verify with the very command a Mac sends.
- A peer's request runs the launch snapshot, not the build folder (`LaunchSnapshot`, `PeerLink.refresh`): at each launch Varnick clones its binary, zmx, build stamp and Phone page files into `.build/snapshots/` (the first 12 characters of the commit, or `unstamped`, then the launch time) and points the link at that binary, so a `make build` changes nothing a peer reaches until Varnick restarts. The relay finds zmx beside itself, so a file the relay needs at run time must be copied there too, or it is the build folder's, which a build rewrites. Only the app takes a snapshot (the relay exits before anything of the app starts). The earlier snapshots are removed only once the link is seen pointing at the new one; a request that arrives mid-swap can fail once, and a running `watch` or `attach` keeps its open files. Where Varnick isn't running from a checkout's `.build`, or the copy fails, the link points at the binary in place. A bundle is never a checkout build, wherever it sits (one under `.build/app/` included): `ResourceFolder.current.inBundle` makes `take()` and `LaunchSnapshot.checkout` nil. The resource folder is a bundle's `Contents/Resources`, else the executable's own folder, found from the executable with links resolved: the relay runs through the `varnick-peer` link, where `Bundle.main` answers for the link's folder, so a lookup that skips the resolving finds the Application Support folder instead. `make build` writes the stamp (`BuildStamp`) as its last step, only when everything before succeeded, so it names the last good build, not the running one; a stamp older than the binary is ignored (a plain `swift build`, or a build that failed after linking), and compare stamps with `isSameBuild(as:)`, never with the time.
- A Mac answers `upgrade` and `restart` in its running Varnick (`PeerManager.handle` before the version check, then `BuildUpgrade`), and its relay (`MacPeerHost.upgrade`, `restart`) forwards them and, with Varnick not running, answers the build fields from the stamps and git with `running: false` and a refused state. The relay must never read `LaunchSnapshot.current` (it would snapshot the snapshot): its stamp is `LaunchSnapshot.relayStamp()`, and the app's readers use `LaunchSnapshot.runningStamp` (in a bundle the resource folder's stamp, read without the "older than the binary" rule, since signing rewrites the binary after the stamp). The relay's reply carries its build, so a stamp read from the link's folder names the wrong one. Everything in `answer(upgrade:)` has to end inside 10 s, since the relay waits that long for the socket and a longer one reads as "Varnick isn't running": a fetch is waited for 8 s, a `begin` 6.5 s, and the report's git reads 1 s in all (the report then has the running commit alone; it takes about 0.1 s even with every core busy). The relay's own fallback, with Varnick not running, gives the same reads 2 s each and 3 s in all. `CheckoutGit` and `BuildProcesses` go through `Subprocess`, and the relay, which is synchronous, waits on them with `MacPeerHost.blocking`.
- The target is origin/main alone (`CheckoutGit`): fetch is `+refs/heads/main:refs/remotes/origin/main` with `gc.auto` and `maintenance.auto` off (a detached gc after a fetch is what XProtect dislikes), read-only commands run with `GIT_OPTIONAL_LOCKS=0` so they never write the user's index, and the only change to the checkout is `merge --ff-only`, which acts on HEAD whatever it names: so `CheckoutGit.settle` reads the branch and the changes again right before it (the fetch before it can take 60 s, and a branch switched or a file edited meanwhile would be moved or built). Never `pull`, `checkout` or `reset`. A fetch runs once at a time (`OriginWatch`): a report with `fetch` and Settings › Peers opening join one under way or start one, and a report without it starts one only when the last try is over 10 minutes old, a failed try counting (`FetchRecord.attempted`), so a failing remote isn't hit at every report.
- The build runs only in the zmx session `varnick-upgrade` (`UpgradeRunner`), never in process: XProtect once killed a Claude process that ran installs, launchctl and a downloaded binary together. Its log is emptied before the upgrade is marked building, and nothing resolves that state while the session is still being started (`BuildUpgrade.pipeline`): the log's last line, `varnick-build-exit=<n>`, is the only record of how `make` ended (a zmx session's exit status says nothing), and an old one or a session not there yet would read as an end. A zmx session with no such line that is gone is a failure. The result is kept in `upgrade/state.json` in Application Support, so a relaunch picks a build up; a built state ends once the running commit is the built one. It runs with Varnick's environment less `ZMX_*` and `GIT_*` and the system tools first on `PATH` (no login shell), so a build step that needs another tool must find it there.
- A restart (`BuildUpgrade.answer(restart:)`) is refused while an upgrade runs, while a `make` or SwiftPM process has the checkout as its working folder (`BuildProcesses`, `ps` then `lsof`), and when no stamp newer than the running build waits, or the one that waits was made with uncommitted changes or off main. It starts after the reply is sent (a second later) as `make run` does, `scripts/restart.sh` under `perl`'s `setsid`, and only Varnick restarts. The panes it says would end (`LauncherModel.restartImpact`) must follow what the next launch does: a Claude or terminal pane survives only with Keep sessions running on now (the sweep kills the session of a restored pane otherwise), and an app's server always does, since the one SIGTERM handler (`AppDelegate.onTerminate`) only closes saved audio and `_exit(0)`s, and `stopAppServers` never runs at a restart. Any more in that handler (stopping app servers, `applicationWillTerminate`, `exit`) would change that list.
- The status menu's Restart Varnick (`BuildUpgrade.restartFromMenu`) shares `spawnRestart` and `restartImpact` with the peers' restart, so the rules above hold for it. It skips the newer-build check, so `BuildUpgrade.newerBuildNote` has to warn when a build on disk would be started and it would void the macOS permission grants: only an ad-hoc signed build does (`startingVoidsGrants` reads the ad-hoc flag of the waiting binary, never the team identifier; a Developer ID build keeps its grants, ADR 0022). The card (`RestartCard`) takes every key while it shows, and `panelHeight` must include it, or a bare search field clips it.
- The relay's process arguments must stay unlike `make run`'s kill pattern (anchored to the bare binary path), or a restart kills a peer's request.
- A zmx run (the build, a headless install; `ZmxRun`) whose `zmx ls --short` can't be answered is still `running` and never `lost`: only a listing that came back may say a session is gone (`zmx ls --short` exits 0 with no output when none exist, and 1 on an unusable socket folder, so empty is a success). But a run no listing has answered for 30 minutes is failed ("Couldn't ask zmx about the build"), or `building` would stay for ever and keep Upgrade and Restart refused.
- A headless host is upgraded from a Mac, never by itself and never with `begin` (its relay answers "upgraded from a Mac, with the installer"): `HeadlessUpgrade` runs `scripts/install-peer.sh <host> --commit <origin/main>` in the zmx session `varnick-install-<slug>` (the slug carries a hash of the address, so two addresses never share a session or a log), judged by its `VERIFY=ok` and `BUILD` markers and never by an exit status. What the installer ships is `RelayFiles.pathspecs` in `RelayComparison.swift`, which also decides "relay unchanged": change both together. The installer ships and reads what is committed at the commit, its far half included; the far half says what it supports in its `# supports: RUN LOCK` line (add a word for a feature the near half adapts to, never remove one), installs on one host queue on `~/.varnick/install.lock`, and takes per-run tarballs (`incoming-<run>.tar.gz`) that other runs' far halves remove once a day old (uninstall removes only its own and the day-old ones, since a newer one may belong to an install queued on the lock). A comparison fetches only past the 10-minute rule. Known limit: `RelayFiles.pathspecs` always counts `PhonePage`, since a headless host's report doesn't say whether it has a page, so a page-only change offers Upgrade on a host with none. A headless row's states (`HeadlessUpgradeState`) are told apart (not compared yet, couldn't compare, ahead of origin/main, up to date), and `offersUpgrade` (behind, or a failed install to retry) is the one rule the row and Upgrade all share.
- Upgrade all and Restart all (`PeerBulk`; the lines are `BulkPlanner`'s, from each machine's last report): Upgrade all begins the other machines together and this Mac after their begin replies, then waits by asking for reports itself, since Settings' poll may not be running; nothing restarts. Restart all lists only Macs with a build waiting, never a headless host, and each Mac is asked again before its confirm (`PeerBuilds.sendRestart`, the same path as one row's Restart Varnick): a list that changed, or a refusal, skips that Mac. This Mac restarts last, once the others have answered or 15 s have passed, and its report is written to `upgrade/restart-all.json` before the restart so the next Varnick shows it once (only a launch other than the one that saved it does, and a file over 10 minutes old is dropped). A confirmation is dropped when Settings stops showing; a run goes on.
- The Tailscale CLI in the app bundle starts the GUI instead unless `TERM` is set.
- A pane with `record.host` (a session on a peer) is that `ssh` client (`startOnHost`), never inside this Mac's zmx and never given `Zmx.kill` (`ownsZmxSession` is false for it). Only the host kills the session, when the Mac in control sends `end` for a session it started for that Mac; the host accepts `end` only from a listed peer or device the session's `varnick-control` label names, and releases instead of killing when the session didn't originate from the asker (the bullet on closing in control, below).
- A Claude client exiting isn't the pane ending: `finish` asks the host's zmx (`clientExited`) and a session still running and labelled for another Mac leaves the pane open on a card. Keep the label, not timing, as the test, and keep a takeover relabelling before it detaches. A card for a lost link or an unreachable host asks again every few seconds (`Away.isLink`), so it can't stick; one that needs the user or a start under way doesn't (`Away.skipsAutomaticCheck`).
- A pane on the host never attaches to a session another Mac controls (`startClaude` checks the label before a restored pane attaches); a second client would make two keyboards type into it. The card on the host asks before closing, since it is the only pane the session has here.
- The launch sweep is unchanged except for one exception: it never kills a session whose `varnick-control` label names a listed peer or a listed device (`Zmx.sessionsToKill(sparing:)`; `cleanUpAfterLastRun` passes both lists' ids), since that Mac or device may be typing into one whose pane here was closed.
- A tab is taken by `take`, answered by the relay alone from zmx and the host's `tabs`: every running Claude and terminal pane that the asker doesn't hold is relabelled first and then detached, in that order (the label before the detach, as for one pane), and the asker attaches each pane without `take` (`LauncherModel.takeOver(tabOf:)`, the page's `/api/take`). A card's Take over takes every card of its tab: on the host's own tab each pane takes itself in turn. The relay's `attach` checks that the session exists and, without take, that its label names the caller (an unlabelled session is its host's). `zmx attach` creates a session for a missing name and has no flag to refuse, so the relay gives it `/usr/bin/false` as the command: one that lost a race ends at once instead of running a login shell. `attach` needs only zmx, and `status` zmx and the saved tabs, so keep both working with Varnick not running.
- Take over relabels, then detaches, then attaches (`ClaudeSession.takeOver`; the relay's `attach` with take on a peer): the Mac that sees its client exit tells a taken session from an ended one by the label, so the label comes first. On the host the pane's client restarts in zmx whatever Keep sessions running says now (`launchClaude` passes `alwaysInZmx`), and a session this Mac started for a peer stops being given that peer's labels (`startedFor`), since attaching with it would hand the session straight back. Only its control label is handed back that way: `varnick-origin` is set when the session is created and stays.
- A client for a pane coming back from a card (take over, Reconnect, going live after a release) starts only once the terminal view is on screen at its real size (`resumeClient`, `startWhenHosted`). While the card shows, the view is in no window and keeps its first grid, so a client started at once is told that size: zmx draws the saved screen and Claude repaints for it, the real size arrives after, and the transcript above the prompt box ends up missing (seen on opening a peer's session a second time). A fresh pane is safe because it starts after `TerminalHost` hosts it; keep every start that follows `away = nil` behind the same wait.
- A tab is the host's (ADR 0034). Its `tabs` listing is `PeerTab`s: `PeerLayout` is `{pane}` or `{axis, fraction, parts}` so the page reads it as plain JSON; a field of `PeerPane` is only ever added, as an optional, with its explicit `CodingKeys` (`kind` and `turn` travel as words, so a kind or turn this build doesn't know reads as nil). - On a headless host (`HeadlessHosting.swift`) every session carries a control label naming a Mac or a device, and release keeps it: it detaches the clients and never clears the label (`Zmx.release`, which clears it, is the Mac host's). - A headless host's `start` runs in this order: the record (saved with `starting`), the pane folder, the pty client (`PtyClient`: `openpty`, `posix_spawn` with SETSID, signals reset), the wait for `varnick=1` and the control label (`zmx get` succeeds before `attach --labels` has set them), then the detach of the relay's own client. - The state lock (`StateFolder.locked`) is held for a read or a write of a file and never across a wait, whether for zmx, the pty or a sleep: the other Mac's polls would stall behind it. A start takes it for each record write on its own.
- A headless host reconciles its records with zmx before any request reads them (`StateFolder.reconcile`; `HeadlessLifecycle` is these rules' code, and this is where they are written): a session gone in this boot is ended, one gone from an earlier boot (the record's `bootID` differs) is lost and left with `ended` unset, and a start that never handed over, with no session, is ended once it is 30 s old. A listing that failed (`Zmx.listedSessions` nil), or a host whose boot id can't be read (for any record but a stuck start), changes nothing, since only a listing that came back may say a session is gone; the hand listing and `recent` say so instead of showing sessions as gone. - Only a lost record is ever started again, and only for a Mac's `start` with `resume`, which `claimResume` decides and marks `starting` under the lock, so two panes can't both start it (the other gets `running` or `closing`). Resuming an ended conversation is the `resume` request, which refuses one a running or starting record has open (`isHeld`, checked in the same lock as the record's save). `VARNICK_BOOT_ID` replaces the boot id for a check, and a Mac's ssh command never sets it.

- The frozen screen is `zmx history --vt` read from the host (sent to a card by `watch`; the `screen` request, served by the relay from zmx alone, is no card's path now and is kept for checks), and it is never fed to a live terminal: it replays the private modes the session had set (mouse, focus, paste, alternate screen), and a shell that received them printed the reports as text. `FrozenScreen.prepare` strips them and cuts to a tail before it is sent, and the view (`FrozenTerminalView`) has no process, drops what the terminal would send, and never becomes first responder. - `watch` is the live screen of a card (ADR 0008, which has the timings and counts), answered by the relay alone like `attach` and `status`, so it works with Varnick not running. It prints one reply line, then frames (`WatchFrames`), with blank keep-alive lines, until its input ends, a write fails or the session's socket closes (Take over, Release and the session ending all close it). `ZmxReader` is the one reader, run by the relay and, in process, by the host's own card; a card for a session on a peer reads the peer's relay through `PeerManager.watch` (`ClaudeSession.startWatching` picks). It sends only history requests (`ZmxWire.historyRequest`), never input, Init or Resize: any of those makes it a terminal, the leader or a sender of focus reports. It never stops reading the socket, or zmx queues output for it without limit, and its socket never raises SIGPIPE (`SO_NOSIGPIPE`; the relay also ignores the signal), since a signal would end every session in the app. A pending frame is replaced by a newer one, never queued. The keep-alive is what ends the relay after the viewer's ssh is killed on a shared connection, which sshd alone doesn't notice. A zmx pin bump rechecks the socket header, the tags and the history request in `ZmxWire`.
- A reader counts as a zmx client, so every client count that says "Controlled on" or "Last controlled on" goes through `Zmx.statuses`, which subtracts the live readers in `ReaderRegistry` (one empty file per reader, written on its first history reply and removed before it disconnects; a file whose pid is gone is skipped and removed). Reading `zmx ls` directly for a count would show "Controlled on" for a Mac that quit. A card runs a reader only while a view of it is on screen in a visible window (`FrozenScreenContainer.onShownChange`, counted per container, since a new one can join before the old leaves) and for a short while after, and never takes the reader's ending for the session's: the card's own check decides that.
- A peer's card holds one `watch` channel to its host while a view of it is shown, on the same shared connection as the panes (ADR 0008 has the count the spike ran). `SSHRunner.stream` keeps the ssh's input a pipe open for its whole life, never `/dev/null`: that is how the relay learns its viewer is gone (Varnick quitting or crashing closes it; cancelling closes it, then terminates the ssh after 1 s and kills it after 2 s, a command that reads its input ending sooner than a killed ssh does). A stream's ending is never a timeout, so it never asks the shared connection to exit, and a channel ending is never the session ending: the card's own check decides that, as for the host's card. `PeerManager.watch` skips lines before the reply, checks its version and `ok`, and refuses a peer known to speak another version before sending anything. A card's frames hop to the main actor and check the generation, like the host's.
- A peer's open tabs (`tabs`, ADR 0034, read by the relay from `sessions.json` and zmx, so it works with Varnick not running) are rows of `panelHeight`'s session-list branch (a header per Mac and a row per tab: `peerListTabs`, built from `peerTabs`, the last `tabs` answer of each Mac) and sit between this Mac's tabs and Recent in `move`, `openSelected` and `sessionSelection`. `peerOpenSessions`, which the board, the remembered tabs and the marks read, is the same answer flattened to its running Claude panes (`PeerTab.openSessions`), so those paths still see sessions. Opening one (↩, `openPeerTab`; ↩ on a Recent or search row whose tab is open there, `openPeerSession`) is `openHostTab`: the tab opens whole in the host's layout, every Claude and terminal pane on its card, never attached, whoever is in control (`opensOnCard`, asked of the host through `settle`, like a restored pane, and starting nothing). Explicitly resuming an ended session is a different path and starts and attaches.
- Done marks belong to the tab's host (ADR 0032, which has who may send `done`, where each host keeps a mark and the rules for taking in an answer). Gotchas: `done` names a tab (`PeerRequest.tab`), never a session; `tabs` carries each tab's name and mark (`PeerTab.name`, `doneAge`), which `PeerTab.openSessions` copies onto each session (`PeerOpenSession.tab`, `tabName`, `doneAge`), `recent` the closed tabs, each with its sessions, name and mark (`PeerRecentTab`, protocol 23), and `start` and `resume` reply with the tab the host put the session in (`PeerReply.tab`), which the asking tab adopts once (`ClaudeTab.awaitsHostTab`, `adopt`), and every listing sets (`followHostTabs`, `take`) for a tab saved before ids were shared or one whose sessions came from a multi-pane host tab; an ended tab's mark reaches the wire from Completed by tab id (`PeerRecentTabs.list`), never from the Recent record; a headless host's records are tabs under the record's id unless a `resume` named another (`HeadlessSession.done` is the tab's mark on each of its records, so `done` finds them by the tab id, and a resume no longer clears it); a new optional field of `PeerOpenSession` goes in its explicit `CodingKeys`; an answer asked before this Mac's own Done, clear or open of a tab id is ignored for it (`actedHereAt`, `askPredatesAct`), so every new place that marks or opens another host's tab calls `noteActed`; an unmarked listing removes only marks flagged `hostHoldsDone`; a mark past Completed's cap of 20 (`insertCompleted`) leaves its ended or remembered card where it was, but a listed open tab its host marks is never a Running or Stopped card, so it is on no card (`boardPeerTabs`). The earlier `resume` per session naming a tab (`hostTabs`, `resumeTab`) is gone with it. A headless host copies no mark onto the reopened records: `claimReopen` clears it. A session with a pane here is never remembered or put in Completed under another host tab's id (`remember`, `takeInHostMark`), or its end would leave a stray ended card. A tab is one machine's, and a tab saved with panes on two machines is split at load (`SavedTab.splitByMachine`); its splits are the host's (below).

The record changes without `onConversationChange`: the host's own pane puts the conversation left behind in the host's Recent. The title is the host pane's, sent only while the host is in control and applied only where this pane has no client.
- A session gone on its host is started again only into the pane the host restored for it and hasn't started (`start` with `resume`, `hostResume`), labelled for the Mac that asked, which then attaches with take. A host with no such pane answers `ended` and the peer's pane closes: that session was ended there on purpose, and nothing is ever started behind the user's back. Resuming an ended session is an explicit action (Recent, search), a different request (`resume`). - A pane's work links travel in `PeerSessionStatus.work` and `PeerOpenSession.work` (`PeerWork`, protocol 18, ADR 0020), beside the turn and with explicit `CodingKeys` like it. - `work_history` (`HistorySync.archiveSchema`, ADR 0020) is in the archive half of the search database, created by `prepare` with `IF NOT EXISTS` and changed by no migration, so it is safe on an existing database and on one an older Varnick made (that Varnick ignores it). - A peer's session rows (`rows`) and Recent (`recent`) are served by the relay alone, `rows` from the search database read-only (the path is `VARNICK_DB`, else the file the running Varnick writes at launch, `PeerSearchDatabase`; the relay isn't started like Varnick) and `recent` from `sessions.json`. `rows` carries the tab that holds each of its conversations (`PeerReply.rowTabs`, protocol 23) and each session's replies beside its prompts (`PeerSessionRow.replies`, nil for a row its Mac hasn't read with them), and a Mac answers it only while no session row of its own has NULL `replies` (`peerRows`): such rows, written by a build that kept none, are read again at the first sync after the upgrade, and every sync ends by giving the rows it couldn't reach (an unreadable transcript, an unlisted folder) empty replies so they never block `rows` for good. Without that, a Mac asking in the minute after the other upgraded would get rows without replies, then ask only for later changes, and get the replies at its next launch. Until then it answers with a failure, and the asker keeps its rows and asks again at its next sync. `rows` limits itself to those changed since a stamp and always lists every id, which is how a session that is gone leaves the other Mac. `HistorySync.pullPeers` writes them to `peer_sessions` and the tabs to `session_tabs` in the sync, reading each Mac in full once per launch, and again when the ids it lists have no rows here (a session whose folder came back, which no stamp of changes shows); a Mac that doesn't answer keeps its rows (the failure is logged), and the rows of a Mac no longer paired are deleted in the same pass, which removing it starts at once. The sync waits for the pull, so keep its timeout short (`peerPullTimeout`). A search row carries its Mac in `favorites.host`, written by `refreshSearch` from the entry that won, so nothing decides it a second time.
- A peer's pages (`pages`) are served by the relay alone, from the Mac's own archive tables read-only (never the `peer_*` ones), in pages of about 2 MB ordered by (`changed`, key), with a cursor of both, since rows written in one sync share `changed`. The cursor's key is a digest, which the relay finds again among the rows of that stamp (not found: the stamp repeats, never skips), so no URL, which can carry sign-in parameters, is saved in `meta` or sent in a request. A reply also says whether more remain and how many pages and search terms the archive holds. `HistorySync.pullPeers` sends it in the same pass as `rows`, one reply per Mac per sync, from the cursor kept for that Mac (`PagesRead`, in `meta` under `peer_pages_read:<id>`, written in the transaction that stores the rows, so a relaunch reads nothing again). A full read, from zero, happens only when this Mac holds no rows from that Mac, or when an ask that says nothing more remains finds fewer pages or search terms kept here than the reply's counts say the Mac holds (a database replaced there, which no cursor shows); the cursor is then reset and the read comes at the next sync. The counts stand in for `rows`' list of ids, since a large archive's URL list is about 1.8 MB per ask. Pulled rows are only inserted or updated, as sent and none skipped (or the counts could never match), and the relay answers its rows and counts from one read transaction. A Mac's pulled rows are never swept: a page gone from its archive stays here, as history is never deleted, so more rows here than its counts say is not a reason to read again. A Mac that doesn't answer keeps its rows and cursor. A Mac that is no longer paired loses its pages and its cursor in the same transaction as its sessions.
- The peers' Recent (`LauncherModel.allRecent`, rebuilt by `rebuildRecent` when its inputs change, and in `saveSessions`) is merged from the last answer of each Mac and this Mac's own: one entry per conversation, records with a host aren't checked for a local transcript (`addRecent`, the restore filter), and a peer's entry takes the conversation's own id as its record id so a row keeps its identity between fetches.

- The relay answers every request but hello only to a Mac this one lists (`PeerList.lists(by)`, the saved list read without writing it, checked before anything else), or to a listed device (`PeerHost.listsDevice`, ADR 0011), since anyone who can ssh in could otherwise read prompts, screens and sessions or attach. A device is refused `rows` and `pages`, the search sync's, which hold the user's prompts and pages for the paired Macs alone; it gets the same `unlisted` reply. The running Varnick takes a device's `start`, `resume` and `end` as a peer's, reading the device file fresh (`PeerManager.handle`), and puts its id in the labels as a peer's. `PeerManager.send` and `attachCommand` fill in `by`. The answer to an unlisted Mac says so (`PeerReply.unlisted`), and a Mac that gets it is `.removedThisMac`: it is read no more, its `peer_sessions` rows and Recent entries go, and only a hello from it (it added this Mac again) brings it back.
- A host pane whose client exits while the session runs and is labelled for the host (or nobody) attaches again (`ClientExit.dropped`, with the reattach limit), never ends the session: a take-over that raced another could otherwise kill work. A pane started for a peer runs `checkControlAfterAttach` too, so its starting client lets go once the label names the peer, and a failed first attach by the peer can't leave two keyboards.
- The device file (ADR 0011) is `devices.json` in the support folder: `DeviceList` in `Devices.swift` is its one reader and writer, and holds its rules. On a Mac only the running Varnick writes it (`PeerManager.addDevice`, `removeDevice`; never the relay); on a headless host `varnick-peer device add` and `device remove` do, under the exclusive state lock. Only the user's own untagged nodes may be listed (`PeerDevice.mayBeListed`, used by both add paths). Ids compare through `Zmx.sameID`, never with `==`. A device is never contacted and never sends a hello.
- `status` and `tabs` replies carry `controlName` (a tab's, and each of its running panes'), filled in by the shared relay (`PeerControllerNames` says how it names a controller). A device is never told another controller's id: the relay leaves out `control` unless it names the asking device (`PeerRelay.hiding`, `PeerTab.hiding`), so the page tells who is in control from `controlName`. A Mac or card names its controller from its own peers and devices first and the reply's name second (`PeerManager.name(of:reported:)`), saying "another Mac" only when nobody does. A change to a reply shape bumps the protocol: both Macs and the headless host run one commit.
- Presence and the phone's push (protocol 27; `phone-page-is-only-a-browser-tab` option 02, ADR 0038):
  - A Mac's `PresenceReader` puts `PeerRequest.presence` (idle seconds, away flag) on the `status` request `PeerManager.sessionStatuses` sends each host every 5 s while it has a pane there; a host's relay writes it, for a listed Mac only and never a device's, to `presence/<mac id>.json` in the support folder (`PresenceFile`, owner-only, whole by rename, dated on the host's clock). A Mac writes its own file for its own page server every 10 s and on a change. The page server alone judges present or away (`presenceOf`; the definition is CONTEXT.md's **Presence**), and a report older than 20 s, or none, **must push, never silence**: any change that makes a missing or stale report read as present silences the phone for the sessions that most need it.
  - **The report also lists the Claude panes the Mac holds a notice for and shows on screen** (`PeerPresence.notices`, `onScreen`; `SessionNotifier.reportPanes` hands them to `PresenceReader.setPanes` every second and on a raise or clear, which writes the own file at once). The page server only has its own copy of a notice, so without them locking and leaving would push a notice the user saw on the Mac. `macView` drops a notice (`seen`) that a fresh report written after the raise once listed and no longer lists, or whose pane a report of a present user shows on screen. A Mac that never listed it (its Settings switch is off, an older report, no lists) is no evidence and the notice stands. A pane on the screen of a Mac that is away does not count: the panel may stay up behind a lock. A new place that raises, clears or hides a notice on the Mac must go through the notifier, or the lists lie in the direction that silences the phone.
  - **Each host is followed on a timer of its own** (`LauncherModel.updatePeerFollowing`, `followPeerSessions(on:)`), so one host that is slow or unreachable never delays the status request, and so the presence, another host gets past the page server's 20 s. A round that waits on every host brings that back.
  - The host's own id is told the controllers' ids in `tabs` (`PeerTab.hiding(keepingControllers:)`, `PeerRelay` `ownPageServer`), which a device never is. The page server must not pass them on: `shapeTab` and `shapePane` read only whether the control names the device asking.
  - `Reading`, `status` and `tabs` carry a failed turn's kind (`failure`, the wire word) and a waiting from Esc or Deny (`esc`) as optional fields with explicit `CodingKeys`.
- Any request but hello to a peer goes through `PeerManager.send` or `attachCommand`, which refuse a peer found to speak another protocol version, except `upgrade` and `restart`, which `PeerClient.exchange` sends and `verdict` reads across versions.
- A paired Mac's tab becomes an ended card (`LauncherModel.endRememberedTabs`) only when all of these hold: this Mac listed it open and remembered it (`remembered`, saved as `State.rememberedTabs`, by tab id), that Mac's latest `sessions` answer succeeded without it, and its Recent, asked after the tab was last listed (`peerRecentSentAt`: the time the ask was sent, an unchanged reply counts), has a closed tab naming it (`PeerRecentTab.tab`, or one of its sessions by zmx name; for the headless host the record's tab id). A tab merely missing ends nothing, since a restarted Mac restores its panes and closes none, and a Mac that doesn't answer ends nothing. Never match by conversation (a /clear moves it), and never read an end from a Recent asked before the last listing, or an old entry of a tab id resumed since would end it. A remembered tab saved before this build is a one-pane tab under its session's pane id, so a paired Mac's tab of several panes is known by its first pane's id and a session that wasn't first matches nothing: an end it had while this Mac was off is missed once. Recent is asked of a Mac that just stopped listing a tab, alone, while that tab was last listed within a minute (`recentWatchWindow`), and of every Mac at most every 5 s when the board opens, never of every Mac every 5 s: the headless host's Recent reads each ended session's whole transcript for its title. The remembered list is forgotten when a tab here takes the id, when marked done, when the Mac is unpaired and 30 days after the last listing, in `rebuildRecent`; and a tab started and ended there between two listings is never on the board.

**Phone page** (`PhonePage/`; ADR 0011)
- Bun is for the page only, never the relay. `PhonePage/` takes no npm package, and `bun test` in it checks the pure decisions (`checks.ts`, `home.ts`, `hosts.ts`, `relay.ts`, `terminal.ts`, `launch.ts`, `watch.ts`, `page/rules.js`, `page/newrules.js`, `page/liverules.js`, `page/tabrules.js`, `page/installrules.js`, `proxy.ts`, `webapp.ts` with the icons' digests, and for push `webpush.ts` against RFC 8291's example, `pushrule.ts`, `pushstore.ts`, `pushsend.ts`, `pushwatch.ts`, `pushserver.ts`, `page/pushrules.js` and the worker's push half in `swpush.test.ts`).
- The page installs as an app per host, because each host is its own origin (`webapp.ts`, `page/sw.js`, `page/install.js`, `page/icons/`; option 01 of `phone-page-is-only-a-browser-tab`):
  - **The worker answers failed page loads only.** `sw.js` handles a GET navigation, and only after the network failed it (a 403, a 502 or any answer is shown as sent). Every other fetch passes untouched, so the port proxy's frames (other origins), `/api/*` and the websockets are unaffected. **It caches nothing from the server:** replies are `no-store` and carry prompts and titles, and a cached copy of the page's code could talk to a newer server. A change that adds a cache, a fetch handler for another mode or any storage to it breaks that. Push (option 02) adds a `push` handler, not a cache.
  - **The manifest and the worker are written per request** with the host's name (`manifestFor`, `workerSource`, from the relay's hello), through the same Host and caller checks as every file: an unlisted device gets 403 for both, and registers nothing. The worker's script holds the name, so `/sw.js` answers only a browser's own worker fetch (`isWorkerFetch`: `Service-Worker: script` or `Sec-Fetch-Dest: serviceworker`) and 404s another site's `<script src>`; every reply carries `Cross-Origin-Resource-Policy: same-origin` except the icons, which hold nothing private and which a browser may fetch outside the page. The manifest's colours are the dark ones only, since a manifest holds one; `index.html`'s `theme-color` tags give both.
  - **The content policy names `manifest-src`, `img-src` and `worker-src`, each `'self'`** (`pageContentPolicy`), and the unlisted page's policy is unchanged. A new kind of file the page loads needs its source named there, or the browser refuses it with no visible error. The worker's own note carries a policy that allows no script, so Try again is a plain link to `/`, which drops a `#t=` address.
  - **A new icon or a changed one goes through `scripts/make-phone-icons.sh`,** which rewrites `page/icons/DIGESTS`; `bun test` fails on a PNG that isn't listed or whose digest differs, and on a size that isn't the one `iconFiles` lists. The manifest's icons are built from `iconFiles`.
  - **Chrome and Safari only update the worker when its bytes change.** The server serves it `no-store`, and the page registers it with `updateViaCache: "none"`. It calls `skipWaiting` and `clients.claim`, safe only because it holds no state.
  - **The Home Screen title is the host's name in two places:** the manifest, and a `<meta name="apple-mobile-web-app-title">` the server writes into `index.html` for iOS (`appTitleToken`).
  - **The terminal's keyboard rules were written in a Chrome tab.** In a standalone window (Android) and anywhere on iOS they are unchecked until tried by hand on a phone.
- Push (`pushrule.ts`, `pushwatch.ts`, `pushsend.ts`, `pushstore.ts`, `pushserver.ts`, `webpush.ts`, `page/push.js`, `page/pushrules.js`, the worker's push half; option 02 of `phone-page-is-only-a-browser-tab`, ADR 0038):
  - **The payload is a privacy surface.** `payloadOf` is the whole of it: a version, the tab's and pane's ids, the kind (`message` for a session's own) and an error's word. A title, a prompt, a folder, a project, a path, presence or a message's words in it goes through Apple's or Google's servers. The worker reads the title from the host over the tailnet (`/api/tab`, 3 s) and shows only the host's name when it can't. Every payload is padded to one size (`paddedSize`) and every push is sent alike (TTL 3600, urgency high, no Topic); a header that varies by kind lets the push service tell kinds apart. A logged line holds the device's name, the kind, a status and the time, never an endpoint, a payload, a title, presence or a key.
  - **A push may go only to a push service** (`isPushEndpoint`: https, port 443, Google's, Apple's, Mozilla's or Microsoft's hosts, no IP, no credentials), checked when a subscription is taken, when one is read back from the file and again in `sendPush`, which follows no redirect. This is what keeps a listed device (or, on loopback, a local process posing as one) from making the server request an arbitrary address, localhost and the tailnet included. A new push service is added to the list; nothing widens it to a pattern. The server's own fetch to a push service is external, so it goes through any HTTP proxy the environment names, unlike the port proxy's forwards to localhost (see Port proxy).
  - **The host's key never changes by itself.** Every subscription is bound to its public half. On a Mac it is a Keychain item of Varnick's own (`PhonePagePush`). Only `errSecItemNotFound` means there is none (`Keychain.lookup`); it is then made with `SecItemAdd` alone, a duplicate meaning "keep the existing one", and never by `Keychain.save`, which deletes first. An item that exists and can't be read is never replaced. If the key can't be read at a launch and the running server already carries a key fingerprint in its labels, the server is left running (`PhonePageRunner.reconcileNow`), not restarted without push, at the price of new page files waiting until the key can be read; one that carries none starts without push (label `varnick-page-push=none`) and starts again with the key once it can be read. A change that regenerates on any read failure voids every phone's subscription. The server's session label carries the key's fingerprint, and the Swift and TypeScript fingerprints (`PhonePagePush.fingerprint`, `fingerprint` in `webpush.ts`) must agree, or the server restarts at every reconcile. A headless host's key is `push-key.json` in `~/.varnick/phone`.
  - **Every push must show a notification.** The worker shows one for a payload it can't read, and none may be silent: iOS revokes a subscription after a few silent pushes, and Chrome shows a generic one. One notification per pane (`tag` is the pane, `renotify`), so a push cannot withdraw an earlier one. The iOS badge is the count of standing notifications, set by the worker after it shows one and cleared by the page when it opens; Android ignores it.
  - **A missing or stale presence report must push** (see Peers, Presence). `route` is the one place it is decided; the host's own pane with no client is its own Varnick's to notify (not "can't be told"), a peer Mac's detached client is.
  - **The page server reads Varnick's files** now: each Claude pane's `.varnick-turn` and `.varnick-message` dates (the newest of the two, `readTurnDates`) under `VARNICK_PANES_FOLDER`, the new folders there, the saved tabs' date (`VARNICK_PROXY_TABS`, on a Mac), and `presence/` under `VARNICK_PRESENCE_FOLDER`. The server watches only while a subscription exists, and asks `tabs` (a whole Varnick process on a Mac) only when a turn's date, the saved tabs or the panes folder changed, every 15 s while a pane is in background or a notice stands, and every 60 s otherwise. One ask serves the port proxy and the watcher (`Shared`). A change that asks every tick brings back the 17,000 processes a day the option rejected. The derived words (background draining, an error) don't change the turn file, which is why the busy cadence exists, and why a notice is read once more after its settle before it goes.
  - **The Done is read again before it is pushed** (`PushWatcher.deliver`), like the Mac's second: an error that follows its waiting in the same turn takes over the Done's settle (`raisedAt` carried), so the phone gets the error and not both. A turn's start (`since`) is counted from when the ask began (`Shared.stamped`), not when its reply was processed, and two readings within `sameTurnMs` (5 s: whole-second ages, the shared answer's 1.5 s cache, the relay's run) are one turn; a narrower window reads a slow ask as a new turn and loses the error.
  - **The settle is per kind** (`settleOf`): 10 s for a Done (`doneSettleMs`, a turn can flip straight back to work), 2 s for Needs you and errors (`urgentSettleMs`, the user is waiting). The second hand test pushed a question 10 s after it was raised; the user opened the app at 5 s and looked for 3 s, so it counted as seen. The `tabs` read before a push stays for every kind, so a 2 s settle still checks that the dialog stands. An error that follows its Done carries the Done's `raisedAt`, so it may be due the moment it is raised. The cap of one push per pane per settle uses the settle of the notice being sent. Mac side: `SessionNotifier` raises Needs you at once and settles Done and errors for about 1 s, so the Mac already differs by kind in the same direction; the phone's times are longer because its presence report takes up to 5 s and a push cannot be taken back.
  - **Sends run off the tick** (`PushWatcher.inFlight`): a retry waits for Retry-After, up to two minutes, and the tick that reads turns and presence must not wait with it. Send a test does not retry at all (`SendOptions.retry`), and has its own 5 s limit per device.
  - **Only a notice that still has a subscription waiting counts toward the 15 s cadence** (`anyWaiting`): one already pushed or dropped for every subscription stands at the idle 60 s, or each Done would keep the host asked every 15 s for as long as the pane waits.
  - **The key never rests in the server's environment, where `ps eww` shows it.** A Mac's Varnick writes it to an owner-only file in the phone folder (`PhonePage.pushKeyHandoff`) just before the start and names that file in `VARNICK_PUSH_KEY_FILE`; the server reads and deletes it as its first act (`takeKeyFile`, before anything slow), and Varnick removes it again after 30 s, or at once if the start failed. A server that is started again by hand reads nothing, and is restarted by Varnick's own reconcile. `VARNICK_PUSH_FOLDER`, `VARNICK_PANES_FOLDER` and `VARNICK_PRESENCE_FOLDER` come together or not at all (`readConfig`); the headless unit sets them. A Mac without the key sends no push and logs why.
  - **Subscriptions** are `push-subscriptions.json` in the phone folder, written only by the page server (a Mac's Settings reads device ids and counts from it, never an endpoint). An unlisted device loses its entries at every look, so removing a device ends its notifications at once.
  - **A pane is open on a device only while its page is visible.** `OpenPanes` counts the terminal and live-screen sockets (`bridge.ts`, `watcher.ts`), and a socket counts only while its `OpenPane` is visible. Android keeps a hidden app's terminal socket for over a minute (86 s and 91 s in the first hand test), so the socket alone says "open" long after the user left, and the first hand test got no push for that reason. The terminal's page therefore sends `{t: "visibility", visible}` on every `visibilitychange`, on `pagehide` and from a socket that opens while hidden (`page/session.js`, `announceVisibility`); the live screen's socket closes when the page hides. A new kind of channel that shows a pane must count itself there, and say when it is hidden, or the phone is held back for what nobody is looking at.
  - **Seen on the phone is a look of `seenAfterMs` (3 s), not an open socket.** A notice raised or standing while the device has the pane open and visible waits (`viewing`); after 3 s without a break it is seen and dropped for good (`open-pane`); a look that ends sooner starts over, and the push goes once the pane is left, after the settle. A dropped decision is never reconsidered, so only a look that was long enough may cause one.
  - **A turn that ends with background work is read as `background`, never as `waiting`, so it raises no Done** (the table's "background stays silent until it drains", the Mac's too). This was the cause of the second hand test: the session's Stop hook listed a shell that had run for 14 hours (`.varnick-stop`'s `background_tasks`), so the pane read `background` at every turn's end. A forgotten background shell silences Done for its session on the phone and the Mac alike; Needs me and errors are not affected. The tick line shows it (`background=1`).
  - **The watcher compares the turn's start as well as its word.** The same word with a start later than `sameTurnMs` is another turn, one that ran and ended between two looks (a short turn, a late ask), and counts as running before it (`between` in `observe`): without it a Done that no ask saw as working is waiting to waiting and nothing is raised. The files' dates are read before the ask, never after it, and the ask must be answered by a relay that began after the newest write (`notBefore`, `Shared.stamped`): a turn file written while the relay runs, or a shared answer from a moment before, would otherwise be counted as seen.
  - **The log says whether the watcher is alive and what it sees:** `push watching N subscriptions` at the start and when the number changes; `push watch tick panes=… working=… waiting=… background=… notices=…` at most once a minute unless it changes; `push watch can't read the host's tabs: <reason>` once per reason; `push watch: a turn ran between two looks`. A server log with none of these is a server that isn't running the watcher (no push key, folders or ids in its environment: see `push off:`).
  - **The log says why a push did or didn't come** (`PushWatcher.logDecision`): `push notice <kind> raised|cleared`, and one `push decide <kind> <device> -> <outcome> controller=<host|mac|mac-detached|device> [presence=<present|away|unknown>]` line whenever a subscription's decision changes, with the outcome `waiting(settle|present|viewing)`, `pushing` or `suppressed(switch|open-pane|seen-on-mac)`, then the send's own line. Never a pane's, tab's or endpoint's id, a title or a report's numbers; a new decision path must log through it.
  - **Unverified until tried on a phone:** whether the worker's fetch of `/api/tab` passes `checkFetchSite` as `same-origin` (if not, every notification names only the host), how long iOS lets a push event run, whether iOS honours `tag`, and whether Chrome makes a WebAPK for the installed app.
- Every list and action is a relay request with the device's id as `by`, spawned with an argument list (`relay.ts`), never through a shell. `by` comes from the server alone (whois on `X-Forwarded-For`, then the node, then `devices.json`) and `buildRequest` writes it last, so nothing a client sends can replace it.
- whois's `Node` has no `ShareeNode` (`status --json`'s peers do): a node shared in shows as `Sharer` non-zero or `Hostinfo.ShareeNode` (`parseWhois`, with a fixture from a real answer). The rule is `PeerDevice.mayBeListed` in `checks.ts` too, so change both together.
- User ids stay text (`parseTailnetJSON`): a 17-digit id isn't exact in a double.
- On a socket serve sends `Host: localhost` and the browser's host only in `X-Forwarded-Host`, so the Host check reads that there and `Host` on loopback.
- `/api/*` answers only the page itself (`checkFetchSite`), because another site open on the phone can send a `no-cors` read with the phone's identity, and a read runs a relay. Relay runs and whois spawns are capped, per device too. Mutations and websocket upgrades need the page's `Origin` (`gateMutation`, `gateUpgrade`). Send no `Access-Control-*` header, ever.
- Bun can't set a socket's mode: the socket's folder must be the user's and 0700, and the socket is chmodded 0600 once bound.
- Which hosts can serve a socket, and why Macs whose Tailscale can't serve a socket listen on loopback: the option's Spike › Results (one app's mount looks right in `serve status` and still answers 502).
- `PROTOCOL_VERSION` in `server.ts` must equal `PeerProtocol.version`: a protocol bump changes both, or the server refuses to start.
- A Mac's server runs in a zmx session named `varnick-phone-page`, never a pane's name (`Zmx.attachCommand(named:)` refuses one): the launch sweep and the relay's `tabs` read a pane id from a name, so a pane's name would get the server killed at the next launch.
- It is started through `PtyClient`, never `zmx run`, which crashes 0.8.1's daemon, and waited for and detached as a headless `start` is.
- Only the setting ends it: not Quit, not Keep sessions running (`stopAppServers` looks at panes), not the sweep. A server that exits by itself (Tailscale not up at login, a protocol mismatch) stays down, and Settings offers Start again with the log's last lines.
- Its files are the launch snapshot's clone of the copy `make build` puts at `.build/release/PhonePage`, in `.build/snapshots/page-<digest>` (`LaunchSnapshot.serverInstall`; without a snapshot, the resource folder's `PhonePage`), so an edit in a checkout reaches a running server only through a build and a restart. The folder is named by the digest, not by the launch, and the session's labels name it (`varnick-page-place`): the server outlives Varnick, and a launch that finds the same digest in the same place leaves it running, so its files must stay. A server without that label (started before snapshots, from the build folder) isn't current and is replaced once. A page folder is removed only after a reconcile, and never the one the running session's label names, so a server that isn't replaced (Bun missing, `stop()` failing, no page in the build) keeps its files.
- Varnick publishes the page's port itself (`PhonePagePublisher`), by the rules in ADR 0011's note: one mount, no funnel, fail closed, the user's own mount left alone. The app's CLI needs `TERM`, and is always loopback whatever its `--help` says, since the Tailscale app's mount answered 502 for every socket when tested (1.102.3). The target follows the running session's `varnick-page-mode` label, not what the CLI can do now. Never run `serve` as root anywhere but the Use a socket button, and keep every read as the user (the rest of the refused-socket rules are in ADR 0011's note). `PhonePagePublisher.swift` takes the CLI as a closure and the port as an argument, and imports nothing of the app's, like `PhonePage.swift`, so a check can run it on a throwaway port (the kit's `ticket11-check.sh`).
- Home's "Other hosts" are the relay's `hosts` reply (name and address of each listed peer, never an id: `PeerHostEntry` has none; from the saved list on a Mac and `state/peers.json` on a headless host, read and never written) read by `hosts.ts` against `tailscale status --json`'s nodes. An address that isn't a node of the tailnet (`alex@check`, an IP, one with a port) gets no link, and a link only says where a host's page would be: the page can't know whether it is published, and the browser's own error is the answer. `hosts` is a request like the rest, so adding it moved the protocol to 14.
- On a headless host the server is the systemd user unit `varnick-phone-page.service`, written only by `scripts/install-peer.sh <host> --page`, which is also the only thing that enables, restarts or stops it by hand (systemd starts it at boot and restarts it on failure). It needs `KillMode=process`: a session the page starts is created by the relay the server spawned, so its zmx daemon is in the unit's cgroup, and systemd's default mode would end every session at a stop or restart. Linger must be on for the user, or the unit stops with the last login (the installer warns). Like Settings above, the installer follows ADR 0011's note (`page_publish` once the page answers, `page_unpublish` for `--no-page` and `--uninstall`). Funnel that is anything but off, unreadable included, also disables and stops the unit (a stop alone would let a reboot bring it back), and a clean run enables it again.
- `PhonePage.swift` and `PhonePageRunner.swift` import nothing of the app's: a scratch package that links `Packages/VarnickPeer` compiles them for a check against real zmx and Bun.

**The tab view on the phone** (`PhonePage/`: `page/tab.js`, `page/tabrules.js`, `home.ts`, the `/api/tab`, `/api/take`, `/api/file` and `/api/end` routes; ADR 0034)
- Home is the host's `tabs` (`shapeTabs`): one row per tab, opened at `#t=<tab>` (and `&p=<pane>`, which the page rewrites as the pane changes). A tab with nothing the phone can show (only Claude and terminal panes, none running) is left out, as the Mac's list leaves it out. `#s=<session>` still opens one session alone, for a start whose answer named no tab.
- The tab shows one pane at a time, a switcher between them. A Claude or terminal pane that runs is the session view (`openSession` with `tab`), so only the shown pane's terminal is open and the cap of three per device holds; switching releases the old one first (`releaseSession`). Any other pane is a note: a file's text from `/api/file` (the relay's `file`, which reads the pane's own path and caps it), or where a page, an app or the Transcript runs. The tab is asked for again every 5 s while the page is visible, and the pane shown changes only if it is gone or began or stopped running.
- Take over in a pane of a tab is `POST /api/take` for the tab and then an attach without `take` (the label names the phone); the page's `take` for a first attach is only for a session it has just started. End is `POST /api/end` naming the tab (`parseEndBody`: a tab or a session, and only the one it names reaches the relay), and what it says is the host's: ended, or handed back.
- The page's JSON for a tab never carries a controller's id (`shapePane`, `shapeTab`), as for a session before.

**Port proxy** (`PhonePage/`: `proxy.ts`, `portproxy.ts`, the proxy half of `server.ts`; `Packages/VarnickPeer/.../PeerProxy.swift`, `LocalAddress.swift`, `PeerRelay.named`; `SessionRecord.proxy`, `ClaudeSession.applyHostProxy`, `HostTabs.swift`, `page/tab.js`; ADR 0035, which holds the rules and why: the port limits, the cross-port rule, Vite's fallback socket, the certificate)
- It is a listener on the host's tailnet addresses, a new door: a change that binds `0.0.0.0` or `::`, or opens a port the rules in ADR 0035 close, serves every custom app to the network the host is on.
- `checkProxyFetch` is not `checkFetchSite`: admitting any `same-site` request lets any app on any port call every other with the viewer's identity (ADR 0035). The Phone page keeps its own `same-origin` checks and sets no cookie, because every proxied app is same-site with it.
- Requests between two ports of a host are broken on purpose, and the `custom-apps` skill says so. The user hasn't confirmed it; reversing it is in ADR 0035's Considered Options.
- Admission is `decideProxyCaller` on `tailscale whois` of `server.requestIP`, never a forwarded header (nothing sits in front), sharing the page's whois cache. Sockets and streamed responses are asked about again at each look and ended when their caller is no longer admitted, unless it could only not be told. Closing or dropping a port ends everything open on it, including what a certificate swap left on the old servers (`Listener.open`, `retire`): only the swap itself stops a server gently. A caller who can't be told gets a 503, not a 403.
- A port opens only when its server answers on localhost and nothing answers on the tailnet address (`planPorts`). A failed bind can't be the check: on Linux a listener opened first keeps a later bind of every address from starting, and on a Mac the more specific bind wins over a server already on every address and takes its tailnet traffic. Raising the look interval or opening a port before its server answers brings both back.
- What a look costs, since it runs for as long as the page is on, is in ADR 0035. The saved tabs' date (`VARNICK_PROXY_TABS`) is what keeps the relay from running each time: a change that stops it being written on a tab change makes the proxy see panes up to 5 minutes late.
- The certificate: Bun 1.3.14's `server.reload({tls})` returns OK and keeps serving the old one, so renewal stops each listener gently and serves its port again (`renewCertificate`); a rebind that fails drops the port. It is asked at the first look whatever the tabs hold (so Settings shows a missing operator before the first pane), hourly while nothing is wanted and each minute while something is. The status file is written before and after the call, which is held to 50 s, so a slow one never makes it look stale.
- The status file (`proxy-status.json`: the support folder on a Mac, the state folder on a headless host) is how the relay learns what the page server holds. Missing, unreadable, older than 60 s or dated ahead means the page server isn't running. It holds ports, reasons, each pane's proxied address (so its path) and the one command a refusal can be fixed with, mode 0600. Every reason's wording is `notes`, `openFailure` and `certificateFailure` in `proxy.ts`; the command is `operatorCommand` there, and Settings shows what the file gives. The Swift ones are `stoppedNote` and `unseenNote`.
- Local addresses are written twice and must answer alike: `PeerPane.isLocalAddress` (Swift, used by `SessionRecord` and, as `PeerProxyAddress.isProxiable`, by the retry of a page that failed to load) and `isLocalAddress` in `page/tabrules.js` (the page; `proxy.ts` imports it). `tab.test.ts` lists the cases, and a scheme other than http and https counts as local so no viewer loads it from its own machine. Which addresses a split may open is `ClaudeSession.httpURL`, once.
- The viewer loads a listing's `proxy` only through `PeerProxyAddress.accepts`, against the node names `TailnetNodes` read from `tailscale status` (ADR 0035). `SessionRecord.staysOnHost` is false once `proxy` is set, and `ClaudeSession.staysOnHost` once the pane has a web view, so a page that loaded stays when the next listing says the proxy went. `ClaudeSession.showLoadError` tells a failed load of the host's name from the listing, not from `proxy`, and a returning address loads at once. A pane of another machine's tab never starts its own copy of the app: `customApp` and `startApp` need `host == nil`.
- A split from afar, and what a headless host does with it, is in ADR 0035. The picker's own text field for a page's address is why its key monitor lets keys through while `pickerAsksAddress` (`main.swift`).
- `portproxy.test.ts` binds throwaway ports on `127.0.0.1` and `::1`, never a tailnet address. Proxy variables: Bun's `fetch` and `node:http` follow `HTTP_PROXY`/`HTTPS_PROXY`, read once when Bun starts and not changeable after, so a forward to localhost went to the proxy (and NO_PROXY with `::1` never matched the bracketed `[::1]`). `new PortProxy` therefore adds `localhost,127.0.0.1,[::1]` to both `NO_PROXY` and `no_proxy` (Bun reads the lowercase one first), and Bun re-reads them at each request, which it does not document. `proxyenv.test.ts` is the check: it runs `portproxy.test.ts` under a dead proxy with no NO_PROXY and sets nothing itself, so a Bun upgrade that stops re-reading fails it. Keep every HTTP request to localhost after a `PortProxy` is built, or add the entries first. Raw sockets (`Bun.connect`) and `WebSocket` never used the proxy.
- A headless host lists no web or app pane (its tabs hold Claude sessions and terminals), so its proxy is idle there. The unit gets `VARNICK_PROXY_FOLDER` and `VARNICK_PROXY_STATUS`; with neither set (a check's server) the proxy is off.
- SwiftPM can keep building a package from its old file list when a file is added to `Packages/VarnickPeer`; `rm .build/release.yaml` makes the next build look again.

**The terminal** (`PhonePage/`: `bridge.ts`, `terminal.ts`, `page/session.js`; ADR 0011; a pane of a tab: see The tab view on the phone, above)
- One websocket per open terminal, at `/ws/terminal`, carrying bytes to the relay's `attach` run in Bun's pseudo-terminal. Its upgrade is checked before anything is spawned (`gateUpgrade`), and a device has at most three terminals open (429 past that).
- `take` is sent only right after a press (Take over, or the Start or Resume that made the session), and never on a reconnect: the first message's `take` counts only as the literal `true`, and the relay refuses an attach without it for a session the device doesn't control.
- Every client re-checks control, as the Mac clients do (`checkControlAfterAttach`, above): about a second after the attach goes live the server asks `status` once, and if the label isn't the device's it closes the pty and sends 4001 with the controller (`recheckControl`). Two takes landing between the relay's label check and its `execve` would otherwise leave two keyboards live. Input is dropped until the screen is live.
- Closing the websocket closes the pty, which ends only the phone's zmx client: the session keeps its label, and the phone stays in control. Never release on close: Android drops a backgrounded tab all the time.
- Every reconnect asks `status` first (`/api/session`): labelled for the device attaches without take, anyone else shows the session view, gone says "Session ended". A client that exits by itself is told from "taken" and "ended" by `status`, never by its exit code (4001 taken, with the controller as a JSON field of the reason; 4002 ended; 4003 dropped; 4004 refused, with the relay's error as the reason). The tries start over only after a connection that lived 10 s.
- A refused attach prints one reply line and exits instead of becoming zmx. Output that starts with `{` is held for up to a second; a child that exits meanwhile with a reply line closes the websocket with its error, and the line never reaches the terminal. Anything else is released at once.
- What was typed or shown stays out of the logs: opens, closes, codes and grids only. The page's CSP allows inline styles, because xterm.js's renderer writes `<style>` elements; scripts stay `'self'`, and `connect-src` names the page's `wss://` address.
- Typing goes straight into xterm through the phone's own keyboard: there is no compose box, Paste, Enter or ^C key (the keyboard has Enter, a long press pastes, and Ctrl then `c` is ^C). The key bar is one row of eight, `Esc Tab ⇧Tab ↑ ↓ ← → Ctrl`, that must stay on one line down to 360px (`#keys` is `flex-wrap: nowrap`, equal `flex: 1 1 0` buttons, `min-width: 0`, 40px tall): a ninth key or a longer label breaks that, so check at 360px. A key press `preventDefault`s `pointerdown` so xterm's input keeps focus and the keyboard stays up; a tap on the terminal calls `term.focus()` (`#term`'s click), which is what raises the keyboard. The sticky Ctrl turns only a single typed character into its control code (`ctrlCode`), so a multi-character paste passes through untouched.
- xterm.js is vendored in `PhonePage/vendor/` at pinned versions, with `VERSIONS` holding each file's SHA-256 and the packages' registry integrity (`bun test` checks the digests). Fetch new versions on a headless host, never on a Mac inside a Claude session, and serve them from `vendor/`, not `node_modules`.
- The keyboard never takes rows from the grid (`refit` in `page/session.js`): a resize each time it came and went had the session redraw at the new height while xterm.js moved lines in and out of its scrollback, and the screen garbled. The grid keeps its rows and `#term` shows its bottom ones. `#term` is `overflow: clip`, never `hidden`: Chrome on Android scrolls a hidden overflow to show xterm.js's input when the keyboard comes up, and nothing scrolls it back.
- xterm.js 6 has no touch scrolling, so `page/session.js` turns a swipe into `scrollLines` in a normal buffer and into wheel events when the program takes the mouse or the alternate screen (Claude Code full screen), which xterm.js reports as the program asked. The compose box was removed on 2026-10-09 at the user's choice, though typing into xterm.js with Gboard was seen to lose backspaces and autocorrect and dictation needs a native field: if either bites, a native field is what brings them back.

**Starting and resuming on the phone** (`PhonePage/`: `launch.ts`, `page/new.js`, `page/newrules.js`, `page/dom.js`; ADR 0011)
- The browser sends only `{folder, agent, prompt}` to `/api/start` and `{tab}` (a closed tab of the host's Recent) to `/api/resume`, which is a `reopen`; `parseStartBody` and `parseResumeBody` read nothing else. The server picks the session id (`crypto.randomUUID()`), sets `by`, and never sends `skipPermissions`, so the host's own setting applies. The prompt, folder, agent and conversation reach the relay only as JSON fields of its one base64 argument.
- A folder must be one of the host's `projects` (for `/api/agents` too) and an agent one of that folder's `agents`, asked fresh each time. A reopen (`reopenTab`) asks `tabs` first: a tab that is open on the host is answered with 409 and its id (`openTab`) and no `reopen` is sent, and the host's refusal in a race is read the same way; otherwise the host reopens the tab whole in its layout and the page opens it. A start's answer carries the tab the host put the session in, which the page opens it in. Home lists the host's tabs (`shapeTabs`) and Recent as closed tabs (`shapeRecent`).
- A start that fails or times out asks `status` for the session it named before it answers: a running session is a success (with no tab known, so it opens alone), or a second tap would make a duplicate.
- The prompt is never logged and never echoed in a reply, a refusal included, and never in `document.title` (browser history, Chrome Sync).
- The prompt is limited as `JSON.stringify` writes it (`promptLimitBytes`), since a newline or a quote costs two bytes in the request, which then goes base64 into one argument. Linux takes 131,072 bytes for one argument; `Relay.ask` refuses a request over `argumentLimit` before it spawns anything.
- Claude's parser reads the first operand as a subcommand even after `--`, so a prompt that is exactly `doctor`, `update`, `mcp` and so on would run that command. `ClaudeCommand.operand` gives a prompt with no whitespace a trailing space, which no command name equals. Keep both (`--` and the space) when changing `arguments`.
- `parseStartBody` still refuses a prompt that starts with a dash, for a host that doesn't put `--` before the prompt yet (before `ClaudeCommand.operand`). Remove the check once every host has that change.
- A Mac host takes up to 25 s to answer `start` and `resume`, and up to 60 s a `reopen` (it waits for each pane's session): the relay is given `launchTimeoutMs` for them, and the request `server.timeout`, past Bun's 30 s idle limit.
- `projects`' `lastUsed` is Foundation's `Date`: seconds since 2001-01-01. `shapeProjects` converts it, and sorts newest first itself.
- The page sets `take` for the terminal only after a Start succeeded (`enterSession` names the one session to take, once) or after a Take over press. A reopened tab is labelled for the phone already, so it attaches without it; a reload, a revisit and every reconnect attach without it. A reopen under way is kept per tab, not per row, since the home reloads while the host answers. New session's last project and agent, and the last lists, are in localStorage per origin (so per host), and the page works without it.

**The live screen on the phone** (`PhonePage/`: `watcher.ts`, `watch.ts`, `page/live.js`, `page/liverules.js`, `page/session.js`; ADR 0008, ADR 0011; Take over on a tab: see The tab view on the phone, above)
- The server runs the relay's `watch` on pipes, never a pseudo-terminal: a reader never sends input, Init or a size, and a pty would make the relay's client a terminal. Nothing is ever written to the relay's input, the first message names the session and nothing else (`take`, `by` and a grid in it are ignored), and any later message from the page closes the socket with 4400. A watch needs the same caller, Host and Origin checks as the terminal (`gateUpgrade`, before anything is spawned) and is sent only to a listed device.
- The relay's input is a pipe held open for the websocket's whole life: closing it is how the relay learns its viewer has gone, which is also what removes its `readers/` file and keeps the Macs' client counts right. When the websocket closes the server closes that input, terminates the relay after 1 s and kills it after 2 s (as `SSHRunner.stream`'s cancel does). The slot (3 a device, 8 in all; `Admission` in `relay.ts`, shared with the terminal) comes back when the relay is gone, not when the socket closes. Never give the relay `stdin: "ignore"`: it would see its viewer gone at once.
- The channel ending never means the session ended. Take over, a release, the session ending and the relay failing all close it the same way, so the page asks `status` after every close (the terminal's rule) and shows whatever that says: this view again with the new controller, the terminal, or "Session ended". A channel that ran for 10 s asks at once; one that failed at once backs off 1, 2, 5, 10, then 30 s.
- A slow phone mustn't grow the server: only the newest frame not yet sent waits (`Outbox`), and a frame goes only while the socket holds under 256 KB unsent, so a stalled connection gets the latest screen when it drains and the rest are dropped (the close line in the log counts them). `Bun.serve` has one `backpressureLimit` (4 MB) for every websocket and closes a socket whose unsent bytes pass it, and JSON writes each escape character as six bytes: so a screen over `longestScreen` (1 MB of text) is skipped as it arrives, a message over `longestMessage` (3 MB) is replaced by `{tooLarge: true}`, and the page says "Screen too large to show" in the bar and goes on. Keep `longestMessage` plus `sendHighWater` under the limit (`watch.test.ts` checks it against a real server). The relay's pipe is read at all times, whatever the socket does. Keep the logs to opens, closes, codes and counts: never a screen.
- The channel is open only while the page is visible. A hidden page closes it (and the host's reader goes with it), a visible one opens it again, and the first frame is then a fresh snapshot. A page that is hidden still shows its last frame, but returning says "Loading screen…" until a fresh one arrives, since the old one is old.
- Each frame is drawn from scratch (`ESC c` through xterm's parser, which `term.reset()` isn't: it would run before a frame still waiting to be parsed) at the grid it came with, in a read-only xterm.js with no scrollback and `pointer-events: none`, never focused. A grid of `0 0`, or past 400 columns or 200 rows, is fitted to the phone instead (`pageGrid` on the server reads the page's own `gridLimits`, so there is one set of limits). The scale is `fitScale` of the width measured from `.xterm-screen`, never above 1. Pinch to zoom is the browser's own: don't put `user-scalable=no` or `maximum-scale` in the viewport meta.
- `Bun.serve` takes one websocket handler for both channels: each socket's `data.kind` says which one it is (`socketHandlers` in `server.ts`), so a third channel adds a kind there.

**Listening and spoken requests** (`Listening.swift`, `Speaking.swift`, `SpokenText.swift`, `SpokenRequests.swift`; ADR 0015)
- The system audio tap must keep excluding Varnick's own process (`ownProcessObject`); without it the wake sound and the answer come back as `[system]` lines. It is looked up when each capture starts, and a failed lookup only logs.
- Saved audio (`SavedAudioFile`, `SavedAudio`; Settings › Listening › Save audio) takes the converted `out` buffer from `analyze`'s closure, which runs on the mic tap's thread and on the system source's IOProc: the closure may only hand the buffer to the file's serial queue (`write`), never encode, create a file or touch the disk, or system audio drops out. `out` is handed over uncopied because it is allocated per call and never changed after; reusing one buffer across calls would corrupt the queued audio.
- An m4a that was never closed is unreadable (`AudioFileOpenURL` fails), so every way out must reach `SavedAudioFile.shutdown`: `Capture.stop` for both `discarding` values and for the stop after a failed start, which must run after the mic tap and the IOProc are gone and stay the only owner of `savedFiles`; and every way Varnick ends, each calling `SavedAudio.closeAll` (`endCapture`'s detached task would not run in time) through a registry of live files: `applicationWillTerminate`, `BuildUpgrade.relaunch` before its `_exit(0)`, and the SIGTERM of `make run`, `scripts/restart.sh` and `make stop`, which skip `applicationWillTerminate`. That SIGTERM handler (`AppDelegate.onTerminate`, main.swift) must stay limited to `closeAll` and `_exit(0)`: anything more (stopping app servers, zmx sessions) ends what a restart leaves running. It is a `signal` handler writing to a pipe, not `SIG_IGN` with a signal source, because an ignored signal stays ignored in every child Varnick starts (their SIGTERM would stop working), while a handled one resets at exec. `closeAll` waits 2 s at most, so a stuck queue can't make `restart.sh`'s 10 s wait time out; a file still open then stays unreadable. The exit is status 0 instead of death by SIGTERM: nothing reads it (the LaunchAgent has no `KeepAlive`, `restart.sh` looks for processes only). `closed` is set in `shutdown`, so a late callback after the tap is removed cannot start a stray file. A signal or crash still leaves the open file unreadable, so a run is cut into 15-minute files (`segmentLength`), each named by its own start time: that bounds the loss, so keep it. A file is made at the first buffer of a segment and removed at close if no frame went in, so a source that delivered no audio leaves none; silence is still audio and is kept. A write that fails logs once (domain and code, no content) and stops that source's saving only. `AVAudioFile.write` raises, not throws, on a buffer in another layout, so `append` compares the layout first. `AVAudioFile` overwrites, so `create` numbers a file whose name exists (`…-mic-2.m4a`, for Listening stopped and started within a second); never replace that with a bare overwrite.
- Varnick's speech must come from this process, so `Speaker` renders it with the synthesizer and plays the buffers on its own engine. Moving it back to `AVSpeechSynthesizer.speak` alone (which only the no-audio fallback does) may play it from a system process the tap does not exclude.
- ElevenLabs audio (`ElevenLabs.swift`, ADR 0033) plays only through `SpeechPlayback`, inside `Speaker`'s queue, as PCM buffers of one format (24 kHz mono float) with an empty buffer at the end; playing it any other way (an `AVPlayer`, a file, a system sound) puts it in a process the tap does not exclude. A line's span covers the wait for ElevenLabs and the fallback after it, so the request goes out after the span opens (`Line.openSpan`) and the installed voice speaks before it closes; the key is read once per queue (`VoiceQueue`) before any span opens, and off the main actor, since a Keychain prompt must not hold a span open or the deadline's clock.
- The fallback to the installed voice is for an error, a status other than 200, an empty body, no first byte within `ElevenLabs.deadline` (1.5 s) of the request, and no new bytes for that long once sound began. Every one cancels the request and stops its playback first, so late audio never plays over the fallback, and a line broken mid-way is spoken again whole. So is a line whose audio all arrived but never played (the engine failed to start). The session follows no redirect, so the key never goes to another host. A `stop()` bumps `stops` and cancels the request, and a stopped line goes to no fallback: a new path in `speakLine` must check `stops` after each `await`. Each line tries ElevenLabs afresh; nothing rests it.
- Nothing of an ElevenLabs line or the key is logged: a failure logs `ElevenLabs.Failure.logKind` (the status code or kind, never the reply's message), and the timing line names who spoke, never the voice's name. The key is read from the Keychain (account `ELEVENLABS_API_KEY`) and only goes in the `xi-api-key` header; it is never read from the environment or `.env` (ADR 0033 has why). With no key saved nothing is sent. With a key saved, the voice-list request (`GET /v1/voices`, when the key is saved and when Settings › Listening appears, whichever voice is chosen) carries only the key. Lines go, and the warm-up (`Speaker.warmUp`, at the wake sound, carrying only the voice id) runs, only with an ElevenLabs voice chosen (`Settings.speaksInElevenLabs`). Any more in a request is a privacy change needing `docs/privacy-and-security.md` and the Settings text.
- `Settings.voice` is the fallback voice once an ElevenLabs voice is chosen (`elevenLabsVoice` holds its id; empty means `voice` speaks). Picking an installed voice empties `elevenLabsVoice`, picking an ElevenLabs voice leaves `voice` alone, and removing the key keeps `elevenLabsVoice`. The voice list (`elevenLabsVoices`) is a cache, shown offline and meanwhile.
- `SpeechSpans` must be open from before a line's first sound to after its last, plus the tail: Listening drops a mic result whose audio began inside one, by audio time (`AudioClock`: time zero is re-anchored at every buffer, so mic drift and gaps don't move recent audio), never by when the result arrives, since finals come 1 to 2 s late. A path that speaks without `Speaker.queue` (`speak` is one line of it), or ends a line's span early, lets Varnick wake itself. The voice queue (`Speaker.VoiceQueue`) takes any number of lines: each line's audio is fetched or rendered as it is added, in a playback held until the line before it has ended (`SpeechPlayback.release`), and **each line has a span of its own**, opened when it can first be heard (at once for a first line, when the line before ends for a queued one) and closed after its last sound. **There is none between lines:** while Varnick is silent waiting for the writer or the web, the mic is heard and written to the transcript (the stopped branch held one span over that wait, and its review found it dropping mic lines). Two synthesizers take turns, by line number, so a line renders while the one before plays; a line is back on one only after the line before it ended. `stop()` drops every line, those not yet added included (`VoiceQueue.say` checks `stops`). A line whose rendering gave no audio and is spoken directly opens its span only after the line before has ended. Nothing heard while a request is answered wakes Varnick or joins the request.
- The wake phrase is "hey" or "hay" within the first three words, or "a" as the first word only, then one word that is the whole of one of `SpokenText.namePatterns`: `^[vw][ao][rl]?[nld][iea](c|ck|k|g)$` (the spellings the transcriber was seen to write, varnik most of all), `^v[ao]rn(et|ey|ie|y)$` and `^b[ao]rn(ick|ik|ic)$`. The last two came from real-voice misses on the user's machine ("Varnet", "Varney", "Barnick"). A b start must only ever go with -ick, -ik and -ic, and -ey, -y and -et only with a v start, or "Barney" and "Barnet" would wake it. It must never wake on a fragment of the name alone, so "nick", "Hey Nick", Warwick, Barney, Barnet, Barnes, Varun, varnish, Vernon and Warner stay asleep; a looser rule (a bare "nick", or a prefix in place of the whole word) woke on near-miss phrases in the measurement. The first pattern was measured with synthesized speech only (clean clips missed 35% against 57.5% for "Hey Launchy", more in heavy noise; none of 864 sound-alike phrases woke it, against 41 for "Hey Launchy"; docs/problems/name-taken-by-another-launcher/options/01-rename-on-one-branch-and-let-varnick-move-its-own-data.md, "Wake phrase"). The widened patterns were measured the same way (agent-lab, `experiments/2026-10-10-wake-pattern-widened`): 1 of 864 sound-alike phrases woke it ("Hey Barney" in noise, transcribed "Varney"), noisy misses went from 94.1% to 89.1% and clean misses from 25.2% to 24.8% (all 12 voices). Real-voice recordings are still few. "a" for "hey" came from 3 of 25 real-voice tries ("A varnick.", "A varnik, fine, 3 failures on my screen.", "A varnick, find cedar pad on my screen."), all the misses. It is taken only as the first word, since "there's a vonic" mid-sentence would otherwise wake it, and it is unmeasured: an eval of the "a" form is pending, and its false wakes are unknown until it is in. The contextual strings given to the mic's analyzer (`Varnick`, `Hey Varnick`, `Jev`, `TypeSafe`) were measured to change no transcript on macOS 26.5.1, so adding to them does not fix a spelling.
- Only final mic results wake it, only while Listening is on and Hey Varnick is on. Mic results while a request is decided, read or spoken never wake it or join a request. Turning either off, or stopping Listening, cancels the request and the voice.
- The panel's search and the spoken search share one ranking, `RelevanceSearch` (ADR 0017): `keyword`, `withMeaning`, `judge(for:)`, `filtered` and `fuse`, with the constants. The module sets no UI state, waits for nothing and logs nothing; the panel keeps its debounce, the judge's `pause`, the statuses, the selection and its log lines, and a spoken request calls the passes back to back. The panel's statuses are set synchronously in `runSearch` (`--search` waits on them), so a pass moved behind an `await` there changes what `--search` and `--search-eval` see. The "no results for" log lines print the query and stay in the panel: a spoken request never reaches them. A spoken request's sessions have two inputs the panel never passes: the session folders the request names and the time window it names, which `RelevanceSearch.spokenSessions` takes as a `SessionFilter` (`folderNames`, `window`) and a boost. The store applies the filter inside its queries, before any cut, as it does the prompt line's `#project`; a window matches a session whose first prompt is before the window's end and whose last prompt is after its start (`first_prompt` and `last_prompt`, read from `sessions` by session and folder, or `peer_sessions`, which `sessions_by_id` indexes so a window costs a lookup per row, not a scan), and a session's row keeps only its last use. A change to a pass, the fusion, the threshold or the choice of judge is one change in the module and reaches both; check the panel with `--search-eval` and `--search` before and after (off and On this Mac must match exactly, TypeSafe within its run-to-run noise).
- **A spoken request is judged by its own call** (option 07; ADR 0036). `SpokenPipeline.judge` scores the first 20 pages and up to 3 sessions wherever Settings › Search says: with TypeSafe and a key, `SpokenJudge` (one Jev call, one yes/no question per row asked by naming its title, pinned to `SpokenRouter.pinnedModel` because the 0.5 threshold's meaning was measured on it, deadline `SpokenRouter.timeout`, no retry); with On this Mac, the on-device reranker on the same rows (a session's site is its folder name); with the filter off, no key, words under three letters or a failure, nobody, and the rows go unjudged (`SpokenText.topRows`, sessions and pages both, at most 5). The panel's filter call (`Reranker`, `jev-latest`) is unchanged. **The body is a privacy surface:** the request (500 characters), today's date and where the week started, and the rows as `SpokenText.judgeRows` describes them, the one place to read or change them; anything more is a privacy change needing `docs/privacy-and-security.md` and the Settings text. **It only scores.** Rows at `RelevanceSearch.threshold` or more are kept, and so are the sessions a named project or a window with `own` selected (`Run.selected`), whatever they score: the judge may rank them and can't drop them. Sessions the time boost moved up are judged as usual. The 0.5 threshold's meaning depends on the pinned model and the row question: change either and the eval has to be run again (agent-lab `2026-10-14-judge-then-web` and `-amended`).
- **Every decision in a spoken request is a model's, never a word list's** (ADR 0037; the user's principle of 2026-10-14; `SpokenRoute.swift`, `SpokenRouter.swift`). One call decides the source, the clock ("time"), something Varnick can't do ("do"), the screen, the project (`folder`), the time (`window`), `own`, `several` and each word of the request. It is Jev's route call, made only when `activeRelevanceFilter == .typesafe` and a key is saved, pinned to `jev-1.13.0`, with a 1.5 s deadline; **when Jev isn't used, fails, times out or lacks a question, the same questions go to Text generation** (`RouteQuestions.fallbackPrompt`, one JSON line back, read leniently by `read(fallback:)`, which also quotes a bare `<…>` placeholder a model copied; its example holds quoted placeholders because a small model copied literal ones in the eval, and an unquoted one made the line invalid JSON, so every request said "I couldn't answer that"; this Mac's Gemma is poor at it by the user's choice). Both come from one `RouteQuestions`, so the wording lives once, and Jev's body is written in order (`jevBody`): projects most recent first, windows by date, as the eval sent them. With no projects in the index the project question is left out and read as none. **Never add a phrase list, a stop-word list or a word rule that decides** (not even as a fallback): add or reword a question. Code only builds labels (`SpokenTime.labels`, `ProjectIndex`), reads replies, and acts on what was chosen. The decisions come before the search, which takes its words, project and time from them (about 0.1–0.25 s with Jev during speech). **Order (`SpokenPipeline.askRoute`, then `prepare`):** "time" (the clock, the time and the date together), then "do" (the can't-do line), then the screen, then the search; `Run.route` says which. When Jev fails and Text generation is unavailable too, `prepare` throws `Failure`, and the answer step says Text generation's unavailable line. Jev's `source` probabilities only order the rows, and "other" is no longer read. The `point` action stays in the questions with the screen on; `time` and `do` are in both variants. **The body is a privacy surface:** the request (500 characters), today's date and time, and the project index twice (once as the folder question's labels, once as `projects` in the state, which `own` refers to); the measured wording for `source`, `action` (with time and do), the window's past and present labels and the written criteria is in agent-lab `2026-10-14-route-decisions-index` and `-route-time-do`, and rewording any of it needs the eval re-run. Anything added to the body needs the ADR, `docs/privacy-and-security.md` and the Settings text. The model is pinned (`jev-latest` moves). With the fallback, the same body goes to wherever Text generation runs.
- `SpokenPipeline.prepare` (the decisions, then the search, then the judge) runs while a request is still being collected, and `respond` and the speech wait for the hold to end (ADR 0017 has what a discarded partial request sends). `SpokenRequests.speculate` keys the run by the exact request text and cancels it on any change; `cancel()` must cancel the run as well as `working`, which does not cancel the task it awaits. After an `await` that catches errors, `prepare` calls `try Task.checkCancellation()`: a cancelled local generation returns what it had instead of throwing, and a failure while cancelled must not rest a server. What `prepare` can still write is harmless: `store.refreshIfChanged()`, and the on-device reranker loading. **The writer, the web call and the lines wait for the hold** (`respond`, the answer step): a partial request is never written for, searched on the web or spoken. Every speculative run is a decisions call (Jev's, or Text generation's: with Claude Code deciding, each restart is a call on the plan), and the clock's request goes to Jev too. `--ask --restart-after <seconds>` exercises the cancel.
- The request, the search words, a folder's name, the rows, the prompts and the answer are never logged (the answer is in the transcript by design; the fixed lines "Let me check." and "Looking that up." are not). A failure logs its step and the error's kind (`Error.logKind`, never `localizedDescription` or the error itself), and the timing line logs durations, places, kinds and counts: the route and who routed (Jev, or why not), the search, where the meaning pass ran, whether a folder was named and the kind of the window (a part of a day, a day or a week), who judged (or off, words too short, the failure's kind) and how many rows were kept of those judged, the writer and whether the marker was offered (or why not) and whether it escalated, the web's end, turns and times, and each line said (by kind) with when it was handed to the voice and first heard. `--ask` prints more, to the terminal only, and nothing is spoken.
- Who writes: `TextGeneration.generateNow` picks the writer at each use from `Settings.activeTextGeneration` (Claude Code, this Mac's Gemma or a server) and returns the place and, when this Mac's model answered because Claude Code failed or rests, the failure's kind (`because`); the timing line's answer part names it (`claudeCode`, or `fallback after Claude Code failed: <kind>`). It writes the answer, and decides when Jev doesn't (above); `several` from the decisions picks the one-result or several prompt. `SpokenRequests.unavailable` words what is said when nothing can write: the server, Claude Code or "Text generation isn't set up.". **The marker** (`SpokenText.escalation`, "NEED_WEB") is in the prompt only when `offersEscalation` holds: Answer from the web on (`Settings.webAnswersOn`), the request names no session folder or time, and no row the writer reads is a session. Withheld, the prompt says "say so plainly" and, for a session, what it shows, because an ignored marker leaves no answer and would cost a second call. When it is offered it takes the place of "say so plainly", as the first eval measured. Whichever writer Text generation is set to may answer with it, Gemma included, by the user's decision; a reply holding it goes to the web.
- **A request that stays local never goes to the web** (`SpokenText.Scope.staysLocal`; narrowed by the coordinator to the user's intent on 2026-10-14, and decided by the route since ADR 0037): one whose `folder` names a project, or whose `own` is true (only the user's own pages, bookmarks, sessions and projects can answer it). Not by the judge, the writer or an empty result, with the switch on or off. With nothing kept it says "I found no sessions in <project> <time>." (`Scope.nothingFound`) when a project or a past or present time was chosen, and "I couldn't find that in your pages, bookmarks or Claude sessions." with neither. **A time with `own` false is not local:** "when does Costco open today" and "what's the weather tomorrow" go to the web. **The window filters sessions only with `own` true** (`Scope.windowFilters`; the sessions it selects are kept whatever the judge scores them); otherwise it only moves in-window sessions up. **A future window, or none ("right now" is none), never filters or boosts** (`SpokenText.scope(from:)` drops it): no session was used then. A window's hours are `SpokenTime.labels`, the Mac's calendar and the named constants for parts of the day; the model picks a label's id, never an hour.
- **The project index** (`ProjectIndex.swift`; option 07) is the folder question's labels, each criterion that project's entry, and the state's `projects`. It is built off the main thread by `LauncherModel.rebuildProjectIndex` after each project scan (`scanProjects`) and each session sync (`AppDelegate.syncHistory`), from `Project.scan`'s repos and the newest 3,000 session rows (`FavoritesStore.sessionFolders`), kept in memory and never logged. A session counts under the project holding its folder: a worktree under the folder above `.claude/worktrees/`, else the nearest repo (`Project.repoRoot(of:)`, which does not follow a worktree's `.git` file to the main checkout, hence the worktree rule). **A folder in no repo counts under none** (a subagent's scratchpad under a temp folder would otherwise be a label, and choosing it would select every such session). A paired Mac's sessions count by folder name and titles only, and its folders can't be checked for a repo from here, so one outside any repo still counts. It is read on a connection of its own (`FavoritesStore.sessionFolders(databasePath:)`), off the main thread; `--ask` waits for the scan and the build (`LauncherModel.projectIndexReady`), since it asks before the app's own scan is done. Other names come from `.git/config`'s origin repo name (the file is read, no `git` runs) and the first `#` heading of `CLAUDE.md` or the README; the description is the first prose line of the README, else `CLAUDE.md`. At most 40 entries, 240 characters each, cut by dropping recent titles and then the description's end. A folder named "none" is left out, as the choice's label is taken. **The files are the user's:** their text goes to TypeSafe (or the fallback's place), so a README that holds something private goes with it; `docs/privacy-and-security.md` says so.
- **Sessions a folder or a time selected are never dropped, and the time is in the row.** A row's "when" is `SpokenTime.when`: a session in the request's window is named by it ("Monday evening, 2 days ago"), any row from the past week by its weekday and part of the day, older rows as before. Today's date and where the week started (the Mac's calendar's first weekday) go with the rows to the judge and the writer. A week-start or window that moves changes what the judge sees: check with `--ask --at <date>` on real sessions.
- **The web call** (`WebAnswer`, `ClaudeCodeState.lookUp`, option 06's call as option 07 asks it) starts only after the hold, from `respond`, and announces "Looking that up." through the answer step's queue only once Claude Code is known usable (`prepareForUse`, then `loginPassed`; otherwise "Claude Code isn't answering, so I can't look that up." alone). It ignores resting, rests Claude Code only for a login or account failure or a `claude` that is missing or won't start (`WebAnswer.endsLogin`), and sets neither `lastOutcome` nor the row's "Answers in …". The prompt carries the request, the date, the time and the unit system and nothing about the rows; the reply is cleaned (`WebAnswer.read`: the "Sources" list, markdown links and bare addresses) because Claude Code's WebSearch description asks for a list of links the prompt may not win against. Never logged: the prompt, the search words, the reply, the answer.

**The text helper** (`TextHelper/`, `TextHelper.swift`, `ClaudeCode.swift`, `Subprocess.stream`; ADR 0029; `text-generation-ignores-the-claude-subscription`, option 01)
- The levers are `@zabaca/agent`'s `minimalOptions()`: no tools (a request may carry `tools`, which becomes the call's whole tool set and is also in `allowedTools`, since a tool that would ask is refused when no one can answer, and a `maxTurns`; only the web answer sends them, `TextHelper/check.sh` guards both forms, and a call with tools answers with the last turn's text, `message.result`, not every turn's), no MCP servers (strict), no settings sources (so none of the user's hooks, plugins, skills or CLAUDE.md), auto-memory and claude.ai connectors off, thinking disabled (accepted and ignored on Haiku 5.5, so `agent.ts` also passes effort `low`, which is what stops it thinking and is faster), non-essential traffic off (one request: no session-title call and no third-party logs), the attribution header off, every reminder dropped, the SDK's one-line system prompt. `agent.ts` adds only: effort `low`, the user's own `claude` (`pathToClaudeCodeExecutable`, spread over the options, since `minimalOptions()` has no parameter for it), `persistSession: false` (a transcript under `~/.claude/projects` would be read as a session by search, Recent and project recency), the empty working folder, partial messages, a spawn that keeps `claude`'s process so it can be killed at once, the filter's folder as the plugin, and the model from the request (`TextHelper.model`, the one place it is pinned). Don't drop a lever or copy a flag by hand: a lever zbc learns reaches Varnick by a version bump.
- Bun runs as `bun --no-env-file --no-install agent.js` with `TextHelper.workingFolder` (empty, under the support folder) as its folder. `--no-env-file` because a `.env` loaded into the helper's environment would go on to `claude`; the folder holds no `bunfig.toml`, and a global one in `HOME` or `XDG_CONFIG_HOME` doesn't reach a plain run (checked on Bun 1.3.14). `bun` is `ResourceFolder.current.helpers/bun` (the bundle's `Contents/Helpers`, else beside the binary), never one from PATH.
- The login shell environment (`ClaudeEnvironment.read`) is read once per launch (`ClaudeCodeState.environment()`; again only after `claude` failed to start, since an update can move the file), from the account's login shell as a pane starts it (`ClaudeSession.claudeShell`, `-l -i -c`, from SwiftTerm's minimal environment and not Varnick's own, so a Varnick started from a pane doesn't feed its pane variables back in), listed with `env -0` between markers because startup files print. Removed: `ANTHROPIC_API_KEY` (it would bill a key, not the plan), `VARNICK_*`, `ZMX_*`, `CLAUDECODE` and the `CLAUDE_CODE_*` variables Claude Code sets for its own children (the list is `ClaudeEnvironment.removedNames`); `CLAUDE_CODE_OAUTH_TOKEN` and the proxy and CA variables of a login the shell sets up stay. **Never set or change `HOME` or `CLAUDE_CONFIG_DIR`:** either breaks the Keychain login. A failed read (non-zero exit, unreadable, over `shellTimeout`: SIGTERM, which an interactive shell ignores, then SIGKILL a second later, so 6 s in all, and a child its startup files started can outlive it) logs its kind and uses Varnick's own environment with the same removals. The environment is held in memory, goes only to `bun` and to `claude auth status` and `--version`, and is never logged or written.
- The protocol is one JSON line on standard input, then the input closed, and JSON lines back: `ready` once the request is read (so the start-up figure is bun's start and the load of `agent.js`), `text` pieces and one `result`, which the helper sends the moment the SDK's result message arrives. Varnick returns at that line, not at the helper's exit, so `claude`'s shutdown costs neither the reply nor the deadline. Nothing else goes to standard output (the entry silences `console.log`), and nothing of the prompt, the reply or the account to standard error (`Subprocess.stream` keeps only a tail of it, and nothing logs it). A failed `result` carries a kind that may be logged, never the SDK's message, which can hold what was said. `TextHelper.run` reads the end as answered, failed(kind) or cancelled; a `result` that arrived is the answer even when the deadline fell after it, and the "aborted" that a deadline's SIGTERM makes the helper send reads as the deadline.
- The reminders filter is passed by its real path (`Resources/mods/reminders`, copied from the pinned `@zabaca/agent` by `make build`; inside a compiled binary it would be under `/$bunfs`, where `claude` can't read it), and the entry checks that `hooks/hooks.json` exists first and answers "filter missing" otherwise, because `claude` skips a missing plugin path with only a log line and sends every reminder again. It needs Claude Code 2.1.291 or newer; an older one ignores it and would send the account's email address, so the local check refuses it (`TextHelper.minimumClaude`, "claude too old").
- The deadline is `TextHelper.deadline` (4 s; the web answer's own, `WebAnswer.deadline`, is 15 s and travels with the call), from the start of `bun` to the `result`, and exists because a failing login makes `claude` retry for minutes instead of failing; the entry also ends a call at once when the SDK reports a retry that is a login, billing or account error (`authentication_failed`, `oauth_org_not_allowed`, `billing_error`, a 401 or 403); an overloaded, server-error or rate-limit retry goes on under the deadline. A cancel (more speech, Hey Varnick turned off) and the deadline send SIGTERM and then SIGKILL a second later (`Subprocess.stream` with `input:`), and on SIGTERM the entry sends SIGTERM to its `claude`, waits 600 ms and kills what is left, then exits: no `claude` may outlive either. It is not killed outright because Claude Code saves `~/.claude.json` under a lock, by a temp file and a rename (read from the installed 2.1.296's code, not run), with an in-place fallback on some errors, and a truncated file or a stale lock would hit every pane. `TextHelper/check.sh` checks that against a fake `claude`; a real login made to fail is for the user to check, never an agent. A one-shot stream writes its input on a thread of its own and closes the descriptor only after it, and sets `F_SETNOSIGPIPE`, so a helper that has gone can't end Varnick with SIGPIPE.
- Claude Code is used when its local check passed (`claude` found, and `claude auth status --json` says logged in; no call is made to check before the first use, the local check gates and the first call tells). Any failure (not found, logged out, `bun` didn't start, the deadline, a failed `result`, unreadable output, no `result`) rests it for `ModelServerState.retryAfter`, and the request runs again at once on this Mac's installed model; a login that no longer works shows as "Not logged in" and a missing or moved `claude` as "claude not found", and both are checked again once the rest is over. A reply that cleans up to nothing is the model's verdict, as with Gemma, not a failure.
- The pins (Bun's version and hash in the `Makefile`; `@zabaca/agent` and the Agent SDK exactly in `TextHelper/package.json`, installed `--frozen-lockfile --omit optional` from `bun.lock`) move together with a check: `TextHelper/check.sh`, one spoken request on Claude Code, and `e2e:reminders` in zbc's package. The SDK drives a `claude` it didn't ship with, so a newer `claude` that breaks the protocol makes every call fail into the fallback until the pins move. `make build` rebuilds `agent.js` when `TextHelper/agent.ts`, `package.json`, `bun.lock` or the Bun pin changes, and writes each file by rename.

**Pointing at the screen** (`ScreenReader.swift`, `ScreenElements.swift`, `ScreenPicker.swift`, `ScreenText.swift`, `ArrowOverlay.swift`, `SpokenPipeline.lookAtScreen`; ADR 0019, 0021)
- The Accessibility read runs in Varnick's own process under Varnick's own grant, never through a helper, a script, bigarrow or a pane. macOS attributes every pane process to Varnick, zmx-hosted ones included (tccd's log, 2026-10-09), so Varnick's grants reach every pane, and a grant to zmx or a helper is never consulted (panes-share-launchys-permissions). `docs/privacy-and-security.md` says so in plain words. Turning the switch off does not revoke the grant; only removing Varnick under Privacy & Security › Accessibility does. Varnick asks macOS for Accessibility and for Screen Recording only from the Grant buttons in Settings (`ScreenReader.askForAccess`, `ScreenText.askForAccess`: their doc comments give the order); everything else only checks (`AXIsProcessTrusted`, `CGPreflightScreenCaptureAccess`), and `ScreenText.recognise` is called only after `hasAccess` is true, since ScreenCaptureKit's shareable-content call can prompt by itself. Screen Recording applies only to a process that started after it was switched on and preflight can't show the difference, so once Grant has been pressed Settings offers Restart Varnick (`LauncherModel.askRestart`: the status menu's confirmation, `restart.sh`, no build) for as long as the row says Needs Screen Recording. Screen Recording is the same Varnick-only grant, and the capture runs only in this process, never from a pane (though any pane inherits the grant and could capture the screen itself). While builds are signed ad hoc a rebuild may stop either grant applying (unverified).
- The tree read is the focused window only (not other windows, not the menu bar), depth first so the elements are in tree order, through layout areas and the like (they are only left out of the list; a scroll bar is not entered), off the main actor in a detached task within named limits (`ScreenReader.budget`, `maxNodes`, `maxDepth`, `callTimeout`): a hung app costs the budget, and the pointer step after the walk is skipped once the budget is spent. Nothing in a view update calls it. Cancelling a speculative run does not stop a read already under way (a detached task ignores it). The frame re-read before the arrow is drawn is one call, also off the main actor. `AXManualAccessibility` is set only for an app that carries Electron's framework, never for Chrome.
- Varnick's own panel is read first, like any window (`ScreenReader.panel()`, `SpokenPipeline.lookAtScreen`; spoken-requests-cant-see-the-screen, 05), under the same TypeSafe gate and no more of its own. There is no state registry and no local matching: its labels go to the same Jev `target` and `present` call with `ScreenReader.panelTitle` ("Varnick", since the panel's own title is empty) as the window's title, so its session, project and page names are sent as any window's labels are (the user's principle of 2026-10-09 in ADR 0016, 0017 and 0019: choosing TypeSafe is consent to send what a feature needs; On this Mac is the privacy setting). The panel is read only when it is the key window, visible and not wholly covered (`LauncherPanel`, `isKeyWindow`, `occlusionState`); a hidden panel, or a pinned one under other windows, is skipped. `present` under 0.5, or an empty list, reads the app behind it, which is `focusedApplication()` and still skips Varnick's own pid (without that the fall-through would read the panel again): the own-pid skip is gone only from the first read. `ScreenReader.panelFirst` is the one switch for the order (false reads only the app behind, as option 01 did); a request about the app behind costs one more Jev call (about 0.12 s). Never add a text-from-a-picture step for the panel: a terminal pane exposes no text (SwiftTerm's Mac accessibility is an empty stub), and the picture of the app behind is still the only one taken. Reading the panel is an Accessibility request to Varnick's own process, answered by its main thread, so the read must stay in the detached task with the main actor only awaiting it (`ScreenReader.read`, `currentFrame`); anything that makes the main thread wait on that task for its answer would hang. The panel's elements are its SwiftUI views' (tabs, buttons, the pin and static text such as a session row's title, folder and agent, with no row grouping), so a change that renames or removes an accessibility label, or draws a control as an unlabelled shape, changes what can be pointed at. `Varnick --ask --app Varnick` reads the running Varnick (an accessory app, which `application(named:)` accepts only by its whole name and after the regular apps, never this command's own process); `--ask` without `--app` has no panel, so it cannot try the panel-first order. A target in Varnick's own pid is a `.gone` miss at draw time unless `panel()` is still true (`SpokenRequests.answer`, `ScreenReader.isVarnick`): a panel hidden or covered during the hold may still answer for its frames. The timing line adds the panel's read, its element count and whether it pointed or fell through, never a name.
- What an element may hold: it is listed by the eval's rule (a frame centred in the window, a label or a window button, not a splitter, scroll bar, value indicator, column, layout area or scroll arrow), so text and headings are listed and a window's visible text near its controls reaches TypeSafe. Its label is title, description, help and placeholder, and the value only of text and of a control whose value is its state or choice (`ScreenReader.stateRoles`: a switch, checkbox, pop-up, slider, stepper, radio or tab); a cell's or any other role's value may be what a person entered. Never the value of a text field, text area, combo box or search field (`ScreenReader.labelParts` does not ask for it), nothing is read inside one (`Walk.visit` does not descend: a draft's text runs are its children, and the pointer step stops at the outermost field above it), and a secure text field is skipped whole, except that its frame (like every entry's) is kept in `Reading.entryFrames` to drop recognised text locally, never sent. The window is capped at 255 elements (a Choice's limit), the first in tree order.
- The description of an element (`ScreenElement.description`) and the two calls in `ScreenPicker.body` are a contract with the eval: the choice's wording, the `present` yes/no, the order of the elements (written by hand, since a dictionary would shuffle them) and the 0.5 on `present` (`ScreenPicker.pointFrom`) were measured as they are. Changing any is a re-measure, and adding to what is sent (request, window title cut to 80 characters, element descriptions) is a privacy change: the ADR, `docs/privacy-and-security.md` and the Settings text. The markers are "dimmed" and "under the pointer" only; a dialog marker was not in the measured format. Gemma never points, so no element reaches a model server; with no Jev (filter not on TypeSafe, no key, a failure) a screen request ends in a spoken miss.
- The overlay (`ArrowOverlay`) is one panel, nonactivating, never key or main, ignoring the mouse (`ignoresMouseEvents` and a `hitTest` of nil), at `.screenSaver` level so it is over Varnick's `.floating` panel, on every Space and over full-screen apps. It is shown with `orderFrontRegardless`, never `makeKeyAndOrderFront` or an activation: that would move focus, and the panel hides when it loses key. It goes up as soon as the pick is made and its frame re-read (after the hold, never before), ahead of the speech's rendering (about half a second), not just before the sound as option 01 said, and stays until `lingers` (8 s) after the speech ends. The timing line has the re-read, the draw and when it was up. It goes at once on a new request (`collect`), a cancel and the switch off. It does not follow a window that moves.
- The text fallback (`ScreenText.windowText`, called by `SpokenPipeline.lookAtScreen.readText` and by Screen access's `look`; ADR 0021) runs when the tree's `present` is under 0.5 or the window lists nothing, and first when Chrome's web area is empty. In Chrome one Jev call chooses among the toolbar's tree elements and the page's recognised lines (each sent once, the elements giving way past a Choice's 255); only lines whose centre is in the empty web area (`Reading.emptyWebArea`) are kept, so tab titles and the toolbar come only from the tree. It needs Screen Recording and the Jev gate; without the grant, or on a miss of any kind, the tree's answer (and Chrome's sentence) stands.
- The picture: the focused window alone (`desktopIndependentWindow`, so Varnick's own panel and arrow are not in it), chosen by overlap with the Accessibility frame (`bestWindow`: at least half, ties to the active window; no Accessibility window is `no window`, never the largest). It is held in memory until Vision has read it and goes out of scope: nothing writes, logs or sends it, and nothing should pass it beyond `ScreenText.read`. Capture plus recognition race `ScreenText.limit` (2 s) in unstructured tasks, not a task group, since a group would wait for a ScreenCaptureKit call that never returns; a timeout is `skipped (timed out)` and a stalled request must never leave Hey Varnick in `.answering`.
- Recognition is `.accurate` with language correction off (`usesLanguageCorrection`): measured on synthetic windows, the same labels in about two thirds of the time; `.fast` is much quicker but split or dropped short labels ("Notif ications", "Wi-Fi"), and a downscaled picture (1,600 px wide, or 1x) was no faster and lost labels, so the capture stays at the window's own scale. A recognised line is cleaned by `ScreenText.withoutDebris` before it is a candidate (bullets, list numbers and lone symbols at its ends, and one last capital letter after a lowercase word, once), so Jev and the spoken note see the clean words while the arrow rings the original box; `isLabel` is checked on the line as read too, so cleaning never admits a line that was too long. Keep the rule conservative, since a label's own digit, capital, lowercase letter or sign ("Step 2", "Option B", "plan b", "100 %", "Zoom Out −") must survive.
- Kept lines are label-shaped (`maxWords` 6, `maxCharacters` 60, `maxLines` 150, a letter or digit in them) and outside every frame in `Reading.entryFrames` (centre in frame): the walk's text fields, text areas, combo boxes, search fields and secure fields, and the field the app reports as focused when it is one. Those frames were read where the window was, so they are carried to the capture's window with `ScreenGeometry.moved`. A line is "text on screen" and goes through `ScreenPicker` unchanged, so its wording and the 0.5 stay the eval's, but how well Jev picks among recognised lines is unmeasured. Accepted by the user (ADR 0021): a field Varnick can't place is not excluded, so typed text of 6 words or fewer there may reach TypeSafe: Chrome pages, canvas apps, remote desktops and VMs (their fields are not in the tree), fields past the walk's node, depth and time limits, and fields that moved before the capture. Fields the tree finds (native, or a web page's in Safari or an Electron app) and the focused field are dropped. `docs/privacy-and-security.md` say so and the Settings text points to SECURITY.md, which points to it; widening what a line may hold is a privacy change needing both. What goes to TypeSafe on this path is the request, the window title and the lines' words: never the image, a box, a longer line or a tree element twice. A recognised target has no element to read again, so the window's frame is re-read and the box follows a moved window (`ScreenGeometry.moved`); a resized one is `gone`. The timing line adds the capture's and recognition's durations, the recognised and kept counts and the skip kind, never a line; `--ask --app` prints the same.
- Accessibility frames (global, origin at the top left of the main display) become AppKit's (origin at the bottom left of the main display) only in `ScreenGeometry` (which also turns a Vision box, normalised from the image's bottom left, into one: `accessibility(normalised:inWindow:)`); a display left of or above the main one has negative coordinates in both, so a conversion done anywhere else breaks on a second display first.
- The timing line adds the read's duration, the element count, who chose, whether Jev found the thing present and the miss's kind. The request, the window title, the labels and the pick are never logged; `Varnick --ask --app` prints the pick to its terminal.

**Screen access** (`ScreenMCP.swift` for `Varnick --mcp`, `ScreenAccess.swift` for the running Varnick's half, `PeerManager.handle`, `ClaudeSession.launchClaude`; ADR 0023)
- A screen request has no `op`. `PeerManager.handle` tells it apart only by that (`head.op == nil` and a `screen` key), before the peer checks, and a line with an `op` is a peer's whatever else it holds. The relay (`PeerRelay`, `MacPeerHost.forward`) refuses a line without a known `op` and forwards only `start`, `resume`, `end`, `projects` and `agents` (and passes `hello`, `upgrade` and `restart` for the app's part of their answers), which is why no paired Mac or device can click. A change that lets the relay pass an unknown line on, or gives a screen request an `op`, hands them the screen.
- `Varnick --mcp` never reads or acts: it is JSON-RPC lines in and out, and one socket request per `tools/call`. Keep every Accessibility, capture and event call out of `ScreenMCP`. Its standard output is the protocol, so nothing else may print there (`print`, a stray log) and `main.swift` runs it before anything else of the app starts, like `--peer`. It exits when its input ends. It shares with the app only `PeerSocket`, `PeerJSON`, `PeerLink` and the constants it reads from `ScreenAccess` (`clickLead`, `signNote`), `ScreenKeys` (`maxCharacters`, `maxKeys`, `longestTyping`), `ScreenPicture` (`longSide`) and `ArrowOverlay` (`lingers`), all `nonisolated`.
- `--mcp-config` and its JSON go first in `ClaudeCommand.arguments` (`mcpConfig`), before `--settings`: the option takes several values and stops at the next option, so anything put between it and `--settings` would be read as another config. `ClaudeSession.launchClaude` passes it for every Claude pane on this Mac: always, since `notify` (see Messages) is listed whatever the switches say, with `--screen` and `--panel` named only for the switches that are on at that start, and the headless relay passes one with `--notify` alone. It is not stored on the record, unlike the other arguments (CODING_STANDARDS.md names the exception): a restart or a resume reads the switch again, which is how a pane gains the tools. The command is the peer link, so a session's server is the build that was running when the session started; `make run`'s kill pattern matches only the bare binary with no arguments, so a restart doesn't end the server (check this if the pattern changes).
- The request's own version (`ScreenRequest.version`) is not the peer protocol's. Bump it when the request or reply shape changes, and a server from an older launch is told to restart the session. A line whose `screen` is another number is answered before anything else is decoded.
- The switch (`Settings.screenAccess`) is read at every call, after the version and before anything else, so turning it off stops running sessions with no restart (`ScreenAccess.switchedOff` also drops the id tables and the Arrow). A click re-reads it after its one-second lead.
- Ids: `e` for a tree element, `t` for recognised text, replaced by the pane's next `look`, in memory only, dropped when `prune` sees the pane gone. An unknown id is "look first", a control that has gone is "gone: look again". The frame is read again for `point` and `click` (`ScreenReader.currentFrame`), twice for a click: before the arrow, and, after the app is in front, for the click itself (refused as gone when it can't be read, never a stale point). Chrome's Accessibility frames can lag a scroll, so ids from a `look` taken before a scroll may be stale: a session looks again after scrolling.
- Own process: `look` never reads Varnick (`focusedApplication` and `application(named:)` skip its pid, and the panel-first read of Hey Varnick is not used), and an id in Varnick's pid is refused (`ScreenReader.isVarnick`). A click that is posted (a point, a recognised line, a control with no press action) is refused when a visible window of Varnick's own, other than the arrow's panel (`ArrowOverlay.owns`), has its frame over the point (`varnickCovers`, by frame and not by z-order, so a pinned panel under another window still refuses). It is asked on the main actor right before the event is posted with nothing awaited between (`checkedToPost`), and for `at` also early, before the queue. A system-wide Accessibility hit test is not used: the arrow's panel covers the display in Varnick's process while a click's arrow is up, so it would find Varnick every time. A press through Accessibility is not checked, since its element is another app's (ids in Varnick's pid are refused).
- A click that has waited, led or brought its app forward for `staleAfter` (9 s) since its request arrived is dropped, since the relay gave up at 15 s and the session must not be clicked for after it was told no. The switch, the pane (closed, or another Mac in control now) and that age are checked again after the click gets its turn, after its lead and after the app is in front (`frontWait` 1 s, started before the request, and `frontSettle` 150 ms come before the last check, so they cost nothing of what follows it. After it, worst case, a press click takes the page search (1 s `budget`, checked once per step, plus the step in progress: a role, a frame and a parent call of 0.25 s each, so up to 1.75 s), the frame read (1 s), the press check (1 s) and the press (1 s), about 4.75 s: 13.75 s against the relay's 15 s, less the main-actor hop before `arrived` is set. A posted click takes about 2.9 s. Another wait or read after that check must shrink `staleAfter`), and the click fires only if the arrow up is still its own (`ArrowOverlay.generation`): a `point`, a Hey Varnick arrow or a hide during the lead refuses it. A refusal after the click's turn begins says "Nothing was clicked" (`ScreenRefusal.stopped`).
- A click is one at a time across all sessions (`acquire` and `release` hand the turn over without letting a third in), the Arrow first, `clickLead` (1 s), then the app brought forward (`bringForward`: `NSRunningApplication.activate`, Accessibility's `AXFrontmost` and `AXRaise` on the target's window, polled until it is frontmost, never Varnick itself; a point's app is the front-most ordinary window's at it, none for the menu bar, Dock or a menu), then the press or the posted click, then the Arrow 2 s more. An app that does not come forward in a second refuses the click ("Nothing was clicked"). `checkedToPost` then asks again, synchronously with the post, that the app is still in front and owns the front window at the point (`frontWindow`; for a point with no app, that none does), that the arrow up is still this click's, and that Varnick's windows aren't over it. An id inside a web area, in a browser or Electron app, or whose search for a web area was cut short in another app (`ScreenReader.content`) gets a posted click at its centre read again after the app came forward, never an `AXPress`, which on a page can report success and do nothing. The search walks to the top and intersects the frame of every web area and scroll area on the way, so an iframe is held to the top-level page; a centre outside that is refused as gone (a lagging frame under the toolbar or tab strip). In a browser or Electron app a search cut short refuses ("Couldn't tell where the page is: look again", nothing clicked) rather than post unchecked. If the centre has moved more than `arrowFollows` from where the arrow was drawn, the arrow is drawn again there, after a check that it is still this click's. A press has its own 1 s messaging timeout, longer than the walk's 0.25 s, and a timeout is reported as sent, not as a failure. The posted click is a mouse-move, a left-down and a left-up at the HID level after `CGPreflightPostEventAccess`; the pointer stays where it went. Replies say what was done, never that it worked.
- `type`, `drag` and `window` (`ScreenInput.swift`; the combo rules and key events in `ScreenKeys.swift`; option 06 of `sessions-cant-see-or-act-on-the-screen`) are built as a click is, and share its queue: `acquire` and `release` serve every action that changes the screen, and `look` and `point` never wait in it. The order is the click's: the turn and `stillAllowed`, the Arrow, `clickLead`, both checks and the Arrow's generation, the app brought forward (not for `window`), both checks again, the reads, the action, the Arrow 2 s more. A refusal before any action keeps click's rule of saying what was done: "Nothing was typed", "Nothing was dragged", "Nothing was moved", and a refusal partway says how far it got ("Stopped after 17 of 42 characters; no keys were pressed", "Let go where it began"; `ScreenRefusal.stopped` carries the sentence and the counts for the log). The request's version stays 1, so a session started before the build keeps its three tools until it restarts; `ScreenArguments.text` is `look`'s flag or `type`'s characters (`ScreenArguments.Text`), kept as sent.
- Each tool has its own age limit at its last check, because each ends by the same 13.75 s as a click (`staleAfter` 9 s, then about 4.75 s worst case): `type` 9 s less its own typing (`ScreenKeys.duration`: `characterPace` per character and, per combo, `comboPace` plus the check's 0.2 s, the ⌘A of `replace` included, so a call with only Return must reach its last check by about 8.75 s and 500 characters with ten keys by 4 s; `ScreenKeys.longestTyping` is that longest typing, 5 s). That limit is tuning: typing itself is held to an absolute deadline (`typingDeadline`, 13.5 s since the request arrived, less the typing still to do) asked in `checkedToType` before every character and key, so a slow focus step or read after the last check ends the call as late, partway if need be, instead of typing past the relay's 15 s, `drag` 7 s (two ends' page search and frame, up to 2.75 s each, then about 0.6 s of motion), `window` 9 s (three settings of 1 s and one read). Any wait or read added after a tool's last check shrinks its limit. `characterPace` (5 ms) is tuned by hand to the fastest pace TextEdit, a field in a Chrome page and Terminal all keep up with; a slower one shrinks `maxCharacters` so the text still takes at most 2.5 s.
- `type` types as key events posted at the HID level, never a field's value set through Accessibility (a web form keeps its own copy of the value; events go through the app's own input path). A character is one key-down and key-up carrying it as the event's Unicode string with no flags (so a held modifier never reaches it), a combo is one key-down and key-up with its modifiers as flags, never modifiers pressed as keys. Before every character and every key, on the main actor with nothing awaited between and the event posted at once (a combo's key-down is posted synchronously after the checks, and its key-up always follows after `comboHold`) (`checkedToType`): the switch and the pane, the age (`typingDeadline`), the app still frontmost, no window of Varnick's key (its panel is nonactivating, so it can hold the keyboard while another app is in front), the Arrow still this call's. Before the first character or ⌘A, and before each combo, also, off the main actor: the system-wide Accessibility focused app is this one (`ScreenReader.keyboardOwner`, a 0.1 s race that leaves Accessibility's process-wide timeout alone; no answer in time refuses, as does another app, so Spotlight or a system panel holding the keyboard gets nothing and a combo that hands the keyboard over stops the call) and, for a combo, the focused element is not a secure text field (a light read: role and subrole, 0.1 s a call, side by side with the keyboard's owner). The first failure stops typing, and the reply says how far it got. Nothing is typed or pressed while a secure text field has focus, checked after the focus is set and before the first character; an app that doesn't report one (Chrome with its tree hidden, a canvas app, a remote desktop, a virtual machine) is typed into. The text, the keys, the app and the session's name never reach the log: it has the tool, the kind, characters typed of asked, keys pressed of asked and durations.
- `type`'s focus: an id outside a page gets `AXFocused` and the app's focused element must then be it or sit inside it within four levels, else "Couldn't put the focus in e5" and nothing is typed; an id in a page, or recognised text, gets a posted click at its centre, read again, with every check a posted click makes (inside the visible page, not overlapped, not under Varnick), and that focus is not verified. Where the caret lands is the app's: `replace` posts ⌘A first, refused when the focus reads as something that takes no typing (only a text field, text area, combo box, search field or web area passes, and so does focus the app doesn't report).
- Key combos are `KeyCombo`s, read against the current layout (`ScreenKeys.parse`, on the main actor like `KeyCombo.keyName`, the other way round; the current ASCII-capable layout when the current one is an input method): a ⌘ combo's character is looked up with ⌘ held (Dvorak–QWERTY ⌘ types the QWERTY letters), a letter is its key whatever its case, another character is the key that types it with ⇧ added when only the shifted key does, one no key types is refused, and `replace`'s ⌘A is looked up the same way (a US key code would be ⌘Q on a French layout). Refused, whole call, before anything is done: Varnick's own anywhere-shortcuts as bound when the call arrives (`Settings.combo` for show or hide, pin and Listening; they would act on Varnick, and showing the panel would send the rest of the call into it), and log out, lock screen and Force Quit at macOS's default bindings (log out and lock refuse both the US Q key and the key that types q on the current layout with ⌘ held, so cmd+shift+a on AZERTY is refused too). Any other combo goes to the app as the user's. A click or drag on the menu bar can still reach Apple menu › Lock Screen or Log Out: known, accepted for now. Text is at most 500 characters with no control or line-separator character, refused whole, never cut, since a session can't read the field to see a cut.
- `drag` posts a left mouse-down, dragged events along a straight line and a mouse-up. Both ends' apps are found before the start's comes forward (a point's is the ordinary window in front there, an id's its owner), and only the start's comes forward. The start is checked as a click is (`checkedToPost`); the end (`checkedToRelease`) is checked before the button goes down and again before it comes up: the switch, the Arrow, Varnick's windows and that the front window there is still the end's app's. If one fails after the mouse-down the pointer goes back to the start and the button is released there; the release is in a `defer`, so a thrown error lets go too. The Arrow is drawn again at the end after a check that it is still this call's. The path between the ends is not checked, and an end under another window once the start's app is forward is refused. The timings (`dragHold`, `dragTime`, `dragStep`, `dragRest`) are tuned by hand.
- `window` sets size, then position, then size again when both are given (macOS keeps a window on its display, so one order would cut a size that doesn't fit at the old place), each with the press's 1 s timeout, through Accessibility only: no pointer and no activation. It refuses a window in full screen or minimized, one whose position or size isn't settable, one whose new title bar (its top 30 points, 20 by 20 of them on a display) would be off every display, and Varnick's own (`ScreenReader.pid(of:)`). The first three are asked again after the lead, before the last check, so they cost nothing of the budget after it. The reply gives the frame read back, which can differ from the one asked. A `w` id (`w1`, the window `look` read) is taken only by `point` and `window`; `click`, `type` and `drag` refuse it (`controlTarget`).
- `look`'s focus line comes from `Reading.focus` (the app's focused element, kept from the read's existing request for it, and matched to a listed control within four levels inside the read's own budget); it is never a marker in `ScreenElement.description`, which is the eval's contract with Jev for Hey Varnick. It is a kind, never a label or a value.
- **A picture shows everything on the window, including typed text, which the listing leaves out, and it goes to Anthropic with the session** (`look` with `picture`, `ScreenPicture.swift`; option 07 of `sessions-cant-see-or-act-on-the-screen`, ADR 0023's amendment). `Reading` never held what a field holds, and `ScreenText` drops the lines inside fields; a picture has neither protection but one: the secure text fields the walk met, and the focused one when it is secure (`Reading.secureFrames`), are painted black in the scaled image just before it is encoded, with 4 points of margin and after the crop, so no resampling carries their pixels. A frame is kept once (the focused field and the walk meet the same one).
  - **The gaps in the black-out** are listed once, in `docs/privacy-and-security.md`. In the code: `Reading.chromeBlind` and `Reading.walkCutShort` (the walk's 3000 nodes or 1 s ran out with nodes unvisited), which make the reply say Varnick reached only part of the window, where otherwise a picture with nothing hidden says "No password fields seen in it". Whatever else is typed (names, messages, numbers) is in the picture. By hand: whether Chrome reports a password field as secure with its page tree on.
  - **The capture is `ScreenText.capture`**, the text step's own (`captureWindow`: ScreenCaptureKit, one window by overlap with the walk's frame, `SCStreamConfiguration` at the window's pixel size, within `ScreenText.limit`), so a `look` that asks for `text` too captures twice. It is refused without Screen Recording (`ScreenRefusal.noScreenRecording`, before the read) and with a short reason on any other failure (`noPicture`). The window is the app's focused window, which Varnick's own windows never are.
  - **The secure frames were read before the capture,** with the window's frame (`Reading.windowFrame`). They are carried to where the window is in the capture (`ScreenGeometry.moved`), and a window of another size (more than 2 points) refuses the call ("changed size while it was captured") rather than guess. A page that scrolled or a field that moved inside the window between the walk and the capture is not followed: the same lag as an id's frame. Unverified: that ScreenCaptureKit's window frame and Accessibility's agree within 2 points for every app, which a mismatch would show as false refusals in windows that have a password field.
  - **The size** is worked out from the socket, not chosen: `PeerSocket.maxLine` (1,000,000 bytes) caps every line in both directions, a peer's request included, and the reply that carries the picture is a line. `ScreenPicture.maxBytes(textBytes:)` leaves room for the listing and the JSON around the base64 (4/3 of the picture), and `ScreenPicture.make` tries JPEG at 0.8 (PNG too at the first size, kept when smaller), then lower qualities, then smaller sizes, before it gives up ("too large to send"). A picture over the cap would not arrive ("Varnick's answer wasn't readable"). Raising the cap is for a change to the relay that also moves peers' requests; it is not needed for this. `PeerSocket.readLine` looks for the newline in each chunk only, since scanning everything read so far, for a reply of hundreds of kilobytes, was quadratic. Unverified: Claude Code's own limit on an image in a tool result.
  - **`look` reads `picture` and `rect` only for a picture (the screen's too, below);** `rect` is cut to the window and refused outside it, and a rectangle without a positive size is refused as `point`'s is. A `rect` sent and unreadable is refused too (the relay sets `rectUnreadable`, since a dropped one would return the whole window); numbers as text and the rectangle as JSON text are read. The reply's text says the picture's pixel size, the area in screen points and the pixels per point, so a session can turn a spot into a point for `click`, and how many password fields were painted black. `ScreenMCP` reads `ScreenPicture.longSide` for the tool's description: a constant, as the others it shares. The request's version stays 1 (the reply's picture is optional).
  - **The log** has `picture <jpeg|png> <w>x<h> <bytes> bytes, hidden <n>` in the counts, and a refusal's kind. Never the picture.
- **A screen picture shows everything on every display, with nothing hidden: Varnick's panel and other sessions included, typed text and password fields included, and it goes to Anthropic with the session** (`look` with `screen` or `display`, `ScreenAccess.screenPictures`; option 08 of `sessions-cant-see-or-act-on-the-screen`, ADR 0023's amendment). The user chose both: Varnick's own windows are not excluded from the display filter, and nothing is painted black, since no walk of the windows on a screen was made to find secure fields. The reply says so each time. Do not add an exclusion or a black-out here without the user, and do not reuse option 07's "No password fields seen" wording for it. The gap is listed once, in `docs/privacy-and-security.md`.
  - **Capture** is `ScreenText.screens`: `SCContentFilter(display:excludingWindows: [])` at the display's point size times `pointPixelScale`, no pointer, within `screensLimit` (5 s for all displays; the relay waits 15 s). Frames are `CGDisplayBounds`, the Accessibility coordinates every other tool uses, and the numbering (`displayOrder`: main display first, then left edge, then top edge) holds while the arrangement does. A `rect` skips displays it doesn't reach before capturing them.
  - **No window is read without `app`:** `look` then lists nothing and does not replace the pane's ids (`targets` is untouched), so a session's last ids stay as stale or good as they were. With `app` the window's own listing comes first (`lookWindow`, `picture` and `rect` dropped from its arguments) and the screen part follows; the new ids are kept only once the screen part succeeds, so a refused call leaves the last look's. The relay's `rectUnreadable` and `displayUnreadable` travel in the request line and are read back in `ScreenArguments.init(from:)`: the keys they were judged from are not in it. `picture` is not taken as well as `screen` or `display`.
  - **The size** shares `PeerSocket.maxLine` among all the pictures and the text: `ScreenPicture.maxBytes(textBytes:count:)` is the total, with room reserved for the Displays list and each picture's line, and each picture is given an equal share of what is left after the ones before it (`screenPictures`). A display starts at `ScreenPicture.startingLongSide(forCount:)` (1568 for one, divided by the square root of the count, not under 640) and the fit loop of `ScreenPicture.make` goes down from there. Unverified: how large a three-display reply is on a busy desktop; whether Claude Code limits the images of one result below the cap.
  - **The reply** carries the pictures in `ScreenReply.images`, in the order the text names them; the relay (`ScreenMCP`) turns each into an image content item. `image` stays for the window's picture, so the request's version is 1 still. An older server shows a screen reply's text and no image.
  - **The log** has `pictures <n>, <jpeg|png> <w>x<h> <bytes> bytes` for each, and a refusal's kind (`no display`, `outside displays`, a capture failure's code). Never a picture or a frame.
- The text step is `ScreenText.windowText`, which `SpokenPipeline.lookAtScreen`'s `readText` also calls; Hey Varnick's behaviour is the measured one, so a change there is a change for both. `look` runs it when the window lists nothing, when Chrome hides its page (only lines in the empty web area) or when `text` is set. Its capture (`ScreenText.captureWindow`) is also the picture's, so a change to the capture is a change for the picture; `ScreenText.withinLimit` races any work against `limit`.
- The log has the tool, the outcome's kind (a refusal's `logKind`), counts and durations; never a label, note, window title, app name or session name. What a session is shown goes to Anthropic, not TypeSafe: adding to what `look` returns, or to what a picture covers (Varnick's own windows are already in a screen picture), is a privacy change for the ADR, `docs/privacy-and-security.md`, the README, the guide and the switch's detail.
- A pane's name on the sign is `ClaudeTab.boardTitle(of:)`, the board card's title, cut to 30 characters; the note to 120.
- By hand after a restart (nothing here is covered by a test): `/mcp` in a session restarted with the switch on lists `varnick` with six tools, whether Claude Code trusts a server from `--mcp-config` without asking, which protocol version it asks for, that a posted click needs nothing beyond Accessibility under the hardened runtime, and how the pane's card state follows a takeover. For the picture: `look` with `picture` at TextEdit returns the listing and an image whose text says its area; with `rect` on a corner it is that corner; a System Settings or Safari password field is black in it; a Chrome login page's shows (the measured gap); a busy window (a photo) arrives under the cap; without Screen Recording the call is refused; the log holds kind, size and bytes only. For the screen picture: `look` with `screen` returns the Displays list and an image for each display whose area matches its frame; `display` 2 returns that display only and a number past the last is refused; `rect` over part of a display returns that part; with `app` the app's listing comes first; on a Mac with two or three displays the reply arrives and each image is readable; a click at a point worked out from an image's area and scale lands there; the log has counts, kinds, sizes and bytes only.

**Panel access** (`PanelMCP.swift` for `Varnick --mcp`'s second set, `PanelAccess.swift` for the running Varnick's half, `ScreenMCP.swift`, `PeerManager.handle`, `ClaudeSession.launchClaude`; ADR 0031; `sessions-cant-read-or-drive-varnick`, option 01)
- A panel request has no `op` either, and a `panel` key of its own with its own version (`PanelRequest.version`, not the screen request's or the peer protocol's). `PeerManager.handle` tells the three apart by `op` and the key, before the peer checks. The relay's refusal of a line without a known `op` is what keeps every paired Mac and device from sending one: the same rule as Screen access, so the same warning (never let the relay pass an unknown line on, never give a panel request an `op`).
- One server, two sets: `Varnick --mcp --pane <id>` lists what `--screen` and `--panel` name, and the screen tools alone with neither (a session started before this build keeps its tools). `ScreenMCP.configuration` takes both switches and gives nil with both off; `launchClaude` passes `--mcp-config` (first, before `--settings`, as Screen access's note above says) when either is on at the start. A tool a set doesn't list is `Unknown tool` in the server before anything is sent. `make check-mcp` checks all of it with no running Varnick. `--mcp` still never reads or acts and its standard output is the protocol.
- The tool list is `PanelMCP.tools`, built from static constants, so the server reads nothing of the app. A tool name must not clash with a screen tool's; `scripts/check-mcp.sh` fails on a repeated name.
- The switch (`Settings.panelAccess`) is read at every call, after the version and before anything else; turning it off also drops the id tables (`PanelAccess.switchedOff`, from the `main.swift` sink). Order of checks: the version, the switch, Varnick starting, the pane, the tool. The pane rule is `CallingPane.find`, shared with `ScreenAccess` (a Claude pane on this Mac that no other Mac or device controls): change it in one place. Accessibility is never checked, and nothing here reads or posts through it: a later adopter that read Varnick through Accessibility would have to keep the read detached from the main actor (Pointing at the screen, above).
- Ids are `s<n>`, per calling pane, in memory, for the pane's life (`PanelIDs`): the same pane or card gets the same id at every read, a new one the next number. `prune` drops the tables of panes that have gone. An id is a label of Varnick's own table, not a credential, like a pane id.
- `panel` reads `LauncherModel` as `LauncherView` picks the content (Settings, the board, a tab, else the search), then what lies over it (the split picker, the Restart Varnick card). **Never the search field's text**: only its mode and whether `query` is empty. A change to what the view shows needs the same change here, as with `panelHeight`.
- A view gets tools by adopting `PanelAccessView` (`PanelViews.swift`) and being added to `PanelViews.all`: nothing changes in `PanelMCP`, `ScreenMCP` or the request. The server lists `<name>_read`, and `<name>_act` if `actionSpecs` is not empty, from the adopter's static `readSpec` and `actionSpecs` (constants: the server never creates a view), and the router finds the adopter by the tool name (`PanelViews.find`), makes it from the model and calls `read` or `perform`. The router keeps the switch, the pane, the ids, the refusals, the log and the reply; an adopter returns text or throws a `PanelRefusal` and holds no state of its own. A tool name must not clash with a screen tool's or `panel`'s. Settings never adopts. `read` is async (the Outline's first read waits for its file) and the router checks the switch and the pane again after it, as after `perform`. `outline_act` is the first `_act`.
- `outline_read` (`OutlinePanelView`; the text is `OutlineReading`'s, Foundation only and run by `--outline-check`; the shape, the bounds and the ids are in ADR 0031). It reads `Outline`'s model, **never a text view**: the caret is `shownForSessions`' record (`remembered`), "in a bullet" only while the panel is up and key. `loadForSession` starts the same read of `outline.json` that `appear` does, off the main actor, without `showingOutline`, a caret or a write, and a call during the load awaits `loadTask`; nothing on a read may reach `OutlineSaver` or `moveAside`, and an unreadable or newer file is refused with `Load.problem`. `focusesOnLoad` is what keeps a session-loaded file from placing a caret; `close()` resets it and `restoreCaret` while loading sets it. A row's `o` id is its path's, so an edit that changes the path (indent, outdent, move) gives it a new id. A cut read continues with `after: oX` (the last row listed), which walks the same list again and so needs the same `at`, `depth` or `as_shown`; the as_shown hint never points at the default read, which ignores the zoom and filter. The bullets go to Anthropic: a field that shows more of the Outline is a privacy change for ADR 0031, the guide, the README, `docs/privacy-and-security.md` and the switch's detail. The log holds the tool, a kind and a count of lines. `panel` reads the same way (`outlineLines`) and publishes and loads nothing.
- `outline_act` (`OutlinePanelView.perform`, `Outline.performForSession`, `OutlineActing`; their doc comments say how). The gotchas: **`insert` (`OutlineEdit.insert`, which a paste already used, now with `lastUnder` and Home as a parent) is the one new tree edit for `add`, and `setDone` the other**. `OutlineTree`'s rules also changed in these ways: `OutlineScope.wholeTree` (below); outdent with it stops at Home, not the zoom's top; and delete, indent and outdent refuse a row the zoom runs through (the bullet zoomed into, or one it is nested in: `holdsZoom`), since moving or removing it breaks the zoom path, `finish` resets the zoom to Home and ⌘Z doesn't bring it back. The keys can't reach those rows. Every action goes through `applyEdit` on the one undo stack; with `forSession` it follows none of the edit's own caret, scroll, beep, header message, kept rows or selection end, so the user's caret moves only as `OutlineActing.caretMove` says (a moved, indented or outdented row, or one above it, is followed; a delete or complete of its own row goes where ⌘⇧⌫ or ⌘↩ would put it; any other row taken from view goes to the nearest row showing; otherwise it stays, and a move that keeps the path stays). **Never set the text of the view that has the caret:** a `set_text` or `set_note` on the field it is in, through any placement (compared by bullet, not path), goes into that view as a key does (the Outline's text-view rule, below); `updateNSView` skips the first responder, so every other edit leaves it alone. Indent, move and outdent use `OutlineScope.wholeTree` (Show completed only: not the filter, the zoom or collapsed bullets, which would refuse rows the session's unfiltered read lists); the rest don't depend on what shows. `complete` is `setDone`, which checks the state when it applies, not when the call was read, since the waits can let the user change it. The waits (the caret landing, 1 s; an input method composing in the caret's row or one above it, or in the view an edit goes into, 3 s) run before `allowed`, which is asked right before the edit and checks the switch, `Task.isCancelled` and that the pane is still one a session may act from (`PanelAccess.mayAct`): the router's checks come after the edit, so a reply of "controlled" for an edit that landed would invite a duplicate on retry. A delete of the bullet the user is zoomed into, or one it is nested in, is refused like the title. Ids are paths: an indent, outdent or move gives the row and what is nested under it new ids, a delete makes them "gone". The log is the router's line: the tool, the action, `edit refused` and the line count, never a bullet's text.
- `board_read` (`BoardPanelView`) runs one `SessionBoard.refresh` and reads `cards`: the tick's own stat of each pane's turn file, on the main actor. It must stay that: never `appear()`, a ticker, a zmx check or `refreshPeersForBoard` (a read must not ask a paired Mac, ssh and all), so a paired Mac's cards are as last fetched, and the Problems tab is as last read (its files are read off the main actor only while the tab shows). The Problems tab is refused while the Problems board switch is off, as `!problems` is. A card's id is its tab's UUID (ADR 0032), never a pane's, so an ended or Completed card and a paired Mac's tab with no tab here get `s` ids too; under each card its Claude sessions are listed with their own pane ids, the ones `pane_read` takes. The board has no `board_act`: Done, Restart and End act on other sessions.
- `pane_read` (`PanePanelView`) reads a terminal's screen on the main actor and only reads: the last `terminal.rows` lines of the buffer, by `getScrollInvariantLine` (the end found by probing, since SwiftTerm doesn't expose the line count). Not `getLine(row:)`, which counts from `yDisp`, the scrolled position: a pane the user scrolled back would return its scrollback. So the read is the live screen whatever the scroll, and never changes the scroll. Trailing blanks are cut per row and empty rows at the end. It never resizes, writes to or focuses the terminal or its view, so reading a pane in a tab that isn't showing leaves its pty size alone (the Sessions and tabs rule on frame changes: `VARNICK_LOG_RESIZE=1` must show no `[resize]` line for a read). A pane showing a card (`awayNote`) has no terminal to read: the card's `screen` is VT text, drawn into a throwaway `HeadlessTerminal` of the card's grid (else of the pane's own terminal's size, never the text's line count, so a long history comes back as its last screenful) and read the same way, marked "Last screen at HH:mm" when `stoppedAt` is set and live otherwise; with `serial` 0 it has none yet. A pane not started has no terminal contents ("not started"). A page, file, custom app or the live transcript gives kind and title only; a card's own id is its tab's, which has no screen: it says so, and points to the card's sessions. The user chose on 2026-10-11 that other panes' visible screens are readable; their scrollback, transcripts and prompts beyond what the card or screen shows, and the search field are not. Wide characters are read with `skipNullCellsFollowingWide` (unverified against real wide text).
- `show` (`PanelAccess.show`) changes the view **only through the model's own functions**: `showSearch` (after `hideBoard`, since `showSearch` leaves a board standing), `showBoard`, `showPane` (which goes through `activate`, so the board closes and the tab comes up focused) and `LauncherModel.run(_:)`, the one function `runCommand` calls for ↩ and `show` calls for a session. Going around them breaks `panelHeight`, the focus rules and "never the board and a tab together" (Focus and keys, Panel size, above). It **never shows, hides, pins or activates the panel**: no `show()`, `bringToFront`, `NSApp.activate` or `makeKey` here, and a change to those functions that began to do so would bring the panel up in front of an app the user is working in. With the panel hidden the reply says the view is there when the user opens it; and with the panel hidden `show` refuses a `pane`, `command: transcript` and any call made while a terminal is on screen, since a tab swapped in or out under a hidden panel is not proven to leave every pty's size alone (`placePanel` resizes the window whatever its visibility). The board, the search and the Problems tab, reached from a non-terminal view, are allowed. **It never takes the keyboard and never wipes what the user typed:** `view: search` with a tab showing goes through `showSearch(focusing:)`, which bumps the focus only if the panel is already key; with no tab it only hides the board or the outline (`showSearch` resets the query); a command runs through `run(_:clearingQuery: false, focusing:)`, so `!kanban`, `!problems` and `!outline` leave the query alone. **The Outline** goes through `showOutline(focusing:)` and `Outline.appear(focusing:)`: with `focusing` false (the panel is not key, or Varnick is not the active app) no caret is placed, neither now nor when the file arrives (`focusesOnLoad`), and `restoreCaret` while it is still loading turns the placing back on, so a panel the user opens next gets its caret. Do not add a `focusToken` bump to a `show` path. `listen` is refused whatever the arguments (it turns on the microphone); `problems` follows `LauncherCommand.available`, as `!problems` does. A pane id must be a pane in a tab, or a card's id for a tab open here (`showTab`, with the card's most urgent session focused): a card with no tab open is refused (opening it reopens a tab or attaches sessions, which is not `show`'s).
- **Resources is not a Panel access view.** It has no read tool and no entry in `PanelViews.all`; `panel` says `Showing: Resources` (`panelText`), `PanelViews.onScreen` returns `NoKeys` so `keys` is refused while it shows, and `show` reaches it only as the command `resources` (`LauncherCommand`, the same list the tool's description is built from) and hides it for `view: search`. - **The key stamp.** The panel's key monitor (`main.swift`) calls `PanelAccess.noteKey(event)` first, which only keeps the time, and not for a key `keys` posted (below). `show` is refused within `typingQuiet` (2 s) of it, and while Settings, the Restart Varnick card or the split picker shows. The stamp must not change what the monitor returns for any key: it is one line before the monitor's own logic, and a refusal or early return above it would drop the stamp for those keys. Only keys with the panel as their window are seen; typing in another app is not the user typing in the panel.
- `keys` (`PanelKeys.swift`; `PanelAccess.keys`, `PanelKey`, `PanelKeyView`, `PanelViews.onScreen`; ADR 0031, option 02) presses keys **through the panel's own path, never to a view directly**: each event is made for the panel's window (`NSEvent.keyEvent`) and given to `NSApp.sendEvent`, which runs the key monitor first, then the view's `key` handler or the first responder. A key sent straight to a view, or to `Outline.key`, would test a path the user's keys don't take, and the Outline's bugs were in that path. No `CGEvent` is made and nothing is posted to the system, so no permission is involved and no other app can get a key; do not change that to `CGEvent.post` (it would reach whichever app is in front). `sendEvent` rather than `postEvent`, so the gate and the event are one synchronous turn with nothing awaited between (a probe showed local monitors see both, and that `postEvent` hands on a copy with the timestamp requantized by about 5e-10 s). Per event: the key-down and key-up for one character or combo, a wait of `characterPace` or `comboPace` (the run loop runs meanwhile), at most `ScreenKeys.maxCharacters` characters and `maxKeys` combos, each refused whole, and `ScreenAccess`'s queue (`acquire`) so a screen `type` and `keys` never interleave; the call must fit in `ScreenAccess.typingDeadline` (the relay gives up at 15 s). A character carries itself and no modifiers; a combo's characters are worked out in `PanelKey.characters(of:)`; both carry the key code of the current layout (`ScreenKeys.parse`), because the board and the Outline read key codes: **a character of `text` is a key too**, so typing "d" on the board is its D (`BoardPanelView.refusal` sees the key code, not whether it came from `text`).
- **The gate** (`PanelAccess.send`, on the main actor, before every event): the switch and the pane (`mayAct`), the panel visible and key with Varnick the active app (a pinned panel behind another app is key in its own window only, and a key sent there would change the Outline under the app the user is in; `keys` never brings the panel up, as `show` never does), no key of the user's within 2 s (`userTypedRecently`) and none waiting in the queue (`NSApp.nextEvent(…, dequeue: false)` for the panel, not stamped), an input method not composing at the start of the call, then `PanelKeys.neverSent` and the view on screen (`PanelViews.onScreen`, in `LauncherView`'s order with the overlays first). The first failure stops the call and the reply says how far it got ("Stopped after sending 3 of 5 characters and 0 of 2 keys: why", else "Nothing was sent: why"). **Posted keys must not count as the user's:** `noteKey` ignores a keyDown whose timestamp is within `PanelKeys.stampTolerance` of one in `postedStamps` (kept a minute, each at least a millisecond after the last). The stamp, not object identity, because `NSApp.postEvent` hands on a copy: the Outline's queue (`landed`) sends a queued key again that way and it must not stamp the user as typing.

**Signing** (`Makefile`, `scripts/signing-identity.sh`, `Varnick.entitlements`; `runs-only-from-a-checkout`, option 01)
- `make build` signs Varnick and zmx with one identity chosen once per build by `scripts/signing-identity.sh`: `SIGN_IDENTITY` (the git-ignored `Makefile.local`, or the environment), else the only "Developer ID Application" identity in the keychain, else ad hoc. Once it has chosen an identity, a failure to sign or verify fails the build; it never falls back to ad hoc, which would change the app's identity behind the user's back and void every privacy grant. A named identity absent from the keychain fails too, and two matches fail rather than guess; `SIGN_IDENTITY=-` is how to sign ad hoc on purpose. Two more guards keep an identity that went away (expired, revoked, its intermediate gone, which `find-identity -v` hides) from becoming an ad-hoc build: the script also lists identities without `-v` and fails if a Developer ID Application one is there, and the Makefile refuses to sign ad hoc in a checkout with a `zmx.signer.<hash>` stamp unless `SIGN_IDENTITY` is `-`. A `security` that can't be read fails the build too.
- Nothing tracked names the identity: no team ID, certificate name or hash in a file, doc, comment or commit message. The script shows the name only when stderr is a terminal, and the build log of an upgrade carries only the first 8 characters of the hash: the recipe lines that would echo the full one (`codesign -s <sha1>`) start with `@`; the stamp is `zmx.signer.<first 8 characters>`, never the whole hash, because make prints a failed target's name in its "*** [target] Error" line (a stamp named by the full hash is renamed on the next build, so it forces no re-sign). Keep that on any new line that handles the identity. The script's failures start with `error:`, so the upgrade card shows the reason (`BuildLog.firstError`).
- A signed Varnick has the hardened runtime and the entitlements in `Varnick.entitlements`, with no secure timestamp (only notarization needs it). An entitlement goes in only for a failure seen, with a comment saying which; a signature with the runtime refuses what the entitlement list doesn't name (the microphone first). Ad hoc builds have neither the runtime nor the entitlements, as before.
- zmx is signed in `.build/zmx-fetch`, and moved into place by rename: a running zmx daemon keeps its file, and signing in place would change pages under it. `.build/release/zmx.signer.<8-character hash prefix or adhoc>` records which signature the zmx in place carries, so a new identity re-signs a copy and renames it without fetching again. Same release, same protocol: running sessions survive (unlike a pin bump, ADR 0004). A Mac that never signed zmx and still has no identity leaves it as fetched.
- `bun` (the text helper's runtime, ADR 0029) is signed the same way, in `.build/bun-fetch` and moved in by rename, recorded by `.build/release/bun.signer.<…>`, with its own identifier (`com.zabaca.varnick.bun`), the hardened runtime and `Bun.entitlements`: `com.apple.security.cs.allow-jit` and nothing else. Without it JavaScriptCore loses its JIT and `SharedArrayBuffer`, and the Agent SDK fails at import ("SharedArrayBuffer is not defined"); Bun's own four other entitlements (unsigned executable memory, no executable page protection, dyld environment variables, no library validation) are not needed, so don't add them. Without an identity it keeps the signature it was fetched with. `make app` puts it in `Contents/Helpers` and signs it with the secure timestamp before the bundle, inside out and never `--deep`; `agent.js` and `mods/reminders` are resources the bundle's signature covers, and nothing writes beside them at run time, so the bundle still verifies after calls. Native `.node` addons or `bun:ffi` with dylibs that aren't Apple's would need `disable-library-validation` (untested).
- **Varnick is started by launchd, so it is its own responsible process** (`scripts/restart.sh`, `scripts/varnick-plist.sh`, `scripts/varnick.plist.in`; ADR 0022). macOS gives a process the TCC grants of its *responsible process* (and shows that process's name in its prompts), which it takes from whatever started it. Measured on the user's machine on 2026-10-10 (figures kept in `.scratch/panes-share-launchys-permissions/`): `scripts/restart.sh` run from a terminal app started a Varnick that used the terminal's grants instead of its own, so Varnick's own Accessibility row did nothing and the prompt named the terminal; every pane process, and every restart Varnick did of itself, kept the chain rooted there. `launchctl kickstart` of the LaunchAgent fixed it, since launchd is then the parent.
  - **Every start goes through launchd.** `scripts/restart.sh` (`make run`, the status menu's Restart, a peer's Restart and Upgrade, which `BuildUpgrade` runs through it) stops this checkout's Varnick, then: if the loaded job `com.zabaca.varnick` (the LaunchAgent of `make install`) runs this checkout's binary (`launchctl print`'s `program`), `launchctl kickstart` of it; otherwise it kickstarts, or bootstraps from a plist in a temporary folder (`scripts/varnick-plist.sh`, the template `make install` uses, removed once loaded), a transient job named `com.zabaca.varnick.run.<checksum of the checkout, the database path and VARNICK_LOG_RESIZE>`; only when launchd refuses both does it start Varnick directly, saying so in `~/Library/Logs/Varnick.log`. Each failing step of the transient job writes its own `restart:` line there first. `make install` (bootstrap of the LaunchAgent), the login start and the app's `open -n` (LaunchServices) already start it from launchd. The peers' relay (`LaunchSnapshot`'s binary, started by ssh) and `HeadlessUpgrade` (a Linux host's systemd) don't start the app. A new way to start Varnick must not exec it from a script or a `Process` of its own: that is the bug.
  - **No `kickstart -k`, so no second Varnick.** The script stops every Varnick that matches the checkout's binary and waits for them (up to 10 s) before it starts one, and `launchctl kickstart` without `-k` does nothing to a running job. A start counts only when a process appears that wasn't there before. The kickstart is repeated, whatever it answered, for up to 15 s, because the job may still count as running for a moment after its Varnick was stopped; it gives up early only when `launchctl print` no longer finds the job, and stops for good, with a log line and no other start, once launchd's `runs` count has gone up and no Varnick is there (a build that dies at launch isn't launched again by another route). A Varnick of another checkout still running is the account lock's to refuse, as before.
  - **A loaded transient job is kickstarted, never removed and loaded again,** because the Varnick it started may be what ran the script. Measured on a throwaway label (2026-10-10): `launchctl bootout` of a job ended only the job's own process; a descendant that had called `setsid` survived, with the job stopped or running, and a job bootstrapped from a plist that was then deleted still kickstarted. A job whose kickstart starts nothing is removed and loaded again as a last resort.
  - **The environment is launchd's, not the terminal's.** The plist sets the working folder and the log, and nothing else but two things the script copies from its caller: the database path it was given and `VARNICK_LOG_RESIZE` (`VARNICK_LOG_RESIZE=1 make run`, below). The LaunchAgent can carry neither, so a restart that passes a database other than `~/Library/Application Support/Varnick/varnick.sqlite`, or has `VARNICK_LOG_RESIZE` set, goes through the transient job, whose plist holds them and whose label names them; one that passes the default (the menu's Restart does when that is the one open) or none kickstarts the LaunchAgent. A Varnick started by `make run` from a terminal used to inherit the terminal's whole environment. The restart is still detached under `setsid` (`make run`, `BuildUpgrade.spawnRestart`), so stopping the job's Varnick leaves the script running. Another variable set for one run is not carried, and `launchctl setenv` stays banned.
  - **Checking it** (by hand, after a restart from a terminal app): Accessibility and Screen Recording read as Varnick's own, the prompt names Varnick, and `launchctl print gui/$(id -u)/com.zabaca.varnick` (or the `.run.` label) shows Varnick running with launchd as its parent. Never run `scripts/restart.sh` from an agent session: it restarts Varnick.
  - **Resources relies on it.** The WebKit rows find Varnick's shared WebKit processes (GPU, network, and any page no pane names) as the ones macOS holds Varnick responsible for (`WebKitProcess.responsible`); a Varnick started from a terminal would leave the terminal responsible for its WebKit processes (inferred), and those rows would be missing from the total. A page a pane's web view names (`WebKitProcess.pageProcess`) is counted whoever is responsible.
- A failed build puts the last good Varnick back. `make build` clones the binary to `Varnick.good` first when the build stamp is no older than it (a good build), and `mv`s the clone back on any failed step; a success removes it. A build interrupted (^C, a kill) leaves the clone, and the next build moves it back over Varnick before it takes a new one. Without it the failed build would leave the relinked binary, signed only by the linker, which macOS knows as a different app (its grants are gone). A checkout with no good build before has nothing to put back: don't start what such a failure leaves. The test is `! Varnick -nt stamp`, not `stamp -nt Varnick`, since the shell compares whole seconds and the stamp is written within one of the signature.
- The build runs unattended in a zmx session (`UpgradeRunner`): the identity's key must be usable by `codesign` without a prompt, or the build waits on a dialog nobody sees.
- `make app` (option 02) is the maintainer's, and the only place the secure timestamp is asked for (`--timestamp` calls Apple's timestamp service on every signing, which `make build` must not do on every upgrade). `app-bundle` builds and signs; `app` goes on to notarize, staple, assess and zip, then `app-image` makes the disk image (below). The identity comes from `scripts/signing-identity.sh --developer-id`, which fails for ad hoc and for any identity that isn't a "Developer ID Application" one (a development certificate would sign, then fail notarization): an app is never ad hoc. Unlike `make build`, it refuses a checkout with tracked changes, and a branch other than main or a HEAD not in origin/main as last fetched, unless `CHECK_BUILD=1`, which runs every step but the zip and the image's notarization (so a check never leaves a `Varnick.zip` or `Varnick.dmg` that looks publishable). It also refuses without `uvx` on the PATH, before the build.
- The bundle holds the catalog in `Contents/Resources/apps`, copied by `scripts/copy-catalog.sh` (tracked files only, so the bundle carries committed files and nothing an untracked file in the working tree adds; no `node_modules`, which in Scratch's hold unsigned native binaries that notarization would reject; no `.DS_Store`); the signature seals the copied files. `app-guard` runs `make check-apps` first.
- A bundle is signed inside out, never with `--deep`: `Contents/MacOS/zmx` first, then the bundle (the runtime, the timestamp, `Varnick.entitlements`, `-i com.zabaca.varnick`). `--deep` applies the bundle's flags and entitlements to every nested binary, and zmx left unsigned or signed without the timestamp or the runtime fails notarization. `--deep` is used only in `codesign --verify`.
- The notary credential is either a profile name (`NOTARY_PROFILE`) or an API key file with its ID and issuer (`NOTARY_KEY`, `NOTARY_KEY_ID`, `NOTARY_ISSUER`), from the git-ignored `Makefile.local` or the command line; a complete key wins, and `app-guard` refuses an incomplete key or a `NOTARY_KEY` that is not a readable file. `NOTARY_AUTH` turns it into the `notarytool` arguments for every `submit` and `log`, and the values stay in the environment (`$NOTARY_KEY` in the recipe), so a recipe line that uses it starts with `@` and make never prints them. Like the identity, none of it enters a tracked file; the credentials in a profile, the team ID, the key ID and the issuer never appear anywhere. The key form exists because the keychain profile cannot be read while the screen is locked. A notarization that isn't Accepted prints `notarytool log` and fails the target. The recipe lines that name the identity start with `@`.
- The disk image (`app-image`, ADR 0026; `scripts/dmg-settings.json`, `scripts/make-dmg-background.swift`):
  - **Made from the one stapled app,** after the zip, and only from `app` (`FROM_APP=1`, internal) or after `app-guard`'s checks: `app-image` refuses to publish unless `xcrun stapler validate` passes on `.build/app/Varnick.app`, so it never notarizes whatever that folder holds. It never rebuilds the app: a check of the layout needs no notarization (`make app-bundle app-image CHECK_BUILD=1`, with a notary credential that is never used). A published image is built as `Varnick-building.dmg` and moved to `Varnick.dmg` only after notarize, staple, validate and `spctl` pass; a failed run leaves no `Varnick.dmg`.
  - **dmgbuild writes the window's layout itself,** with no Finder window, so it works with the screen locked. It is run by `uvx` with dmgbuild, `ds_store` and `mac_alias` pinned to exact versions in the `Makefile` (`DMGBUILD`); a new pin is checked by building the image and reading the layout back (`ds_store`: the window's bounds, the two icon positions, the icon size). The settings file is JSON in appdmg's format, read from the checkout root, so its paths point into `.build/app/`.
  - **No `hide_extension` on the app.** dmgbuild hides the extension with `SetFile -a E`, which writes Finder information onto the bundle, and `codesign --verify --strict` then fails ("resource fork, Finder information, or similar detritus not allowed"): so would Varnick's own strict check of the copy it moves off the image. A label that reads "Varnick.app" is the price. The option asked for the extension hidden; this is why it isn't.
  - **The background is drawn at build time** from `FoldMark.swift` at 640x400 pixels (72 dpi) and 1280x800 (144 dpi): `tiffutil -cathidpicheck` refuses two pictures whose resolutions don't differ exactly so, which `rep.size` in points sets. It stays in the image as `.background.tiff`. The icon positions in the settings file and the arrow in the script are the same numbers, kept together by hand. Finder's window bounds may include the title bar, so the content can be about 28 points shorter than the picture (inferred, hand test): nothing sits near the bottom.
  - **Signed with the Developer ID and the secure timestamp, no hardened runtime.** Then notarized, stapled, and assessed with `spctl -t open --context context:primary-signature`, which must say `source=Notarized Developer ID`. `CHECK_BUILD=1` writes `Varnick-check.dmg` (signed, `codesign --verify` and `hdiutil verify` run) and stops before the notary service: the first notarization of an image is the first real `make app`.
  - **Checking an image:** `hdiutil attach -nobrowse -readonly -mountpoint <a folder of your own> <image>`, then detach. Never open it in Finder or with `open`.

**One Varnick per account** (`AccountLock.swift`, `StopStart.swift`, the entry point; `runs-only-from-a-checkout`, option 02)
- The app's start makes the support folder 0700 (`DatabaseLocation.makePrivateFolder`, also what the database's folder uses, since the lock is its first writer) and takes an exclusive `flock` on `varnick.lock` in it, holding it to exit; the file then holds the process id and the executable's resolved path. Two copies used to be possible, and still are across the old name: `launchctl kickstart` beside a `make run` build started a second Varnick, driving the same zmx sessions and hotkeys. A copy waits up to 15 s (a restart overlaps the old copy's exit; `scripts/restart.sh` waits 10 s), then stops with `error: Varnick is already running from <path> (process <pid>)`.
- The lock is taken on the app's start right after `AppStartMigration.run`, before `AppDelegate()` (the order is in "The installed app"). The migration makes the support folder by moving Launchy's, so a lock taken earlier creates `…/Varnick` first and makes that step skip. Once the rename's Cleanup removes the migration, the lock becomes the first step. The relay, the MCP server and the command-line modes exit before that point and must never take it or wait on it: they run beside the app.
- The descriptor is opened `O_CLOEXEC` and never closed, so the kernel releases the lock at any exit, a crash included. Without close-on-exec, a shell, zmx, claude or Bun that Varnick starts inherits it and holds the lock after Varnick quits (as they held the peer socket before 938e1e6). Don't reopen, `dup` or pass it on.
- It is only between copies that take it: a Launchy (the old name) takes no lock, so the lock doesn't stop Varnick starting beside a running Launchy. The rename's guards do that.
- `stopStart` is the one way for the app's start to stop with a message: an `error:` line on stderr, then an alert (nobody reads stderr from Finder or a LaunchAgent), then exit 1 (the move offer's Quit is the one exception: it already showed an alert, so it writes the line and exits). A command-line mode's refusal (`MacNotMoved`) keeps stderr only, since a terminal reads it.
- Checking the lock: `AccountLock` is Foundation only (with `DatabaseLocation.swift`) and takes the folder as a parameter, so a harness compiles them with `swiftc` against a temporary folder; never run the app to test it.

**The installed app** (`InstalledApp.swift`, the entry point, `BuildUpgrade.swift`, `Settings.swift` › `OpenAtLoginRow`; `runs-only-from-a-checkout`, option 02; "the app" is `ResourceFolder.current.inBundle`)
- The app's start runs in this order, after every command-line mode, the relay and the MCP server have exited: the log, the move offer, the rename's migration, the lock. The log comes first so every line below, a refusal included, lands in `~/Library/Logs/Varnick.log`; the offer (below) takes a copy macOS translocated (`/AppTranslocation/` in the executable's path), or one running off a disk image, before the peer link or the Phone page can point at a path that is gone at the next launch; the migration and the lock keep the order in "One Varnick per account". The log lives outside the support folder, so opening it doesn't create `…/Varnick` ahead of the migration.
- **Move to Applications** (`MoveToApplications.swift`, the alert `offerMoveToApplications` beside `stopStart`; `downloaded-app-moved-by-hand`, option 01, ADR 0026):
  - **Where it sits, and what it may touch.** It runs where the translocation refusal ran, so before the migration, the lock, the peer link and the Phone page. It reads no settings, no support folder and no database, creates nothing (the support folder included), and saves nothing: the only thing it reads from the support folder is whether `varnick.lock` is held (`AccountLock.probe`: one non-blocking `flock`, released at once, `O_RDONLY`, no create, no write).
  - **The image test** runs only for a bundle under `/Volumes`: `hdiutil info -plist` lists the attached images, and the bundle's volume must be one of them, so an external disk or a network volume runs as before. Anywhere else (Downloads moved by Finder, the Desktop, `~/Applications`) the app runs untouched. A copy that is translocated is offered whatever else is true; its original comes from `SecTranslocateCreateOriginalPathForURL`, which Security exports but no public header declares, looked up with `dlsym` at run time, so a macOS that drops it falls back to today's message with a reason. The image's device is the whole disk when `hdiutil info` names one, else the volume's own.
  - **The checks, in order,** each a stop with today's message and a reason, except the second: a running copy with no team (ad hoc) can't move, so it stops before any file step; Applications writable (`isWritableFile`: a standard account is told Finder will ask for an administrator, and no prompt of ours appears); no Varnick running in this account (the offer shows again naming its path; a checkout's Varnick counts, since the lock would refuse the moved copy anyway; checked again right before the Trash step); nothing else at `/Applications/Varnick.app`, tested with `lstat` so a link there, even a dangling one, is refused and never trashed, and another bundle id is named; and an original that already is the target (the steps run from the quarantine on).
  - **The steps.** The new copy lands under a hidden, unique name (`/Applications/.Varnick-moving-<UUID>.app`; a leftover hidden copy is never deleted, only what this run made): a rename when the original is on Applications' volume (nothing left behind), else `ditto` (the original stays), and a rename that fails falls back to the copy. It is verified and its quarantine cleared **before** the old copy goes to the Trash (the option has the check after, which would trash a good old copy behind a bad new one); a failure there puts the original back by rename, with the quarantine values it had, or removes the copy. Then `trashItem` takes the old copy and a rename puts the new one in place. If that last rename fails, the old copy is put back from `trashItem`'s resulting URL and the new one is undone; only when the old one can't come back does the message say it is in the Trash.
  - **Quarantine.** `com.apple.quarantine` is read, then removed (`removexattr`, no-follow), from the bundle and every item in it, only after `SecStaticCodeCheckValidityWithErrors` (all architectures, strict, nested code) passes with the running copy's own designated requirement as the requirement, so a copy signed by anyone else fails; the running copy's team must exist (else the stop above). No team ID is written anywhere. Every value removed is kept so a failed rename-move writes it back to the original, and a failed check removes nothing. Strict validation is why the app on the image carries no Finder information (see the image's notes under Signing).
  - **Opening and ejecting.** The moved copy is opened with `open -n`, as Restart does, and this process ends with `_exit(0)`. The old copy took no lock and made no migration, peer link or Phone page, so the new one has nothing to wait for. Ejecting from an image is a detached helper (`perl` `setsid`, as `spawnRestart` does) that waits for this pid, then runs `hdiutil detach <device>` up to five times, never forced; it is started only after `open` succeeded.
  - **Checking it:** `MoveToApplications` is Foundation and Security only and takes every place as a parameter (`Places`: Applications, the support folder, the Trash as a closure, the same-volume test as a closure; the attached images, the volumes root and the translocation lookup too), so a harness compiles it with `InstalledApp.swift`, `AccountLock.swift` and `DatabaseLocation.swift` alone, against a signed `Varnick.app` from `make app-bundle` copied into temporary folders (`cp -c`) and a quarantine written with `xattr -w`. A temporary image is attached `-nobrowse` at a temporary mount point and detached by its whole-disk device; a test must give `image(containing:)` a path that exists (a missing path resolves differently from the mount point's). Never run the app, and never touch the real Applications, Trash, Downloads or support folder. Not coverable without a translocated app: the real lookup, the alert, the helper after the app's exit from an image, and what macOS does after the move (quarantine really keeping the copy from being translocated, the Downloads prompt).
- Standard output and error are redirected only there (`InstalledApp.redirectOutput`, skipped when standard error is a terminal, a log that can't be opened leaving both alone). The relay is the same executable and prints its reply to standard output, as do the MCP server and the command-line modes: a redirect anywhere above the app's start would send those replies into the log and break every peer. A new mode goes above that point and writes to the real stdout.
- Restart in the app (the status menu's item and Settings' offer after a Screen Recording grant) runs `/usr/bin/open -n <the bundle>` and ends the process with `_exit(0)`, like the checkout's restart ends it with a SIGTERM: `applicationWillTerminate` doesn't run, so `restartImpact`'s claim that an app pane's server survives holds. It relies on the lock: the new copy waits up to 15 s for this one to release it. The checkout's path (`scripts/restart.sh`, with its refusals) is unchanged; a peer's Restart of an installed Mac stays refused with the installed-app text.
- The refusal texts for "no checkout" are written once (`NoCheckout`): in the app "Installed app: update it by downloading the newest build", and for a headless host's upgrade and comparison "Upgrade it from a Mac that runs Varnick from a checkout"; outside the app and outside a checkout the old text stays. The report shapes carry them as refusals and are unchanged.
- Open at login (`SMAppService.mainApp`) is shown only in the app, reads the status each time Settings shows (and each second), registers only when the user turns it on, and saves nothing. Don't register it from anywhere else, and never in a check: it adds a Login Items entry for the account.
- The skill link (`InstalledApp.linkSkill`) is made after the delegate exists, from the resource folder's `skills/custom-apps`: when nothing is at `~/.claude/skills/custom-apps` (a dangling link counts) or the link points into a `<name>.app/Contents/Resources/skills/custom-apps` (relinked through a rename, so the path is never missing). A user's folder or a link into a checkout is left alone.
- Grant shows Varnick in Finder (`PermissionGrant.revealIfMissing`) because macOS answers the requests silently after the first time and a Varnick whose row was removed never returns by asking: the bundle in the app, not the executable inside it. Screen Recording does it whenever the grant is still missing after its request; Accessibility only from the second press in a process, since the first press's prompt returns at once and has just added Varnick's row switched off, so Finder would come forward over the prompt with a hint that is wrong (the user only has to switch it on). The first press of the launch is the only one that can prompt (measured 2026-10-10).
- Checking: `InstalledApp` is Foundation only and takes its paths as parameters, so a harness compiles it alone with `swiftc` against temporary folders. Never run the app to check any of this, and never touch the real `~/.claude/skills`.

**Catalog apps** (`AppCatalog.swift`, `AppsView.swift`, `apps/`, `scripts/check-apps.sh`; `custom-apps-must-be-written-first`, option 01, ADR 0027)
- **The switch is the marker.** An app is on when `~/.varnick/custom-apps/<name>/` is a real folder (not a link) holding `.varnick-catalog` whose name is the folder's own. There is no UserDefaults key and no saved field. Anything else with that name is the user's: never written into, never trashed, never refreshed. A marker naming another app, or a link, counts as the user's.
- **A restored app pane finds its app by folder name,** so an installed copy must never be missing or half written under a pane that runs it. Copies are made under a hidden name (`.<name>.installing-<uuid>`, which the loader skips) and renamed into place last, with `RENAME_EXCL` so a folder that appeared meanwhile is refused. Off and refresh wait while any pane's `record.app` has that name (`LauncherModel.openAppFolders`, restored panes not yet shown included, a project's app of the same name too). Refresh trashes the old copy and renames the new one in, so the path is missing between the two; that is why it never runs under a pane, and why `CustomApp.available` (the picker, `find`, restore) calls `AppCatalog.waitUntilIdle()` first, which waits on the lock the three operations hold. Any other reader of the user's apps folder needs the same call.
- **Varnick never deletes an app folder:** off and refresh move it to the Trash (`trashItem`, a closure in `Places`). The one removal is a leftover hidden staging folder of the same app, which is an unfinished copy and never an app. The skill link is removed only when it is a link to this app's installed `skill` folder, and a skill path taken by anything else leaves the app on and the row saying so.
- **The digest and the copy leave out `node_modules` and `.DS_Store` at any depth,** as the Makefile's `rsync` does, and the marker at the root. A refresh carries the old `node_modules` across only when `bun.lock` and `package.json` are byte for byte the same; otherwise the next pick installs again. Nothing is fetched by turning on or refreshing.
- **The first pick of an installed catalog app installs frozen to its lockfile.** `ClaudeSession.startApp` decides in Swift (`AppCatalog.isInstalledCopy`: a user app, a real folder, whose marker names that very folder) and passes `frozen` or `plain` to `appScript`, which runs `bun install --frozen-lockfile` or plain `bun install`. A copy the user renamed (`my-scratch`) keeps a marker naming `scratch`, so it installs plainly and the user can add a dependency; a project's app never counts. A lockfile out of step with `package.json` fails in the pane, which is review's job to prevent. The argument is never empty, in case zmx's argument passing drops an empty one (not checked).
- **The catalog is read from the resource folder** (`ResourceFolder.current.folder/apps`), so a checkout build reads its last `make build`'s copy. An app dropped from the catalog stays installed and listed until the user turns it off.
- **Launch refresh** runs from `applicationDidFinishLaunching` after `cleanUpAfterLastRun` (tabs restored), on a detached task, with the running names taken on the main actor first, and not at all when `savedStateFailed` (sessions.json didn't decode): the panes that own last run's app servers, still alive in zmx, are unknown then, as the zmx sweep also assumes. `AppCatalog` takes a lock around on, off and refresh. A refresh's failure is kept per app in memory, and the row shows it while the update is pending; nothing is saved. Settings reads the rows and runs the switches on a detached task (`AppsSettingsView`), never on the main thread, with the switch disabled meanwhile.
- **Nothing on the installed app's early path touches the catalog.** The launch refresh and the section are the only callers.
- **Checking:** `AppCatalog` is Foundation and CryptoKit only and takes every place as a parameter (`Places`: the catalog, the user's apps, the skills, the Trash as a closure, the running names), so a harness compiles it alone with `swiftc` against temporary folders, with the Trash moving into a temporary folder. Never the real `~/.varnick`, `~/.claude/skills` or Trash. `make check-apps APPS=<folder>` checks a temporary copy of the catalog (the manifest is checked as strict JSON by JavaScriptCore through `osascript`, which every Mac has, since plutil takes any plist) (a tracked `node_modules` needs the copy to be a repository).

**The outline** (`Outline.swift`, `OutlineTree.swift`, `OutlineClipboard.swift`, `OutlineFile.swift`, `OutlineView.swift`, `OutlineCheck.swift`; `no-outline-in-varnick`, option 01, ADR 0030)
- **Its file** follows ADR 0030 (never written over when unreadable or newer, a new field raises the version, saved on change, on close and at Quit, a bullet's text never logged). `outline.json` never goes in `sessions.json`. `OutlineFile` is the one reader and writer, and nothing reaches `OutlineSaver` while `Outline.load` is anything but `ready`. `saveForQuit` waits on the writes' serial queue, so an older copy never lands over a newer one; a restart is a signal and runs nothing.
- **The tree's rules live in `OutlineTree` only,** a value that takes no clock, file or view (dates and ids come in). A row is a path of placement ids, never a bullet id: a mirror's nested bullets show once per placement, and the caret, the zoom and the filter name paths. Anything the tree can't reach from its top bullet is dropped when it is saved.
- **No bullet inside itself** is held by `OutlineTree` alone, checked on indent and `.placeMirror` (`contains`), and a refusal beeps and says so in the header. A mirror is the only way to meet it, so every edit that places a bullet somewhere new must ask the tree, never the view.
- **Undo is the outline's stack alone** (`Outline.undoOrRedo`; the numbers are in the option's Undo section). `OutlineTextView` keeps `allowsUndo` off: a text view with its own undo would undo typing out of order with structure, and the Edit menu's Undo must never reach it, so `key` takes ⌘Z and ⌘⇧Z even with nothing to undo. Every edit goes through `Outline.apply`, which records it; one that bypasses it is not undoable and clears nothing.
- **Zoom** is `OutlineTree.zoom`, a row path saved with the file; a row's path always starts at the top bullet, zoomed or not, so the caret, the undo stack and a row's view keep their identity when the zoom moves. `effectiveZoom` is Home whenever the path leads nowhere (read, edit, undo). The title is the zoomed bullet's own row (its text view has the zoom path), which the tree refuses to move, join, delete or place beside (`restructuredPath`), and `Outline.key` handles it before the bullets' keys. Undo keeps the current zoom (`keepingView`) and zooms out only as far as it takes to show the caret's row (`zoomShowing`); zooming is not an edit and is not undone.
- **Notes and completed bullets.** A note's text view has its bullet's path, as the title's has the zoomed row's, so views are found by path and kind (`OutlineTextView.registryKey`, `Kind`), and the caret by `OutlineCaret.field`. An empty note is no note in the tree (`setNote` removes it, the reader repairs it), so `Outline.notePath` is what keeps an empty note's field on screen while it has the caret, and what shows a note in full; it is cleared a turn after a note view resigns, because a view being removed resigns during a SwiftUI update. Show completed hides a completed bullet with what is nested under it in `visibleRows`, so anything that finds "the row above" or "the next row" must use those rows, and `ensuringBullet` keeps a line to type in when everything at Home is hidden. Show completed, like the zoom, is a view setting: saved, not undone, so turning it off can add a bullet (the line to type in) that no undo step knows of, and `undoOrRedo` runs `ensuringBullet` itself for the same reason. A collapsed note is the full text in a container cut to two lines: the layout adds "…" only when the second line wraps, so `OutlineTextView.draw` adds it when more text follows a line that ends at a line break. A note takes the caret expanded (`becomeFirstResponder`), so a caret placed on its last line is on a line that shows.
- **Filter** (⌘F; the **Filter** entry in `CONTEXT.md` keeps it apart from search and the Relevance filter; `Outline.setFilter`, `OutlineTree.visibleRows(_:)`) is not part of the tree and is never saved. The rows are `refreshRows()`' and nothing else's: a row the filter hides is in no list that `cross`, `showing` and the caret use, so anything that sends the caret somewhere goes through `keep(_:)` (`moveCaret`, `apply`, undo, `caretEntered`), which holds every bullet the caret has been in until the filter changes. The tree's edits get the same `OutlineScope` (`applying(_:scope:)`), so "the row above", "the next row" and a move's sibling are the ones on screen, and move and indent step over siblings that are hidden. Under a filter every ancestor shows open, so collapsing does nothing and has no triangle. The field is the one text field in the outline, so "the caret is in the filter" is "the first responder is a field editor" (`filterHasFocus`), not a flag the view keeps; while it is, `Outline.key` leaves ⌘Z and every typing key to it and takes only ↓, ↩ and esc.
- **Mirrors.** The copy ⌥⌘C makes is `Outline.mirrorToPlace`, bullet ids kept for the launch and never on the pasteboard. By ⌥⌘V one may be gone (left out) or may end up inside itself (all refused), and the tree decides both.
- **Copying and pasting bullets.** `OutlineClipboard` (Foundation only) is the one reader and writer of both forms, indented text and Varnick's own copy (`OutlineDraft`s, JSON with `version: 1`, no ids); the pasteboard is touched in `Outline` only (`copy`, `pastedBullets`), and no log line holds clipboard text. A copy is written as both types at once, so another app's copy replaces both and a stale own copy can't outlive it. The own copy is versioned: a version this build doesn't know, or data that doesn't decode, falls back to the text. A paste always makes new bullets (`OutlineEdit.insert`, which panel access's `add` and `insert` are to use too), a mirror's placement included. `Outline.key` takes ⌘V, the Paste shortcut's default, only while bullets are selected; in a bullet's text it reaches `OutlineTextView.paste` through the Edit menu, which asks the outline first (`pasteBullets(into:)`) and puts one line in at the caret only when the outline declines. The Mirrors bullet's "never on the pasteboard" stays true of ⌥⌘C.
- **Selection** (`Outline.selection`, `OutlineSelection`; `CONTEXT.md`'s **Selection**) is a run of sibling row paths, never bullet ids, so it is published and never saved. The rules for starting, extending and climbing are `OutlineTree`'s (`selecting`, `extending`, pure functions of the rows that show). It follows each edit through the run paths in the edit's result (`OutlineEditResult.applied(_:caret:run:)`) and ends when a selected path stops showing (`refreshRows`), a text view takes the caret (`caretEntered`), or the filter field takes focus; everything that ends it leaves `remembered` where esc would put the caret, and puts the caret back, since no text view has it meanwhile. The tree's run edits (`OutlineRun`: indent, outdent, move, delete, complete, place mirrors) are the single-row edits too, with the caret's row as a run of one, so a change to one changes both. A step records the selection it was taken with, and undo selects those bullets again only when all of them show. ⇧↑ and ⇧↓ start it by the end of the text selection the keys move (`OutlineTextView.movingEnd`, known only for a key's change), so a view that skips `textViewDidChangeSelection`'s call to `selectionChanged(from:)` starts it wrongly.
- **Tags** are `OutlineTags`' alone (`CONTEXT.md`'s **Tag**): change the rule there only. A text view recolours them from `didChangeText`, so one that skips that call shows stale colours, and its `mouseDown` and `acceptsFirstResponder` must both leave a click on a tag alone, or the window puts the caret there first.
- **Text views.** Each row's text is an `OutlineTextView` (TextKit 1: the caret's line and x come from its layout manager). Nothing in `updateNSView` publishes, and the outline never sets the text of the view that has the caret: `syncFromModel` does it once the caret has left (`resignFirstResponder`), and `Outline.moveCaret` moves the first responder a tick later, after scrolling to the row, retrying until the row's view exists. Keys that arrive meanwhile are queued and sent again once the caret lands (`queuedEvents`, `landed`, which counts the keys it sent again in `replaying` until `key` has seen them). **A session's `keys` (Panel access) share this queue:** its events go through the key monitor to `Outline.key` like the user's, so one that arrives while the caret moves is queued and sent again by `postEvent`, which hands on a copy; the copy keeps its stamp so it doesn't count as the user typing, and `keys` waits after each key (`Outline.keysSettled`: no pending caret, nothing queued, nothing still being sent again, at most a second, else the call stops) so the next key is not handled ahead of the queued ones and none is handled twice. Anything new that sends a key again, or holds one back, must keep that count true. A bullet is one paragraph, so its text view refuses line breaks and tabs; a note takes line breaks. **A session's edit to that bullet's text or note (Panel access) goes into that view as a key does** (`Outline.typeIntoCaretView`, `OutlineTextView.replaceAsKey`): it waits while the view has marked text (3 s, then refused), `shouldChangeText` is asked first so the delegate's rules hold (no line break in a bullet), only the changed range (`OutlineActing.smallestChange`, with both ends on character boundaries in both texts, so never inside a surrogate pair, a skin-tone emoji or a letter with its accent) is replaced in the text storage with the typing attributes, the selection is set again around it (`OutlineActing.selection`: ending at or before the range stays, which includes a caret exactly at the start of the range or at an insertion point, so a caret there stays before the new text; starting at or after its end shifts by the change in length; overlapping lands at the end of the new text), then `didChangeText` so the tags are coloured and `textChanged` applies it, as an undo step of its own (`sessionTextEdit` makes `typing` false, so it neither joins the user's typing run nor lets the next key join it, and the step keeps the user's caret). All of it runs in one main-actor turn with nothing awaited, and `setTextQuietly` is never used on the view with the caret. Any other change to the caret's bullet from outside is lost at the user's next key. **A session's `set_text` and `set_note` are refused if stale** (`OutlineKnowledge`, `PanelAccess.outlineKnown`, `Outline.performForSession`'s `fresh`): they replace the whole field, so keys the user typed after the session's read would be deleted. `outline_read` records (`OutlineReading.listed`, called for each row it lists, the title included) a hash of the full text and note per calling pane and row path, even where the read cut them; the edit is refused "Read it first" for a row never listed and "Changed since you read it: read again" when the field's text now differs, asked right after `allowed`, with nothing awaited before the edit. A session's own `set_text` or `set_note` updates what it knows of that field only. The rows an `outline_act` reply names count too (`PanelAccess.learnedOutline`, `carriedOutline`, called after the edit changed something): the new rows an `add` lists, as a read of their text and note; an indented, outdented or moved row and a mirror's new row, carrying what the session knew of the row they came from (`OutlineKnowledge.carry`), so a field it never read stays unread and one the user changed since stays changed. A new listing path in `OutlineReading` that skips `listed` makes its rows unreadable to edit; ids and knowledge are dropped together (`switchedOff`, `prune`), and the hashes are never logged.
- **`--outline-check`** is a command-line mode, so it touches only the paths it is given and exits above the app's start; a read of the support folder there would make the rename's folder step skip.

**Resources** (`ResourceReport.swift`, `ProcessTable.swift`, `WebKitProcess.swift`, `Resources.swift`, `ResourcesView.swift`; `memory-use-is-invisible`, option 01)
- **The attribution is a pure function** (`ResourceReport.build`: `ProcessEntry`s, the open tabs and a `ResourceContext` in, a report out) in a file that imports Foundation only, so it can be checked without the app. Keep it free of app state. Every Varnick process is placed once: the app, a pane (first pane wins a process two claim, as two web views sharing a page process), a helper, or the share of a tab of another machine. A new place for a process must keep that. A pane's own client pid counts only while that process is still Varnick's child, since SwiftTerm never clears it and the system reuses pids.
- **A process is Varnick's by ancestry or by what it is, never by its name.** Varnick and its descendants; each zmx process whose session starts `varnick-` and its descendants (the daemon's parent is launchd, so ancestry from Varnick would miss it); `varnick-peer --peer` relays and the ssh mux masters under `SSHRunner.controlDirectory`, with their descendants; and the WebKit processes macOS holds Varnick responsible for. The binary runs as `varnick-peer` for its relay and every pane's MCP tool (`PeerLink.name`), and the file it runs from can be gone (an older launch's snapshot), so it is known by `path ?? argv[0]` (`ProcessEntry.executableName`). Claude Code is known by its folder (`/claude/versions/`) or `claude` as its file name, because the kernel's name for it is a version number. A new kind of process Varnick starts outside its own tree needs a rule in `build`, or it falls out of the total and, if it is a Claude, into the greyed row.
- **Arguments are read for a few processes only** (`ResourceContext.wantsArguments`: zmx, ssh, Varnick's own binary, any process with no path), cut to six arguments of 300 characters, and used only to match: never shown, logged or kept past the report. ssh's are read because a background connection's title (its `argv[0]`) names the socket in Varnick's folder, which is how Varnick's links are told from the user's own. A Claude pane's zmx arguments carry its prompt after the sixth, so the cap is what keeps it out; do not raise `ProcessTable.argumentLimit` past the session name. No `ps`, `footprint` or zmx call is made: libproc and sysctl only.
- **Two private calls, both in `WebKitProcess.swift` and both failing soft:** `WKWebView._webProcessIdentifier` (asked through `responds(to:)` first, since key-value coding on a missing key throws an Objective-C exception Swift cannot catch; nil before the page's process has started, and read again at every measure, since a page that goes to another site can move to a new process) and `responsibility_get_pid_responsible_for_pid` (looked up with `dlsym`; nil if absent, and the view says so). Both were tried on 2026-10-13 in a scratch program: the first answers a real WebContent pid after a load, the second names the calling process. Without the first, pages show together as "Web pages in no pane"; without the second, WebKit's shared processes and any page no pane names leave the total.
- **Measuring** happens only while Resources shows in a visible panel (`Resources.measure` checks `isShown` and `SessionBoard.panelIsVisible`; the ticker ends itself on a hidden panel and `panelDidShow` starts it). The walk and the report run off the main actor, one at a time. MLX is touched only while one of its models is loaded (`isLoaded` on the embedder, the reranker and text generation) and only with its Metal library, since it aborts the app without; its count is in use plus cached. The graphics split is the task ledger's `ledger_tag_graphics_footprint` less MLX's figure; that MLX's buffers are inside the ledger is inferred, not checked.
- **Rows keep their order** (`RowOrder`): ranked by size when first seen, and again after a reset, which happens when Resources opens (`close` clears it) and when the set of tabs, here or on another machine, changes; hiding and showing the panel keeps it. A process that a pane's descendant double-forks away from (reparented to launchd) is not found: it is its own responsible process, so neither ancestry nor responsibility reaches it (checked 2026-10-13 with a scratch program), and it drops out of the total. A figure that changes never moves a row; a new process goes last in its pane.
- **Settings › Resources is the same table with its own model** (`LauncherModel.settingsResources`, `Resources(inSettings: true)`; `ResourcesTable` is shared, `scrolls` false because Settings' page scrolls). A shared model would let the panel's selection, open rows and order leak into Settings, and Settings would measure for a view that is not on screen. `Resources.isShown` is the one test every reading and key goes through: the panel's view is shown with Settings not over it, the tab with Settings showing it (the tab's view calls `settingsTab(shown:)` from `onAppear` and `onDisappear`, which also clears it, so switching tabs or closing Settings stops the ticker; `panelDidShow` starts it again after a hide). Its keys are `Resources.key` in the key monitor after Settings' own esc and the pane question, only while `isShown`, so ⌘W is taken even with no tab selected and never reaches the tab underneath; esc is Settings' (`key` leaves it alone there). ↩ and a pane's confirmation `activate` the tab and then close Settings (`show`, `onNeedsConfirmation`), since `activate` leaves Settings alone; a confirmation closes Settings whenever the tab is showing. ⌘⇧M in Settings still falls to `toggleResources`, which closes Settings and shows the panel's view, so two Resources views never show or measure together. The tab's table has no scroll view of its own: `SettingsView` wraps Settings' scroll view in the `ScrollViewReader` that brings the selected tab into view (a reader inside the scroll view would not scroll it). A new Settings tab that measures must be gated the same way.

**Tasks** (`Packages/TaskHarness`, `TaskPage.swift`, `TaskPane.swift`, `TaskClaude.swift`, `TaskJev.swift`, the conversation mode of `TextHelper/agent.ts`, `Subprocess.open`, `scripts/task-practice-shop.py`; ADR 0039; `tasks-cant-be-handed-to-varnick`, option 01)
- **Secret fields are the person's alone, and this comes before everything else.** Which fields are secret is ADR 0039's rule, applied in the page script (`isSecret`, which also follows a field the page swaps for another input) and again in `SecretField`. The script never sends a secret field's value, only whether it is filled; `PageField.init` drops one that arrived anyway; the runner never fills one (`fill` in the script refuses too). Everything a model or a log sees of a page goes through `PageSnapshot` and `PageField`: a new read of the page, a new state for Jev or Claude, a new step line or log line must be built from those and never from raw script output. `task-check` and `scripts/check-task-bridge.sh` assert that no typed password or card number reaches a message, a state, the trail or a step, and that a flipped or swapped password field stays secret.
- The Tasks switch (`Settings.tasksOn`, default false for every install) is read before every action (`TaskRunner.Config.enabled`, a `SwitchFlag` the switch's observer sets, since the harness runs off the main actor and `Settings` is main-actor state) and watched (`TaskController` stops a running task when it goes off). `!task`, the picker's Task tile and the stop shortcut (`ShortcutAction.stopTask`, ⌘., hidden while the switch is off) exist only while it is on. Any new way in must check it.
- A Task pane is a web pane (`SessionRecord.url` set) with `SessionRecord.task`, so every web-pane rule applies (the address bar, `load`, the retry). It is never saved: `saveSessions` and `sessionExited` go through `SavedTab.withoutTasks()`, and every list built from the saved state (paired Macs, the phone, Recent, Completed, the ended cards) relies on that. A new place that builds a tab record from `tab.saved` or `root.layout` has to prune too, or a restart will bring a dead Task pane back as a Browser pane.
- The web view's data store is `WKWebsiteDataStore.nonPersistent()`, made in `ClaudeSession.makeWebView` for the pane alone. Replacing it with the default, or sharing one between panes, puts the user's logins into a task. The script and the message handler live in the world `TaskScript.world`; a handler registered in the page's world could be called by the page.
- The person's clicks and keys pause the task through `isTrusted` events only (`pointerdown`, `keydown`, in `TaskScript.touchSource`, which runs in every frame, where the snapshot script runs in the main frame only). The harness's own `el.click()` is untrusted, so it never pauses itself; a site that ignores untrusted clicks can't be driven this way (how common is unknown).
- `Gate.asks` is the one rule for the person's Allow, for buttons and for links (`TaskRunner.gate` runs it): a search box's submit never asks; a button that submits a form does; any button, and any link, on a page that has a form does; so does a link with no real address. A search box is a form with role search, a search element or a form whose only text field is a search input (`searchForm` in the script): a search input among other fields is not one, and treating it as one would let a checkout's Place order through. A new action that presses something has to go through `gate`. A link to a page followed on a page with no form, or a script-handled button on a page with no form, is an ordinary click.
- Every action on the page (`click`, `fill`, `goBack`, `open`, the release of a held submit) goes through `TaskRunner.checkpoint` first, which is where the Tasks switch, Stop and a pause are honoured and where a pause the person caused ends the step under way (`StepAborted`: the page may have changed under it). A new action on the page must use those wrappers, not `page.` directly. A fill that did not happen leaves its field unsettled (`fillField`).
- Elements keep one id for as long as their document lives (a `WeakMap` in the script, with a per-document token), and everything keyed on a field (`settled`, `requested`, `userOnly`, `askedUser`, the bank's `field`) is keyed on it. Position-based ids would shift when a form reveals a field and put a value in the wrong one, or let the terms box leave `userOnly` and be ticked.
- A submit the page makes while a field is filled is held: the script sets a lock attribute on the document element during `fill`, a capture listener in the harness's world cancels `submit` events, and a small script in the page's own world (`TaskScript.guardSource`) makes `form.submit()` and `requestSubmit()` do nothing but mark the form. An isolated world's change to a built-in is invisible to the page, so the second script has to live in the page's world; the page can see the two attributes, which is accepted.
- Two Claude conversations per task (values, guidance), each one message at a time in the order sent (`ClaudeConversation.send` chains them), because the helper's generator also waits for the previous `result` before it takes the next message. A message with no answer in 15 s ends that conversation (the helper is asked to stop, SIGTERM after a second and SIGKILL a second later), and the next message starts a new one from scratch: `System2.ask` carries the role and the task as a `preface`, which the implementation puts before the message that starts a conversation, and the harness writes each guidance message from the full state (the page, the trail, the bank), so nothing is lost but Claude's own earlier replies. Stop and closing the pane end both. The helper dies with its input, so nothing outlives Varnick.
- Below 0.7 System 1 asks Claude and waits, however often; only Claude's own suggestion, or its "continue", lets a choice below the bar stand for one step (`exploreNext`). The budgets end a task that asks forever. Each of the two conversations is told the other's replies since its last message (`relay`), and System 1's state carries the preview scores, the bank (a value only the person gives is "(the person's)") and whether Claude is working on values.
- System 1 failure is counted in `System1Switch`: three Jev failures in a row give Jev up for the task, and `TaskJev` checks `Settings.typesafeGateKey` before each call and throws `System1Unavailable` once the filter has left TypeSafe, which gives Jev up at once. Claude makes the choices through the guidance conversation (`ClaudeSystem1`), so a Jev outage doubles that conversation's traffic. This Mac's Gemma is never System 1 here: its answer probabilities were measured not to separate right from wrong, and the 0.7 bar means nothing on them.
- The request shape of a `noul` question to Jev follows the spoken judge's (a plain `instructions` string, `true` and `false` criteria with generic wording). It is unmeasured on the live endpoint for these questions, and the 1.5 s deadline is the route's, which may be short for a call that scores 30 previews. No Jev call was made while this was built; follow-up test 2 in agent-lab measures Jev itself.
- The log: `NSLog` lines of a Task say only durations and kinds (`ClaudeConversation`). Never an address, a title, a label, a value, the task or a reply.
- **Spike findings (2026-10-15, a throwaway process with no visible window, a local server on 127.0.0.1, nothing downloaded and no daemon).**
  - *A hidden web view keeps working.* Loading, scripts, script-built DOM, `callAsyncJavaScript` round trips (0.1 to 0.2 ms) and navigation worked with the view in no window, in a window never shown, shown and then ordered out, offscreen and at alpha 0; a navigation after six minutes hidden took 13 ms. Page timers are throttled (a 100 ms interval ran about 8 times in 3 s, then 4 or 5 times in 30 s) and `requestAnimationFrame` never fires, so a page that draws only from animation frames makes no progress while the panel is hidden. The harness drives everything from outside the page and needs neither. Not tested: Varnick's own panel (`NSPanel`) rather than a plain window, and App Nap.
  - *The data store.* Two `WKWebsiteDataStore.nonPersistent()` stores kept separate cookies (each pane got its own session id on the same server), `isPersistent` was false, and the stores held records for the host in memory only. No `WKWebView` file appeared under the process's own folders in `~/Library` (checked for the cache and WebKit folders; the only file was from `URLSession` in the test driver).
  - *Reading and acting.* The isolated world sees the page's DOM and neither sees the other's variables. Setting a value through the element prototype's setter and firing `input` and `change` reached a React-style tracked input and a Vue-style model; a plain assignment did too, because the page's own tracker property is invisible from another world. `el.click()` runs the page's handler and is not trusted. A password stays redacted after the page turns it into a text box. A same-origin frame is reachable from the world, so the snapshot reads the main document only and the script is installed in the main frame only: a field in a frame is neither read nor filled, which cannot leak and cannot be driven. Not done: five real sites (no real site was visited), password AutoFill (believed absent in a `WKWebView`), and whether a page's own programmatic focus takes the panel's keyboard (needs the panel). They are in the hand check.
  - *Peeks.* A `fetch` and `DOMParser` in the world fetched 12 pages in parallel in 8 ms from the local server, with the pane's cookie and without moving the visible page. On a page whose CSP says `connect-src 'none'` the page's own `fetch` failed and the world's succeeded, so a CSP does not stop the peeks. Only the page's own origin is fetched, so "same-site" means the same origin, and a page built by scripts previews empty (`DOMParser` runs none).
  - *The conversation mode with the user's own `claude`: not measured.* In the sandbox this was built in, even a one-shot helper request answers `authentication_failed` (the login there is not one the helper's options carry), so the time to the result of a second and a tenth message against a fresh run is open. The protocol, ordering, one process for the whole conversation and the stop rules are checked against `fake-claude.py` (`TextHelper/check.sh`).
- **Checking.** `swift run --package-path Packages/TaskHarness task-check` runs the loop on an in-memory shop with recorded answers (102 checks). `scripts/check-task-bridge.sh` compiles the harness and the pane's real page bridge into a throwaway process and runs five tasks, and the page script against the pages made to trip it (a checkout with an address lookup and a revealed field, an onchange that submits, a password the page flips or swaps), against `scripts/task-practice-shop.py` in a hidden web view with scripted answers. `make build` builds the app. None of them runs Varnick, so the pane's views, the keys, the spoken lines and the pause on a real click are checked by hand after a restart (the option's "Testing Decisions").

**Automations** (`Automations.swift`, `AutomationsView.swift`, `RunsBoard.swift`, `Packages/VarnickPeer/.../AutomationCadence.swift` and `Automation.swift`, `ClaudeCommand`, `make check-slots`; ADR 0040; `prompts-cant-run-on-a-schedule`, option 01, slice 1: this Mac alone)
- **A run is a typed prompt's pane with two marks on its `SessionRecord`: `automation` (for life) and `runUnopened` (until it is opened).** Both are Optional, so an older build shows the tab as an ordinary one. `automation` is why a run's MCP config lists `notify` alone at every start, a restart and an opened run's included (`ClaudeSession.launchClaude`); `runUnopened` is the hidden-tab rule. They live on the record, not on `SavedTab`, because a record survives every place that rebuilds a saved tab (`splitByMachine`, `migrated`, `withoutTasks`, a layout's `replacing`).
- **The hidden-tab rule: `tabs` holds every tab, `shownTabs` is the list for the eye.** `ClaudeTab.isHiddenRun` is true while a pane of the tab has `runUnopened`. Everything that looks a pane or a tab up by id, saves (`saveSessions`), sweeps (`cleanUpAfterLastRun`), notifies (`SessionNotifier`, `readDormantTurns`), lists a host's tabs to other Macs and the phone (`MacPeerHost.tabs` reads the saved state) or rebuilds Recent reads `tabs`. These read `shownTabs`, and a new list of tabs for the eye must too: the tab strip (`TabStrip.refresh`), the projects column (`TabProjects`), the session list and every index into it (`peerRowsStart`, `recentRowsStart`, `sessionRowID`, `openSelected`, `PanelKeys`), the board's Sessions cards (`SessionBoard.refresh`), search's tab rows (`tabHolding`, and `SessionTabs.read`, which keeps the database from naming the tab) and the ⌘⇧[ cycle (through the strip). A list that misses one floods with runs. Not hidden on purpose: Resources (a run holds a claude and an MCP server, and the memory is the point of that view) and the host's listing (slice 1 has no run flag in `tabs`; the phone and other Macs see a run tab as an ordinary tab, which is also how the page server sees its turn).
- **A run opens when its tab is shown** (`activate` calls `runOpened`), when Automations goes off (`releaseRuns`, from the switch's watch and at launch) or the automation is deleted (`deleteAutomation`; an automation's own switch releases nothing, and its hidden runs are still ended by their limits), or when the pane shows a card because another Mac took it over (`tendRuns`). A tab that closed unopened never reaches Recent, the ended cards or Completed: `sessionExited` hands it to `runClosed` before any of that. `activate` is the only place a tab is shown from, and the `sessionExited` shortcut comes before the lists a closing tab goes into; a new way to show a tab must go through `activate`. The tab shown when the visible one closes is chosen from `shownTabs`, never `tabs`: a hidden run chosen there would be opened, and so never ended. A run's record keeps `automation` wherever it is rebuilt: `openRun` (an ended run resumed) and `applyRunFields` (a run's conversation resumed from search) both set it and the permissions, or the resumed pane would get Screen access and Panel access. A new place that builds a record for a conversation must do the same. An ended run resumed is first looked for among the open panes by its conversation (`openRun`, as `resumeSession` does), so a second claude never starts on it.
- **The slot function is one pure function of the cadence, the zone, the last slot and now** (`AutomationSlot.check`; the relay calls it unchanged in slice 2). A slot at exactly now is due; one under 12 hours old is run, an older one is missed (`catchUpWindow`, exclusive); every older slot is missed, newest first and capped at 20. A time of day a clock skips (spring forward) moves to the next valid time; a step through the day ("every 2 hours") leaves that time out; a repeated hour (fall back) runs at its first time. Cases run in the zone the automation keeps, which is the zone of the Mac that last saved it: `make check-slots` covers every preset, a zone different from the host's, both daylight-saving days, the 12-hour bound, many missed slots giving one due, and a slot exactly at the check's minute; it also covers a run's command line (the mode and the allowed tools) and the file's reading (a newer or unreadable file). The check builds `Packages/VarnickPeer` alone, so it needs no `make build`, and it must stay Foundation-only for the Linux relay.
- **A check is one synchronous pass on the main actor** (`AutomationRunner.check`): tend the runs, judge the slots, start, then write the automation once with the runs and `lastSlot`. A start that fails is a run recorded "couldn't start" and its slot is not tried again. A new automation, a changed cadence or zone, a switch turned on and Automations turned on all set `lastSlot` to now, so nothing before them is caught up. Run now does not touch `lastSlot`.
- **One run of an automation at a time.** `isRunGoing` is a run whose stored state is running or waiting and whose pane is still here, after `tendRuns` has brought the stored state up to date from the pane's turn. A run that waits on the user blocks the next slots (they are recorded skipped) until it is answered or ended after 24 hours.
- **Limits are checked only for unopened runs, and only by the once-a-minute check,** so a run can overshoot by a minute. Working past the limit counts the minutes the Mac was awake while the turn is working or background, or not known yet (`AutomationRun.worked`, added by each check: a gap between two checks over 150 s was a sleep and adds nothing, so a wake doesn't end a run for the night it slept through); waiting counts from the turn file; Done counts 10 minutes from the turn file's date. Ending a run records its state first, then `ClaudeSession.endSession` (a restored pane that never started kills its session in `conclude`, a started one is closed as ⌘W closes it), then `Zmx.endConfirmed` off the main actor. If the confirmation fails it is only logged.
- **Permissions are stored on the record.** With no override a run takes Settings › Claude's Skip permissions at its start (`record.skipPermissions`); Ask stores false; Allowed tools only stores `dontAsk` (`--permission-mode dontAsk`, never with skip) and false; Skip stores true. `allowedTools` go into `--settings`'s `permissions.allow` beside `notify`'s. `RunLaunch` keeps them on the run, so opening an ended run resumes with the same ones.
- **`dontAsk` was checked by hand on Claude Code 2.1.301 (2026-10-15, a throwaway interactive `claude` in its own zmx session, hook dumps in the problem's scratch folder).** A tool call allowed by no rule is refused with no dialog, `PermissionRequest` never fires, Claude says so and goes on, and `Stop` fires as usual. Read-only commands such as `uname` and `echo` need no rule and ran. The refused call fires no `PostToolUse`. `zmx run` made that session and left two crash reports in `~/Library/Logs/DiagnosticReports` (the doc's warning under Checking by hand), though the session worked.
- **The run list is kept honest by four rules.** A run that started and has no end date is never dropped when the list passes 20 (`AutomationRun.isKept`: the overlap rule, the limits and the hidden tab all find a run through this list); every way a run ends dates it (`endRun`, `runClosed`, and `tendRuns` for a pane that is gone, including an ordinary tab the user closed). Consecutive skipped or missed slots with the same reason are one record with a `count`. A run nobody opened keeps its notice after its process ends (`endedRun`, `SessionNotifier`), and choosing it resumes the conversation (`openRun`); the notice goes when it is chosen. Deleting an automation (Settings › Automations) releases its going runs as ordinary tabs and drops its list. Save in the editor changes only the editor's fields on the stored automation, so a run that started while the editor was open, and the last slot, are kept.
- **The file is `automations.json`** (`AutomationFile`, owner-only, atomic): not JSON, not decoding or `version` above 1 leaves `AutomationStore.problem` set, which stops every check and every save; Settings says so. A run state a newer build wrote reads as done. Nothing moves the file aside: the user fixes or deletes it.
- **The editor's Allowed tools field is free text in Claude Code's rule syntax** and is passed through as it is. A wrong rule is Claude Code's to ignore or refuse.
- **Not in slice 1:** the headless host (its file, its systemd timer, protocol 29, the Mac holding remote runs, the run flag in `tabs`, the phone's Runs) and a notice for a run ended at its limit (the pane is gone, so neither the notifier nor the page server has a turn to read).
- **By hand, after the user restarts Varnick with the switch on** (never from an agent: a run is a real Claude session on the user's plan, and `make run` and restarts are the user's): the list is the option's "By hand" section for slice 1.

- The phone's push (option 02 of `phone-page-is-only-a-browser-tab`) is checked by hand, after the user restarts Varnick on every Mac and reinstalls the headless host (one commit), with a phone that has the installed app on the tailnet. Never run these from an agent: they use the user's phone, Macs and screens. The thresholds are CONTEXT.md's **Presence**.
  - Home › Notifications › Turn on asks the permission from the tap; Send a test shows a notification naming the host.
  - Done while away: lock the Mac that controls a session, or leave it idle past the threshold, and let a turn finish. The push comes some 10 to 15 s after the turn ends, titled with the session.
  - Send a prompt from the app and go to the phone's home screen at once, leaving the app running: the push still comes after the settle (2 s for a question or an error, 10 s for a Done), whatever the app's socket does. A question raised with the app closed arrives within about 4 s, before the app can be opened and looked at for 3 s. `push decide` lines in `~/Library/Application Support/Varnick/phone/server.log` say what was decided and why.
  - Present at the Mac (typing there, the session driven from it): the Mac's own notice and no push, however long the notice stands; locking afterwards pushes it only if the Mac still holds it. Open the pane at the Mac, then lock and leave: no push.

  - Each switch (Needs me, Done, Errors) silences only its own; a pane open on the phone's terminal or live view gets no push for it; a session started from the phone, or on a headless host driven from an idle Mac, pushes after 10 s.
  - Remove the phone in Settings › Peers › Devices: the next notice doesn't come. Restart and rebuild: no subscribing again, nothing for turns already waiting, and `ps eww` on the server shows no key.

**The rename (short-lived; removed by the option's Cleanup)** (`FirstLaunchMigration.swift`, `OldLaunchy.swift`, `AppStartMigration.swift`, `MacNotMoved.swift`, the entry point, the `Makefile`, `scripts/restart.sh`, `scripts/old-launchy-folder.sh`, the installer's two halves; `name-taken-by-another-launcher`, option 01, whose phase 6 removes all of it)
- **Ours or not.** An unrelated keystroke launcher is also called Launchy (its macOS build is an executable `Launchy` with data in `~/Library/Launchy`, per its public source; apps of the same name may use `Application Support/Launchy`), so neither the folder's name nor a process's proves anything. The folder is ours when it holds `sessions.json`, `search-db-path`, `launchy-peer` (a dangling link counts) or `peer.sock` (`OldLaunchy.isOurFolder`; `scripts/old-launchy-folder.sh` is the same test in shell for the Makefile and `restart.sh`, so change both together). A running app is ours when a path it has (the file, the exec path, `argv[0]`) ends in `.build/release/Launchy`, it isn't a relay or MCP server, and it is this account's; a process whose paths can't be read counts as ours. The migration (the refusal and the folder move), `MacNotMoved`, `cutover-check` and `restart.sh` all use it and fail closed only for what passes it; any other `…/Launchy` is left alone and Varnick starts fresh beside it. A folder of ours with none of those entries is not recognised.
- Only the app's start migrates, and only at the end of the entry point, after every command-line mode has had its turn and before `AppDelegate()` is made. Nothing on that path may read `Settings.shared`, the support folder or the database first: a read that creates an empty `…/Varnick` makes the folder step skip for good. A new mode goes above that point and exits (`--outline-check` is one: it reads only the paths it is given).
- Before any step, `FirstLaunchMigration.refusal` stops the app with an `error:` line (nothing changed) while our `…/Launchy` exists and a Launchy app is running (a process named `Launchy`, other than its relay and a pane's MCP server; found by `proc_name` as well as the executable's path, since the running Launchy's file is gone at the cutover), and, when `…/Varnick` doesn't exist, unless `launchy.sqlite` is in the working folder's `db/` (or beside the path `VARNICK_DB` chose, or that path exists). Without it, a Varnick built in a worktree and started by a restart that matched the running Launchy's relative name would end every session and move the Mac's data. It also stops when both folders exist and `…/Varnick` has no sessions file, since that would start empty. Varnick.app's working folder is `/`, so it never passes the database test: the cutover is a build from the checkout Launchy ran from, not the app.
- The steps run in this order, each skipped when its target exists, each logging one line with no values: end the old zmx sessions, copy the settings domain (`heyLaunchy` becomes `heyVarnick`; it counts as already done only when the new domain has the peer id, never because it is non-empty, since any stray write would otherwise skip it for good and start Varnick with a new identity), move the support folder, rename each pane folder's `.launchy-…` files to `.varnick-…` (which the new code reads; every run, so a crash after the move loses nothing), copy the web data, copy the database. Sessions end before the folder moves so no hook writes into a moving folder; the domain and folder are in place before `Settings.storeSkipPermissionsIfAbsent`; all of it comes before `PeerLink.refresh`, so the relay never answers from an un-migrated domain. Both folders present: nothing is merged. A failed folder move stops the app before the database step, and a database that can't be copied stops it too, never an empty folder or database beside the real one.
- The database step is a copy that never replaces or touches the original, so a rollback to Launchy finds it as it was. It runs only without `VARNICK_DB` and when `varnick.sqlite` isn't in the support folder; the source is the first that exists of the file the support folder's `search-db-path` names, `db/varnick.sqlite`, `db/launchy.sqlite` under the working folder. It copies into `varnick.sqlite.partial` with `sqlite3_backup_*` (which takes in the WAL), runs `quick_check`, empties the copy's WAL, and moves it into place with `renamex_np(…, RENAME_EXCL)`; any failure removes the partial and stops the app with an `error:` naming both files. The original is not opened by SQLite when it can be avoided: the system's SQLite rewrites a quiet database's `-shm` on a read-only open, and makes a `-wal` and `-shm` beside one that has none (and can't open a WAL database read-only without them), so the files are copied aside first (`stage`) and read there, unless they change while being copied, which means a writer is at work and the original is then read through SQLite. The system's SQLite also keeps a closed database's `-wal` and `-shm`, so a copy is moved into place without its own.
- Every other mode, and any unknown `--` flag, refuses with an `error:` line while our `…/Launchy` exists and `…/Varnick` doesn't, except the relay and the MCP server. The cutover itself is an app start with no argument.
- Every `error:` line a guard prints ends by saying the cutover is the user's step, done from Terminal.app, and that an agent must stop and report: agents follow what an error says, and none of these is theirs to act on.
- Checking the steps: `FirstLaunchMigration` is Foundation only and takes every place and domain name as a parameter, so a throwaway harness compiles it alone with `swiftc`. A temporary home (`HOME`, `CFFIXED_USER_HOME`) doesn't move UserDefaults: use made-up domain names such as `test.varnick.<uuid>`, never `com.zabaca.varnick` or `com.zabaca.launchy`, delete them (and their plist in `~/Library/Preferences`) afterwards, and check that `defaults read com.zabaca.varnick` still says the domain doesn't exist. No command-line mode copies settings. Old-named sessions are made in a throwaway `ZMX_DIR` (see Checking by hand), never `/tmp/zmx-<uid>`. The database step is checked with databases made by `sqlite3` calls in a temporary folder, one whose WAL holds a write (copy the three files aside while the writing connection is open), and the source's three files must keep their bytes and modification times.
- Guards, each short-lived: `make build` fails first with an `error:` line while `.build/release/Launchy` or `Launchy.good` exists, which stops Upgrade, Upgrade all and `make run` on a Mac not yet cut over; `make stop` and `scripts/restart.sh` also stop a Launchy binary, by this checkout's absolute path only (a Launchy started by `make run` has the relative argv `.build/release/Launchy`, which matches from every checkout); `make run`, `install` and `uninstall` (`cutover-check`) and `scripts/restart.sh` refuse, before stopping anything, while the Mac still runs our Launchy and the checkout has no `db/launchy.sqlite`, since a worktree passes the build guard; in the checkout that does have it, `make clean` and `make install` (`cutover-confirm`) refuse unless `CUTOVER=1` is given, since `clean` removes the binary that holds the build guard and `install` would then install Varnick's LaunchAgent for the next login (the cutover's two steps pass it, and an agent must not); `scripts/restart.sh` also refuses when `.build/release/Varnick` isn't there (the status menu's and a peer's Restart run it with no build), appending why to `Launchy.log` while the Mac still runs Launchy, else `Varnick.log`; `make install` and `make uninstall` boot out `com.zabaca.launchy` and remove its plist; the Linux installer's far half refuses where `~/.launchy` exists, with `OLDROOT=present` that the near half reports as `error:`, and removes what the near half shipped.
- Never run `make run`, `make stop`, `make install`, `make uninstall`, the built binary, or the restart script with the real `pkill` or `pgrep` in a check: a pattern can match the running Launchy. Put stand-ins that only record their arguments first on `PATH`.

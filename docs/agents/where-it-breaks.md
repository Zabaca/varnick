# Where Varnick breaks

Failure modes that come from how Varnick is built: what a change can break even when it follows `CODING_STANDARDS.md`. `varnick-reviewer` checks every diff against this list (its Correctness axis); `varnick-planner` names the items a plan touches.

**Saved state** (`SessionStore.swift`, `Settings.swift`)
- `sessions.json` decodes as one `State`; a decode failure falls back to `State()` and silently drops every open tab and recent session. A renamed or retyped field breaks old files the same way a new non-optional one does.
- `Settings.storeSkipPermissionsIfAbsent` tells an existing install by `sessions.json` existing, so it must run first in `applicationDidFinishLaunching`, before `makeModel` (its first `SessionStore.save` creates the file) and before anything reads `Settings.shared`; the relay and the command-line modes never call it. Skip permissions is stored once because a value worked out on each read would turn on at the second launch.

**The claude command line** (`ClaudeSession.startClaude` and the headless relay's `launch` in `HeadlessLaunch.swift`; the script, shell arguments and argument list are `ClaudeCommand`, in `Packages/VarnickPeer`)
- claude runs via the account's login shell (zsh, bash or sh from the account record, else `/bin/zsh`; the relay uses the account's own shell) as `-l -i -c 'exec claude "$@"'`, with its arguments passed positionally: user text (prompt, agent name, paths) goes in as its own argument, outside the script string.
- New sessions use `--session-id <id>`, resumes `--resume <id>`. The prompt follows `--` and has a trailing space when it has no whitespace (`ClaudeCommand.arguments`, `operand`), so a prompt that starts with a dash is a prompt, and one that is a command's name (`doctor`) isn't that command.
- The environment is deliberately minimal; claude gets only what is set for it, nothing inherited from the launcher.
- Screen access's `--mcp-config <json>` is `ClaudeCommand.arguments`'s optional `mcpConfig`, first of all; it is the one argument not stored on the record (see Screen access below).
- Restart (`ClaudeSession.restart`, the Restart button, ⌘⌥R, R on a board card) starts claude again in the same pane through `launchClaude(restarting: true)`, so it reads the current hook settings and gets the first turn word, the cleared subagent work records and a cleared stop file like any start (a stop file saved within `PaneFolder.staleWindow` of the restart would otherwise show the last run's background tasks). It resumes the conversation if its transcript exists (the hook's `transcript_path` when that is this conversation's file, else the computed path) and otherwise starts it again under its own id, with the prompt only while the pane has never moved off its first conversation (`record.conversation == nil`), since after /clear or /resume the prompt isn't that conversation's. The new zmx session is labelled with `record.origin` whatever `startedFor` is, or `hostEnd` would release a taken-over peer session instead of ending it. `restarting` makes `finish` ignore the old client's exit, so nothing may call `conclude` on its own while it is set; a pane closed meanwhile is concluded when the restart reaches its end. Only a pane that runs here with its client attached restarts (`canRestart`): never a card, a session on a peer (the host would have to start it, and the relay has no restart request), a pane not started yet, or one started for a peer (`startedFor`: the label would hand the session back to that peer). A pane in zmx has its zmx session killed and confirmed gone from a listing that came back (`Zmx.endConfirmed`, every call time-limited) before anything starts; zmx missing, silent, or still listing it makes the restart stop with `restartFailure` shown in the pane, never a launch, since a bare claude beside a live session would be a second one. The old client's exit is waited for too, and a restart's quick death (`launchedAt`, not `startedAt`) says it ended right after restarting.
- The folder of `VARNICK_SESSION_FILE` (`PaneFolder`) must exist before claude starts: the hook's `cat >` fails into a missing one, and the pane silently stops following `/clear` and `/resume`. Claude panes still running in zmx from before the `scratch` folder was renamed `panes` write through a link at the old name (`PaneFolder.migrateOldScratchFolder`), so that link stays until none of them runs.
- The turn hooks (ADR 0010, `ClaudeCommand.hookSettings`) are in the same `--settings` as the SessionStart hook, so a value claude rejects would cost the session file too. Each must print nothing and exit 0 (`UserPromptSubmit`'s output goes to Claude, `PermissionRequest`'s is a decision) and write only when the word changes, since the turn file's date is when that turn began, except `UserPromptSubmit`, which always writes working: a prompt begins a working period, and after Esc or a Deny the file still says working, so a write only on a change would leave the age counting from before it; they find the file from `VARNICK_SESSION_FILE`'s folder, so that variable stays beside it. Their SessionStart entries are only `clear` and `resume`: a compaction can come mid-turn, and the pane that starts claude writes the first word. `clear` writes working instead of waiting over a `plan` turn: approving a plan with "clear context" denies it, so no `PostToolUse` follows (untested whether that `clear` runs the hook). The permission entry's regular expression must keep matching every tool but `AskUserQuestion` and `ExitPlanMode`, which have entries of their own, or a dialog marks twice or not at all. Subagents and teammates run the lead's hooks and write the lead's turn file, so any of them can mark the pane, and an idle lead must go back to waiting, not working (`ClaudeCommand.askedCommand`, `answeredCommand`, `leadEndedCommand`). A `PermissionRequest` adds one file per asker to `.varnick-turn.askers/` (the input's `agent_id`, else `lead`; searched only before `hook_event_name`, since `tool_input` can hold any key) and, for the first asker, copies the turn file to `.varnick-turn.before` with `cp -p`: the date must stay, since the stop file counts as the turn's only within `PaneFolder.staleWindow` of it. `PostToolBatch` and `SubagentStop` remove that agent's file, and the one that empties the directory (`rmdir`) moves `.before` back, or writes working without it, only while the word is still permission. `Stop`, `StopFailure` and `UserPromptSubmit` drop the lead's file, since a Deny of the lead's own request fires no hook, and with other askers left they set `.before` to the word they wrote. What's left: a lead Deny followed by a subagent's request before the next prompt keeps the mark after that answer until the next prompt or stop; a request racing the answer that empties the directory, within milliseconds, can leave the restored word on the card while its dialog is open until its asker's next hook; there is no hook between Allow and the tool's end, so the mark stays while an allowed tool runs. `agent_id` is on a subagent's and a named agent's `PermissionRequest`, `PostToolBatch` and `SubagentStop` (2.1.295; after an Esc on the dialog too); a team's teammate is untested, and a Claude Code that drops it makes every asker `lead`, so any batch answers it. `PostToolBatch` is in every pane's settings, Skip permissions on or off: a pane with Skip permissions has shown a dialog (a teammate's Bash call, 2026-10-09). Hooks reach only panes started after the build is installed and Varnick restarted. The transcript correction (`PaneFolder.corrected`, shared by the app and both relays) is why `ClaudeSession.checkTurn` must watch the transcript's date too, and why `UserPromptSubmit` rewrites the file after an Esc. It matches Claude Code's undocumented interrupt text (`TranscriptReader.stoppedAt`), so a Claude Code that words it differently stops the correction with no error. `TranscriptReader.pendingBackground` reads the `turn_duration` field names (workflows only) and the English start of the notifications' `<summary>`: a renamed one, or a last `turn_duration` before the 64 KB tail, shows the card as Stopped with no error. Background shells, agents and teammates come from `.varnick-stop` (option 01, Background work): `PaneFolder.runningTasks` reads `background_tasks`' `type` strings (`shell`, `subagent`, `teammate`), `status`, `id` and `description`, so a renamed field or type, or a Claude Code that stops listing them, shows none with no error; they are subtracted by the notification's `<task-id>` (a shell's at any time, a subagent's only after the stop file's date) and a stop by the user by the English plain text that names the agents' descriptions. A teammate is busy or idle from the lead's transcript (`TranscriptReader.busyTeammates`, read incrementally in the app, whole on every ask in a relay, which is a new process each time): the `idle_notification` JSON (`from`, `timestamp`) in the `<teammate-message teammate_id=…>` wrapper of a user entry, the `Agent` tool call's `input.name` and `input.description` (the description is how a task is matched to a name), and the `SendMessage` call's `input.to`; a change to any shows an idle teammate as busy (a card stuck in Running) or a busy one as idle, with no error. An end in mid-turn arrives as an `attachment` entry, which `TranscriptReader.pendingBackground` must keep reading beside the user entries, or a shell that ended while a later turn ran shows as running. The `Stop` entry must write by rename and run in the same event as the turn word (the freshness window `PaneFolder.staleWindow` assumes it), and `StopFailure`'s entry must keep re-dating the file, or an API error drops the shells.
- The Problems board is behind a switch, off by default (Settings › Experimental, `Settings.problemsBoard`; on a headless host the file `~/.varnick/problems`, written by `install-peer.sh --problems` and removed by `--no-problems` or `--uninstall`, read by `HeadlessPeerHost.problemsBoard`). The host that runs a session decides, from its own switch, whoever asked for it, and reads it at each start or restart: `ClaudeCommand.arguments(problems:)` passes it to `hookSettings(problems:)`, which leaves the `WorkHooks` entries out when off and is otherwise byte-identical (a new caller must say which, there is no default; `Varnick --hook-settings` says true). A running session keeps the hooks it started with. Only the hooks and the display are gated: pane folders, `work-log`, `work_history`, `SessionRecord.workLinks`, `PeerWork` and `Varnick --problems` are not, so recorded links are kept; the Problems tab is the only place that shows them, so they are hidden while the switch is off and back when it is on. Everything that shows the Problems tab or reaches it needs the switch: `SessionBoard.hasProblems` gates the tab button, Tab and `show(.problems)`, and `LauncherCommand.available` gates `!problems`; a new way to open the tab must go through `show`.
- The work-link hooks (ADR 0020, `WorkHooks`, in the same `--settings`) follow the turn hooks' rules: POSIX sh with grep, cut, tail, awk and git, no jq, working in bash, zsh and dash and on the headless Linux host; print nothing and exit 0 whatever happens, never block a tool (`PreToolUse` exit 2 would), write by rename, and find the pane folder from `VARNICK_SESSION_FILE`'s folder. `SessionStart`'s work entry is the one that prints, and to Claude: one line and the open problems, only where `$VARNICK_PROJECT` has `.claude/skills/work/SKILL.md` and `docs/problems`. Its `awk` runs under `LC_ALL=C` and cuts titles by bytes: in a UTF-8 locale macOS awk aborts on a cut inside a character, which drops the problem from the list. A JSON key is matched only after `{` or `,` with its quote raw (`field`), so a path quoted inside the content being written, whose quotes are escaped, can't pass for `file_path`; a value with a backslash escape is not matched, so such a path makes no link. A subagent's `agent_id` goes into a file name only if it is letters, digits, dashes and underscores. The `/work` marker is `VARNICK-WORK|<pane id>|<nonce>|<kind>|<value>|<repo>|` with the pane folder's own name, built by `work.sh` when it runs together with the file `.work-mark.<nonce>` in the pane folder (printing the script links nothing, and a marker for another pane is ignored); the hook after Bash reads every marker in its whole input, accepts one only if its nonce's file exists and deletes the file, and the last accepted wins, so a marker replayed in output (a transcript read back) changes nothing; `work.sh` sweeps nonce files over an hour old, and it refuses a repo or slug with `|`, a quote or a backslash. The hooks read their JSON keys with one `grep -E` and no filter language, so a new key they need goes into that pattern and the `case` after it. Every hook that changes a record appends a line to `work-log`, whose date is how the app learns to read the records again (`ClaudeSession.checkWork`), so `SubagentStop` logs an `end` line too, and a new hook that writes a record without logging leaves the app stale. An option record is never replaced by the path hook, only by `/work` (and `none`); a subagent with no record inherits the session's option only for the problem that option belongs to, so for another problem the path hook gives it a record of its own. The log line's seven tab-separated fields (`PaneWork.logged`) are read by the app and by the relay (`PeerWork.read`, which sends them to a paired Mac). The repo in a record is the main checkout (`git rev-parse --git-common-dir`), compared with a project's folder by `WorkRepo.key` (symlinks resolved), so a project listed through a symlink matches. A pane that starts claude removes the subagents' records (`PaneFolder.clearSubagentWork`, also in the relay's launch) and appends an `end` line to the log when it removed any, because a removal the log doesn't show leaves the app's cached record, and the dead subagent's link, live. `SessionRecord.workLinks` is optional, set once in `sessionExited` from the log (on a record with a `host`, from the host's last `status` answer), and `sessionExited` also writes it to `work_history` (below).
- A teammate outlives its lead's conversation across /clear, a continuation ("clear context") and /resume, so the teammate ledger (`TeamLedgers`, `TranscriptReader.busyTeammates`) reads the pane's earlier conversations too (`PaneFolder.earlierTranscripts`: the pane id's own, then those `.varnick-conversations` lists), or a teammate whose spawn is in one counts busy forever and the card stays in Running. A description is matched against the newest conversation with a spawn carrying it, so an old spawn of a finished teammate doesn't inflate the count; a name's busy and idle times come from all of them. The hook's file holds only the latest conversation and Claude Code's transcripts don't name the one before, so `PaneFolder.recordConversation` appends to that list as `corrected` reads a waiting turn: a conversation that never had a waiting read is missing from it. Pairing unspawned teammates by number was dropped because it could match the wrong one; don't bring it back.
- `/rename` names are read from Claude Code's undocumented transcript format (`TranscriptReader.customTitle`, `TranscriptSession.customTitle`: `custom-title` entries with a `customTitle` field), read whole by the history sync (the `custom_title` column) and, in a pane, from the last 64 KB each time the transcript changes (`ClaudeSession.checkRename`, kept in the pane's `TitleRecord`). A renamed entry type stops it with no error: the pane and search show Claude's own title (`ai-title`, also undocumented), or the first prompt's first line, instead of the user's name.

**App panes** (`ClaudeSession.startApp`; the contract is in the `custom-apps` skill)
- An app server's zmx session must end with its pane: `finish` kills it, but a server that exits on its own goes through `appEnded`, not `finish`, so the pane stays open to show its output.
- An app pane owns its zmx session whatever Keep sessions running says (`ownsZmxSession`): a restored pane's session must be in the launch sweep's keep set, and `finish` must kill a never-shown one's. Quit ends app servers only with the setting off (`stopAppServers`).
- The server's port is `record.appPort`, never `record.url`: the address follows navigation. A pane reconnecting to a running session must not pick a port (the server holds the old one); only a pane running the app picks, and then moves `url` to the new root. A record saved before `appPort` existed has the port only in its `url`: `settlePort` falls back to it and stores it, so never reconnect on port 0.

**Panel size** (`LauncherModel.panelHeight`, `LauncherView`)
- The panel is fixed-size, so `panelHeight` must add exactly the rows `searchContent` shows, in every branch: settings, board (fixed, like settings), tab, prompt (the prompt line, then the suggestions or the sessions listed under it), search (`?`), `?` alone (the empty state's height), command, empty field (the session list). A mismatch clips content or leaves a gap. What a query does is its `LauncherModel.Mode`, read from its first character; every branch and key handler switches over it, so none can disagree.

**Focus and keys**
- After a session ends, focusing search has to wait a tick (see `focusSearch`); focus set synchronously is dropped.
- A key handler that returns `.handled` for a key it didn't act on swallows it (Tab, arrows).
- While the session board shows (`showingBoard`), no terminal is on screen (`showsTerminal` is off, so the tab shortcuts don't act), and `SessionBoard.key` takes esc, the arrows, ↩, D, R and the End session, Mark session done and Restart session keys before the shortcuts: ⌘W must never reach the hidden tab's pane. Anything that shows a tab goes through `activate`, which closes the board; only the exit of the tab underneath keeps it open. The board stats each pane's turn file once a second on the main actor (cheap, like `checkConversation`) and asks zmx once, off the main actor, when it opens; nothing in its view reads a file or publishes. A paired Mac's board cards come from `peerOpenRows` less the sessions marked done (by pane id, never by conversation, or two board cards share an id), refreshed through `refreshPeersForBoard` every 5 s with a 4 s timeout so one silent Mac can't hold the others up; a pane here on a peer takes its turn from `ClaudeSession.follow`. A board card's id is the pane's, or for a paired Mac's session the id its pane would get, and a paired Mac's session is found, marked and replaced in Completed by pane id, never by conversation, which /clear moves on (`peerOpenRow`, `rebuildRecent`, `put`). A tab under the board or Settings is activated without focusing it (`activate`): a frozen card's container would take ⇧↩ as Take over.
- The board's Problems tab (`ProblemsBoard`, `ProblemsModel`) reads project folders and runs git, so it reads only off the main actor (`ProblemsReader.read`, a detached task `ProblemsBoard` keeps): when the tab shows (`SessionBoard.show`, `appear`) and every 5 s while the panel is visible, never while the tab or the panel is hidden, and never from the view. A new `start` or `stop` cancels the read under way, which stops at the next project, so Tab held down or repeated `panelDidShow` never stack reads. The reader returns each project's problems and ties as read; `ProblemRules` (pure, run on the main actor after the read, and what `Varnick --problems [--work <pane folder>]… [--ended <pane folder>]… [--sent <pane folder>]… [--sent-json <file>]… [folder…]` prints) makes the cards, so a later branch adds its inputs to the rules, not the reader. Problems reads its files only while it shows, but the Sessions cards keep their one-second tick (`SessionBoard.refresh`, a stat of each pane's turn file and work log) on both tabs, because Problems takes its chips and live links from them (`ProblemsBoard.sessionsChanged`, which only rebuilds the cards from the files as last read, no disk); the paired Macs are asked only on Sessions, and returning to it asks them again. The zmx check runs once, when the board opens. Tab and ⇧Tab are taken by `SessionBoard.key` on both tabs, and on Problems it also takes ↩, the arrows, esc, D, E, R, the End session key, the Mark session done key and the Restart session key, so none reaches the tab underneath. A chip's id must stay its Sessions card's id: `ProblemsBoard.openSession` is `SessionBoard.open`, which finds ended, Completed and paired-Mac sessions by it. A new key in `ProblemsBoard.key` must first ask whether `chipSelection` is set, and `settleChip` must keep clearing it when its card is gone, collapsed or no longer lists the chip. Evidence and chips show only in a card in `opened` (there is no Show evidence switch; E is taken so it never types into the pane underneath), so every check that a chip can be selected asks `opened`, not a second flag. A tied branch counts only with commits `refs/heads/main` lacks (the tie itself is `issue-tracker.md`'s), so a repository whose main branch has another name never shows Building from ties. An option whose status is missing or unknown reads as proposed and says so in its card's evidence. Only a project folder that is a main checkout (`Project.scan` leaves worktrees out) is read, and git reads it with optional locks off (`CheckoutGit`).
- Done on the board ends the pane through `ClaudeSession.end`, so a session goes into Completed only in `sessionExited`, once the pane has closed; a close that doesn't happen clears the mark through `onKept`, and a conversation open in a pane drops out of Completed in `rebuildRecent`, before the save.
- Only Done takes a session off the board. A Claude pane that closes any other way leaves an ended card (`LauncherModel.ended`, saved as `State.ended`) in `sessionExited` beside Recent, once the pane is out of its tab, and never with Done (`markedDone` goes to Completed alone). The one close Recent leaves out that does leave a card is a frozen view of a session another Mac controls whose own check found it gone: `ClaudeSession.endedByUser` (read-only outside) tells the user's close, which leaves none, from that. A card on a peer that its own check found gone (not the user's close, and only `isViewOfSessionControlledElsewhere` or `opensOnCard`, `addClosed`) may only have lost a Mac that restarted and restores the session, so it goes into `remembered` and becomes a card only when that Mac's Recent names its pane id; every other close, `/exit` and claude exiting in a pane in control included, adds the card at once. Every reader of a cached listing that could clear or hide a card (`openConversations`, `peerOpenRows`, `rebuildRecent`, `remember`) goes through `listedSessions`, which leaves out a session closed here after the listing's ask was sent. Ended cards are found, replaced and dropped by pane id (`put`) or, when a conversation is open here or on a paired Mac, by conversation, in `rebuildRecent` before every save (Recent's rule, not Completed's); a paired Mac's listing of a session whose pane just closed is dropped from the cache in `noteClosed`, and a listing whose ask was sent before the close is ignored for that pane id (`closedHereAt`, `listedPaneIDs`, and in `remember`), or that rule would clear the card at once. `addCompleted` removes the ended card with the same id, so a session is never in both. Nothing else removes one, and there is no cap, so the relay decodes a longer `sessions.json`.

**Search store** (`KnowledgeBase.swift`, `HistorySync.swift`, `Embedder.swift`, `LocalReranker.swift`, `RelevanceSearch.swift`, `ModelServer.swift`)
- One WAL database, `varnick.sqlite` in the support folder in every mode (`DatabaseLocation`; `VARNICK_DB` overrides it, an empty one being taken as the path itself, so a script sets it only for a non-empty path). Only the app's start creates it where history exists: the first-launch copy (see "The rename") fills it from the checkout's `db/` once, and the checkout's `db/` is not read after that. An empty database at the default path counts as copied for good, so nothing but that step may make it while a source exists, and the command-line modes that open it (`--sync`, `--search`, `--ask`, `--search-eval`) refuse without `VARNICK_DB` while it doesn't exist (`error: Varnick has no database yet: open Varnick once first, or set VARNICK_DB`). The relay never copies and never refuses: it reads `search-db-path`, which the app rewrites at each launch. `HistorySync` updates the search tables in place in one transaction while `FavoritesStore` reads, and the store reloads its vectors when `PRAGMA data_version` changes. Rows keep their id across syncs so ids held in the in-memory vectors stay valid; renumbering rows breaks that.
- Claude sessions (`session:` rows, built from `~/.claude/projects` transcripts, and the paired Macs' rows in `peer_sessions`) never go to any reranker: its candidates are a ranking's pages (`RelevanceSearch.filtered`), and a spoken request that reads sessions only skips the filter. A session holds the user's prompts and, for each, the last text Claude wrote before the next (its reply, cut at 1,000 characters; ADR 0018). They stay on the user's paired Macs: a peer's are copied here for Recent and search (`PeerOp.rows`), this Mac's go to a paired Mac the same way, and nowhere else, never to a reranker, TypeSafe or any other service. Replies reach only the exchange texts (the `entries` table, the embedder, a paired Mac): the search row's description, which keyword search, the snippet, the preview and a spoken answer read, stays the prompts. With Search embeddings on a server, see the model server bullet. Keep every peer row `source == FavoritesStore.sessionSource`. A prompt (anything typed without a leading `?` or `!`) never reaches a reranker, TypeSafe or a log either: it runs only the store's session queries and the chosen embedder (`listPromptSessions`), cut to 1,000 characters, and the "no results" log lines print the query, so they stay in search mode. A filter on those sessions (`SessionFilter`) goes inside the store's queries, before the cut to a count.
- MLX is shared by the whole process (the embedder, the local reranker and the text generator). Check `MLXRuntime.hasMetalLibrary` before any MLX call, the command-line modes' included: without the metallib MLX aborts the app, and that ends every session in it. It is worked out once, from the resource folder's `mlx.metallib` (`ResourceFolder`), and when the file is there it sets `GPU.metallib` to that path, so MLX never guesses at the binary's folder; a new MLX use that skips the check would load the library from wherever MLX guesses. The first model to load sets the 64 MB cache cap (`MLXRuntime.capCache()`). Wrap loading, scoring and generating in `withError`; touch no MLX in an `init` (they run on the main thread at launch), since MLX's default error handler exits the app too.
- A model server (an OpenAI-compatible address on the tailnet; `ModelServer`, `ServerEmbedder`, `ServerGenerator`) is reached only through `ModelServer.post`. It accepts only `http` or `https` addresses whose name resolves only to tailnet (100.64.0.0/10, fd7a:115c:a1e0::/48) or loopback addresses, checked before anything is sent, and follows no redirect and no system proxy (`connectionProxyDictionary` is empty: a proxy would get the prompts and the key in the clear). The name is resolved again when the connection is made, so an answer that changes in between is a known gap; there is no IP pinning. It logs the kind of failure and the status code, never the request, the reply's body or the key (`MODEL_SERVER_KEY`, in the Keychain).
- What goes to a model server, and to nothing else (never a reranker, TypeSafe or a log; the exceptions go to TypeSafe alone and are never logged: the spoken request's text, and, with the relevance filter on TypeSafe, a spoken request's search words and the title, site and own description of its first 20 pages, as a typed search sends them, and, with Point at the screen on, a screen request's window title and its controls' descriptions; see below): with Search embeddings on a server, the searches typed (`?` ones too), the search words of a spoken request (`RelevanceSearch.withMeaning` embeds them through `embedQuery`, as the panel does), the prompts typed in the panel (cut to 1,000 characters), and every page's embed text and every session exchange's (title, folder, prompt and Claude's reply), the paired Macs' included; with Text generation on a server, and with Hey Varnick on, what the user says after the wake phrase and the kind, title, site or folder, date and description (cut to 300 characters) of the few rows read to answer it: for a page its own summary only (`Reranker.metaDescription`: never the history title, search terms or address), for a session its prompts, the paired Macs' too. Vectors from a server are stored only after a Check that passed within 10 minutes in this launch, under the one model key (`toEmbed`, `refreshSearch` and the stored `embedding_model` are unchanged, so switching either way embeds only new and changed entries).
- The fallback rule lives in `ModelServerState.place` and nowhere else: work the user waits on (a search, the sessions under the prompt line, a spoken request through `TextGeneration.generateNow`) uses a server not known to have failed and otherwise falls back to this Mac's installed model; background work (the sync) needs a server that passed a Check and otherwise waits, and never loads this Mac's model; On this Mac never contacts the server. A change of the choice, or a Check that found another model, stops a sync under way (`HistorySync.SyncEmbedder.stillChosen`). A failure rests the server only for the request's own address and model (`failed(_:for:)`), and a local failure never does.
- The server embedder's vectors are compared with `EmbeddingReferences` (made-up sentences, three vectors from this Mac's model). An mlx-swift or mlx-swift-lm bump, or a change to `Embedder`'s method or prefix, can move them: rerun `Varnick --embed-reference` (it prints each fresh vector's cosine to the shipped one, 1.0 to 1e-6) and `Varnick --embed-check <address>`.
- The local reranker's row format is a contract with the checkpoint (`LayaScorer`, `LayaModel`): the question prefix, the state (query, host, title cut to 60 Unicode scalars), [MASK] replaced, right padding with [PAD], and the weights' PyTorch names. Drift lowers ranking with no error, so rerun `Varnick --rerank-eval` after touching them or bumping mlx-swift or swift-transformers. Run it on the long-row set kept locally, outside the repository, too (23 searches, rows of 28 to 512 tokens counting the prefix and [SEP], 220 of 460 past 129, with their Python MLX scores, same eval file layout) as `Varnick --rerank-eval <checkpoint> <eval file> <reference file> --max-diff 1e-3`. The eval's rows are too short for the sliding band, so a wrong band only fails there, and only at that bar: an off-by-one band moves these rows by 9.6e-3 and passes the default 0.01, where a correct build is off by 2.3e-4. The MRR bar is relative to the reference file's own MRR, so any set with its reference scores works. `tokenizer.json` is pinned by SHA-256 and checked before swift-transformers reads it, which `fatalError`s on files it doesn't support.
- The TypeSafe request carries each page's title, site and own description (`Reranker.metaDescription`: the first blank-line-separated part of the description field, unless it is the history title, the search terms or the URL). The rest of that field, the URL and the tags never go: URLs can carry private ids and login tokens.
- On this Mac never sends anything to TypeSafe for the filter, including after a failure: a failed local check shows unfiltered results with the warning, and a failed load turns the filter off until Retry.
- The checkpoint and the eval data encode the user's browsing history: never commit, upload or log them (no titles, queries, scores or file contents), and import only the five files in `LayaCheckpoint.files`.
- `refreshSearch` deletes every row it didn't write and `toEmbed` deletes every embedding key it doesn't know, so session rows and session embeddings must be written and counted as current in those same passes, or the next sync removes them. A session has no vector of its own once embedded: its exchanges are keyed `session:<id>#<n>` in `entries` (`SessionExchanges`), `toEmbed` counts every exchange key of every session it lists as current (the paired Macs' too, built from their prompts and replies with this Mac's embedder), and a session's old single vector, `session:<id>`, is counted as current as stored until one of its exchanges has a vector, then dropped; `refreshSearch` writes the row's own embedding as nil from then on. Until then the old vector is scored as one more of the session's vectors, so a Mac whose embedder can't run yet still searches sessions. Positions stay put as a session grows, so only the last exchange or two change; a changed title changes every exchange of its session. `FavoritesStore` reads exchange vectors straight from `entries` (the current model's only), each mapped to its session's row through the key, so several matrix rows share one row id: `semantic` and `semanticSessions` keep each session's best score before the cut to the candidate limit, because fusion adds a score for every list entry. A new kind of key in `entries` must be counted current in `toEmbed` and skipped by that store query. Both, and `sessionsDigest`, take their sessions from `sessionEntries`, which adds the peers' rows without the folder check (the host made it); a new source of session rows goes through it.
- A session's title in the search database comes from `sessionEntries` (this Mac's own sessions) in the order of the naming bullet below, from `session_names`, `sessions.custom_title` and `sessions.title`; the digest, the exchanges (each starts with the title), the search rows and `PeerOp.rows` all take it from there, so a name change re-embeds the session's exchanges. `custom_title` is NULL on rows an earlier build wrote: `syncSessions` reads those transcripts again once, and `peerRows` refuses (`RepliesNotRead`) while any is NULL. The relay opens the database read-only beside a Varnick that may not have restarted, so `sessionEntries` checks that the table and the column exist and `peerRows` skips the NULL check without the column. A peer's sessions keep the title the host sent.
- A page row can carry a host too (`favorites.host`): the paired Mac that alone visited it, when none of the entry's URLs is a page or bookmark of this Mac's own. A paired Mac's pages (`peer_pages`, `peer_search_terms`, `peer_page_meta`) are built into search rows through `entries`, merged by URL with this Mac's before grouping, so `refreshSearch`, `toEmbed` and `archiveSignature` count them current and nothing deletes them. Pulled rows never go into `pages`, `search_terms` or `page_meta`: the relay passes on only this Mac's own, and removing a Mac removes exactly its rows. A request for a page's description (`toFetch`) goes only to a URL this Mac holds (`Entry.fetchURL`), never to one only a paired Mac visited.
- `pages`, `search_terms` and `page_meta` carry `changed` (real unix milliseconds, never whole seconds times 1000: a stamp below a cursor already handed out is skipped), which the relay's cursor orders by. The hot upsert (`upsertSQL`, `upsertTermSQL`) runs for every Chrome row each minute and must move `changed` only when a value `pages` sends changes; `store` stamps every description it writes.
- SQL built from user text uses bound parameters; FTS queries quote or escape user input so stray quotes or operators don't throw.

**Sessions and tabs**
- Ending a session keeps the tab model consistent: removing the last pane removes the tab, and `activeTab`, `sessionSelection` and `renamingTab` never point at a removed tab.
- Nothing inside a SwiftUI view update (`body`, `makeNSView`, `updateNSView`) may block on a subprocess, spin the main run loop (`Process.waitUntilExit`, `RunLoop.run`) or publish model state: a spun run loop re-enters SwiftUI mid-update (a restored split kept the search-size height and stranded a web view). Start panes after the update, as `TerminalHost` does.
- A pane's content (terminal, web view, file) takes its container's size one main-queue turn after the container gets it (`HostContainer.fitNow`), never through an autoresizing mask. Every frame change of a terminal is sent to its pty, and Claude with `"tui": "fullscreen"` draws on the alternate screen, which has no scrollback, so a shrink and a grow in one turn (the panel at the board's size, then `placePanel`'s) clips the screen for good: Claude sees its old size again and doesn't repaint. Deferred, the two collapse into no change. A client starts through `launchProcess`, which fits first; a container out of a window fits nothing, so a hidden pane's pty keeps its size.
- A session is named, on the board and in search, by the ⌘⇧R name of its one-pane tab, else its /rename name, else Claude's latest title, else (search) the first prompt's first line or (a pane) its prompt. Varnick no longer writes titles; its text generation is for spoken requests, loaded on the first one. The ⌘⇧R name lives only in `sessions.json` (`SavedTab.name`, a tab's name), so the sync copies it into the `session_names` table (`SessionNames`, `HistorySync.syncNames`), and a pane's label is the tab's name only while the tab has one pane. A `sessions.json` that doesn't decode means the names are unknown, never that there are none: the step writes and deletes nothing. A name outlives its tab, and is deleted when a one-pane tab holds the conversation with no name; a tab with several panes writes and deletes nothing. So every way of opening a conversation in a new tab on this Mac must give that tab the name back (`LauncherModel.resume` and `hostResumeConversation` do, from `FavoritesStore.tabName(ofSession:)`), or the next sync finds the new tab unnamed and deletes the row. Naming a one-pane tab writes the row at once (`HistorySync.keepName`), so a tab closed before the next sync keeps it. Names are bound as parameters and never logged. A pane on a peer reads no transcript here: its host's label is what shows.
- Whether a session can be resumed is computed from its directory path (non-alphanumerics become `-`), so changing how `directory` is set changes which sessions resume.

**Peers** (`SSHRunner.swift`, `MacPeerHost.swift`, `Peers.swift`, `Packages/VarnickPeer`; ADR 0007)
- `Packages/VarnickPeer` is built by both the app and the Linux relay (`varnick-peer`), so a change there must compile on Linux too: `swift build` in the package on a Linux machine with Swift (swiftly puts it at `~/.local/share/swiftly/bin/swift`), with anything Darwin-only under `#if os(Linux)` or `#if canImport(Darwin)`, and no AppKit, SwiftUI, CryptoKit or app type. The app reaches it through `public`, since `package` access stops at the path dependency: a new declaration the app uses needs `public`, and a struct it builds field by field a public initialiser. The Mac's own answers are `MacPeerHost` (the `PeerHost` seam); the support folder is `SupportFolder`, and on a Mac its path never moves.
- Every call to another Mac goes through `SSHRunner`, which builds the `ssh` command for three kinds: `run` for a request (off the main actor, with a deadline), `terminalCommand` for a pane's terminal and `stream` for a command that runs until cancelled (a card's `watch`). Never a bare `Process` for `ssh`, never `waitUntilExit`, never from `body`. A Mac that isn't in the peer list is contacted only by Find Macs and Add.
- A change to a request or reply shape bumps `PeerProtocol.version`, or two builds misread each other with no error. The relay parses a request's version before anything else, so keep `PeerRequestHead` to `v`, `op` and `by`. The exception is `upgrade` and `restart` (`PeerProtocol.answersAnyVersion`): the frozen shapes and envelope are in the doc comments of `PeerMaintenanceAsk`, `PeerUpgradeReport`, `PeerRestartReport`, `PeerReply` and `PeerRequestHead`. A reply to them sets nothing but the envelope keys and its own report, since an older asker decodes the whole `PeerReply`, and is `ok` even for a refusal, since `PeerClient.verdict` drops the body of a failed one.
- A socket or control path over 103 bytes fails to bind with no useful error, and a long `ControlPath` also needs ssh's 17-character temporary suffix (`PeerSocket.path`, `SSHRunner.controlPath` check both). A path with a space goes into an ssh `-o` value in double quotes.
- On a Mac the relay never writes UserDefaults, since the app may be running. Only a hello with `pair` set adds a peer, so a refresh doesn't undo a removal.
- A headless host (`Sources/varnick-peer` in the package; its install root, state rule and installer are in ADR 0009, which also says to reinstall it at every protocol bump, now its row's Upgrade button; see the upgrade bullets below) answers everything but a hello only to a Mac in `peers.json` (or a device, below), checked first, and never calls a Mac back. A `peers.json` that isn't a list, or can't be read, fails a pairing instead of being replaced. Point a check at a copy of the binary, never at `~/.varnick`.
- A Mac's SSH command (`PeerLink.remoteCommand`) tries the macOS link, then `$HOME/.varnick/varnick-peer`, and `exec`s it so the relay is the ssh's own process. Keep it one POSIX literal that a request is appended to: `scripts/install-peer.sh` reads it from `PeerSocket.swift` at HEAD to verify with the very command a Mac sends.
- A peer's request runs the launch snapshot, not the build folder (`LaunchSnapshot`, `PeerLink.refresh`): at each launch Varnick clones its binary, zmx, build stamp and Phone page files into `.build/snapshots/` (the first 12 characters of the commit, or `unstamped`, then the launch time) and points the link at that binary, so a `make build` changes nothing a peer reaches until Varnick restarts. The relay finds zmx beside itself, so a file the relay needs at run time must be copied there too, or it is the build folder's, which a build rewrites. Only the app takes a snapshot (the relay exits before anything of the app starts). The earlier snapshots are removed only once the link is seen pointing at the new one; a request that arrives mid-swap can fail once, and a running `watch` or `attach` keeps its open files. Where Varnick isn't running from a checkout's `.build`, or the copy fails, the link points at the binary in place. A bundle is never a checkout build, wherever it sits (one under `.build/app/` included): `ResourceFolder.current.inBundle` makes `take()` and `LaunchSnapshot.checkout` nil. The resource folder is a bundle's `Contents/Resources`, else the executable's own folder, found from the executable with links resolved: the relay runs through the `varnick-peer` link, where `Bundle.main` answers for the link's folder, so a lookup that skips the resolving finds the Application Support folder instead. `make build` writes the stamp (`BuildStamp`) as its last step, only when everything before succeeded, so it names the last good build, not the running one; a stamp older than the binary is ignored (a plain `swift build`, or a build that failed after linking), and compare stamps with `isSameBuild(as:)`, never with the time.
- A Mac answers `upgrade` and `restart` in its running Varnick (`PeerManager.handle` before the version check, then `BuildUpgrade`), and its relay (`MacPeerHost.upgrade`, `restart`) forwards them and, with Varnick not running, answers the build fields from the stamps and git with `running: false` and a refused state. The relay must never read `LaunchSnapshot.current` (it would snapshot the snapshot): its stamp is `LaunchSnapshot.relayStamp()`, and the app's readers use `LaunchSnapshot.runningStamp` (in a bundle the resource folder's stamp, read without the "older than the binary" rule, since signing rewrites the binary after the stamp). The relay's reply carries its build, so a stamp read from the link's folder names the wrong one. Everything in `answer(upgrade:)` has to end inside 10 s, since the relay waits that long for the socket and a longer one reads as "Varnick isn't running": a fetch is waited for 8 s, a `begin` 6.5 s, and the report's git reads 1 s in all (the report then has the running commit alone; it takes about 0.1 s even with every core busy). The relay's own fallback, with Varnick not running, gives the same reads 2 s each and 3 s in all. `CheckoutGit` and `BuildProcesses` go through `Subprocess`, and the relay, which is synchronous, waits on them with `MacPeerHost.blocking`.
- The target is origin/main alone (`CheckoutGit`): fetch is `+refs/heads/main:refs/remotes/origin/main` with `gc.auto` and `maintenance.auto` off (a detached gc after a fetch is what XProtect dislikes), read-only commands run with `GIT_OPTIONAL_LOCKS=0` so they never write the user's index, and the only change to the checkout is `merge --ff-only`, which acts on HEAD whatever it names: so `CheckoutGit.settle` reads the branch and the changes again right before it (the fetch before it can take 60 s, and a branch switched or a file edited meanwhile would be moved or built). Never `pull`, `checkout` or `reset`. A fetch runs once at a time (`OriginWatch`): a report with `fetch` and Settings › Peers opening join one under way or start one, and a report without it starts one only when the last try is over 10 minutes old, a failed try counting (`FetchRecord.attempted`), so a failing remote isn't hit at every report.
- The build runs only in the zmx session `varnick-upgrade` (`UpgradeRunner`), never in process: XProtect once killed a Claude process that ran installs, launchctl and a downloaded binary together. Its log is emptied before the upgrade is marked building, and nothing resolves that state while the session is still being started (`BuildUpgrade.pipeline`): the log's last line, `varnick-build-exit=<n>`, is the only record of how `make` ended (a zmx session's exit status says nothing), and an old one or a session not there yet would read as an end. A zmx session with no such line that is gone is a failure. The result is kept in `upgrade/state.json` in Application Support, so a relaunch picks a build up; a built state ends once the running commit is the built one. It runs with Varnick's environment less `ZMX_*` and `GIT_*` and the system tools first on `PATH` (no login shell), so a build step that needs another tool must find it there.
- A restart (`BuildUpgrade.answer(restart:)`) is refused while an upgrade runs, while a `make` or SwiftPM process has the checkout as its working folder (`BuildProcesses`, `ps` then `lsof`), and when no stamp newer than the running build waits, or the one that waits was made with uncommitted changes or off main. It starts after the reply is sent (a second later) as `make run` does, `scripts/restart.sh` under `perl`'s `setsid`, and only Varnick restarts. The panes it says would end (`LauncherModel.restartImpact`) must follow what the next launch does: a Claude or terminal pane survives only with Keep sessions running on now (the sweep kills the session of a restored pane otherwise), and an app's server always does, since Varnick has no SIGTERM handler and `stopAppServers` never runs at a restart. Handling SIGTERM would change that list.
- The status menu's Restart Varnick (`BuildUpgrade.restartFromMenu`) shares `spawnRestart` and `restartImpact` with the peers' restart, so the rules above hold for it. It skips the newer-build check, so `BuildUpgrade.newerBuildNote` has to warn when a build on disk would be started and it would void the macOS permission grants: only an ad-hoc signed build does (`startingVoidsGrants` reads the ad-hoc flag of the waiting binary, never the team identifier; a Developer ID build keeps its grants, ADR 0022). The card (`RestartCard`) takes every key while it shows, and `panelHeight` must include it, or a bare search field clips it.
- The relay's process arguments must stay unlike `make run`'s kill pattern (anchored to the bare binary path), or a restart kills a peer's request.
- A zmx run (the build, a headless install; `ZmxRun`) whose `zmx ls --short` can't be answered is still `running` and never `lost`: only a listing that came back may say a session is gone (`zmx ls --short` exits 0 with no output when none exist, and 1 on an unusable socket folder, so empty is a success). But a run no listing has answered for 30 minutes is failed ("Couldn't ask zmx about the build"), or `building` would stay for ever and keep Upgrade and Restart refused.
- A headless host is upgraded from a Mac, never by itself and never with `begin` (its relay answers "upgraded from a Mac, with the installer"): `HeadlessUpgrade` runs `scripts/install-peer.sh <host> --commit <origin/main>` in the zmx session `varnick-install-<slug>` (the slug carries a hash of the address, so two addresses never share a session or a log), judged by its `VERIFY=ok` and `BUILD` markers and never by an exit status. What the installer ships is `RelayFiles.pathspecs` in `RelayComparison.swift`, which also decides "relay unchanged": change both together. The installer ships and reads what is committed at the commit, its far half included; the far half says what it supports in its `# supports: RUN LOCK` line (add a word for a feature the near half adapts to, never remove one), installs on one host queue on `~/.varnick/install.lock`, and takes per-run tarballs (`incoming-<run>.tar.gz`) that other runs' far halves remove once a day old (uninstall removes only its own and the day-old ones, since a newer one may belong to an install queued on the lock). A comparison fetches only past the 10-minute rule. Known limit: `RelayFiles.pathspecs` always counts `PhonePage`, since a headless host's report doesn't say whether it has a page, so a page-only change offers Upgrade on a host with none. A headless row's states (`HeadlessUpgradeState`) are told apart (not compared yet, couldn't compare, ahead of origin/main, up to date), and `offersUpgrade` (behind, or a failed install to retry) is the one rule the row and Upgrade all share.
- Upgrade all and Restart all (`PeerBulk`; the lines are `BulkPlanner`'s, from each machine's last report): Upgrade all begins the other machines together and this Mac after their begin replies, then waits by asking for reports itself, since Settings' poll may not be running; nothing restarts. Restart all lists only Macs with a build waiting, never a headless host, and each Mac is asked again before its confirm (`PeerBuilds.sendRestart`, the same path as one row's Restart Varnick): a list that changed, or a refusal, skips that Mac. This Mac restarts last, once the others have answered or 15 s have passed, and its report is written to `upgrade/restart-all.json` before the restart so the next Varnick shows it once (only a launch other than the one that saved it does, and a file over 10 minutes old is dropped). A confirmation is dropped when Settings stops showing; a run goes on.
- The Tailscale CLI in the app bundle starts the GUI instead unless `TERM` is set.
- A pane with `record.host` (a session on a peer) is that `ssh` client (`startOnHost`), never inside this Mac's zmx and never given `Zmx.kill` (`ownsZmxSession` is false for it). Only the host kills the session, when the Mac in control sends `end` for a session it started for that Mac; the host accepts `end` only from a listed peer or device the session's `varnick-control` label names, and releases instead of killing when the session didn't originate from the asker (the bullet on closing in control, below).
- A Claude client exiting isn't the pane ending: `finish` asks the host's zmx (`clientExited`) and a session still running and labelled for another Mac leaves the pane open on a card. Keep the label, not timing, as the test, and keep a takeover relabelling before it detaches. A card for a lost link or an unreachable host asks again every few seconds (`Away.isLink`), so it can't stick; one that needs the user or a start under way doesn't (`Away.skipsAutomaticCheck`).
- A pane on the host never attaches to a session another Mac controls (`startClaude` checks the label before a restored pane attaches); a second client would make two keyboards type into it. The card on the host asks before closing, since it is the only pane the session has here.
- The launch sweep is unchanged except for one exception: it never kills a session whose `varnick-control` label names a listed peer or a listed device (`Zmx.sessionsToKill(sparing:)`; `cleanUpAfterLastRun` passes both lists' ids), since that Mac or device may be typing into one whose pane here was closed.
- The relay's `attach` checks that the session exists and, without take, that its label names the caller (an unlabelled session is its host's). `zmx attach` creates a session for a missing name and has no flag to refuse, so the relay gives it `/usr/bin/false` as the command: one that lost a race ends at once instead of running a login shell. `attach` needs only zmx, and `status` zmx and the saved tabs, so keep both working with Varnick not running.
- Take over relabels, then detaches, then attaches (`ClaudeSession.takeOver`; the relay's `attach` with take on a peer): the Mac that sees its client exit tells a taken session from an ended one by the label, so the label comes first. On the host the pane's client restarts in zmx whatever Keep sessions running says now (`launchClaude` passes `alwaysInZmx`), and a session this Mac started for a peer stops being given that peer's labels (`startedFor`), since attaching with it would hand the session straight back. Only its control label is handed back that way: `varnick-origin` is set when the session is created and stays.
- A client for a pane coming back from a card (take over, Reconnect, going live after a release) starts only once the terminal view is on screen at its real size (`resumeClient`, `startWhenHosted`). While the card shows, the view is in no window and keeps its first grid, so a client started at once is told that size: zmx draws the saved screen and Claude repaints for it, the real size arrives after, and the transcript above the prompt box ends up missing (seen on opening a peer's session a second time). A fresh pane is safe because it starts after `TerminalHost` hosts it; keep every start that follows `away = nil` behind the same wait.
- Closing a pane in control of a session on a peer sends `end`, and the host decides (`LauncherModel.hostEnd`): if the session's `varnick-origin` zmx label names the asker it is killed and its pane closed; otherwise (the host started it itself, so there is no label, or for another Mac) it is released: `Zmx.release` clears `varnick-control` and then detaches every client, in that order like a take over, and the host's card goes live (`goLiveAfterRelease`, also done by the card's own check when it finds the label no longer names a peer). The label is the live source. It is written with the control label as the session is created for a peer, from `SessionRecord.origin`, which `hostStart` and `hostResumeConversation` save and `hostResume` reuses, so a session the host starts again after zmx lost it (a reboot) keeps its real origin; the label is only given at creation (`startedFor` set), never re-applied from the record by a later attach. Sessions from before the label existed have none and are released. A session with no pane on the host ends, since nothing would own it once released. The peer's closed pane never asks to be started again: it is over (`endedByUser`), and a `released` reply only takes its conversation out of the peer's Recent (`onReleased`). Keep the decision on the host; the peer can't tell where a session came from.
- On a headless host (`HeadlessHosting.swift`) every session carries a control label naming a Mac or a device, and release keeps it: it detaches the clients and never clears the label (`Zmx.release`, which clears it, is the Mac host's). A Mac reads a missing label as the host in control, and nothing there types. `end` is the same rule as `hostEnd`: the label must name the asker, then origin kills and anything else releases.
- A headless host's `start` runs in this order: the record (saved with `starting`), the pane folder, the pty client (`PtyClient`: `openpty`, `posix_spawn` with SETSID, signals reset), the wait for `varnick=1` and the control label (`zmx get` succeeds before `attach --labels` has set them), then the detach of the relay's own client. The folder before claude starts is the hook's, and the first turn is written where the session file is cleared (ADR 0010). The labels are written in the one attach, so a start never creates a session in two steps. Claude's environment is built fresh there (`claudeEnvironment`), `DISABLE_AUTO_UPDATE=true` included, since oh-my-zsh's update prompt blocks `zsh -l -i`.
- The state lock (`StateFolder.locked`) is held for a read or a write of a file and never across a wait, whether for zmx, the pty or a sleep: the other Mac's polls would stall behind it. A start takes it for each record write on its own.
- A headless host reconciles its records with zmx before any request reads them (`StateFolder.reconcile`; `HeadlessLifecycle` is these rules' code, and this is where they are written): a session gone in this boot is ended, one gone from an earlier boot (the record's `bootID` differs) is lost and left with `ended` unset, and a start that never handed over, with no session, is ended once it is 30 s old. A listing that failed (`Zmx.listedSessions` nil), or a host whose boot id can't be read (for any record but a stuck start), changes nothing, since only a listing that came back may say a session is gone; the hand listing and `recent` say so instead of showing sessions as gone. The records are read before zmx is asked and written only if still unchanged, so a start finishing meanwhile is never ended. Nothing ends a session by itself, and orphans stay in the list.
- Only a lost record is ever started again, and only for a Mac's `start` with `resume`, which `claimResume` decides and marks `starting` under the lock, so two panes can't both start it (the other gets `running` or `closing`). A record that ended in this boot answers `ended`: starting it would be unasked. With no boot id for the host a record isn't called lost, so a Reconnect answers `ended` without marking it, and the hand listing says "unknown". A restart that fails puts the record back as lost with the conversation it claimed (`launch` has already cleared the hook's file), and neither that nor the hand-over writes over a record ended meanwhile by a hand `end`. Resuming an ended conversation is the `resume` request, which refuses one a running or starting record has open (`isHeld`, checked in the same lock as the record's save). `VARNICK_BOOT_ID` replaces the boot id for a check, and a Mac's ssh command never sets it.
- Two Macs taking a session at once can leave both attached (a take landing between the other's detach and attach), so a second or two after any client attaches the pane reads the label once and lets go of its client if another Mac is named (`checkControlAfterAttach`). A client for a session expected to exist is started with `/usr/bin/false` as its command (`attachToLocalSession`, like the relay's attach), never with the claude command line, which would start a second session if the first ended meanwhile.
- The frozen screen is `zmx history --vt` read from the host (sent to a card by `watch`; the `screen` request, served by the relay from zmx alone, is no card's path now and is kept for checks), and it is never fed to a live terminal: it replays the private modes the session had set (mouse, focus, paste, alternate screen), and a shell that received them printed the reports as text. `FrozenScreen.prepare` strips them and cuts to a tail before it is sent, and the view (`FrozenTerminalView`) has no process, drops what the terminal would send, and never becomes first responder. Keep both when changing either. The screen carries the grid it was drawn on, read before and after the history, and the view keeps that grid and fits it by font size. A font change on a laid-out view makes SwiftTerm resize the terminal to the frame and lose its buffer, so `fittingFontSize` measures with the frame at zero; keep that. No grid falls back to the pane's size.
- `watch` is the live screen of a card (ADR 0008, which has the timings and counts), answered by the relay alone like `attach` and `status`, so it works with Varnick not running. It prints one reply line, then frames (`WatchFrames`), with blank keep-alive lines, until its input ends, a write fails or the session's socket closes (Take over, Release and the session ending all close it). `ZmxReader` is the one reader, run by the relay and, in process, by the host's own card; a card for a session on a peer reads the peer's relay through `PeerManager.watch` (`ClaudeSession.startWatching` picks). It sends only history requests (`ZmxWire.historyRequest`), never input, Init or Resize: any of those makes it a terminal, the leader or a sender of focus reports. It never stops reading the socket, or zmx queues output for it without limit, and its socket never raises SIGPIPE (`SO_NOSIGPIPE`; the relay also ignores the signal), since a signal would end every session in the app. A pending frame is replaced by a newer one, never queued. The keep-alive is what ends the relay after the viewer's ssh is killed on a shared connection, which sshd alone doesn't notice. A zmx pin bump rechecks the socket header, the tags and the history request in `ZmxWire`.
- A reader counts as a zmx client, so every client count that says "Controlled on" or "Last controlled on" goes through `Zmx.statuses`, which subtracts the live readers in `ReaderRegistry` (one empty file per reader, written on its first history reply and removed before it disconnects; a file whose pid is gone is skipped and removed). Reading `zmx ls` directly for a count would show "Controlled on" for a Mac that quit. Take over and Release detach every client, so they end readers; a card still showing another Mac in control starts one again after a backoff. A card runs a reader only while a view of it is on screen in a visible window (`FrozenScreenContainer.onShownChange`, counted per container, since a new one can join before the old leaves) and for a short while after, and never takes the reader's ending for the session's: the card's own check decides that.
- A peer's card holds one `watch` channel to its host while a view of it is shown, on the same shared connection as the panes (ADR 0008 has the count the spike ran). `SSHRunner.stream` keeps the ssh's input a pipe open for its whole life, never `/dev/null`: that is how the relay learns its viewer is gone (Varnick quitting or crashing closes it; cancelling closes it, then terminates the ssh after 1 s and kills it after 2 s, a command that reads its input ending sooner than a killed ssh does). The parent's pipe ends are close-on-exec, or a pane started meanwhile (`forkpty`) would hold the input's write end open after cancel and orphan the ssh and relay on quit. A stream's ending is never a timeout, so it never asks the shared connection to exit, and a channel ending is never the session ending: the card's own check decides that, as for the host's card. `PeerManager.watch` skips lines before the reply, checks its version and `ok`, and refuses a peer known to speak another version before sending anything. A refusal (another version, or this Mac unlisted) updates the peer's status like `send` and stops the card until it is shown again, never a retry loop. No reply in time is a failed attempt. A card's frames hop to the main actor and check the generation, like the host's.
- A peer's open sessions in the session list (`sessions`, read by the relay from `sessions.json` and zmx, so it works with Varnick not running) are rows of `panelHeight`'s session-list branch (a header per Mac and a row each) and sit between this Mac's tabs and Recent in `move`, `openSelected` and `sessionSelection`. A session this Mac has a pane for is left out of them. Opening one (↩, or ↩ on a Recent or search row whose session is open there) is `openPeerSession`: the pane opens on the card, never attached, whoever is in control and with or without a client there (`opensOnCard`, asked of the host through `settle`, like a restored pane, and starting nothing). Control moves only when the user presses Take over; the one case that attaches is a label that already names this Mac. The pane keeps `opensOnCard` for its life, so a session found gone later (the card's check, Retry) closes it (`sessionGone`) instead of starting it again. Explicitly resuming an ended session is a different path and starts and attaches.
- A peer's pane never follows /clear and /resume through its own hook file (it is written on the host, so `checkConversation` is off for `isOnPeer`). It takes the conversation from `status` (`PeerFollow.fill`: the hook's last report, else the saved record), polled by `LauncherModel.followPeerSessions` while any pane is on a peer and when the panel opens, never on the main actor. The record changes without `onConversationChange`: the host's own pane puts the conversation left behind in the host's Recent. The title is the host pane's, sent only while the host is in control and applied only where this pane has no client.
- A session gone on its host is started again only into the pane the host restored for it and hasn't started (`start` with `resume`, `hostResume`), labelled for the Mac that asked, which then attaches with take. A host with no such pane answers `ended` and the peer's pane closes: that session was ended there on purpose, and nothing is ever started behind the user's back. Resuming an ended session is an explicit action (Recent, search), a different request (`resume`). A restored pane, Reconnect and Retry, and the pane's own check of a lost or unreachable card all resume a session found gone; a card showing another Mac in control closes instead. `running` and `closing` answers are looked at again, never taken as success: take control only if the label names this Mac.
- Tailscale SSH (a Mac's own Tailscale serving SSH) reports every remote command as exit 0, so an ssh exit status says nothing about a peer's answer. Read the reply JSON (`PeerClient.exchange` does, whatever the status), and never take `status == 0` from `SSHRunner` for success; `Tailscale.status`'s check is of the local CLI, which is fine. A check made by hand echoes `$?` on the remote side, inside the command.
- A session's turn travels as text (`PeerSessionStatus.turnWord`, key `turn`) and `Turn` is read from it, so a word this build doesn't know is nil and the card shows "Turn not known" instead of the reply failing; a strict decode would fail every `status` ask to that host. The rest is in ADR 0010. A new optional field in `PeerSessionStatus` or `PeerOpenSession` must also be added to its explicit `CodingKeys`, or it never reaches the wire (the compiler doesn't say).
- A pane's work links travel in `PeerSessionStatus.work` and `PeerOpenSession.work` (`PeerWork`, protocol 18, ADR 0020), beside the turn and with explicit `CodingKeys` like it. A link names its repository as `group/name` (`PeerWork.project(of:)`), never a path, and a link from another host is a `WorkSession` with `foreign` set: its `repo` is compared with `PeerWork.project(of: source.project)` in `WorkSession.resolved(for:)`, never with `WorkRepo.key`, so a new place that compares links with a project must resolve them first or a peer's chips match nothing (and a local session's must not be resolved, or a path that ends in the same two folders would match another project's). Keep `PeerWork.maxLinks` and `now` to options only: the reply is read for every open session on every ask. `PeerRelay` strips `work` for a device. A link makes an option Building only while its pane is live (`SessionBoard.Card.isLive`: open here, or listed open by its host) and the option isn't shipped, rejected or abandoned. A pane on a peer drops its live records when the host answers not running or doesn't answer (`ClaudeSession.dropHostLive`) and keeps the history, so a host that stops listing it takes the Building with it. A link in a saved record with a `host` is a `group/name` one: never feed it to anything that expects a folder. Mixed versions are not supported by the protocol, as for every shape change: the mismatched peer is refused before any reply is read.
- `work_history` (`HistorySync.archiveSchema`, ADR 0020) is in the archive half of the search database, created by `prepare` with `IF NOT EXISTS` and changed by no migration, so it is safe on an existing database and on one an older Varnick made (that Varnick ignores it). It is written by `HistorySync.recordWork` when a pane on this Mac closes (a detached utility task: opens its own connection with the 5 s busy timeout, never from the main actor's thread) and by `syncWork`, which copies the saved records' links on each sync, for this Mac's own records and for those hosted by a headless host (told apart by the saved peer's `info.headless`, the relay-only flag in its hello; its `host` column holds the peer id and its `repo` is `group/name`), never a paired Mac's, which keeps its own; both upsert, so a row only grows (origin, subagent types as a union, last-used), and nothing deletes it. `Varnick --work-history` refuses to run without `VARNICK_DB`. A new reader must not assume the table exists in a database an older build made, as `tabNames` does for `session_names`.
- A peer's session rows (`rows`) and Recent (`recent`) are served by the relay alone, `rows` from the search database read-only (the path is `VARNICK_DB`, else the file the running Varnick writes at launch, `PeerSearchDatabase`; the relay isn't started like Varnick) and `recent` from `sessions.json`. `rows` carries each session's replies beside its prompts (`PeerSessionRow.replies`, nil for a row its Mac hasn't read with them), and a Mac answers it only while no session row of its own has NULL `replies` (`peerRows`): such rows, written by a build that kept none, are read again at the first sync after the upgrade, and every sync ends by giving the rows it couldn't reach (an unreadable transcript, an unlisted folder) empty replies so they never block `rows` for good. Without that, a Mac asking in the minute after the other upgraded would get rows without replies, then ask only for later changes, and get the replies at its next launch. Until then it answers with a failure, and the asker keeps its rows and asks again at its next sync. `rows` limits itself to those changed since a stamp and always lists every id, which is how a session that is gone leaves the other Mac. `HistorySync.pullPeers` writes them to `peer_sessions` in the sync, reading each Mac in full once per launch, and again when the ids it lists have no rows here (a session whose folder came back, which no stamp of changes shows); a Mac that doesn't answer keeps its rows (the failure is logged), and the rows of a Mac no longer paired are deleted in the same pass, which removing it starts at once. The sync waits for the pull, so keep its timeout short (`peerPullTimeout`). A search row carries its Mac in `favorites.host`, written by `refreshSearch` from the entry that won, so nothing decides it a second time.
- A peer's pages (`pages`) are served by the relay alone, from the Mac's own archive tables read-only (never the `peer_*` ones), in pages of about 2 MB ordered by (`changed`, key), with a cursor of both, since rows written in one sync share `changed`. The cursor's key is a digest, which the relay finds again among the rows of that stamp (not found: the stamp repeats, never skips), so no URL, which can carry sign-in parameters, is saved in `meta` or sent in a request. A reply also says whether more remain and how many pages and search terms the archive holds. `HistorySync.pullPeers` sends it in the same pass as `rows`, one reply per Mac per sync, from the cursor kept for that Mac (`PagesRead`, in `meta` under `peer_pages_read:<id>`, written in the transaction that stores the rows, so a relaunch reads nothing again). A full read, from zero, happens only when this Mac holds no rows from that Mac, or when an ask that says nothing more remains finds fewer pages or search terms kept here than the reply's counts say the Mac holds (a database replaced there, which no cursor shows); the cursor is then reset and the read comes at the next sync. The counts stand in for `rows`' list of ids, since a large archive's URL list is about 1.8 MB per ask. Pulled rows are only inserted or updated, as sent and none skipped (or the counts could never match), and the relay answers its rows and counts from one read transaction. A Mac's pulled rows are never swept: a page gone from its archive stays here, as history is never deleted, so more rows here than its counts say is not a reason to read again. A Mac that doesn't answer keeps its rows and cursor. A Mac that is no longer paired loses its pages and its cursor in the same transaction as its sessions.
- The peers' Recent (`LauncherModel.allRecent`, rebuilt by `rebuildRecent` when its inputs change, and in `saveSessions`) is merged from the last answer of each Mac and this Mac's own: one entry per conversation, records with a host aren't checked for a local transcript (`addRecent`, the restore filter), and a peer's entry takes the conversation's own id as its record id so a row keeps its identity between fetches.
- Resuming an ended session on a peer (Recent or search, `resumeOnPeer`) is the `resume` request, never `start` with `resume`: it starts `claude --resume` under a new session id the asking pane chose, labelled for the asker, in a background tab (`hostResumeConversation`). The pane asks for it only with `resumesOnPeer`, which the model sets for that click and Retry on a failed one sets again, and which is cleared as soon as the host answers; nothing restored or retried by itself sets it, so the automatic path above keeps its guarantee. A frozen view of a session another Mac controls that closes isn't put in Recent (`isViewOfSessionControlledElsewhere`). The host refuses a conversation it has open in a running session; the asker takes that one over instead, from the open sessions it already lists.
- The relay answers every request but hello only to a Mac this one lists (`PeerList.lists(by)`, the saved list read without writing it, checked before anything else), or to a listed device (`PeerHost.listsDevice`, ADR 0011), since anyone who can ssh in could otherwise read prompts, screens and sessions or attach. A device is refused `rows` and `pages`, the search sync's, which hold the user's prompts and pages for the paired Macs alone; it gets the same `unlisted` reply. The running Varnick takes a device's `start`, `resume` and `end` as a peer's, reading the device file fresh (`PeerManager.handle`), and puts its id in the labels as a peer's. `PeerManager.send` and `attachCommand` fill in `by`. The answer to an unlisted Mac says so (`PeerReply.unlisted`), and a Mac that gets it is `.removedThisMac`: it is read no more, its `peer_sessions` rows and Recent entries go, and only a hello from it (it added this Mac again) brings it back.
- A host pane whose client exits while the session runs and is labelled for the host (or nobody) attaches again (`ClientExit.dropped`, with the reattach limit), never ends the session: a take-over that raced another could otherwise kill work. A pane started for a peer runs `checkControlAfterAttach` too, so its starting client lets go once the label names the peer, and a failed first attach by the peer can't leave two keyboards.
- The device file (ADR 0011) is `devices.json` in the support folder: `DeviceList` in `Devices.swift` is its one reader and writer, and holds its rules. On a Mac only the running Varnick writes it (`PeerManager.addDevice`, `removeDevice`; never the relay); on a headless host `varnick-peer device add` and `device remove` do, under the exclusive state lock. Only the user's own untagged nodes may be listed (`PeerDevice.mayBeListed`, used by both add paths). Ids compare through `Zmx.sameID`, never with `==`. A device is never contacted and never sends a hello.
- `status` and `sessions` replies carry `controlName`, filled in by the shared relay (`PeerControllerNames` says how it names a controller). A device is never told another controller's id: the relay leaves out `control` unless it names the asking device (`PeerRelay.hiding`), so the page tells who is in control from `controlName`. A Mac or card names its controller from its own peers and devices first and the reply's name second (`PeerManager.name(of:reported:)`), saying "another Mac" only when nobody does. A change to a reply shape bumps the protocol: both Macs and the headless host run one commit.
- Any request but hello to a peer goes through `PeerManager.send` or `attachCommand`, which refuse a peer found to speak another protocol version, except `upgrade` and `restart`, which `PeerClient.exchange` sends and `verdict` reads across versions.
- A paired Mac's session becomes an ended card (`LauncherModel.endRememberedSessions`) only when all of these hold: this Mac listed it open and remembered it (`remembered`, saved as `State.remembered`, by pane id), that Mac's latest `sessions` answer succeeded without it, and its Recent, asked after the session was last listed (`peerRecentSentAt`: the time the ask was sent, an unchanged reply counts), has an entry whose `session` is the pane's name (`PeerRecentSession.session`, protocol 16: the relay fills it from the record's id, and a conversation /clear left behind has a fresh id that matches nothing). A session merely missing ends nothing, since a restarted Mac restores its panes and closes none, and a Mac that doesn't answer ends nothing. Never match by conversation (a /clear moves it), and never read an end from a Recent asked before the last listing, or an old entry of a pane id resumed since would end it. Recent is asked of a Mac that just stopped listing a session, alone, while that session was last listed within a minute (`recentWatchWindow`), and of every Mac at most every 5 s when the board opens, never of every Mac every 5 s: the headless host's Recent reads each ended session's whole transcript for its title. The remembered list is forgotten when a pane here takes the id, when marked done, when the Mac is unpaired and 30 days after the last listing, in `rebuildRecent`; and a session started and ended there between two listings is never on the board.

**Phone page** (`PhonePage/`; ADR 0011)
- Bun is for the page only, never the relay. `PhonePage/` takes no npm package, and `bun test` in it checks the pure decisions (`checks.ts`, `home.ts`, `hosts.ts`, `relay.ts`, `terminal.ts`, `launch.ts`, `watch.ts`, `page/rules.js`, `page/newrules.js`, `page/liverules.js`).
- Every list and action is a relay request with the device's id as `by`, spawned with an argument list (`relay.ts`), never through a shell. `by` comes from the server alone (whois on `X-Forwarded-For`, then the node, then `devices.json`) and `buildRequest` writes it last, so nothing a client sends can replace it.
- whois's `Node` has no `ShareeNode` (`status --json`'s peers do): a node shared in shows as `Sharer` non-zero or `Hostinfo.ShareeNode` (`parseWhois`, with a fixture from a real answer). The rule is `PeerDevice.mayBeListed` in `checks.ts` too, so change both together.
- User ids stay text (`parseTailnetJSON`): a 17-digit id isn't exact in a double.
- On a socket serve sends `Host: localhost` and the browser's host only in `X-Forwarded-Host`, so the Host check reads that there and `Host` on loopback.
- `/api/*` answers only the page itself (`checkFetchSite`), because another site open on the phone can send a `no-cors` read with the phone's identity, and a read runs a relay. Relay runs and whois spawns are capped, per device too. Mutations and websocket upgrades need the page's `Origin` (`gateMutation`, `gateUpgrade`). Send no `Access-Control-*` header, ever.
- Bun can't set a socket's mode: the socket's folder must be the user's and 0700, and the socket is chmodded 0600 once bound.
- Which hosts can serve a socket, and why Macs whose Tailscale can't serve a socket listen on loopback: the option's Spike › Results (one app's mount looks right in `serve status` and still answers 502).
- `PROTOCOL_VERSION` in `server.ts` must equal `PeerProtocol.version`: a protocol bump changes both, or the server refuses to start.
- A Mac's server runs in a zmx session named `varnick-phone-page`, never a pane's name (`Zmx.attachCommand(named:)` refuses one): the launch sweep and the relay's `sessions` read a pane id from a name, so a pane's name would get the server killed at the next launch.
- It is started through `PtyClient`, never `zmx run`, which crashes 0.8.1's daemon, and waited for and detached as a headless `start` is.
- Only the setting ends it: not Quit, not Keep sessions running (`stopAppServers` looks at panes), not the sweep. A server that exits by itself (Tailscale not up at login, a protocol mismatch) stays down, and Settings offers Start again with the log's last lines.
- Its files are the launch snapshot's clone of the copy `make build` puts at `.build/release/PhonePage`, in `.build/snapshots/page-<digest>` (`LaunchSnapshot.serverInstall`; without a snapshot, the resource folder's `PhonePage`), so an edit in a checkout reaches a running server only through a build and a restart. The folder is named by the digest, not by the launch, and the session's labels name it (`varnick-page-place`): the server outlives Varnick, and a launch that finds the same digest in the same place leaves it running, so its files must stay. A server without that label (started before snapshots, from the build folder) isn't current and is replaced once. A page folder is removed only after a reconcile, and never the one the running session's label names, so a server that isn't replaced (Bun missing, `stop()` failing, no page in the build) keeps its files.
- Varnick publishes the page's port itself (`PhonePagePublisher`), by the rules in ADR 0011's note: one mount, no funnel, fail closed, the user's own mount left alone. The app's CLI needs `TERM`, and is always loopback whatever its `--help` says, since the Tailscale app's mount answered 502 for every socket when tested (1.102.3). The target follows the running session's `varnick-page-mode` label, not what the CLI can do now. Never run `serve` as root anywhere but the Use a socket button, and keep every read as the user (the rest of the refused-socket rules are in ADR 0011's note). `PhonePagePublisher.swift` takes the CLI as a closure and the port as an argument, and imports nothing of the app's, like `PhonePage.swift`, so a check can run it on a throwaway port (the kit's `ticket11-check.sh`).
- Home's "Other hosts" are the relay's `hosts` reply (name and address of each listed peer, never an id: `PeerHostEntry` has none; from the saved list on a Mac and `state/peers.json` on a headless host, read and never written) read by `hosts.ts` against `tailscale status --json`'s nodes. An address that isn't a node of the tailnet (`alex@check`, an IP, one with a port) gets no link, and a link only says where a host's page would be: the page can't know whether it is published, and the browser's own error is the answer. `hosts` is a request like the rest, so adding it moved the protocol to 14.
- On a headless host the server is the systemd user unit `varnick-phone-page.service`, written only by `scripts/install-peer.sh <host> --page`, which is also the only thing that enables, restarts or stops it by hand (systemd starts it at boot and restarts it on failure). It needs `KillMode=process`: a session the page starts is created by the relay the server spawned, so its zmx daemon is in the unit's cgroup, and systemd's default mode would end every session at a stop or restart. Linger must be on for the user, or the unit stops with the last login (the installer warns). Like Settings above, the installer follows ADR 0011's note (`page_publish` once the page answers, `page_unpublish` for `--no-page` and `--uninstall`). Funnel that is anything but off, unreadable included, also disables and stops the unit (a stop alone would let a reboot bring it back), and a clean run enables it again.
- `PhonePage.swift` and `PhonePageRunner.swift` import nothing of the app's: a scratch package that links `Packages/VarnickPeer` compiles them for a check against real zmx and Bun.

**The terminal** (`PhonePage/`: `bridge.ts`, `terminal.ts`, `page/session.js`; ADR 0011)
- One websocket per open terminal, at `/ws/terminal`, carrying bytes to the relay's `attach` run in Bun's pseudo-terminal. Its upgrade is checked before anything is spawned (`gateUpgrade`), and a device has at most three terminals open (429 past that).
- `take` is sent only right after a press (Take over, or the Start or Resume that made the session), and never on a reconnect: the first message's `take` counts only as the literal `true`, and the relay refuses an attach without it for a session the device doesn't control.
- Every client re-checks control, as the Mac clients do (`checkControlAfterAttach`, above): about a second after the attach goes live the server asks `status` once, and if the label isn't the device's it closes the pty and sends 4001 with the controller (`recheckControl`). Two takes landing between the relay's label check and its `execve` would otherwise leave two keyboards live. Input is dropped until the screen is live.
- Closing the websocket closes the pty, which ends only the phone's zmx client: the session keeps its label, and the phone stays in control. Never release on close: Android drops a backgrounded tab all the time.
- Every reconnect asks `status` first (`/api/session`): labelled for the device attaches without take, anyone else shows the session view, gone says "Session ended". A client that exits by itself is told from "taken" and "ended" by `status`, never by its exit code (4001 taken, with the controller as a JSON field of the reason; 4002 ended; 4003 dropped; 4004 refused, with the relay's error as the reason). The tries start over only after a connection that lived 10 s.
- A refused attach prints one reply line and exits instead of becoming zmx. Output that starts with `{` is held for up to a second; a child that exits meanwhile with a reply line closes the websocket with its error, and the line never reaches the terminal. Anything else is released at once.
- What was typed or shown stays out of the logs: opens, closes, codes and grids only. The page's CSP allows inline styles, because xterm.js's renderer writes `<style>` elements; scripts stay `'self'`, and `connect-src` names the page's `wss://` address.
- Typing goes straight into xterm through the phone's own keyboard: there is no compose box, Paste, Enter or ^C key (the keyboard has Enter, a long press pastes, and Ctrl then `c` is ^C). The key bar is one row of eight, `Esc Tab ⇧Tab ↑ ↓ ← → Ctrl`, that must stay on one line down to 360px (`#keys` is `flex-wrap: nowrap`, equal `flex: 1 1 0` buttons, `min-width: 0`, 40px tall): a ninth key or a longer label breaks that, so check at 360px. A key press `preventDefault`s `pointerdown` so xterm's input keeps focus and the keyboard stays up; a tap on the terminal calls `term.focus()` (`#term`'s click), which is what raises the keyboard. The sticky Ctrl turns only a single typed character into its control code (`ctrlCode`), so a multi-character paste passes through untouched.
- xterm.js is vendored in `PhonePage/vendor/` at pinned versions, with `VERSIONS` holding each file's SHA-256 and the packages' registry integrity (`bun test` checks the digests). Fetch new versions on a headless host, never on a Mac inside a Claude session, and serve them from `vendor/`, not `node_modules`.
- The keyboard never takes rows from the grid (`refit` in `page/session.js`): a resize each time it came and went had the session redraw at the new height while xterm.js moved lines in and out of its scrollback, and the screen garbled. The grid keeps its rows and `#term` shows its bottom ones. `#term` is `overflow: clip`, never `hidden`: Chrome on Android scrolls a hidden overflow to show xterm.js's input when the keyboard comes up, and nothing scrolls it back.
- xterm.js 6 has no touch scrolling, so `page/session.js` turns a swipe into `scrollLines` in a normal buffer and into wheel events when the program takes the mouse or the alternate screen (Claude Code full screen), which xterm.js reports as the program asked. The compose box was removed on 2026-10-09 at the user's choice, though typing into xterm.js with Gboard was seen to lose backspaces and autocorrect and dictation needs a native field: if either bites, a native field is what brings them back.

**Starting and resuming on the phone** (`PhonePage/`: `launch.ts`, `page/new.js`, `page/newrules.js`, `page/dom.js`; ADR 0011)
- The browser sends only `{folder, agent, prompt}` to `/api/start` and `{conversation}` to `/api/resume`; `parseStartBody` and `parseResumeBody` read nothing else. The server picks the session id (`crypto.randomUUID()`), sets `by`, and never sends `skipPermissions`, so the host's own setting applies. The prompt, folder, agent and conversation reach the relay only as JSON fields of its one base64 argument.
- A folder must be one of the host's `projects` (for `/api/agents` too) and an agent one of that folder's `agents`, asked fresh each time. A conversation must be one the host's `recent` offers, and its folder and agent are the Recent row's, never the body's. A conversation a running session has open (its `conversation`, else its own id, as `conversation(of:)` does on a Mac) is answered with 409 and that session's row, and `resume` isn't sent; when the host refuses all the same, in a race, `sessions` is read again and the row returned the same way. The page offers Take over on that row.
- A start or resume that fails or times out asks `status` for the session it named before it answers: a running session is a success, or a second tap would make a duplicate.
- The prompt is never logged and never echoed in a reply, a refusal included, and never in `document.title` (browser history, Chrome Sync).
- The prompt is limited as `JSON.stringify` writes it (`promptLimitBytes`), since a newline or a quote costs two bytes in the request, which then goes base64 into one argument. Linux takes 131,072 bytes for one argument; `Relay.ask` refuses a request over `argumentLimit` before it spawns anything.
- Claude's parser reads the first operand as a subcommand even after `--`, so a prompt that is exactly `doctor`, `update`, `mcp` and so on would run that command. `ClaudeCommand.operand` gives a prompt with no whitespace a trailing space, which no command name equals. Keep both (`--` and the space) when changing `arguments`.
- `parseStartBody` still refuses a prompt that starts with a dash, for a host that doesn't put `--` before the prompt yet (before `ClaudeCommand.operand`). Remove the check once every host has that change.
- A Mac host takes up to 25 s to answer `start` and `resume`: the relay is given `launchTimeoutMs` for them, and the request `server.timeout`, past Bun's 30 s idle limit.
- `projects`' `lastUsed` is Foundation's `Date`: seconds since 2001-01-01. `shapeProjects` converts it, and sorts newest first itself.
- The page sets `take` for the terminal only after Start or Resume succeeded (`enterSession` names the one session to take, once) or after a Take over press, including the one on a refused resume's row. A reload, a revisit and every reconnect attach without it. A resume under way is kept per conversation, not per row, since the home reloads while the host answers. New session's last project and agent, and the last lists, are in localStorage per origin (so per host), and the page works without it.

**The live screen on the phone** (`PhonePage/`: `watcher.ts`, `watch.ts`, `page/live.js`, `page/liverules.js`, `page/session.js`; ADR 0008, ADR 0011)
- The server runs the relay's `watch` on pipes, never a pseudo-terminal: a reader never sends input, Init or a size, and a pty would make the relay's client a terminal. Nothing is ever written to the relay's input, the first message names the session and nothing else (`take`, `by` and a grid in it are ignored), and any later message from the page closes the socket with 4400. A watch needs the same caller, Host and Origin checks as the terminal (`gateUpgrade`, before anything is spawned) and is sent only to a listed device.
- The relay's input is a pipe held open for the websocket's whole life: closing it is how the relay learns its viewer has gone, which is also what removes its `readers/` file and keeps the Macs' client counts right. When the websocket closes the server closes that input, terminates the relay after 1 s and kills it after 2 s (as `SSHRunner.stream`'s cancel does). The slot (3 a device, 8 in all; `Admission` in `relay.ts`, shared with the terminal) comes back when the relay is gone, not when the socket closes. Never give the relay `stdin: "ignore"`: it would see its viewer gone at once.
- The channel ending never means the session ended. Take over, a release, the session ending and the relay failing all close it the same way, so the page asks `status` after every close (the terminal's rule) and shows whatever that says: this view again with the new controller, the terminal, or "Session ended". A channel that ran for 10 s asks at once; one that failed at once backs off 1, 2, 5, 10, then 30 s.
- A slow phone mustn't grow the server: only the newest frame not yet sent waits (`Outbox`), and a frame goes only while the socket holds under 256 KB unsent, so a stalled connection gets the latest screen when it drains and the rest are dropped (the close line in the log counts them). `Bun.serve` has one `backpressureLimit` (4 MB) for every websocket and closes a socket whose unsent bytes pass it, and JSON writes each escape character as six bytes: so a screen over `longestScreen` (1 MB of text) is skipped as it arrives, a message over `longestMessage` (3 MB) is replaced by `{tooLarge: true}`, and the page says "Screen too large to show" in the bar and goes on. Keep `longestMessage` plus `sendHighWater` under the limit (`watch.test.ts` checks it against a real server). The relay's pipe is read at all times, whatever the socket does. Keep the logs to opens, closes, codes and counts: never a screen.
- The channel is open only while the page is visible. A hidden page closes it (and the host's reader goes with it), a visible one opens it again, and the first frame is then a fresh snapshot. A page that is hidden still shows its last frame, but returning says "Loading screen…" until a fresh one arrives, since the old one is old.
- Each frame is drawn from scratch (`ESC c` through xterm's parser, which `term.reset()` isn't: it would run before a frame still waiting to be parsed) at the grid it came with, in a read-only xterm.js with no scrollback and `pointer-events: none`, never focused. A grid of `0 0`, or past 400 columns or 200 rows, is fitted to the phone instead (`pageGrid` on the server reads the page's own `gridLimits`, so there is one set of limits). The scale is `fitScale` of the width measured from `.xterm-screen`, never above 1. Pinch to zoom is the browser's own: don't put `user-scalable=no` or `maximum-scale` in the viewport meta.
- `Bun.serve` takes one websocket handler for both channels: each socket's `data.kind` says which one it is (`socketHandlers` in `server.ts`), so a third channel adds a kind there.

**Listening and spoken requests** (`Listening.swift`, `Speaking.swift`, `SpokenText.swift`, `SpokenRequests.swift`; ADR 0015)
- The system audio tap must keep excluding Varnick's own process (`ownProcessObject`); without it the wake sound and the answer come back as `[system]` lines. It is looked up when each capture starts, and a failed lookup only logs.
- Varnick's speech must come from this process, so `Speaker` renders it with the synthesizer and plays the buffers on its own engine. Moving it back to `AVSpeechSynthesizer.speak` alone (which only the no-audio fallback does) may play it from a system process the tap does not exclude.
- `SpeechSpans` must be open from before the first sound to after the last, plus its tail: Listening drops a mic result whose audio began inside it, by audio time (`AudioClock`: time zero is re-anchored at every buffer, so mic drift and gaps don't move recent audio), never by when the result arrives, since finals come 1 to 2 s late. A path that speaks without `Speaker.speak`, or ends the span early, lets Varnick wake itself.
- The wake phrase is "hey" or "hay" within the first three words, then one word that is the whole of `SpokenText.namePattern` (`^[vw][ao][rl]?[nld][iea](c|ck|k|g)$`: the spellings the transcriber was seen to write, varnik most of all). It must never wake on a fragment of the name alone, so "nick", "Hey Nick", Warwick, Barney, Varun and varnish stay asleep; a looser rule (a bare "nick", or a prefix in place of the whole word) woke on near-miss phrases in the measurement. The pattern was measured with synthesized speech only; real-voice recordings are pending, and taking "a" for "hey" ("A varnick" was a common transcription) is a candidate left out until they are in. The contextual strings given to the mic's analyzer (`Varnick`, `Hey Varnick`, `Jev`, `TypeSafe`) were measured to change no transcript on macOS 26.5.1, so adding to them does not fix a spelling.
- Only final mic results wake it, only while Listening is on and Hey Varnick is on. Mic results while a request is decided, read or spoken never wake it or join a request. Turning either off, or stopping Listening, cancels the request and the voice.
- The panel's search and the spoken search share one ranking, `RelevanceSearch` (ADR 0017): `keyword`, `withMeaning`, `judge(for:)`, `filtered` and `fuse`, with the constants. The module sets no UI state, waits for nothing and logs nothing; the panel keeps its debounce, the judge's `pause`, the statuses, the selection and its log lines, and a spoken request calls the passes back to back. The panel's statuses are set synchronously in `runSearch` (`--search` waits on them), so a pass moved behind an `await` there changes what `--search` and `--search-eval` see. The "no results for" log lines print the query and stay in the panel: a spoken request never reaches them. A change to a pass, the fusion, the threshold or the choice of judge is one change in the module and reaches both; check the panel with `--search-eval` and `--search` before and after (off and On this Mac must match exactly, TypeSafe within its run-to-run noise).
- A spoken request runs the relevance filter wherever Settings › Search says, unless it reads sessions only (sessions are never judged): `SpokenPipeline.prepare` calls `judge(for:)` on the search words, so the rule "TypeSafe only with the filter on TypeSafe and a key; On this Mac never falls back to TypeSafe" has one home. On TypeSafe that sends the search words and the title, site and own description of the first 20 pages (`Reranker`), new since ADR 0016; `docs/privacy-and-security.md` and the Settings text say so, and anything more in that body is a privacy change needing the same. When the filter judged any page of the chosen kind relevant, only those are read (`SpokenText.rows`, `relevant:`), so a page wrongly judged irrelevant is not heard; a failed or unavailable judge leaves the fused order. The timing line and `--ask` name who filtered.
- The decide step asks TypeSafe's Jev (`SpokenRouter`, ADR 0016) only when `activeRelevanceFilter == .typesafe` and a key is saved: a key alone, the filter On this Mac or off sends nothing, and Text generation decides, as on any failure, no source in the reply or after 1.5 s. The body carries the request text and the two fixed questions, never a title, folder or project name, search word or row. With Point at the screen on (`Settings.screenPointingOn`) the questions are `SpokenRouter.questions(screen: true)`: a fourth source, `screen`, and a fifth action, `point`, as measured (arm J4p of the screen-pointing eval, agent-lab 20fb286; the old name replaced by "Varnick" in them and in the picker's context, which moved no decision rate, so the thresholds stand; Gemma's G4 prompt is `SpokenText.decidePrompt(for:screen:)`), and off they are the originals the thresholds were measured on (with the old name; "Varnick" in its place changed none of them). The `point` action is what keeps a screen request from reading as "other" and being refused, so it stays when the questions are edited; off-topic is read before the source. The session folder names (`sessionFolderNames`) are compared with the request in `SpokenText.plan` and stay in this process. Jev's "other" (0.5 or more) is answered with a fixed line and no search or Text generation. That body is the decide step's alone; the filter's call is separate (above). Anything added to the request body is a privacy change: it needs the ADR, `docs/privacy-and-security.md` amended and the Settings text changed. The model is pinned (`jev-latest` moves); changing it or the questions changes the thresholds' meaning (`SpokenRouter.offTopicFrom`, `alsoSessionsFrom`), which were measured on made-up requests.
- `SpokenPipeline.prepare` (decide, search, filter) runs while a request is still being collected, and `respond` and the speech wait for the hold to end (ADR 0017 has what a discarded partial request sends). `SpokenRequests.speculate` keys the run by the exact request text and cancels it on any change; `cancel()` must cancel the run as well as `working`, which does not cancel the task it awaits. After an `await` that catches errors, `prepare` calls `try Task.checkCancellation()`: a cancelled local generation returns what it had instead of throwing, and a failure while cancelled must not rest a server. What `prepare` can still write is harmless: a server Check recorded in `ModelServerState`, `store.refreshIfChanged()`, and resting a server on a real failure. The timing line's decide, search and filter now overlap the hold; `waited` is what the end of the hold still waited for. `--ask --restart-after <seconds>` exercises the cancel.
- The request, the search words, the rows and the answer are never logged (the answer is in the transcript by design). A failure logs its step and the error's kind (`Error.logKind`, never `localizedDescription` or the error itself), and the timing line logs durations, places and kinds: who decided (Jev, or where Text generation ran and why Jev was not used), where the meaning pass ran, who filtered (or off, sessions only, or the failure's kind), the render and the first sound.

**Pointing at the screen** (`ScreenReader.swift`, `ScreenElements.swift`, `ScreenPicker.swift`, `ScreenText.swift`, `ArrowOverlay.swift`, `SpokenPipeline.lookAtScreen`; ADR 0019, 0021)
- The Accessibility read runs in Varnick's own process under Varnick's own grant, never through a helper, a script, bigarrow or a pane. macOS attributes every pane process to Varnick, zmx-hosted ones included (tccd's log, 2026-10-09), so Varnick's grants reach every pane, and a grant to zmx or a helper is never consulted (panes-share-launchys-permissions). `docs/privacy-and-security.md` says so in plain words. Turning the switch off does not revoke the grant; only removing Varnick under Privacy & Security › Accessibility does. Varnick asks macOS for Accessibility and for Screen Recording only from the Grant buttons in Settings (for Accessibility `ScreenReader.askForAccess`, in order: `AXIsProcessTrustedWithOptions` with the prompt, the pane, and with Varnick still not trusted a second later Varnick selected in Finder; for Screen Recording `ScreenText.askForAccess`, in order: `CGRequestScreenCaptureAccess`, one `SCShareableContent` call, the pane, and with the grant still missing Varnick selected in Finder; macOS answers the requests silently after the first time and Varnick then never reaches the list, so both end with Finder showing the app, or outside one the binary, to drag in or pick with +, through `PermissionGrant`; Settings' hint says so); everything else only checks (`AXIsProcessTrusted`, `CGPreflightScreenCaptureAccess`), and `ScreenText.recognise` is called only after `hasAccess` is true, since ScreenCaptureKit's shareable-content call can prompt by itself. Screen Recording applies only to a process that started after it was switched on and preflight can't show the difference, so once Grant has been pressed Settings offers Restart Varnick (`LauncherModel.askRestart`: the status menu's confirmation, `restart.sh`, no build) for as long as the row says Needs Screen Recording. Screen Recording is the same Varnick-only grant, and the capture runs only in this process, never from a pane (though any pane inherits the grant and could capture the screen itself). While builds are signed ad hoc a rebuild may stop either grant applying (unverified).
- The tree read is the focused window only (not other windows, not the menu bar), depth first so the elements are in tree order, through layout areas and the like (they are only left out of the list; a scroll bar is not entered), off the main actor in a detached task within named limits (`ScreenReader.budget`, `maxNodes`, `maxDepth`, `callTimeout`): a hung app costs the budget, and the pointer step after the walk is skipped once the budget is spent. Nothing in a view update calls it. Cancelling a speculative run does not stop a read already under way (a detached task ignores it). The frame re-read before the arrow is drawn is one call, also off the main actor. `AXManualAccessibility` is set only for an app that carries Electron's framework, never for Chrome.
- Varnick's own panel is read first, like any window (`ScreenReader.panel()`, `SpokenPipeline.lookAtScreen`; spoken-requests-cant-see-the-screen, 05), under the same TypeSafe gate and no more of its own. There is no state registry and no local matching: its labels go to the same Jev `target` and `present` call with `ScreenReader.panelTitle` ("Varnick", since the panel's own title is empty) as the window's title, so its session, project and page names are sent as any window's labels are (the user's principle of 2026-10-09 in ADR 0016, 0017 and 0019: choosing TypeSafe is consent to send what a feature needs; On this Mac is the privacy setting). The panel is read only when it is the key window, visible and not wholly covered (`LauncherPanel`, `isKeyWindow`, `occlusionState`); a hidden panel, or a pinned one under other windows, is skipped. `present` under 0.5, or an empty list, reads the app behind it, which is `focusedApplication()` and still skips Varnick's own pid (without that the fall-through would read the panel again): the own-pid skip is gone only from the first read. `ScreenReader.panelFirst` is the one switch for the order (false reads only the app behind, as option 01 did); a request about the app behind costs one more Jev call (about 0.12 s). Never add a text-from-a-picture step for the panel: a terminal pane exposes no text (SwiftTerm's Mac accessibility is an empty stub), and the picture of the app behind is still the only one taken. Reading the panel is an Accessibility request to Varnick's own process, answered by its main thread, so the read must stay in the detached task with the main actor only awaiting it (`ScreenReader.read`, `currentFrame`); anything that makes the main thread wait on that task for its answer would hang. The panel's elements are its SwiftUI views' (tabs, buttons, the pin and static text such as a session row's title, folder and agent, with no row grouping), so a change that renames or removes an accessibility label, or draws a control as an unlabelled shape, changes what can be pointed at. `Varnick --ask --app Varnick` reads the running Varnick (an accessory app, which `application(named:)` accepts only by its whole name and after the regular apps, never this command's own process); `--ask` without `--app` has no panel, so it cannot try the panel-first order. A target in Varnick's own pid is a `.gone` miss at draw time unless `panel()` is still true (`SpokenRequests.answer`, `ScreenReader.isVarnick`): a panel hidden or covered during the hold may still answer for its frames. The timing line adds the panel's read, its element count and whether it pointed or fell through, never a name.
- What an element may hold: it is listed by the eval's rule (a frame centred in the window, a label or a window button, not a splitter, scroll bar, value indicator, column, layout area or scroll arrow), so text and headings are listed and a window's visible text near its controls reaches TypeSafe. Its label is title, description, help and placeholder, and the value only of text and of a control whose value is its state or choice (`ScreenReader.stateRoles`: a switch, checkbox, pop-up, slider, stepper, radio or tab); a cell's or any other role's value may be what a person entered. Never the value of a text field, text area, combo box or search field (`ScreenReader.labelParts` does not ask for it), nothing is read inside one (`Walk.visit` does not descend: a draft's text runs are its children, and the pointer step stops at the outermost field above it), and a secure text field is skipped whole, except that its frame (like every entry's) is kept in `Reading.entryFrames` to drop recognised text locally, never sent. The window is capped at 255 elements (a Choice's limit), the first in tree order.
- The description of an element (`ScreenElement.description`) and the two calls in `ScreenPicker.body` are a contract with the eval: the choice's wording, the `present` yes/no, the order of the elements (written by hand, since a dictionary would shuffle them) and the 0.5 on `present` (`ScreenPicker.pointFrom`) were measured as they are. Changing any is a re-measure, and adding to what is sent (request, window title cut to 80 characters, element descriptions) is a privacy change: the ADR, `docs/privacy-and-security.md` and the Settings text. The markers are "dimmed" and "under the pointer" only; a dialog marker was not in the measured format. Gemma never points, so no element reaches a model server; with no Jev (filter not on TypeSafe, no key, a failure) a screen request ends in a spoken miss.
- The overlay (`ArrowOverlay`) is one panel, nonactivating, never key or main, ignoring the mouse (`ignoresMouseEvents` and a `hitTest` of nil), at `.screenSaver` level so it is over Varnick's `.floating` panel, on every Space and over full-screen apps. It is shown with `orderFrontRegardless`, never `makeKeyAndOrderFront` or an activation: that would move focus, and the panel hides when it loses key. It goes up as soon as the pick is made and its frame re-read (after the hold, never before), ahead of the speech's rendering (about half a second), not just before the sound as option 01 said, and stays until `lingers` (8 s) after the speech ends. The timing line has the re-read, the draw and when it was up. It goes at once on a new request (`collect`), a cancel and the switch off. It does not follow a window that moves.
- The text fallback (`ScreenText.windowText`, called by `SpokenPipeline.lookAtScreen.readText` and by Screen access's `look`; ADR 0021) runs when the tree's `present` is under 0.5 or the window lists nothing, and first when Chrome's web area is empty. In Chrome one Jev call chooses among the toolbar's tree elements and the page's recognised lines (each sent once, the elements giving way past a Choice's 255); only lines whose centre is in the empty web area (`Reading.emptyWebArea`) are kept, so tab titles and the toolbar come only from the tree. It needs Screen Recording and the Jev gate; without the grant, or on a miss of any kind, the tree's answer (and Chrome's sentence) stands.
- The picture: the focused window alone (`desktopIndependentWindow`, so Varnick's own panel and arrow are not in it), chosen by overlap with the Accessibility frame (`bestWindow`: at least half, ties to the active window; no Accessibility window is `no window`, never the largest). It is held in memory until Vision has read it and goes out of scope: nothing writes, logs or sends it, and nothing should pass it beyond `ScreenText.read`. Capture plus recognition race `ScreenText.limit` (2 s) in unstructured tasks, not a task group, since a group would wait for a ScreenCaptureKit call that never returns; a timeout is `skipped (timed out)` and a stalled request must never leave Hey Varnick in `.answering`.
- Recognition is `.accurate` with language correction off (`usesLanguageCorrection`): measured on synthetic windows, the same labels in about two thirds of the time; `.fast` is much quicker but split or dropped short labels ("Notif ications", "Wi-Fi"), and a downscaled picture (1,600 px wide, or 1x) was no faster and lost labels, so the capture stays at the window's own scale. A recognised line is cleaned by `ScreenText.withoutDebris` before it is a candidate (bullets, list numbers and lone symbols at its ends, and one last capital letter after a lowercase word, once), so Jev and the spoken note see the clean words while the arrow rings the original box; `isLabel` is checked on the line as read too, so cleaning never admits a line that was too long. Keep the rule conservative, since a label's own digit, capital, lowercase letter or sign ("Step 2", "Option B", "plan b", "100 %", "Zoom Out −") must survive.
- Kept lines are label-shaped (`maxWords` 6, `maxCharacters` 60, `maxLines` 150, a letter or digit in them) and outside every frame in `Reading.entryFrames` (centre in frame): the walk's text fields, text areas, combo boxes, search fields and secure fields, and the field the app reports as focused when it is one. Those frames were read where the window was, so they are carried to the capture's window with `ScreenGeometry.moved`. A line is "text on screen" and goes through `ScreenPicker` unchanged, so its wording and the 0.5 stay the eval's, but how well Jev picks among recognised lines is unmeasured. Accepted by the user (ADR 0021): a field Varnick can't place is not excluded, so typed text of 6 words or fewer there may reach TypeSafe: Chrome pages, canvas apps, remote desktops and VMs (their fields are not in the tree), fields past the walk's node, depth and time limits, and fields that moved before the capture. Fields the tree finds (native, or a web page's in Safari or an Electron app) and the focused field are dropped. `docs/privacy-and-security.md` say so and the Settings text points to SECURITY.md, which points to it; widening what a line may hold is a privacy change needing both. What goes to TypeSafe on this path is the request, the window title and the lines' words: never the image, a box, a longer line or a tree element twice. A recognised target has no element to read again, so the window's frame is re-read and the box follows a moved window (`ScreenGeometry.moved`); a resized one is `gone`. The timing line adds the capture's and recognition's durations, the recognised and kept counts and the skip kind, never a line; `--ask --app` prints the same.
- Accessibility frames (global, origin at the top left of the main display) become AppKit's (origin at the bottom left of the main display) only in `ScreenGeometry` (which also turns a Vision box, normalised from the image's bottom left, into one: `accessibility(normalised:inWindow:)`); a display left of or above the main one has negative coordinates in both, so a conversion done anywhere else breaks on a second display first.
- The timing line adds the read's duration, the element count, who chose, whether Jev found the thing present and the miss's kind. The request, the window title, the labels and the pick are never logged; `Varnick --ask --app` prints the pick to its terminal.

**Screen access** (`ScreenMCP.swift` for `Varnick --mcp`, `ScreenAccess.swift` for the running Varnick's half, `PeerManager.handle`, `ClaudeSession.launchClaude`; ADR 0023)
- A screen request has no `op`. `PeerManager.handle` tells it apart only by that (`head.op == nil` and a `screen` key), before the peer checks, and a line with an `op` is a peer's whatever else it holds. The relay (`PeerRelay`, `MacPeerHost.forward`) refuses a line without a known `op` and forwards only `start`, `resume`, `end`, `projects` and `agents` (and passes `hello`, `upgrade` and `restart` for the app's part of their answers), which is why no paired Mac or device can click. A change that lets the relay pass an unknown line on, or gives a screen request an `op`, hands them the screen.
- `Varnick --mcp` never reads or acts: it is JSON-RPC lines in and out, and one socket request per `tools/call`. Keep every Accessibility, capture and event call out of `ScreenMCP`. Its standard output is the protocol, so nothing else may print there (`print`, a stray log) and `main.swift` runs it before anything else of the app starts, like `--peer`. It exits when its input ends. It shares with the app only `PeerSocket`, `PeerJSON`, `PeerLink` and the constants it reads from `ScreenAccess` (`clickLead`, `signNote`) and `ArrowOverlay` (`lingers`), all `nonisolated`.
- `--mcp-config` and its JSON go first in `ClaudeCommand.arguments` (`mcpConfig`), before `--settings`: the option takes several values and stops at the next option, so anything put between it and `--settings` would be read as another config. Only `ClaudeSession.launchClaude` passes it (the headless relay never does), for a Claude pane on this Mac with the switch on at that start. It is not stored on the record, unlike the other arguments (CODING_STANDARDS.md names the exception): a restart or a resume reads the switch again, which is how a pane gains the tools. The command is the peer link, so a session's server is the build that was running when the session started; `make run`'s kill pattern matches only the bare binary with no arguments, so a restart doesn't end the server (check this if the pattern changes).
- The request's own version (`ScreenRequest.version`) is not the peer protocol's. Bump it when the request or reply shape changes, and a server from an older launch is told to restart the session. A line whose `screen` is another number is answered before anything else is decoded.
- The switch (`Settings.screenAccess`) is read at every call, after the version and before anything else, so turning it off stops running sessions with no restart (`ScreenAccess.switchedOff` also drops the id tables and the Arrow). A click re-reads it after its one-second lead.
- Ids: `e` for a tree element, `t` for recognised text, replaced by the pane's next `look`, in memory only, dropped when `prune` sees the pane gone. An unknown id is "look first", a control that has gone is "gone: look again". The frame is read again for `point` and `click` (`ScreenReader.currentFrame`), twice for a click: before the arrow, and, after the app is in front, for the click itself (refused as gone when it can't be read, never a stale point). Chrome's Accessibility frames can lag a scroll, so ids from a `look` taken before a scroll may be stale: a session looks again after scrolling.
- Own process: `look` never reads Varnick (`focusedApplication` and `application(named:)` skip its pid, and the panel-first read of Hey Varnick is not used), and an id in Varnick's pid is refused (`ScreenReader.isVarnick`). A click that is posted (a point, a recognised line, a control with no press action) is refused when a visible window of Varnick's own, other than the arrow's panel (`ArrowOverlay.owns`), has its frame over the point (`varnickCovers`, by frame and not by z-order, so a pinned panel under another window still refuses). It is asked on the main actor right before the event is posted with nothing awaited between (`checkedToPost`), and for `at` also early, before the queue. A system-wide Accessibility hit test is not used: the arrow's panel covers the display in Varnick's process while a click's arrow is up, so it would find Varnick every time. A press through Accessibility is not checked, since its element is another app's (ids in Varnick's pid are refused).
- A click that has waited, led or brought its app forward for `staleAfter` (9 s) since its request arrived is dropped, since the relay gave up at 15 s and the session must not be clicked for after it was told no. The switch, the pane (closed, or another Mac in control now) and that age are checked again after the click gets its turn, after its lead and after the app is in front (`frontWait` 1 s, started before the request, and `frontSettle` 150 ms come before the last check, so they cost nothing of what follows it. After it, worst case, a press click takes the page search (1 s `budget`, checked once per step, plus the step in progress: a role, a frame and a parent call of 0.25 s each, so up to 1.75 s), the frame read (1 s), the press check (1 s) and the press (1 s), about 4.75 s: 13.75 s against the relay's 15 s, less the main-actor hop before `arrived` is set. A posted click takes about 2.9 s. Another wait or read after that check must shrink `staleAfter`), and the click fires only if the arrow up is still its own (`ArrowOverlay.generation`): a `point`, a Hey Varnick arrow or a hide during the lead refuses it. A refusal after the click's turn begins says "Nothing was clicked" (`ScreenRefusal.stopped`).
- A click is one at a time across all sessions (`acquire` and `release` hand the turn over without letting a third in), the Arrow first, `clickLead` (1 s), then the app brought forward (`bringForward`: `NSRunningApplication.activate`, Accessibility's `AXFrontmost` and `AXRaise` on the target's window, polled until it is frontmost, never Varnick itself; a point's app is the front-most ordinary window's at it, none for the menu bar, Dock or a menu), then the press or the posted click, then the Arrow 2 s more. An app that does not come forward in a second refuses the click ("Nothing was clicked"). `checkedToPost` then asks again, synchronously with the post, that the app is still in front and owns the front window at the point (`frontWindow`; for a point with no app, that none does), that the arrow up is still this click's, and that Varnick's windows aren't over it. An id inside a web area, in a browser or Electron app, or whose search for a web area was cut short in another app (`ScreenReader.content`) gets a posted click at its centre read again after the app came forward, never an `AXPress`, which on a page can report success and do nothing. The search walks to the top and intersects the frame of every web area and scroll area on the way, so an iframe is held to the top-level page; a centre outside that is refused as gone (a lagging frame under the toolbar or tab strip). In a browser or Electron app a search cut short refuses ("Couldn't tell where the page is: look again", nothing clicked) rather than post unchecked. If the centre has moved more than `arrowFollows` from where the arrow was drawn, the arrow is drawn again there, after a check that it is still this click's. A press has its own 1 s messaging timeout, longer than the walk's 0.25 s, and a timeout is reported as sent, not as a failure. The posted click is a mouse-move, a left-down and a left-up at the HID level after `CGPreflightPostEventAccess`; the pointer stays where it went. Replies say what was done, never that it worked.
- The text step is `ScreenText.windowText`, which `SpokenPipeline.lookAtScreen`'s `readText` also calls; Hey Varnick's behaviour is the measured one, so a change there is a change for both. `look` runs it when the window lists nothing, when Chrome hides its page (only lines in the empty web area) or when `text` is set.
- The log has the tool, the outcome's kind (a refusal's `logKind`), counts and durations; never a label, note, window title, app name or session name. What a session is shown goes to Anthropic, not TypeSafe: adding to what `look` returns is a privacy change for the ADR, `docs/privacy-and-security.md` and the switch's detail.
- A pane's name on the sign is `ClaudeTab.boardTitle(of:)`, the board card's title, cut to 30 characters; the note to 120.
- By hand after a restart (nothing here is covered by a test): `/mcp` in a session restarted with the switch on lists `varnick` with three tools, whether Claude Code trusts a server from `--mcp-config` without asking, which protocol version it asks for, that a posted click needs nothing beyond Accessibility under the hardened runtime, and how the pane's card state follows a takeover.

**Signing** (`Makefile`, `scripts/signing-identity.sh`, `Varnick.entitlements`; `runs-only-from-a-checkout`, option 01)
- `make build` signs Varnick and zmx with one identity chosen once per build by `scripts/signing-identity.sh`: `SIGN_IDENTITY` (the git-ignored `Makefile.local`, or the environment), else the only "Developer ID Application" identity in the keychain, else ad hoc. Once it has chosen an identity, a failure to sign or verify fails the build; it never falls back to ad hoc, which would change the app's identity behind the user's back and void every privacy grant. A named identity absent from the keychain fails too, and two matches fail rather than guess; `SIGN_IDENTITY=-` is how to sign ad hoc on purpose. Two more guards keep an identity that went away (expired, revoked, its intermediate gone, which `find-identity -v` hides) from becoming an ad-hoc build: the script also lists identities without `-v` and fails if a Developer ID Application one is there, and the Makefile refuses to sign ad hoc in a checkout with a `zmx.signer.<hash>` stamp unless `SIGN_IDENTITY` is `-`. A `security` that can't be read fails the build too.
- Nothing tracked names the identity: no team ID, certificate name or hash in a file, doc, comment or commit message. The script shows the name only when stderr is a terminal, and the build log of an upgrade carries only the first 8 characters of the hash: the recipe lines that would echo the full one (`codesign -s <sha1>`) start with `@`; the stamp is `zmx.signer.<first 8 characters>`, never the whole hash, because make prints a failed target's name in its "*** [target] Error" line (a stamp named by the full hash is renamed on the next build, so it forces no re-sign). Keep that on any new line that handles the identity. The script's failures start with `error:`, so the upgrade card shows the reason (`BuildLog.firstError`).
- A signed Varnick has the hardened runtime and the entitlements in `Varnick.entitlements`, with no secure timestamp (only notarization needs it). An entitlement goes in only for a failure seen, with a comment saying which; a signature with the runtime refuses what the entitlement list doesn't name (the microphone first). Ad hoc builds have neither the runtime nor the entitlements, as before.
- zmx is signed in `.build/zmx-fetch`, and moved into place by rename: a running zmx daemon keeps its file, and signing in place would change pages under it. `.build/release/zmx.signer.<8-character hash prefix or adhoc>` records which signature the zmx in place carries, so a new identity re-signs a copy and renames it without fetching again. Same release, same protocol: running sessions survive (unlike a pin bump, ADR 0004). A Mac that never signed zmx and still has no identity leaves it as fetched.
- A failed build puts the last good Varnick back. `make build` clones the binary to `Varnick.good` first when the build stamp is no older than it (a good build), and `mv`s the clone back on any failed step; a success removes it. A build interrupted (^C, a kill) leaves the clone, and the next build moves it back over Varnick before it takes a new one. Without it the failed build would leave the relinked binary, signed only by the linker, which macOS knows as a different app (its grants are gone). A checkout with no good build before has nothing to put back: don't start what such a failure leaves. The test is `! Varnick -nt stamp`, not `stamp -nt Varnick`, since the shell compares whole seconds and the stamp is written within one of the signature.
- The build runs unattended in a zmx session (`UpgradeRunner`): the identity's key must be usable by `codesign` without a prompt, or the build waits on a dialog nobody sees.
- `make app` (option 02) is the maintainer's, and the only place the secure timestamp is asked for (`--timestamp` calls Apple's timestamp service on every signing, which `make build` must not do on every upgrade). `app-bundle` builds and signs; `app` goes on to notarize, staple, assess and zip, then `app-image` makes the disk image (below). The identity comes from `scripts/signing-identity.sh --developer-id`, which fails for ad hoc and for any identity that isn't a "Developer ID Application" one (a development certificate would sign, then fail notarization): an app is never ad hoc. Unlike `make build`, it refuses a checkout with tracked changes, and a branch other than main or a HEAD not in origin/main as last fetched, unless `CHECK_BUILD=1`, which runs every step but the zip and the image's notarization (so a check never leaves a `Varnick.zip` or `Varnick.dmg` that looks publishable). It also refuses without `uvx` on the PATH, before the build.
- The bundle holds the catalog in `Contents/Resources/apps`, copied by `scripts/copy-catalog.sh` (tracked files only, so the bundle carries committed files and nothing an untracked file in the working tree adds; no `node_modules`, which in Scratch's hold unsigned native binaries that notarization would reject; no `.DS_Store`); the signature seals the copied files. `app-guard` runs `make check-apps` first.
- A bundle is signed inside out, never with `--deep`: `Contents/MacOS/zmx` first, then the bundle (the runtime, the timestamp, `Varnick.entitlements`, `-i com.zabaca.varnick`). `--deep` applies the bundle's flags and entitlements to every nested binary, and zmx left unsigned or signed without the timestamp or the runtime fails notarization. `--deep` is used only in `codesign --verify`.
- The notary credential is either a profile name (`NOTARY_PROFILE`) or an API key file with its ID and issuer (`NOTARY_KEY`, `NOTARY_KEY_ID`, `NOTARY_ISSUER`), from the git-ignored `Makefile.local` or the command line; a complete key wins, and `app-guard` refuses an incomplete key or a `NOTARY_KEY` that is not a readable file. `NOTARY_AUTH` turns it into the `notarytool` arguments for every `submit` and `log`, and the values stay in the environment (`$NOTARY_KEY` in the recipe), so a recipe line that uses it starts with `@` and make never prints them. Like the identity, none of it enters a tracked file; the credentials in a profile, the team ID, the key ID and the issuer never appear anywhere. The key form exists because the keychain profile cannot be read while the screen is locked. A notarization that isn't Accepted prints `notarytool log` and fails the target. The recipe lines that name the identity start with `@`.
- The disk image (`app-image`, ADR 0026; `scripts/dmg-settings.json`, `scripts/make-dmg-background.swift`):
  - **Made from the one stapled app,** after the zip, and only from `app` (`FROM_APP=1`, internal) or after `app-guard`'s checks: `app-image` refuses to publish unless `xcrun stapler validate` passes on `.build/app/Varnick.app`, so it never notarizes whatever that folder holds. It never rebuilds the app: a check of the layout needs no notarization (`make app-bundle app-image CHECK_BUILD=1`, with a notary credential that is never used). A published image is built as `Varnick-building.dmg` and moved to `Varnick.dmg` only after notarize, staple, validate and `spctl` pass; a failed run leaves no `Varnick.dmg`.
  - **dmgbuild writes the window's layout itself,** with no Finder window, so it works with the screen locked. It is run by `uvx` with dmgbuild, `ds_store` and `mac_alias` pinned to exact versions in the `Makefile` (`DMGBUILD`); a new pin is checked by building the image and reading the layout back (`ds_store`: the window's bounds, the two icon positions, the icon size). The settings file is JSON in appdmg's format, read from the checkout root, so its paths point into `.build/app/`.
  - **No `hide_extension` on the app.** dmgbuild hides the extension with `SetFile -a E`, which writes Finder information onto the bundle, and `codesign --verify --strict` then fails ("resource fork, Finder information, or similar detritus not allowed"): so would Varnick's own strict check of the copy it moves off the image. A label that reads "Varnick.app" is the price. The option asked for the extension hidden; this is why it isn't.
  - **The background is drawn at build time** from `FoldMark.swift` at 640x400 pixels (72 dpi) and 1280x800 (144 dpi): `tiffutil -cathidpicheck` refuses two pictures whose resolutions don't differ exactly so, which `rep.size` in points sets. It stays in the image as `.background.tiff`. The icon positions in the settings file and the arrow in the script are the same numbers, kept together by hand. Finder's window bounds may include the title bar, so the content can be about 28 points shorter than the picture (inferred, hand test): nothing sits near the bottom.
  - **Signed with the Developer ID and the secure timestamp, no hardened runtime.** Then notarized, stapled, and assessed with `spctl -t open --context context:primary-signature`, which must say `source=Notarized Developer ID`. `CHECK_BUILD=1` writes `Varnick-check.dmg` (signed, `codesign --verify` and `hdiutil verify` run) and stops before the notary service: the first notarization of an image is the first real `make app`.
  - **Checking an image:** `hdiutil attach -nobrowse -readonly -mountpoint <a folder of your own> <image>`, then detach. Never open it in Finder or with `open`.

**One Varnick per account** (`AccountLock.swift`, `StopStart.swift`, the entry point; `runs-only-from-a-checkout`, option 02)
- The app's start makes the support folder 0700 (`DatabaseLocation.makePrivateFolder`, also what the database's folder uses, since the lock is its first writer) and takes an exclusive `flock` on `varnick.lock` in it, holding it to exit; the file then holds the process id and the executable's resolved path. Two copies used to be possible, and still are across the old name: `launchctl kickstart` beside a `make run` build started a second Varnick, driving the same zmx sessions and hotkeys. A copy waits up to 15 s (a restart overlaps the old copy's exit; `scripts/restart.sh` waits 10 s), then stops with `error: Varnick is already running from <path> (process <pid>)`.
- The lock is taken on the app's start right after `AppStartMigration.run`, before `AppDelegate()` (the order is in "The installed app"). The migration makes the support folder by moving Launchy's, so a lock taken earlier creates `…/Varnick` first and makes that step skip. Once the rename's Cleanup removes the migration, the lock becomes the first step. The relay, the MCP server and the command-line modes exit before that point and must never take it or wait on it: they run beside the app.
- The descriptor is opened `O_CLOEXEC` and never closed, so the kernel releases the lock at any exit, a crash included. Without close-on-exec, a shell, zmx, claude or Bun that Varnick starts inherits it and holds the lock after Varnick quits (as they held the peer socket before 938e1e6). Don't reopen, `dup` or pass it on.
- It is only between copies that take it: a Launchy (the old name) takes no lock, so the lock doesn't stop Varnick starting beside a running Launchy. The rename's guards do that.
- `stopStart` is the one way for the app's start to stop with a message: an `error:` line on stderr, then an alert (nobody reads stderr from Finder or a LaunchAgent), then exit 1 (the move offer's Quit is the one exception: it already showed an alert, so it writes the line and exits). A command-line mode's refusal (`MacNotMoved`) keeps stderr only, since a terminal reads it.
- Checking the lock: `AccountLock` is Foundation only (with `DatabaseLocation.swift`) and takes the folder as a parameter, so a harness compiles them with `swiftc` against a temporary folder; never run the app to test it.

**The installed app** (`InstalledApp.swift`, the entry point, `BuildUpgrade.swift`, `Settings.swift` › `OpenAtLoginRow`; `runs-only-from-a-checkout`, option 02; "the app" is `ResourceFolder.current.inBundle`)
- The app's start runs in this order, after every command-line mode, the relay and the MCP server have exited: the log, the move offer, the rename's migration, the lock. The log comes first so every line below, a refusal included, lands in `~/Library/Logs/Varnick.log`; the offer (below) takes a copy macOS translocated (`/AppTranslocation/` in the executable's path), or one running off a disk image, before the peer link or the Phone page can point at a path that is gone at the next launch; the migration and the lock keep the order in "One Varnick per account". The log lives outside the support folder, so opening it doesn't create `…/Varnick` ahead of the migration.
- **Move to Applications** (`MoveToApplications.swift`, the alert `offerMoveToApplications` beside `stopStart`; `downloaded-app-moved-by-hand`, option 01, ADR 0026):
  - **Where it sits, and what it may touch.** It runs where the translocation refusal ran, so before the migration, the lock, the peer link and the Phone page. It reads no settings, no support folder and no database, creates nothing (the support folder included), and saves nothing: the only thing it reads from the support folder is whether `varnick.lock` is held (`AccountLock.probe`: one non-blocking `flock`, released at once, `O_RDONLY`, no create, no write).
  - **The image test** runs only for a bundle under `/Volumes`: `hdiutil info -plist` lists the attached images, and the bundle's volume must be one of them, so an external disk or a network volume runs as before. Anywhere else (Downloads moved by Finder, the Desktop, `~/Applications`) the app runs untouched. A copy that is translocated is offered whatever else is true; its original comes from `SecTranslocateCreateOriginalPathForURL`, which Security exports but no public header declares, looked up with `dlsym` at run time, so a macOS that drops it falls back to today's message with a reason. The image's device is the whole disk when `hdiutil info` names one, else the volume's own.
  - **The checks, in order,** each a stop with today's message and a reason, except the second: a running copy with no team (ad hoc) can't move, so it stops before any file step; Applications writable (`isWritableFile`: a standard account is told Finder will ask for an administrator, and no prompt of ours appears); no Varnick running in this account (the offer shows again naming its path; a checkout's Varnick counts, since the lock would refuse the moved copy anyway; checked again right before the Trash step); nothing else at `/Applications/Varnick.app`, tested with `lstat` so a link there, even a dangling one, is refused and never trashed, and another bundle id is named; and an original that already is the target (the steps run from the quarantine on).
  - **The steps.** The new copy lands under a hidden, unique name (`/Applications/.Varnick-moving-<UUID>.app`; a leftover hidden copy is never deleted, only what this run made): a rename when the original is on Applications' volume (nothing left behind), else `ditto` (the original stays), and a rename that fails falls back to the copy. It is verified and its quarantine cleared **before** the old copy goes to the Trash (the option has the check after, which would trash a good old copy behind a bad new one); a failure there puts the original back by rename, with the quarantine values it had, or removes the copy. Then `trashItem` takes the old copy and a rename puts the new one in place. If that last rename fails, the old copy is put back from `trashItem`'s resulting URL and the new one is undone; only when the old one can't come back does the message say it is in the Trash.
  - **Quarantine.** `com.apple.quarantine` is read, then removed (`removexattr`, no-follow), from the bundle and every item in it, only after `SecStaticCodeCheckValidityWithErrors` (all architectures, strict, nested code) passes with the running copy's own designated requirement as the requirement, so a copy signed by anyone else fails; the running copy's team must exist (else the stop above). No team ID is written anywhere. Every value removed is kept so a failed rename-move writes it back to the original, and a failed check removes nothing. Strict validation is why the app on the image carries no Finder information (see the image's notes under Signing).
  - **Opening and ejecting.** The moved copy is opened with `open -n`, as Restart does, and this process ends with `_exit(0)`. The old copy took no lock and made no migration, peer link or Phone page, so the new one has nothing to wait for. Ejecting from an image is a detached helper (`perl` `setsid`, as `spawnRestart` does) that waits for this pid, then runs `hdiutil detach <device>` up to five times, never forced; it is started only after `open` succeeded.
  - **Checking it:** `MoveToApplications` is Foundation and Security only and takes every place as a parameter (`Places`: Applications, the support folder, the Trash as a closure, the same-volume test as a closure; the attached images, the volumes root and the translocation lookup too), so a harness compiles it with `InstalledApp.swift`, `AccountLock.swift` and `DatabaseLocation.swift` alone, against a signed `Varnick.app` from `make app-bundle` copied into temporary folders (`cp -c`) and a quarantine written with `xattr -w`. A temporary image is attached `-nobrowse` at a temporary mount point and detached by its whole-disk device; a test must give `image(containing:)` a path that exists (a missing path resolves differently from the mount point's). Never run the app, and never touch the real Applications, Trash, Downloads or support folder. Not coverable without a translocated app: the real lookup, the alert, the helper after the app's exit from an image, and what macOS does after the move (quarantine really keeping the copy from being translocated, the Downloads prompt).
- Standard output and error are redirected only there (`InstalledApp.redirectOutput`, skipped when standard error is a terminal, a log that can't be opened leaving both alone). The relay is the same executable and prints its reply to standard output, as do the MCP server and the command-line modes: a redirect anywhere above the app's start would send those replies into the log and break every peer. A new mode goes above that point and writes to the real stdout.
- Restart in the app (the status menu's item and Settings' offer after a Screen Recording grant) runs `/usr/bin/open -n <the bundle>` and ends the process with `_exit(0)`, like the checkout's restart ends it with a SIGTERM: `applicationWillTerminate` doesn't run, so `restartImpact`'s claim that an app pane's server survives holds. It relies on the lock: the new copy waits up to 15 s for this one to release it. The checkout's path (`scripts/restart.sh`, with its refusals) is unchanged; a peer's Restart of an installed Mac stays refused with the installed-app text.
- The refusal texts for "no checkout" are written once (`NoCheckout`): in the app "Installed app: update it by downloading the newest build", and for a headless host's upgrade and comparison "Upgrade it from a Mac that runs Varnick from a checkout"; outside the app and outside a checkout the old text stays. The report shapes carry them as refusals and are unchanged.
- Open at login (`SMAppService.mainApp`) is shown only in the app, reads the status each time Settings shows (and each second), registers only when the user turns it on, and saves nothing. Don't register it from anywhere else, and never in a check: it adds a Login Items entry for the account.
- The skill link (`InstalledApp.linkSkill`) is made after the delegate exists, from the resource folder's `skills/custom-apps`: when nothing is at `~/.claude/skills/custom-apps` (a dangling link counts) or the link points into a `<name>.app/Contents/Resources/skills/custom-apps` (relinked through a rename, so the path is never missing). A user's folder or a link into a checkout is left alone.
- Grant for Screen Recording shows the bundle in Finder in the app, not the executable inside it.
- Checking: `InstalledApp` is Foundation only and takes its paths as parameters, so a harness compiles it alone with `swiftc` against temporary folders. Never run the app to check any of this, and never touch the real `~/.claude/skills`.

**Catalog apps** (`AppCatalog.swift`, `AppsView.swift`, `apps/`, `scripts/check-apps.sh`; `custom-apps-must-be-written-first`, option 01, ADR 0027)
- **The switch is the marker.** An app is on when `~/.varnick/custom-apps/<name>/` is a real folder (not a link) holding `.varnick-catalog` whose name is the folder's own. There is no UserDefaults key and no saved field. Anything else with that name is the user's: never written into, never trashed, never refreshed. A marker naming another app, or a link, counts as the user's.
- **A restored app pane finds its app by folder name,** so an installed copy must never be missing or half written under a pane that runs it. Copies are made under a hidden name (`.<name>.installing-<uuid>`, which the loader skips) and renamed into place last, with `RENAME_EXCL` so a folder that appeared meanwhile is refused. Off and refresh wait while any pane's `record.app` has that name (`LauncherModel.openAppFolders`, restored panes not yet shown included, a project's app of the same name too). Refresh trashes the old copy and renames the new one in, so the path is missing between the two; that is why it never runs under a pane, and why `CustomApp.available` (the picker, `find`, restore) calls `AppCatalog.waitUntilIdle()` first, which waits on the lock the three operations hold. Any other reader of the user's apps folder needs the same call.
- **Varnick never deletes an app folder:** off and refresh move it to the Trash (`trashItem`, a closure in `Places`). The one removal is a leftover hidden staging folder of the same app, which is an unfinished copy and never an app. The skill link is removed only when it is a link to this app's installed `skill` folder, and a skill path taken by anything else leaves the app on and the row saying so.
- **The digest and the copy leave out `node_modules` and `.DS_Store` at any depth,** as the Makefile's `rsync` does, and the marker at the root. A refresh carries the old `node_modules` across only when `bun.lock` and `package.json` are byte for byte the same; otherwise the next pick installs again. Nothing is fetched by turning on or refreshing.
- **The first pick of an installed catalog app installs frozen to its lockfile.** `ClaudeSession.startApp` decides in Swift (`AppCatalog.isInstalledCopy`: a user app, a real folder, whose marker names that very folder) and passes `frozen` or `plain` to `appScript`, which runs `bun install --frozen-lockfile` or plain `bun install`. A copy the user renamed (`my-scratch`) keeps a marker naming `scratch`, so it installs plainly and the user can add a dependency; a project's app never counts. A lockfile out of step with `package.json` fails in the pane, which is review's job to prevent. The argument is never empty, in case zmx's argument passing drops an empty one (not checked).
- **The catalog is read from the resource folder** (`ResourceFolder.current.folder/apps`), so a checkout build reads its last `make build`'s copy. An app dropped from the catalog stays installed and listed until the user turns it off.
- **Launch refresh** runs from `applicationDidFinishLaunching` after `cleanUpAfterLastRun` (tabs restored), on a detached task, with the running names taken on the main actor first, and not at all when `savedStateFailed` (sessions.json didn't decode): the panes that own last run's app servers, still alive in zmx, are unknown then, as the zmx sweep also assumes. `AppCatalog` takes a lock around on, off and refresh. A refresh's failure is kept per app in memory, and the row shows it while the update is pending; nothing is saved. Settings reads the rows and runs the switches on a detached task (`AppsSettingsView`), never on the main thread, with the switch disabled meanwhile.
- **Nothing on the installed app's early path touches the catalog.** The launch refresh and the section are the only callers.
- **Checking:** `AppCatalog` is Foundation and CryptoKit only and takes every place as a parameter (`Places`: the catalog, the user's apps, the skills, the Trash as a closure, the running names), so a harness compiles it alone with `swiftc` against temporary folders, with the Trash moving into a temporary folder. Never the real `~/.varnick`, `~/.claude/skills` or Trash. `make check-apps APPS=<folder>` checks a temporary copy of the catalog (the manifest is checked as strict JSON by JavaScriptCore through `osascript`, which every Mac has, since plutil takes any plist) (a tracked `node_modules` needs the copy to be a repository).

**Checking by hand**
- `NSLog` lines (the spoken request timing, failures) go to stderr, which `make run` and the LaunchAgent append to `~/Library/Logs/Varnick.log`; they are not in `log show`. Read that file after a spoken request. A Varnick started any other way (from a terminal, or by a build that predates this) writes them to its own stderr.
- To see every size a pane's pty gets (the start and each change), run `VARNICK_LOG_RESIZE=1 make run` and read `[resize]` lines in `~/Library/Logs/Varnick.log` (not `log stream`). Set it that way only: never `launchctl setenv`, which leaves it on for every later start.
- Measure search with `Varnick --search-eval <terms> <output>` on a copy of the database (`VARNICK_DB`), with `VARNICK_EVAL_FILTER` (typesafe, local, off) to pick the filter and, for typesafe, `TYPESAFE_API_KEY` in the environment: it runs the app's own fused search and filter and prints MRR and top-k for the target pages. The terms and output are personal like the checkpoint; keep them out of the repo.
- Foundation finds the home folder and Application Support without `$HOME`, so a check run with only a temporary `HOME` still reads and writes the user's real `~/Library/Application Support/Varnick`. Set `CFFIXED_USER_HOME` to the temporary folder too (it moves Application Support but not UserDefaults: those writes reach the real preferences, so `defaults read com.zabaca.varnick` afterwards and delete the keys a check added), or pass the folder in, as `PaneFolder.migrateOldScratchFolder(in:)` takes it.
- Test zmx with a throwaway absolute `ZMX_DIR` (0.8.1 panics on a relative one, and refuses a long path: a scratch folder's is too long, so use a short one such as `/tmp/xyz`), never the user's `/tmp/zmx-<uid>`, and make sessions the way Varnick does, `zmx attach` through a pty (`script -q /dev/null zmx attach …`): sessions `zmx run` creates crash 0.8.1's daemon on the child side of fork and leave crash reports. Set `VARNICK_ZMX_DIR` too (Varnick and its relay read it), and unset `ZMX_SESSION` if the shell is itself in a zmx session, or `zmx attach` switches sessions and fails.

**The rename (short-lived; removed by the option's Cleanup)** (`FirstLaunchMigration.swift`, `OldLaunchy.swift`, `AppStartMigration.swift`, `MacNotMoved.swift`, the entry point, the `Makefile`, `scripts/restart.sh`, `scripts/old-launchy-folder.sh`, the installer's two halves; `name-taken-by-another-launcher`, option 01, whose phase 6 removes all of it)
- **Ours or not.** An unrelated keystroke launcher is also called Launchy (its macOS build is an executable `Launchy` with data in `~/Library/Launchy`, per its public source; apps of the same name may use `Application Support/Launchy`), so neither the folder's name nor a process's proves anything. The folder is ours when it holds `sessions.json`, `search-db-path`, `launchy-peer` (a dangling link counts) or `peer.sock` (`OldLaunchy.isOurFolder`; `scripts/old-launchy-folder.sh` is the same test in shell for the Makefile and `restart.sh`, so change both together). A running app is ours when a path it has (the file, the exec path, `argv[0]`) ends in `.build/release/Launchy`, it isn't a relay or MCP server, and it is this account's; a process whose paths can't be read counts as ours. The migration (the refusal and the folder move), `MacNotMoved`, `cutover-check` and `restart.sh` all use it and fail closed only for what passes it; any other `…/Launchy` is left alone and Varnick starts fresh beside it. A folder of ours with none of those entries is not recognised.
- Only the app's start migrates, and only at the end of the entry point, after every command-line mode has had its turn and before `AppDelegate()` is made. Nothing on that path may read `Settings.shared`, the support folder or the database first: a read that creates an empty `…/Varnick` makes the folder step skip for good. A new mode goes above that point and exits.
- Before any step, `FirstLaunchMigration.refusal` stops the app with an `error:` line (nothing changed) while our `…/Launchy` exists and a Launchy app is running (a process named `Launchy`, other than its relay and a pane's MCP server; found by `proc_name` as well as the executable's path, since the running Launchy's file is gone at the cutover), and, when `…/Varnick` doesn't exist, unless `launchy.sqlite` is in the working folder's `db/` (or beside the path `VARNICK_DB` chose, or that path exists). Without it, a Varnick built in a worktree and started by a restart that matched the running Launchy's relative name would end every session and move the Mac's data. It also stops when both folders exist and `…/Varnick` has no sessions file, since that would start empty. Varnick.app's working folder is `/`, so it never passes the database test: the cutover is a build from the checkout Launchy ran from, not the app.
- The steps run in this order, each skipped when its target exists, each logging one line with no values: end the old zmx sessions, copy the settings domain (`heyLaunchy` becomes `heyVarnick`; it counts as already done only when the new domain has the peer id, never because it is non-empty, since any stray write would otherwise skip it for good and start Varnick with a new identity), move the support folder, rename each pane folder's `.launchy-…` files to `.varnick-…` (which the new code reads; every run, so a crash after the move loses nothing), copy the web data, copy the database. Sessions end before the folder moves so no hook writes into a moving folder; the domain and folder are in place before `Settings.storeSkipPermissionsIfAbsent`; all of it comes before `PeerLink.refresh`, so the relay never answers from an un-migrated domain. Both folders present: nothing is merged. A failed folder move stops the app before the database step, and a database that can't be copied stops it too, never an empty folder or database beside the real one.
- The database step is a copy that never replaces or touches the original, so a rollback to Launchy finds it as it was. It runs only without `VARNICK_DB` and when `varnick.sqlite` isn't in the support folder; the source is the first that exists of the file the support folder's `search-db-path` names, `db/varnick.sqlite`, `db/launchy.sqlite` under the working folder. It copies into `varnick.sqlite.partial` with `sqlite3_backup_*` (which takes in the WAL), runs `quick_check`, empties the copy's WAL, and moves it into place with `renamex_np(…, RENAME_EXCL)`; any failure removes the partial and stops the app with an `error:` naming both files. The original is not opened by SQLite when it can be avoided: the system's SQLite rewrites a quiet database's `-shm` on a read-only open, and makes a `-wal` and `-shm` beside one that has none (and can't open a WAL database read-only without them), so the files are copied aside first (`stage`) and read there, unless they change while being copied, which means a writer is at work and the original is then read through SQLite. The system's SQLite also keeps a closed database's `-wal` and `-shm`, so a copy is moved into place without its own.
- Every other mode, and any unknown `--` flag, refuses with an `error:` line while our `…/Launchy` exists and `…/Varnick` doesn't, except the relay and the MCP server. The cutover itself is an app start with no argument.
- Every `error:` line a guard prints ends by saying the cutover is the user's step, done from Terminal.app, and that an agent must stop and report: agents follow what an error says, and none of these is theirs to act on.
- Checking the steps: `FirstLaunchMigration` is Foundation only and takes every place and domain name as a parameter, so a throwaway harness compiles it alone with `swiftc`. A temporary home (`HOME`, `CFFIXED_USER_HOME`) doesn't move UserDefaults: use made-up domain names such as `test.varnick.<uuid>`, never `com.zabaca.varnick` or `com.zabaca.launchy`, delete them (and their plist in `~/Library/Preferences`) afterwards, and check that `defaults read com.zabaca.varnick` still says the domain doesn't exist. No command-line mode copies settings. Old-named sessions are made in a throwaway `ZMX_DIR` (see Checking by hand), never `/tmp/zmx-<uid>`. The database step is checked with databases made by `sqlite3` calls in a temporary folder, one whose WAL holds a write (copy the three files aside while the writing connection is open), and the source's three files must keep their bytes and modification times.
- Guards, each short-lived: `make build` fails first with an `error:` line while `.build/release/Launchy` or `Launchy.good` exists, which stops Upgrade, Upgrade all and `make run` on a Mac not yet cut over; `make stop` and `scripts/restart.sh` also stop a Launchy binary, by this checkout's absolute path only (a Launchy started by `make run` has the relative argv `.build/release/Launchy`, which matches from every checkout); `make run`, `install` and `uninstall` (`cutover-check`) and `scripts/restart.sh` refuse, before stopping anything, while the Mac still runs our Launchy and the checkout has no `db/launchy.sqlite`, since a worktree passes the build guard; in the checkout that does have it, `make clean` and `make install` (`cutover-confirm`) refuse unless `CUTOVER=1` is given, since `clean` removes the binary that holds the build guard and `install` would then install Varnick's LaunchAgent for the next login (the cutover's two steps pass it, and an agent must not); `scripts/restart.sh` also refuses when `.build/release/Varnick` isn't there (the status menu's and a peer's Restart run it with no build), appending why to `Launchy.log` while the Mac still runs Launchy, else `Varnick.log`; `make install` and `make uninstall` boot out `com.zabaca.launchy` and remove its plist; the Linux installer's far half refuses where `~/.launchy` exists, with `OLDROOT=present` that the near half reports as `error:`, and removes what the near half shipped.
- Never run `make run`, `make stop`, `make install`, `make uninstall`, the built binary, or the restart script with the real `pkill` or `pgrep` in a check: a pattern can match the running Launchy. Put stand-ins that only record their arguments first on `PATH`.

# Varnick carries out a task in a browser of its own, with Jev choosing each step and Claude steering

The user wants to hand Varnick a task that takes many steps on a website ("find how much delivery to Canada costs", "create an account for Robin Vale") and get on with something else. Hey Varnick never acts (ADR 0015), and a Claude session with Screen access (ADR 0023) can act only on the user's own screen, a Claude turn for every click. agent-lab's pilots of 2026-10-14 (hybrid-browser 1 to 15) solved all five tasks on a made-up shop in both runs, against 7 of 10 for Claude alone, with 2 to 6 times fewer Claude calls, by splitting the work: the harness owns the loop, a fast model (System 1) chooses each step, and Claude (System 2) writes values and steers. The problem and its options are in `docs/problems/tasks-cant-be-handed-to-varnick/`; this records option 01, accepted 2026-10-14 with the problem's recommended decisions.

## Decision

**A Task pane is a browser of Varnick's own.** It is a `WKWebView` made with a non-persistent website data store of its own: it shares nothing with Browser panes or another Task pane, is empty when the pane opens and is gone when it closes. A second task in the same pane keeps the first one's cookies and cart. The pane is behind a Tasks switch (Settings › Experimental, off by default): `!task` and the split picker's Task tile exist only while it is on, a running task stops at its next step when it goes off, and nothing else runs. A Task pane is never saved (a restart ends its task, and the tab comes back without it, or not at all when it held nothing else), never reaches Recent, Completed or an ended card, and is not listed to paired Macs or the phone, because every one of those lists is built from the saved state. One task runs at a time on this Mac.

**It reads and acts inside the page, never on the screen,** so it needs no permission and no app comes to the front. All page work is a script in an isolated content world of the web view's own, so the page's scripts can't see or change it. Typing sets the field's value through the element prototype's own setter and fires input, change and blur events, which is what React-style controlled inputs and Vue-style models listen to. A click is the element's own `click()`. Peeks at links are `fetch` and `DOMParser` in the same world, with the pane's cookies, from the pane's own origin only, and the visible page does not move.

**The harness owns the loop** (`Packages/TaskHarness`, Foundation only, behind three seams: the page, System 1 and System 2). It is the port of the pilots' hybrid-browser-15, constants and all: a best-first frontier that peeks every body link, scores the previews as a ranking only, follows the best and backs up within depth 3 and 8 follows; a value bank keyed by meaning, where a correction replaces the old entry; digit checks in code for phone and postcode fields; stuck rules that never bar a way into a form and refuse a back from a form page while a value is on its way; a budget of 40 System 1 turns, 20 Claude messages and 5 minutes. Two departures from the pilots, both the user's: the answer's shape is a System 1 question at the start with no marker list (ADR 0037's rule, carried over to tasks), and every form submit but a search box's waits for the person's Allow, where the pilot asked only at the shop's named buttons. It asks on a button that submits a form, on any button of a page that has a form (a script-handled "Place order" is a submit too), and on any link of a page that has a form or that has no real address to go to (`#`, `javascript:`, a link in a button's role). A submit the page makes itself while a field is filled (its own onchange handler) is held by the page bridge and gated the same way. A search box is a form with role search, a search element, or a form whose only text field is a search input, never a word; a search input among other fields (a checkout's address lookup) is not one. Every action on the page passes a pause checkpoint first, and each element keeps one id for as long as its document lives, so a field a form reveals moves no other.

**System 1 is Jev, with Claude as the fallback, and never this Mac's Gemma.** Jev is used as the other TypeSafe features use it: only while the relevance filter is on TypeSafe with a key saved. The call is the spoken route's shape (one shared state, many named questions) on the route's pinned version and its 1.5 s deadline. A Jev call that fails goes to Claude for that step, and three failures in a row give Jev up for the rest of the task. Without Jev, Claude makes the same choices through the same harness, checks and gates, in the guidance conversation: it is given the state and the questions and answers with one JSON object, a picked label counting as probability 1. Gemma's answer probabilities were measured not to separate right from wrong (the screen-pointing eval), so a 0.7 bar on them would mean nothing. System 1 acts alone at P of 0.7 or more, and its content scores only rank.

**System 2 is the user's own Claude Code, in a conversation kept open for each role of a task.** This amends ADR 0029, which passed over a kept-open conversation for Text generation because one conversation for every request grows without end and lets each answer see unrelated ones. A task's conversation is one task's and is meant to see its own earlier steps. The text helper gains a conversation mode: the request's `prompt` is the first message, each later line `{"message": …}` is the next, every message gets a `ready` and its own `result`, and the helper holds one `claude` open until its input closes. It has the same levers as a one-shot request (Haiku 5.5, effort low, no tools, none of the user's settings, hooks or memory, no saved transcript, the reminders filter). Messages go to one conversation one at a time, in the order sent. The deadline is 15 s a message, as the web answer's; a miss ends that conversation (the helper is stopped) and the next message starts a new one from the full state the harness writes. There are two conversations per task, values and guidance, as in the pilots, so a background value request never queues behind a blocking guidance message; each is told the other's replies since its last message. Both end with the task, with Stop, with the pane and with Varnick, and nothing of them outlives Varnick (the helper reads its input to the end).

**What is the person's stays the person's.** A password, a one-time code and any card field (type password, an `autocomplete` of current-password, new-password, one-time-code or any `cc-` purpose, or a field that was ever a password, so a "show password" button doesn't expose it) are recognised from the field itself, never from its label. Their values are never read: the script sends only whether they are filled, the type that holds a field (`PageField`) drops one that arrived anyway, and the harness never fills one. The person types them, ticks the terms box Claude marked as theirs, and allows each submit ("Allow", or "I'll do it" and then the page's own button). A click or a key in the page, by the person (a trusted event, never the script's own), pauses the task before its next action; Resume hands it back after reading the page again; Stop cancels the calls in flight, ends both conversations and leaves the page as it is.

## Considered options

- **The user's own browser and apps through Accessibility (option 02):** not built here. It needs an exception to the rule that agents never drive the screen without approval each time, and the user's logins.
- **Headless Chrome with a profile of Varnick's own (option 03):** not built here. It is the pilots' engine, but it downloads a browser binary (the XProtect history of ADR 0013) and has no page for the person to type their password in.
- **System 1 on this Mac with Clef-flash (option 05)** and **starting a task by voice (option 04):** later.
- **Asking Claude for System 1's choices through Gemma:** no; see above.

## Consequences

- **New outflows,** to TypeSafe with Jev in use and to Anthropic through the user's Claude Code. `docs/privacy-and-security.md` says what goes where (TypeSafe, Anthropic through Tasks, and what acts as you), and the Tasks switch's text points there. Nothing of the user's own browsers goes anywhere: the pane's website data is its own and empty at the start.
- **A second kind of conversation in the text helper,** and `Subprocess.open`, a process kept open with an input to write to. `TextHelper/check.sh` covers the conversation against `fake-claude.py`.
- **Unmeasured,** and the reason the harness is a port and not a claim: WebKit and Varnick's own snapshot against the pilots' Chrome and Playwright's snapshot; Jev's own speed and its 0.7 bar (the pilots used Clef); the shape asked of Jev (the pilots' test 3 used Clef); asking at every submit; real sites, whose logins, scripts, bot checks and far more links the pilots never saw; the task's Jev questions on the live endpoint (their request shape follows the spoken judge's and is untried). `docs/agents/where-it-breaks.md`, Tasks, says what the spike found and what is still open.
- **Every task starts logged out.** That suits "create an account" and public facts, not "check my order on a site I use". Keeping data per site is later.
- **Without Jev it is slower and dearer,** close to Claude alone. The pane says "Without Jev: each step asks Claude".
- **Sites written for people may resist it:** script-built pages that a fetch previews empty, bot checks, and forms that ignore script events.
- Amended by ADR 0041: the loop becomes the Website capability of a Task, and the Task pane is called the Website pane.

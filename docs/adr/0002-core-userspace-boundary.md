# Core and Userspace are separated by the sandbox policy, not by convention

The agent edits the clone it is running inside, so the code that holds the conversation is code the agent could otherwise break — and the conversation is what you would use to fix it. The sandbox policy therefore denies writes to `packages/core/**`, `packages/harness/**`, `vite.config.*`, `package.json`, `sandbox-policy.json`, and `sandbox-policy.baseline.json`, making the split kernel-enforced rather than a rule in `CLAUDE.md`. The agent's blast radius is Userspace; Core is changed through the escalation path in [ADR-0005](./0005-two-profiles-live-userspace-cloned-core.md).

**The Harness and the generated policy are on that list because they are how the fence is built.** `CONTEXT.md` defines the Harness as Core's runtime half, and `packages/harness/src/sandbox.ts` is what generates the policy; `sandbox-policy.json` is what the next launch reads. An agent that can write either can widen its own boundary on the next launch, which makes every other entry advisory. This was found while implementing the policy, by reading the list literally.

**The baseline is on it for the same reason, one step further out.** `sandbox-policy.baseline.json` records what the generator produced, and is how the next launch tells a developer's edit from a strengthening varnick has since made — an edit is kept, a strengthening is applied. An agent that can write the baseline can present its own widening as varnick's own work and have it believed, without ever touching the policy. See the third correction in [ADR-0003](./0003-containment-wraps-the-process-tree.md).

## Consequences

- **Surfaces must be discovered, not registered.** A new Surface cannot require appending to an imports array in Core, because the agent cannot write Core. Discovery is filesystem-based — `userspace/surfaces/*` scanned at load. Getting this wrong blocks the product's main loop on day one.
- **The build-pipeline escape mostly closes as a side effect.** With `vite.config` and `package.json` scripts denied, an agent cannot reach the host by writing a Vite plugin or a `postinstall` script. What remains is application code the host runs — a real and knowingly accepted hole, since the whole point is that the agent's output becomes running code.
- **Two gaps in that list, found by implementing it and left open deliberately.** `package.json` names the root one only: `packages/userspace/package.json` stays writable, so a `postinstall` there still runs on the host's next install. Closing it would also stop the agent adding a dependency to Userspace, which is ordinary work — so it stays open and is measured by the probes in ticket 04 and written down in ticket 13 rather than quietly assumed shut. Separately, `vite.config.*` at the clone root matches nothing today, since the real config is `packages/core/vite.config.ts` and already covered; the entry is kept because a root config is exactly the file a future change would add.
- **The protection is real but partial, and is described that way.** Userspace code executes in the host process when loaded. The Sandbox protects `$HOME` and everything under it — which is where repositories usually live, but not where they must — and it bounds the network. It does not protect the clone from the code the agent writes into it, and it does not protect a repository stored outside a home directory, because reads are allow-by-default outside `denyRead`. See ADR-0003's fourth correction.

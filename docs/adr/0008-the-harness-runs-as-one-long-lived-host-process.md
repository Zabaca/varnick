# The Harness runs as one long-lived host process, and the credential does not live in it

Core runs in the Tauri webview and has no kernel, no keychain, and no filesystem. The Harness needs all three. Every capability therefore runs on the host, and Core reaches all of them through one seam — a Tauri command that routes to either the Rust host or a Node process the host starts and owns, spoken to over newline-delimited JSON on stdio.

**The runtime is long-lived, and that is a correctness requirement rather than a latency optimisation.** `srt`'s proxies live in the process that called `SandboxManager.initialize()`. A process-per-call would establish a Sandbox, exit, and leave `checkSandbox` answering `ok` about a Sandbox that no longer exists — the worst available failure, because the state that means "contained" would be the state that lied. Containment wraps the agent's whole process tree ([ADR-0003](./0003-containment-wraps-the-process-tree.md)), but it travels in the argv rather than through parentage — the agent is spawned by the Rust host, not by the runtime, which is the third rejection below. What must outlive the call is the *wrapping*, and it is only good while the proxies backing it are alive. The Session mirror separately serialises saves through a per-store queue, and two processes have no queue between them.

**The credential is answered by the Rust host and never reaches the runtime.** Routing is one function with an explicit arm per capability and a closed default, so an unknown request is refused rather than forwarded, and it is a unit test rather than a convention. The runtime *also* refuses the credential request explicitly instead of leaving it unhandled — an unhandled case is a case someone can quietly implement later.

## Rejected

- **A Node process per call.** Loses the Sandbox between calls, for the reason above.
- **Moving the capabilities into Rust.** This would mean a second implementation of the policy generation and of the Agent SDK integration — the product's only real claim, written twice, in two languages, drifting.
- **Letting the runtime hold the credential so it can spawn the agent itself.** The runtime holds the Sandbox, so this reads as natural and is the trap this decision most invites. It would put the value across the bridge, which is the one thing that may never happen. `EstablishedSandbox.wrap()` returns argv and env for a `{ shell: false }` spawn, so the runtime computes the wrapping — no secret — and the Rust host performs the spawn, where the secret already is. The agent is inside `srt` either way.

## Consequences

- **One seam, not one command per capability.** Adding a capability adds a route, not an IPC surface. The three improvisations this replaced — a bundler-ignored dynamic import, a statically imported store constructed lazily, and a hand-written command — were three answers to one question, and two of them worked only because nothing had called them from a real webview yet.
- **A missing host is a value, not an exception.** The dev server in a plain browser tab has no host behind it. That reaches each actor's own failure state carrying the reason, the same way a missing credential does.
- **The runtime is not sandboxed, and must not be confused with the agent.** It is varnick's own code holding the fence, not the code being fenced. The agent is not its child either — the Rust host spawns it, wrapped. One consequence is worth stating plainly: the Session mirror lives outside the agent's writable tree, so the agent cannot tamper with the record of what it did.
- **The runtime entry is resolved as a development path, and packaging is not solved.** It resolves relative to the repository, which is right for `bun tauri dev` and wrong for a bundled application; `VARNICK_HARNESS_ENTRY` and `VARNICK_HARNESS_RUNNER` are the overrides. `PRODUCT.md` puts deployment out of v1, so this is a known edge rather than a gap — shipping an application means packaging the runtime as a sidecar, and no ticket owns that yet because no ticket ships an application.
- **The runtime and the client are now driven together, and they had already disagreed.** This consequence used to say the join was untested and that testing it needed a runner on `PATH`. It did not: the Rust half forwards the runtime's payload verbatim, so the join is TypeScript to TypeScript. By the time anyone drove it, the runtime was answering `{}` where the client required `ok: true` — so `check-sandbox` failed on every launch, no agent could start, and the message blamed a version mismatch. Both sides' own tests passed throughout. `packages/harness/src/join.test.ts` is that test; it fails with `malformed` the moment the two shapes diverge again.

# Each Varnick upgrades itself when a paired Mac asks, and Restart Varnick is a separate press

A Mac's running Varnick upgrades itself when a Mac it lists asks: it fetches origin/main from GitHub with its own Keychain, fast-forwards main in its checkout and runs `make build` in a zmx session of its own, and nothing restarts. Restarting is a second request, pressed when the user chooses, which first lists the panes it would end. Two new requests carry this, `upgrade` (a report, or with `begin` the start) and `restart` (what would end, or with `confirm` the restart), and the relay reads them before it checks the protocol version, so a Mac on any protocol from 15 on can be asked. The headless host (the Ryzen) has no app and no checkout: its Upgrade runs `scripts/install-peer.sh <host> --commit <origin/main>` from a Mac, in a zmx session there, and its new relay is live at once. Upgrade all and Restart all do the same on every machine after one confirmation, the other machines first and this Mac last. The problem and its options are in `docs/problems/peers-upgraded-by-hand/`; this records option 03.

## Considered Options

- **Options 01 and 02** (the upgrade run in a terminal tab, or by Launchy with progress, with a probe over SSH outside the relay and the newest main this Mac holds as the target): not built. A Launchy started from an SSH login lacks the GUI session's Keychain, and `launchctl kickstart` there starts a second Launchy beside one `make run` started. They stay on record.
- **Upgrade and restart as one step**: not chosen. A build that finishes while sessions are busy would end them.
- **Upgrading to a chosen branch or commit, or to a local main**: out of scope. Origin/main is what every Mac and the Ryzen agree on.
- **Letting the relay run the binary on disk**: not chosen, see the snapshot below.

## Consequences

- **The target is origin/main and nothing else.** Each Mac fetches GitHub itself, so a Mac never takes a commit another Mac holds but hasn't pushed, and a Mac with unpushed merges shows them as ahead, not as the newest build. A failed fetch refuses an upgrade rather than falling back to the last origin/main, since a Mac with a stale one could take the Ryzen back to an older relay.
- **Upgrade builds; Restart Varnick is separate.** The cost is a second press per Mac and a "restart Varnick to update" state that can last. A failed build leaves the old build running, since the stamp `make build` writes last, only on success, names the last good build. Restart Varnick is the detached restart `make run` does, started by that Mac's Varnick from its own GUI session, never launchd from an SSH login (ADR 0007: no Keychain there).
- **A build changes nothing until Varnick restarts.** Each launch clones its binary, zmx, build stamp and Phone page files into `.build/snapshots/`, which `make build` never writes, and points the peer link and the Phone page server at the clone. A Mac stays on one protocol, relay and app together, until Restart Varnick. Letting the relay run the binary on disk put a Mac's relay on a protocol its app didn't speak the moment `make build` finished (seen on the Studio on 2026-10-06). The clone takes no space on APFS until the build changes.
- **The two requests are frozen, a carve-out from "the relay reads a request's version first".** Their shapes and the envelope around them never change except by adding optional fields an older build ignores, or a newer asker couldn't read an older host's reply, and the very mismatch these requests exist to cure would block them. The doc comments on `PeerMaintenanceAsk`, `PeerUpgradeReport`, `PeerRestartReport`, `PeerReply` and `PeerRequestHead` in `Packages/VarnickPeer` list what is frozen. They are answered only to a listed Mac, never to a device, and the asking side skips the refusal of a peer known to speak another version for these two alone.
- **The Ryzen is upgraded from a Mac, in one step.** Nothing there can build itself, and its relay starts afresh per request, so there is no restart. The installer ships what is committed at origin/main, not the working tree, and takes its far half from that commit. A Mac compares the Ryzen's commit with its own origin/main on the files the installer ships, and shows "relay unchanged", with no Upgrade, when only other files changed. ADR 0009's "reinstall at every protocol bump" is now the Upgrade button on the host's row (Settings › Peers), which runs the same installer; running it by hand still works.
- **A new power for a listed Mac:** making another Mac fetch, build and restart Varnick. It stays bounded: only origin/main, only a clean main checkout, and a restart is refused unless a new build is waiting and nothing builds. ADR 0007's list of what a listed Mac may ask gains it.
- Every Mac, and the Ryzen, must be brought by hand to the first build with the two requests (protocol 15), once. After that every update, protocol bumps included, goes through the buttons. A Mac whose Varnick isn't running can't be upgraded: nothing here starts it.
- The build runs in a zmx session Varnick starts, never in process, because XProtect once killed a Claude process that ran installs, launchctl and a downloaded binary together. The session outlives Varnick, and the next launch reads how it ended from the log.
- The rules that keep these requests working are in `docs/agents/where-it-breaks.md` (Peers and Phone page).

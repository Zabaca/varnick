# The relevance filter can run in Launchy with our own MLX port of Laya

Settings › Search gets a choice for the relevance filter: TypeSafe, On this Mac or Off. On this Mac judges the top 20 pages with a checkpoint distilled from TypeSafe's Jev on the user's own history, running in Launchy's process with MLX the way semantic search does (ADR 0003). The model code is a translation of Laya's decision model (ModernBERT encoder, decision head, row builder; about 300 lines against `mlx-swift` and `swift-transformers`, no new package), and the user imports the checkpoint once from a folder on disk. We chose this over keeping TypeSafe only, which sends every pause's search and 20 page titles to a third party, needs a key and a network and settles about 1.1 s after typing stops; and over vendoring `laya-mlx-swift`, a package we would then have to track. On the prototype's 200 searches it ranks level with TypeSafe (MRR 0.752 against 0.752), so the reasons are privacy, offline use, latency and cost, not quality. The problem and its options are in `docs/problems/relevance-filter-needs-typesafe/`.

## Consequences

- TypeSafe becomes optional, and stays the default. On this Mac never falls back to TypeSafe, not even after a failure: a failed check shows unfiltered results with the usual warning.
- The checkpoint encodes the user's browsing history, so it never goes in the repo, the app or Hugging Face. It lives in Application Support next to the embedding model, copied in from a folder the user picks, and another Mac needs the folder copied by hand. It ages as history grows.
- The row format and the weights' names are a contract with the checkpoint, and nothing flags drift: ranking gets worse with no error. `Launchy --rerank-eval` scores the prototype's eval with the app's own code against Python's scores (largest difference 0.01, no flips, MRR within 0.005 of the reference file's own MRR, so synthetic sets work; the spec's fixed 0.7532 is what the real eval's reference holds), and every `mlx-swift` or `swift-transformers` upgrade has to rerun it, also on the synthetic long-row set in the private folder with `--max-diff 1e-3`, because only 17 of the eval's 4,000 rows are long enough for the sliding band to matter and an off-by-one band moves the long rows by 9.6e-3, under the default bar, against 2.3e-4 for a correct build. `swift-transformers` is pinned exactly for the same reason, and `tokenizer.json` is pinned by SHA-256 because building a tokenizer passes about 20 `fatalError` calls that would end Launchy and every session in it.
- MLX's 64 MB buffer cache cap and the 10-minute idle unload now cover two models, the embedder's 650 MB and about 0.85 GB at peak for this one, and MLX runs one evaluation at a time per process, so a rerank can wait behind a history-sync embedding batch.
- The model runs in fp16 as shipped, with the scorer's last projection and the temperature step in fp32; bf16 flips candidates on the eval.
- ADR 0003 stays as written.

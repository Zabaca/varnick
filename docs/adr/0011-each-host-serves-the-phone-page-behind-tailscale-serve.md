# Each host serves the Phone page behind `tailscale serve`, to the user's own devices

Every host serves a web page, the Phone page, to the user's own devices, such as the Pixel 8a: a Bun server beside the host's relay, on an owner-only Unix socket, published with `tailscale serve` on HTTPS port 8444, tailnet only, by Varnick on a Mac and by the installer on Linux (see the note at the end). The server decides nothing about sessions: every list and every action is a request to the host's own relay, run locally with the device's id as `by`, so the rules the relay and the host's Varnick enforce for a peer hold for a device unchanged. A device is listed per host by its tailnet node, found by `tailscale whois` on the address serve forwards. The relay and the host's Varnick accept a listed device wherever they accept a peer, except for the search sync's requests; a device can be in control of a session, and is never contacted. On a Mac, Varnick runs the server in zmx under a fixed name; on Linux a systemd user unit runs it, installed by the Ryzen's installer. Bun is for the page only, never the relay. The problem and its options are in `docs/problems/sessions-out-of-reach-from-the-phone/`; this records option 01, with the spike of 2026-10-06 in its Results.

## Considered Options

- **Launchy serves the page (option 02)**: not chosen. It answers from the app's own model, but it is Mac only and puts a listener in the app, and the user's Linux host needs the page too.
- **One hub page for every host (option 03)**: not chosen. One address and one device list, but everything depends on one Mac being up, and a hop through it reaches the other hosts.
- **Within option 01:** ttyd for the terminal (it takes its command's arguments from the URL, so a reconnect would repeat a take, and it adds a second process and listener per host); the relay binary as the server (Foundation on Linux has no server, and Launchy takes no new dependencies); any untagged device of the user instead of a list; Tailscale app capabilities in the tailnet policy; a plain child process of Launchy instead of zmx (a restart would drop the phone's terminal); a path under the existing browser terminal's port; and letting go of control when the phone disconnects (Android backgrounds a tab all the time).

## Consequences

- A second way in beside SSH, for the user's own devices. This amends ADR 0007's "No listening port" for that one door. [ADR 0035](0035-remote-web-and-app-panes-go-through-a-port-proxy-in-each-hosts-phone-page-server.md) adds more doors from the same server: one TLS listener on the tailnet addresses per port that an open tab's web or app pane uses.
- Nothing listens on TCP, except where a host's Tailscale can't serve a socket: the Studio's 1.92.2 and the Air's app (the spike and ticket 04, in the option's Results), and a Mac whose tailscaled refuses a socket to a user who isn't root (the note at the end). There the server listens on loopback, any local process could claim to be the phone, and the page says so.
- Who is calling comes from serve's `X-Forwarded-For` and whois, trusted only because the socket is the user's. Serve's identity headers name the user, the same for every device. Serve replaces forged `X-Forwarded-*` and `Tailscale-User-*` headers, but `Origin` passes through: every change is a POST, and every websocket is checked against it.
- The socket sits in a 0700 folder, since Bun binds it before it can be chmodded.
- The terminal is the relay's `attach` in Bun's pseudo-terminal. Closing the tab ends only the phone's zmx client, and the phone stays in control, as a Mac whose link dropped does.
- The protocol version goes up once, for devices as askers and for the controller's name in `status` and `sessions`. Every Mac and the headless host then run one commit (ADR 0009).
- The server asks nobody outside the tailnet, except to push a notice to the phone: [ADR 0038](0038-each-hosts-phone-page-server-pushes-notices-to-the-phone-through-the-vendors-push-services.md) adds that one outbound request, to the vendors' push services, with its own rules.
- Funnel stays off. Nothing in Varnick or the installer runs `tailscale funnel`, and each publishes only the one mount 8444 (see the note at the end).
- On a headless host a device can be in control. This amends ADR 0009's "always in control" by a Mac.

## Changed by the user, 2026-10-06: Launchy and the installer publish 8444 themselves

The user no longer runs `tailscale serve` by hand. The sentences above were edited to match, and these are the rules, kept here and nowhere else:

- **On a Mac,** with Serve the phone page on and the server running, Varnick runs `serve --bg --https=8444 <target>` (the server's socket, or its loopback address). It runs `serve --https=8444 off` when the setting goes off. It looks again at launch, on a change and on Try again, and Settings says Published, Publishing, Unpublishing or why not. Nothing retries by itself.
- **A socket refused to a Mac's user** (Homebrew's tailscaled 1.102.5, which this Mac got on 2026-10-06). Serve answers `401 Unauthorized: must be root, or be an operator and able to run 'sudo tailscale' to serve a path or Unix socket`. For a path or a Unix target tailscaled lets only root through, or an operator whose `sudo --other-user=<user> --list tailscale` it can run; it is started by launchd with no PATH, so that sudo can't find `/opt/homebrew/bin/tailscale` and fails even for an operator in `admin`. A loopback proxy needs no such check. Varnick handles it so:
  - **Fallback, with no click.** A publish to a socket refused that way restarts the server on loopback and publishes there in the same run. Settings says the page is on loopback and any program on the Mac can reach it. The mount moves from the socket to loopback by the ours-or-the-user's rule below.
  - **Remembered.** The refusal is kept in UserDefaults with the Tailscale version that gave it, and while it stands every launch listens on loopback and tries no socket. It ends when the version differs, so an upgraded tailscaled gets one try and, if refused again, falls back again, and when the setting is turned on, so a toggle tries once as the user.
  - **The button, Use a socket,** shows only on loopback for this reason. It restarts the server on the socket and publishes as the user, so it succeeds with no prompt once the fix below is in. Only if that is refused again does it run the same `serve` as root through `osascript`'s password prompt, the one place Varnick asks for a password. Root runs the user-owned `/opt/homebrew/bin/tailscale`, the same exposure as `sudo tailscale`. On success the socket is recorded as published and the refusal ends, so a later launch finds 8444 on the socket and asks for nothing. On a cancel, a failure or two minutes without a password it returns to loopback and says why. A conflict, Funnel or an unreadable state is refused before anything restarts or asks.
  - **The fix outside Varnick** is to give launchd's PATH Homebrew's: `sudo launchctl config system path "/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin"`, then a reboot.
- **On the Ryzen,** `install-peer.sh --page` publishes 8444 to the unit's socket once the page answers, and a plain re-run keeps or puts back the mount. `--no-page` and `--uninstall` take it down. `PAGE_VERIFY=ok` is part of every run that publishes. The refused socket above doesn't apply there, and the installer is unchanged: Linux sudo's `secure_path` normally finds `tailscale`.
- **One mount, never funnel:** only `https:8444` is ever served or unserved, and `tailscale funnel` is only ever asked its `status`.
- **Fail closed:** with Funnel on for 8444, or Funnel's or serve's state unreadable, nothing is published. On the Ryzen that also disables and stops the unit, and a mount this run just made is taken down if Funnel turns on right after.
- **Ours or the user's:** only `<target>` (the address the server has now) and the address Varnick last published, which a Mac records in UserDefaults (`phonePagePublishedTarget`), count as this page's. A mount at the recorded one but not the current one (the mode changed) is moved. Anything else on 8444 is the user's: another target (a `127.0.0.1:18444` the user mounted included, when it isn't the current one), a TCP forward, or other paths beside `/`. It is shown as a conflict and neither overwritten nor unpublished, whichever way the run goes; on the Ryzen the run ends non-zero.
- **Taking it down** (the setting off, `--no-page`, `--uninstall`) happens only where the port points at one of those. On a Mac only after the setting changes or with a session still running, so a plain launch with the setting off runs no `serve`. It is run as the user, which tailscaled lets through for a mount made as root: the config sent then holds no Unix target (read in `authorizeServeConfigForGOOSAndUserContext`, v1.102.5, and not run against a root-made mount), unless another path or socket is mounted on the node, which answers 401 and shows.
- **A failed publish** leaves the server running and the page unpublished, with the reason (serve's first line of complaint, or "didn't finish in 25 s"). Every `serve` call has a 25 s deadline and every read 8 s, on both sides.
- **`PAGE_PUBLISH_PORT`** (an installer environment variable, default 8444) moves only the port published, for a check's throwaway port such as 8449. The unit's `VARNICK_PAGE_PORT` is always 8444, so a page published elsewhere refuses a browser with 421 (its Host check), which still shows serve reaching the socket.

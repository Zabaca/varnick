# A headless host runs Varnick's relay alone, and an installer builds it there

A machine with no Varnick app, the always-on Ryzen, is a peer like a Mac. Its relay, a Linux build of the one the Macs run (`varnick-peer`, from `Packages/VarnickPeer`), is all of Varnick there: it answers every request itself from zmx and a state folder it owns, started per SSH request with nothing resident. The protocol and its checks live once in that Foundation-only package, which the app and the Linux relay both build; hosts differ at one seam, `PeerHost`, with a Mac adapter in the app and a headless one in the relay. A Mac adds it by address and starts sessions there with `^linux`, always in control of them. (A Device can be in control there too: ADR 0011.) Its hello says `headless` (optional, protocol 11), so a Mac's row reads "relay only" where a Mac peer's reads "Varnick running". The problem and its options are in `docs/problems/sessions-hosted-only-on-macs/`; this records option 01. It amends ADR 0007's "the host's Varnick runs each session": on Linux, claude signs in from its credentials file, which is why ADR 0007 had the app start claude, so a headless host's relay starts sessions itself from an SSH login.

## Considered Options

- **Installing the relay at the macOS path on Linux** (`~/Library/Application Support/Launchy`): not chosen. It needs no change on a Mac, but puts a macOS folder on Linux to save one line there.
- **A cross-built relay** (a Swift SDK for Linux on a Mac): not chosen. It would put a second toolchain on a Mac. The Ryzen builds its own relay instead, with Swift from swiftly installed there once.
- **Option 02** (a separate relay written without the shared package) stays on record as the fallback should Swift fail to build the relay on the Ryzen.

## Consequences

- The relay's install root is the folder its binary is in, links resolved, as zmx is found beside it. `~/.varnick` holds `varnick-peer`, its own pinned `zmx` (never the existing browser terminal's), `src/` (the package), `config.json`, `build` (the commit it was built from) and `state/`. A copy elsewhere has its own config and state, so a check never needs to touch the real ones.
- `state/` is written only by the relay, under an exclusive `flock` on `state/.lock` (a shared one to read), each file written to a temporary file and renamed into place. A headless host never touches UserDefaults, and keeps its state under the install root rather than `/tmp`, which is cleaned. zmx's own sockets are in `/tmp/zmx-<uid>` there, as on the Macs.
- `scripts/install-peer.sh <user@host>` sends `Packages/VarnickPeer` at the Mac's commit and builds it on the host, static (`--static-swift-stdlib`, so removing or replacing the toolchain can't break the relay). Nothing is built or installed on a Mac. Re-running converges: the id, config and zmx stay and the binary is replaced beside the running one. Its far half is piped into `bash -s` and prints `KEY=value` markers that the near half judges, because Tailscale SSH reports every remote command as exit 0.
- A Mac's SSH command tries the macOS link and then `$HOME/.varnick/varnick-peer`; the hello's `headless` field is what moved the protocol to 11. Every protocol bump means reinstalling the headless host from the Macs' commit, since two builds on different protocols can't use each other. Amended by ADR 0013: that reinstall is the Upgrade button on the host's row in Settings › Peers (and in Upgrade all), which runs the installer from a Mac at origin/main (`--commit`) and judges it by its markers; running it by hand still works.
- With `--page`, the installer also puts the Phone page under the install root (`PhonePage/`, `phone/` for its socket) and a systemd user unit that runs it, and removes them with `--no-page` or `--uninstall`; ADR 0011 holds why, and publishes 8444 to it with `tailscale serve` (the note at the end of ADR 0011 has the rules).
- The sessions it starts are records in `state/sessions.json`, and its relay creates each in zmx through a pty of its own, so a session outlives the ssh call that made it. `rows` and `pages` answer as a host with nothing yet, so a Mac's sync stores nothing and logs nothing for them. Its ended sessions are in `recent`, and a Mac's reconnecting pane can start again a session a reboot took (the rules are in `docs/agents/where-it-breaks.md` › Peers).

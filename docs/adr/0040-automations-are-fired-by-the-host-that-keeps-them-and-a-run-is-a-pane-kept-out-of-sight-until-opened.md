# Automations are fired by the host that keeps them, and a run is a pane kept out of sight until opened

Builds on [ADR 0004](0004-pane-processes-live-in-zmx.md) (a pane's process lives in zmx), [ADR 0010](0010-a-panes-turn-comes-from-hooks-that-write-to-the-pane-folder.md) (the turn and the notices come from hooks that write to the pane folder) and [ADR 0030](0030-the-outline-is-one-json-file-varnick-owns-of-bullets-and-placements-never-written-over-when-unreadable.md) (a file that can't be read is never written over). The problem and the option are in `docs/problems/prompts-cant-run-on-a-schedule/`, option 01, accepted 2026-10-15 with the user's decisions of that day. The mechanics and what breaks them are in `docs/agents/where-it-breaks.md`, Automations.

An **Automation** (`CONTEXT.md`) is a saved prompt with a folder, an optional agent and a cadence. The host that keeps it fires it: nothing else decides when, and no other machine is needed awake. A **Run** is one slot's session: a Claude pane started exactly as a typed prompt is, in zmx, in a tab that nobody sees until the user opens it. This ADR covers slice 1, this Mac alone; the headless host's half (a systemd user timer that runs the relay once a minute, protocol 29) is slice 2 and amends [ADR 0009](0009-a-headless-host-runs-varnicks-relay-alone.md) then.

- **Fired by the running Varnick.** Once a minute, at launch and a few seconds after a wake. Nothing resident is added: no launchd job, no daemon, so a run needs nothing the app's own launch doesn't give it (ADR 0013 records why launchd stays out of sessions). A Mac that sleeps or a Varnick that is quit fires nothing, and catches up once.
- **Anything the user does starts the clock from now.** A new automation, a changed cadence or zone, an automation switched on and Automations switched on all set the last slot to the time of the change, so a slot before it is never caught up. Only a sleep or a quit between two checks catches a slot up (once), and a Run now touches nothing.
- **One pure function says what is due,** in the shared package (`AutomationSlot.check`), so the relay calls it unchanged in slice 2. The newest slot since the last fired is due if it is under 12 hours old, every other slot since is recorded missed and never run. The cadence is a preset kept as data (every 15 or 30 minutes, every 1, 2, 3, 4, 6 or 12 hours, daily, weekdays, weekly at a time), in the zone of the Mac that saved it.
- **A run is a typed prompt.** It has the same command line, hooks, transcript, search, notices, resume and pane. Its record is marked as a run of the automation, and unopened. Its MCP config lists `notify` alone, so it never gets Screen access's or Panel access's tools. Its permissions are Varnick's Skip permissions at its start, unless the automation overrides them (Ask, Allowed tools only as `--permission-mode dontAsk`, Skip), and are stored on the record like any pane's.
- **Kept out of sight by a rule on lists, not by a place.** The tab stays in the model's list of tabs, which saving, the launch sweep, the notifier and the host's listing read, so a restart restores it and its notice still comes. `shownTabs` leaves it out of every list for the eye until it is opened. Turning Automations off opens every run at once.
- **The list is a file of its own** (`automations.json`), never `sessions.json`, written only by the running Varnick and never over a file it can't read or that a newer build wrote. Each automation keeps its last 20 runs.
- **A run ends its process, not its conversation.** A turn past the working limit, 24 hours of waiting on the user, or 10 minutes of Done with nobody opening it ends the run's zmx session, and its tab closes into the run list and never Recent. Opening an ended run resumes the conversation in a new tab.

## Considered Options

- **Print mode (option 02):** not chosen. A dialog becomes a refusal and the run is not a pane, so it has no live view, no Needs you and no resume as a session.
- **launchd or a detached daemon on a Mac:** not chosen. The user's rules keep both out of sessions (XProtect once killed a Claude process that ran `launchctl`), and a run inside the running Varnick needs neither.
- **Run tabs in a list of their own (not in `tabs`):** not chosen. Every place that looks a pane up, saves, sweeps or notifies would have to read two lists, and one that missed would lose a notice or kill a session silently. A list that forgets to leave a run tab out is seen at once.
- **Skip permissions never inherited:** the user chose the opposite. A run follows the setting a typed prompt follows, and each automation can override it.

## Consequences

- **An unattended run on a Mac can reach the screen** through the macOS grants every pane inherits (`panes-share-launchys-permissions`), with a shell and no tool for it. With Skip permissions on, which is every install that predates the setting, a run runs any command without asking. The editor says so; only closing that problem would change it.
- **Each run draws on the user's Claude subscription,** unattended. The 15-minute floor and the one-run-at-a-time rule bound it; nothing caps it.
- **Until the headless host has runs (slice 1),** a run tab is listed to paired Macs and the phone as an ordinary tab, which is what lets the host's page server push its notices. Slice 2 marks it in the listing instead (the amendment below); the page server still reads it whole, so it still pushes.
- **A run ended at its limit tells no one.** The pane is gone, so neither the Mac's notifier nor the page server has a turn to read; it is marked in the run list only.
- **A session can make an automation that runs unattended,** as the amendment below records. Whoever reads a session's output with Anthropic reads the prompts the list shows.

## Amendment, 2026-10-15: sessions make, edit and switch automations

A Claude session on this Mac can list, make, edit and switch automations through four tools on Varnick's MCP server (`automations_list`, `automation_create`, `automation_edit`, `automation_switch`), with no approval step of Varnick's. The user decided it; this replaces the deferral above (slice 3 of option 01, this Mac only).

- **Behind the Automations switch and nothing else.** The tools are listed in every Claude pane started or restarted while the switch is on, never in a run's session (which stays `notify` alone) and not behind Panel access, whose grant is reading every screen and pressing keys. The running Varnick refuses a call while the switch is off.
- **Answered by the running Varnick, written only through the automation store,** as Panel access's calls are: one request line on the socket, the checks in a fixed order, the file's one writer. Not through the `notify` path, which records a call after it has been answered and so can't hand back an id, a list or a refusal.
- **A session may not set Skip, but it may grant an unattended run tool rules.** It may follow Varnick's Skip permissions setting, choose Ask or Allowed tools only, set `allowed_tools` (a broad rule such as `Bash` included), and switch an automation the user set to Skip; it can't set Skip or edit such an automation. So with Skip off, a session can give an unattended run more than a typed prompt gets. That is the user's decision, relayed by the coordinator on 2026-10-15, and the mark names the rules a session set so the user can see it.
- **The user's loss stays the user's.** Delete (which drops the run history) and Run now are not tools; a session that wants an automation to stop switches it off.
- **The user sees a mark, not a notice,** on the automation's row and beside its runs until they have seen it. A run raises its own notices, so an automation made or turned on while the user was away is seen at its first run at the latest.
- **Claude Code's own dialog is the only approval:** the tools are not in a session's allow list, so a pane with Skip permissions off asks before each call.

Considered and not chosen: a `propose` tool the user approves (the user decided against an approval step); tying the tools to Panel access (it would make the user grant reading screens and pressing keys to get this); a switch of their own (the Automations switch is already that decision); a notice besides the mark (it is mostly raised for the pane the user is looking at, needs a message only the hook writes or a new kind in both languages, and the first run tells them anyway).

## Amendment, 2026-10-15: the headless host fires its own (slice 2, protocol 29)

A headless host keeps and fires the automations a Mac saved on it, with every Mac asleep. The user decided the four open points: the saving Mac attaches to each headless run as an unseen view; the four tools stay this Mac's and the host's automations are managed in Settings only; "Varnick's setting" on the host is the host's own Skip permissions; the Automations switch is each Mac's own.

- **A systemd user timer runs the relay once a minute** (`varnick-peer tick`, a `oneshot` service with `KillMode=process`), so nothing stays running between ticks and a run's zmx session outlives the tick that started it. What was measured on the user's machine, and what it does not show, is in `docs/agents/where-it-breaks.md`, Automations. Installed once with the installer's `--automations`.
- **The host keeps the Macs' two files in its state folder,** under its state lock, and fires with the Mac's rules (the slot function, the overlap rule, the limits, the catch-up window, the permissions stored on the record). A run there is labelled for the Mac that last saved the automation, which holds the unseen view, so the host's page server routes by that Mac's presence and the notices are the pane's as they are on a Mac.
- **A run nobody opened is marked in the host's `tabs`,** so other Macs keep it out of their lists while their Automations switch is on and the phone lists it under Runs. Opening it from anywhere takes the mark off.
- **Considered and not chosen:** the saving Mac following the run without a view (it needed a change to the push rule and a notice with no pane); the four tools taking a host now (the engine slice adds a Task and its input to the same requests, and a host's folders can only be checked there); turning one Mac's Automations switch off also switching its automations off on the host (it would lose their own on and off).
- **Consequence:** one ssh channel per run going, on the connection the panes share, for the unseen views.

## Amendment, 2026-10-29: Automations is no longer an experimental switch

At the user's word (2026-10-29), Automations is always on, as Panel access and Sessions can open panes stopped being switches on 2026-10-17 (ADR 0031's amendment). The `automationsOn` setting and its row in Settings › Experimental are gone, and the stored key is removed at launch, not carried over. Settings › Automations is always listed and the board's Runs tab is always shown; Tasks stays an Experimental switch and keeps its own guards.

- **What the switch gated:** whether the runner checked and fired anything; whether Run now worked; whether any Claude pane listed the four automation tools (and the running Varnick refused a call while it was off); whether Settings › Automations and the Runs tab existed (Tasks alone kept the tab); whether this Mac asked headless hosts for their tabs and set their run tabs aside; and, when it went off, the release of every unopened run tab as an ordinary tab. It was also the user's consent: with it off, no install could run an unattended prompt or have a session make one.
- **Consequence:** every install now lists `automations_list`, `automation_create`, `automation_edit` and `automation_switch` to every Claude session it starts or restarts (a run's session still lists `notify` alone), and fires a saved automation on its cadence with no consent gate beyond saving one. A session can still not set Skip, delete or run one now. At the first launch of this build, an install whose switch was stored off starts every saved automation's clock from now (`startAutomations`, as turning the switch on did), so nothing before it is caught up and a stale enabled automation does not fire at once; an install whose switch was stored on, or never stored, keeps its clocks. This is not checked by running it.
- **Gone with the switch:** `AutomationRefusal.off`, the "Automations is off" Run now refusal, the switch's watch (its switch-on reset of every `lastSlot` and its switch-off `releaseRuns`), and the Runs tab's watch of both switches. `releaseRuns` stays for an automation's deletion, which still releases its unopened runs, and is now always given the automation.
- **Unchanged:** an automation follows Settings › Claude's Skip permissions unless it says otherwise; the four tools and their limits; a run's session lists `notify` alone; each automation's own on and off switch; `automations.json` and `runs.json`; protocol 29, the headless relay and its timer; the headless host section of Settings › Automations. The items `docs/agents/where-it-breaks.md` lists as unverified at runtime (the restart catch-up, the headless host, a run past its limit) are no more verified by this change.

## Amendment, 2026-10-29: a run may file a bullet in the Outline, and read nothing (`outline_append`)

At the user's word (2026-10-29), so that an automation such as the daily recap can file its result where the user keeps their notes, an automation's run may be given one write-only tool, `outline_append(heading, text, note?)`. It reverses one line of this ADR and of ADR 0031's amendment of 2026-10-17, "a run of an automation lists `notify` alone", for this tool and no other. This is the one statement of the rule; the code is `OutlineAppendTool` (the arguments, shared with `Varnick --mcp`) and `OutlineAppendAccess` (the call).

- **What it does.** It finds the top-level bullet whose text is exactly `heading` (case-sensitive, the first if there are two), makes it at the end of the top level if there is none, and adds a new last bullet under it with `text` and the optional `note`. It answers the new bullet's id and whether the heading was made, and never returns any of the Outline. It reads, lists, moves, changes, completes and deletes nothing, and one call adds one bullet. A heading whose bullet is marked done is refused ("the heading is marked done; open it or pick another heading"): its row can be hidden, and a second heading of the same name would be a duplicate.
- **Bounds, checked before anything is saved and named in the refusal.** `heading` 1 to 80 characters and at most 320 UTF-8 bytes, `text` 1 to 300 characters and at most 1,200 bytes (a character can carry any number of combining marks, so characters alone bound nothing), each one line, a line break being any of U+000A to U+000D, U+0085, U+2028 and U+2029; `note` at most 20,000 bytes of UTF-8, line breaks allowed; no tabs or other control characters.
- **Opt-in per automation.** An automation's run lists the tool only when its `allowed_tools` holds the exact rule `mcp__varnick__outline_append` (a server-wide rule does not name it), read at each start like the other sets. That also lets the run call it without a dialog, so the mark the user sees on the automation already names it. **Taking the rule out of the allowed tools stops future runs only:** a run already going, or one resumed later from its own conversation, keeps the tool until it ends, because its record holds the rule it started with. A Task step, the voice session, an ordinary pane (which has `outline_act`) and a headless host's run never list it, and the running Varnick refuses a call from any pane that is not an automation's run whose record names it.
- **The app's own state stays the writer.** The call is a socket request of its own (`outlineAppend`, told apart as the automation requests are), answered on the main actor in a fixed order: Varnick starting, the pane, the record naming the tool, the arguments' limits, the Outline switch, the file read, then one edit. The edit is `OutlineEdit.insert` with `lastUnder` through `Outline.performForSession`, as `outline_act`'s `add` is: the heading made and the bullet under it are one edit and one undo step, the saver writes the file, and the rules of ADR 0030 hold (off means nothing loads, writes, moves or deletes the file; an unreadable or newer file is refused and never written over). Right before the edit it checks that the heading is still where it was found or still absent, and that the run is still one.
- **Consequence.** An unattended run, which may have been steered by what it read, can put text of its own composing into the user's Outline, where it shows like any bullet, on this Mac and on the Phone page of a listed device. It cannot read the Outline, so nothing of it goes to Anthropic through this tool. The user can undo it with one ⌘Z, delete it, or stop future runs by taking the rule out of the automation's allowed tools (above).
- **Not changed.** Skip-permissions inheritance, the other tools, the Outline switch, and what the earlier amendments leave unverified at runtime. This change was built and its pure parts checked (`make check-mcp`, `make check-slots`, `Varnick --outline-check`); a run's call into a live Outline has not been hand-tested.

- Amended by ADR 0041: an Automation is a trigger (a cadence, a Task and its input), and its Runs are kept in a runs file of their own.
- Amended by ADR 0042: A pane kept out of sight until it is opened can also be the host's voice session, which is not a run: it has a pane's full MCP set.

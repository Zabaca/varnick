# A Chromium pane embeds zebkit and serves CDP, so a session can drive the page the user sees

A session couldn't read or drive a Browser pane: `pane_read` gave its kind and title, and acting meant clicks at screen coordinates. The **Chromium pane** is a second web pane kind whose page is Chromium 157, from [zebkit](https://github.com/ikey4u/zebkit) 0.4.0 (Chromium as a library, LGPL-2.1), attached to the pane's own NSView under the Browser pane's address bar. The engine serves the Chrome DevTools Protocol on 127.0.0.1, and `pane_read` on a Chromium pane gives the endpoint and the pane's target, so a session drives the same page the user is looking at. Built as a prototype at the user's word of 2026-11-11, with no problem file. A standalone app proved it first: nodriver ran a Google search and a Google sign-in step in it.

- **One engine per process, started at launch.** zebkit starts once and never again after it stops, and only outside any run of the main run loop: its message pump counts the main run loop's entries and exits, and an engine started inside a run (the first build started it lazily, from a main-queue block) sees that run exit without its entry and traps, which crashed Varnick on 2026-11-11. So Varnick `dlopen`s `Zebkit.framework` first thing in `applicationDidFinishLaunching` (a late call stops at a precondition), only once a Chromium pane has shown in the account (a flag in Varnick's defaults, never cleared yet) (an idle engine and its helpers cost about 200 MB). The first Chromium pane on a Mac asks for a restart. A build without the framework runs (the tile isn't listed), and `--mcp` never maps it. Every Chromium pane shares the engine, its profile (`chromium-profile` in Varnick's support folder) and its CDP endpoint, on a port the system picks at each start.
- **One timer pumps the engine.** zebkit asks for a pump through a wakeup callback, from any of its threads, and every pump ends by asking for the next. The first build queued a main-queue block per wakeup, so the pumps never died out and grew by one with each wakeup from an engine thread; and a pump was measured at about 10 ms, waiting in an event loop of its own (zebkit.h says it doesn't wait), which inside a main-queue block holds the main queue. On 2026-11-11 every Claude pane stopped answering within minutes of a Chromium pane opening. So one run-loop timer in the common modes holds the earliest deadline asked for, and the pump runs from its call, where the pump's loop still drains the main queue; every pump goes through that timer, the first after start and the one after a page is made too; a pump the engine refuses is asked for again 10 ms later. Measured on a results page over three minutes, in a harness: a main-queue block waited up to 1.2 s and rising with a block per wakeup, under 2 ms with the timer, at under one pump a second. A pump over 250 ms is logged; it is ordinary when an event the pump delivered ran a menu or a drag, since the pump delivers Varnick's events too.
- **The framework sits beside the binary.** Its helpers crash at start when the host executable is anywhere else. `make build` fetches the release, pinned by SHA-256 like zmx and Bun, into `.build/release`. It isn't in `Varnick.app` yet.
- **Signed with Varnick's identity.** The hardened runtime's library validation refuses the package's ad-hoc framework, so the build signs its helper and then the framework with the same identity. Neither gets the hardened runtime: the helper runs the renderers, whose V8 needs JIT.

## Considered Options

- **Linking the framework:** passed over. Varnick would fail to start without it, and every launch would map it.
- **Off-screen views drawn by Varnick:** passed over for now. `attach_native` puts the page in the pane as a subview, with the system's own input, and needs no event forwarding.

## Consequences

- **A session can read and act in a logged-in page.** It goes to Anthropic with the session, as a terminal's screen does. `docs/privacy-and-security.md` and where-it-breaks ("What the tools do not promise") say so.
- **CDP has no password.** Any process on this Mac can drive the profile while the engine runs, as with Chrome's `--remote-debugging-port`.
- **Accepted gaps of the prototype:** no switch in Settings › Experimental (the tile shows whenever the framework is there); popups open as zebkit's own window, not as a pane; `pane_open` has no Chromium kind; the helpers aren't counted in Resources.

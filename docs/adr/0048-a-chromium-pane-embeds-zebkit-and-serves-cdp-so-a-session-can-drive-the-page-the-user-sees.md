# A Chromium pane embeds zebkit and serves CDP, so a session can drive the page the user sees

A session couldn't read or drive a Browser pane: `pane_read` gave its kind and title, and acting meant clicks at screen coordinates. The **Chromium pane** is a second web pane kind whose page is Chromium 157, from [zebkit](https://github.com/ikey4u/zebkit) 0.4.0 (Chromium as a library, LGPL-2.1), attached to the pane's own NSView under the Browser pane's address bar. The engine serves the Chrome DevTools Protocol on 127.0.0.1, and `pane_read` on a Chromium pane gives the endpoint and the pane's target, so a session drives the same page the user is looking at. Built as a prototype at the user's word of 2026-11-11, with no problem file. A standalone app proved it first: nodriver ran a Google search and a Google sign-in step in it.

- **One engine per process, started when a page first wants it** (amended 2026-11-12; it was started at launch, behind a defaults flag and a restart). zebkit starts once and never again after it stops, and only outside any run of the main run loop: its message pump counts the main run loop's entries and exits, and an engine started inside a run (the first build started it lazily, from a main-queue block) sees that run exit without its entry and traps, which crashed Varnick on 2026-11-11. So the start is made by `VarnickApplication` as it dispatches an event of its own (`RunLoopGate`: application-defined, with a subtype and data1 that are never those of the event zebkit leaves its wait by), and only when no run of the main loop is under way, which the gate takes from two sources: a run-loop observer in the common modes, added first thing at launch, whose count of entries and exits is zero, and the loop's own current mode being none (which also sees a run in a mode the observer can't). A pane on screen that finds the engine not running asks for it, shows that it is starting, and loads when told the start settled. The gate posts its event at the request; one that is dispatched inside a run (the nested loop of a block, say) is let go, and the exit of the outermost run posts it again, so the start comes by itself at the first dispatch between runs, never by polling the main queue from inside a run. While the start waits a timer ticks every 2 s, for two things: an event posted and still not dispatched is replaced (a loop that drops events it doesn't know would lose it), and a wait of 10 s is logged once with the count and mode, so a count stuck above 0 isn't silent (an exit with no entry is logged once too). A pane in a tab that isn't on screen has no window, so it asks for nothing until shown (from the code; not yet seen). A failed start is final for the process: the pane says so in a plain sentence, and the reason is in the log. `chromiumStartsAtLaunch` is no longer read; a copy left in defaults is ignored and not deleted. A build without the framework runs (the tile isn't listed), and `--mcp` never maps it. Every Chromium pane shares the engine (an idle one with its helpers costs about 200 MB, from the first page until Varnick quits), its profile (`chromium-profile` in Varnick's support folder) and its CDP endpoint, on a port the system picks at each start. **Measured in a throwaway harness, not kept in the repo**, that compiled the shipped gate and started the real engine, each case in a fresh profile, then pumped 15 s with a main-queue wait probe every 50 ms: a start requested from a main-queue block started at the next dispatch, 0.03 s later, with the main loop having no current mode; one requested before a block opened a nested loop of its own (default and modal-panel modes) waited the 4 s the block ran and started 0.05 s after it returned, and one that waited 13 s logged the wait once; one requested a second into a nested loop opened from an event's dispatch (a modal panel's shape; default and modal-panel modes) started at once, inside that loop; one whose posted events a loop threw away started 1 s after the loop closed. Every case then pumped normally (the main-queue wait never passed 20 ms), and none trapped. **Untested, to check by hand:** a real menu's tracking loop, a real modal panel (the folder picker), a sheet, and a pane or divider drag; whether those loops hand the gate's event to `sendEvent` or drop it (the timer covers a drop, at a cost of seconds); inside Varnick itself rather than the harness.
- **One timer pumps the engine.** zebkit asks for a pump through a wakeup callback, from any of its threads, and every pump ends by asking for the next. The first build queued a main-queue block per wakeup, so the pumps never died out and grew by one with each wakeup from an engine thread; and a pump was measured at about 10 ms, waiting in an event loop of its own (zebkit.h says it doesn't wait), which inside a main-queue block holds the main queue. On 2026-11-11 every Claude pane stopped answering within minutes of a Chromium pane opening. So one run-loop timer in the common modes holds the earliest deadline asked for, and the pump runs from its call, where the pump's loop still drains the main queue; every pump goes through that timer, the first after start and the one after a page is made too; a pump the engine refuses is asked for again 10 ms later. Measured on a results page over three minutes, in a harness: a main-queue block waited up to 1.2 s and rising with a block per wakeup, under 2 ms with the timer, at under one pump a second. A pump over 250 ms is logged: it is the engine's own work, or something run inside its wait that ran a loop of its own, and Varnick's clicks and keys wait until it returns (next bullet).
- **The pump's wait is Varnick's, not AppKit's.** Inside a pump the engine waits by asking the application for its next event (any event, the default mode, no end) and leaves by posting an application-defined one. With AppKit answering, a mouse press whose release came after a pump lost its click: on 2026-11-11, in the projects column, 10 of 10 presses with a pump between down and up never tapped, and 38 of 38 without one did; keys were unaffected. So Varnick's application object (`VarnickApplication`) answers that one call with a plain run of the run loop and takes the leaving event as the signal to stop, so the engine's wait never reads AppKit's event queue and a pump no longer delivers Varnick's events: they are handled once it returns. After it, 34 of 34 presses tapped, 5 of them with a pump between down and up, and in the harness a pump took about 0.07 ms where it had taken 5 to 10 ms. It rests on how zebkit 0.4.0 waits and leaves. A release that waits another way gets AppKit's answer, and the lost clicks, without an error; one that waits the same way but leaves another way gets AppKit's answer after 5 s, with a line in the log, since nothing else would end the wait. A loop opened inside the wait asks AppKit as ever, and a leaving event posted while one is open is passed on to it. **Untested:** how long input waits while a session drives a page hard (a context menu and `alert()` are answered in the next bullet).
- **What a page asks of its pane is answered by Varnick, never by the engine's own windows** (amended 2026-11-13, option 02 of `two-browser-panes`, step 3; the Chromium tile only, page panes stay WebKit). Every answer is a handler set on the page, and on each window it opens, since a popup would otherwise be decided for by its opener's handlers and report to none. Measured in a harness that ran Varnick's pump (the timer and the application-answered wait) in a throwaway profile, with script run as the person's act.
  - **Dialogs.** `alert` returns, `confirm` is false, `prompt` is null (WebKit's answer with no UI delegate) and "leave this page?" leaves. The handler answers inside its callback, since the engine holds the page until it is answered, so the engine's modal alert never opens. Measured: `[false,null,"alert-returned"]`, beforeunload left, and no loop of any other kind inside a pump. The option's recommendation said `prompt` is answered empty; null is what is built.
  - **The context menu** is the engine's own item list, shown by `zebkit_view_context_menu_show`, which runs the system's menu loop until the menu closes. Inspect Element is not among the items, and is dropped. Measured: a main-queue block queued from the callback runs inside the pump's wait, where the menu's loop held the engine (four nested waits in the event-tracking mode); run from the pump's own timer, the loop starved the pump, since a timer is not fired again inside its own callback (a script run while the menu was open never answered); run from a one-shot timer of its own set after the pump returns (`ChromiumPump.afterPump`), the engine kept being pumped, a script run while the menu was open answered, and the main queue stayed responsive.
  - **New windows.** Every `target=_blank`, `window.open` and sign-in popup arrives as a view, and is put in a pane of its own beside the page's, which takes focus (decided, not in the option: as a new tab would). Only a `window.open` popup is linked to its opener (`window.opener` and `postMessage` worked); a `target=_blank` window has no opener, as in Chrome. The view is attached to a view of ours inside the callback, because its own window is on screen from its creation until something attaches it (seen: visible at the callback, hidden once attached); the pane is made around it a turn later, and a popup the site closes closes its pane. A tab waiting for Take over can't take a pane, and a tab with no room (the page's pane would fall under the minimum width) can't either: the pane says so and the window closes.
  - **Downloads.** The page's handler makes a free name in Downloads (an empty file made exclusively, which the engine replaces: `report.bin`, `report (1).bin`) on a background thread, then answers with that path from the main one; the engine holds the download 30 s for the answer, so a macOS prompt for the Downloads folder never blocks a pump (**unverified:** the harness never saved to `~/Downloads`, so the prompt's behaviour, and a refusal cancelling the download with that said in the pane, are from the header and code alone). The engine does not set macOS's quarantine attribute, and one set on the reserved file is lost when the engine replaces it, so Varnick sets it (`com.apple.quarantine`, through the resource key) at once, inside the pump, when the download's report says it is complete; the note "Saved X in Downloads." is queued, and goes to the pane of the page that opened a popup as well, since the popup's pane may be gone. A pane closed meanwhile cancels what is in flight (decided, not in the option). A page that closes itself leaves its downloads running with no more reports, so each of its files is marked when it first has contents (the engine keeps it empty and writes beside it until the end), checked every 2 s for 10 minutes and removed if still empty then. Empty reserved files are also removed at quit; a restart by SIGTERM skips quit and leaves those of downloads under way. A navigation to a file also reports a failed load to the page's load callback, which the failure card of step 6 must not take for a failure.
  - **A view freed by the engine** (its close callback is the last use of it) is forgotten at once, inside the callback; only the pane's own work is queued.
  - **Untested, to check by hand:** the pane's focus and layout after a popup opens, a context menu's items (Back, Forward, Reload, Copy, Open Link in New Window, Save Image As) run from the menu, a Japanese input method in a field. **Unverified, from the headers alone:** `<input type=file>` and File System Access pickers, for which the engine shows its own system dialog when no function is set (`zebkit_view_on_file_chooser` is the hook; not built in this step), a sheet or modal inside a pump being unknown; a `<select>`'s native popup possibly tracking inside a pump; CDP's `Target.createTarget` making an engine window outside the panel; a page looping `alert()`, which each call answers at once and so keeps the pump busy; and a pane closed while its context menu is open inside `zebkit_view_context_menu_show`.
- **The framework sits beside the binary.** Its helpers crash at start when the host executable is anywhere else. `make build` fetches the release, pinned by SHA-256 like zmx and Bun, into `.build/release`. It isn't in `Varnick.app` yet.
- **Signed with Varnick's identity.** The hardened runtime's library validation refuses the package's ad-hoc framework, so the build signs its helper and then the framework with the same identity. Neither gets the hardened runtime: the helper runs the renderers, whose V8 needs JIT.

## Considered Options

- **Linking the framework:** passed over. Varnick would fail to start without it, and every launch would map it.
- **Off-screen views drawn by Varnick:** passed over for now. `attach_native` puts the page in the pane as a subview, with the system's own input, and needs no event forwarding.

## Consequences

- **A session can read and act in a logged-in page.** It goes to Anthropic with the session, as a terminal's screen does. `docs/privacy-and-security.md` and where-it-breaks ("What the tools do not promise") say so.
- **CDP has no password.** Any process on this Mac can drive the profile while the engine runs, as with Chrome's `--remote-debugging-port`.
- **Accepted gaps of the prototype:** no switch in Settings › Experimental (the tile shows whenever the framework is there); `pane_open` has a Chromium kind (amended 2026-11-13), a bridge until the `page` kind itself opens Chromium; the helpers aren't counted in Resources. (Popups, downloads, dialogs and the context menu are answered by Varnick as of 2026-11-13.)

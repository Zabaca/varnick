# A Chromium pane embeds zebkit and serves CDP, so a session can drive the page the user sees

A session couldn't read or drive a Browser pane: `pane_read` gave its kind and title, and acting meant clicks at screen coordinates. The **Chromium pane** was a second web pane kind (since 2026-11-13 it is no kind of its own: the Browser pane gets Chromium where it can run, see the bullet "Which engine a page gets" below) whose page is Chromium 157, from [zebkit](https://github.com/ikey4u/zebkit) 0.4.0 (Chromium as a library, LGPL-2.1), attached to the pane's own NSView under the Browser pane's address bar. The engine serves the Chrome DevTools Protocol on 127.0.0.1 on demand (amended 2026-11-13, below), and `pane_read` on a Chromium pane serves it and gives the endpoint and the pane's target, so a session drives the same page the user is looking at. Built as a prototype at the user's word of 2026-11-11, with no problem file. A standalone app proved it first: nodriver ran a Google search and a Google sign-in step in it.

- **One engine per process, started when a page first wants it** (amended 2026-11-12; it was started at launch, behind a defaults flag and a restart). zebkit starts once and never again after it stops, and only outside any run of the main run loop: its message pump counts the main run loop's entries and exits, and an engine started inside a run (the first build started it lazily, from a main-queue block) sees that run exit without its entry and traps, which crashed Varnick on 2026-11-11. So the start is made by `VarnickApplication` as it dispatches an event of its own (`RunLoopGate`: application-defined, with a subtype and data1 that are never those of the event zebkit leaves its wait by), and only when no run of the main loop is under way, which the gate takes from two sources: a run-loop observer in the common modes, added first thing at launch, whose count of entries and exits is zero, and the loop's own current mode being none (which also sees a run in a mode the observer can't). A pane on screen that finds the engine not running asks for it, shows that it is starting, and loads when told the start settled. The gate posts its event at the request; one that is dispatched inside a run (the nested loop of a block, say) is let go, and the exit of the outermost run posts it again, so the start comes by itself at the first dispatch between runs, never by polling the main queue from inside a run. While the start waits a timer ticks every 2 s, for two things: an event posted and still not dispatched is replaced (a loop that drops events it doesn't know would lose it), and a wait of 10 s is logged once with the count and mode, so a count stuck above 0 isn't silent (an exit with no entry is logged once too). A pane in a tab that isn't on screen has no window, so it asks for nothing until shown (from the code; not yet seen). A failed start is final for the process: the pane says so in a plain sentence, and the reason is in the log. `chromiumStartsAtLaunch` is no longer read; a copy left in defaults is ignored and not deleted. A build without the framework runs (its pages are WebKit's), and `--mcp` never maps it. Every Chromium pane shares the engine (an idle one with its helpers costs about 200 MB, from the first page until Varnick quits), its profile (`chromium-profile` in Varnick's support folder) and its CDP endpoint, served on demand (next bullet). **Measured in a throwaway harness, not kept in the repo**, that compiled the shipped gate and started the real engine, each case in a fresh profile, then pumped 15 s with a main-queue wait probe every 50 ms: a start requested from a main-queue block started at the next dispatch, 0.03 s later, with the main loop having no current mode; one requested before a block opened a nested loop of its own (default and modal-panel modes) waited the 4 s the block ran and started 0.05 s after it returned, and one that waited 13 s logged the wait once; one requested a second into a nested loop opened from an event's dispatch (a modal panel's shape; default and modal-panel modes) started at once, inside that loop; one whose posted events a loop threw away started 1 s after the loop closed. Every case then pumped normally (the main-queue wait never passed 20 ms), and none trapped. **Untested, to check by hand:** a real menu's tracking loop, a real modal panel (the folder picker), a sheet, and a pane or divider drag; whether those loops hand the gate's event to `sendEvent` or drop it (the timer covers a drop, at a cost of seconds); inside Varnick itself rather than the harness.
- **One timer pumps the engine.** zebkit asks for a pump through a wakeup callback, from any of its threads, and every pump ends by asking for the next. The first build queued a main-queue block per wakeup, so the pumps never died out and grew by one with each wakeup from an engine thread; and a pump was measured at about 10 ms, waiting in an event loop of its own (zebkit.h says it doesn't wait), which inside a main-queue block holds the main queue. On 2026-11-11 every Claude pane stopped answering within minutes of a Chromium pane opening. So one run-loop timer in the common modes holds the earliest deadline asked for, and the pump runs from its call, where the pump's loop still drains the main queue; every pump goes through that timer, the first after start and the one after a page is made too; a pump the engine refuses is asked for again 10 ms later. Measured on a results page over three minutes, in a harness: a main-queue block waited up to 1.2 s and rising with a block per wakeup, under 2 ms with the timer, at under one pump a second. A pump over 250 ms is logged: it is the engine's own work, or something run inside its wait that ran a loop of its own, and Varnick's clicks and keys wait until it returns (next bullet).
- **The pump's wait is Varnick's, not AppKit's.** Inside a pump the engine waits by asking the application for its next event (any event, the default mode, no end) and leaves by posting an application-defined one. With AppKit answering, a mouse press whose release came after a pump lost its click: on 2026-11-11, in the projects column, 10 of 10 presses with a pump between down and up never tapped, and 38 of 38 without one did; keys were unaffected. So Varnick's application object (`VarnickApplication`) answers that one call with a plain run of the run loop and takes the leaving event as the signal to stop, so the engine's wait never reads AppKit's event queue and a pump no longer delivers Varnick's events: they are handled once it returns. After it, 34 of 34 presses tapped, 5 of them with a pump between down and up, and in the harness a pump took about 0.07 ms where it had taken 5 to 10 ms. It rests on how zebkit 0.4.0 waits and leaves. A release that waits another way gets AppKit's answer, and the lost clicks, without an error; one that waits the same way but leaves another way gets AppKit's answer after 5 s, with a line in the log, since nothing else would end the wait. A loop opened inside the wait asks AppKit as ever, and a leaving event posted while one is open is passed on to it. **Untested:** how long input waits while a session drives a page hard (a context menu and `alert()` are answered in the next bullet).
- **What a page asks of its pane is answered by Varnick, never by the engine's own windows** (amended 2026-11-13, option 02 of `two-browser-panes`, step 3; built on the Chromium tile, which is how it was checked, and now on every Chromium page). Every answer is a handler set on the page, and on each window it opens, since a popup would otherwise be decided for by its opener's handlers and report to none. Measured in a harness that ran Varnick's pump (the timer and the application-answered wait) in a throwaway profile, with script run as the person's act.
  - **Dialogs.** `alert` returns, `confirm` is false, `prompt` is null (WebKit's answer with no UI delegate) and "leave this page?" leaves. The handler answers inside its callback, since the engine holds the page until it is answered, so the engine's modal alert never opens. Measured: `[false,null,"alert-returned"]`, beforeunload left, and no loop of any other kind inside a pump. The option's recommendation said `prompt` is answered empty; null is what is built.
  - **The context menu** is the engine's own item list, shown by `zebkit_view_context_menu_show`, which runs the system's menu loop until the menu closes. Inspect Element is not among the items, and is dropped. Measured: a main-queue block queued from the callback runs inside the pump's wait, where the menu's loop held the engine (four nested waits in the event-tracking mode); run from the pump's own timer, the loop starved the pump, since a timer is not fired again inside its own callback (a script run while the menu was open never answered); run from a one-shot timer of its own set after the pump returns (`ChromiumPump.afterPump`), the engine kept being pumped, a script run while the menu was open answered, and the main queue stayed responsive.
  - **New windows.** Every `target=_blank`, `window.open` and sign-in popup arrives as a view, and is put in a pane of its own beside the page's. That pane takes focus only when the page's own pane had it and the tab is on screen (decided, not in the option): otherwise a session driving a page over CDP could take what the user types. Only a `window.open` popup is linked to its opener (`window.opener` and `postMessage` worked); a `target=_blank` window has no opener, as in Chrome. The view is attached to a view of ours inside the callback, because its own window is on screen from its creation until something attaches it (seen: visible at the callback, hidden once attached); the pane is made around it a turn later, and a popup the site closes closes its pane. A tab waiting for Take over can't take a pane, and a tab with no room (the page's pane would fall under the minimum width) can't either: the pane says so and the window closes.
  - **Downloads.** The page's handler makes a free name in Downloads (an empty file made exclusively, which the engine replaces: `report.bin`, `report (1).bin`) on a background thread, then answers with that path from the main one; the engine holds the download 30 s for the answer, so a macOS prompt for the Downloads folder never blocks a pump. The header doesn't say the request outlives that deadline (it does for permissions, navigations and authentication), so past `deadlineUnixMs` less 2 s nothing is answered: the file is removed and the pane says the wait timed out; a page that closed itself meanwhile is said the same way (**unverified:** the harness never saved to `~/Downloads`, so the prompt's behaviour, and a refusal cancelling the download with that said in the pane, are from the header and code alone). The engine does not set macOS's quarantine attribute, and one set on the reserved file is lost when the engine replaces it, so Varnick sets it (`com.apple.quarantine`, through the resource key) at once, inside the pump, when the download's report says it is complete; the note "Saved X in Downloads." is queued, and goes to the pane of the page that opened a popup as well, since the popup's pane may be gone. A pane closed meanwhile cancels what is in flight (decided, not in the option). A page that closes itself leaves its downloads running with no more reports, so each of its files is marked when it first has contents (the engine keeps it empty and writes beside it until the end), checked every 2 s for 10 minutes and removed if still empty then. Empty reserved files are also removed at quit; a restart by SIGTERM skips quit and leaves those of downloads under way. A navigation to a file also reports a failed load to the page's load callback, which the failure card of step 6 must not take for a failure.
  - **A view freed by the engine** (its close callback is the last use of it) is forgotten at once, inside the callback; only the pane's own work is queued.
  - **Untested, to check by hand:** the pane's focus and layout after a popup opens, a context menu's items (Back, Forward, Reload, Copy, Open Link in New Window, Save Image As) run from the menu, a Japanese input method in a field, and "Saved X in Downloads." readable over the Chromium page on both the popup's pane and the opener's (whether a SwiftUI overlay draws above the page is unverified). **Unverified, from the headers alone:** `<input type=file>` and File System Access pickers, for which the engine shows its own system dialog when no function is set (`zebkit_view_on_file_chooser` is the hook; not built in this step), a sheet or modal inside a pump being unknown; a `<select>`'s native popup possibly tracking inside a pump; CDP's `Target.createTarget` making an engine window outside the panel; a page looping `alert()`, which each call answers at once and so keeps the pump busy; and a pane closed while its context menu is open inside `zebkit_view_context_menu_show`.
- **CDP is served on demand** (amended 2026-11-13, option 02 of `two-browser-panes`, step 2; it was served from the engine's start until Varnick quit, with no authentication, so any local process could list and drive every pane, logged in wherever the user had logged in). The engine starts with no CDP (`zebkit_cdp_listen` is not called at start). The one path that serves it is `ChromiumEngine.serveCDP`, called by a session's `pane_read` of a Chromium pane that has a page (a pane with no page, an engine not running and a failed engine keep their answers and start nothing). Every such read starts the idle time over: 30 minutes by default, and CDP stops (`zebkit_cdp_stop`, one log line with the port, one when it started) at the deadline, when the last Chromium page closes, and at quit. `pane_open` serves nothing: the page doesn't exist when it answers, and the reply tells the session to read again. The user opening a page by hand serves nothing either: only a session's read does.
  - **Rules in the code.** Listen is never called inside a pump: a read that finds a pump under way (it is a main-actor job and can run in the pump's wait) listens after it, through `ChromiumPump.afterPump`, and answers then; listen was only measured outside a pump, and so are the stops. The deadline is wall-clock time, checked when the timer fires and at the workspace's wake, since a timer's clock may stand still while the Mac sleeps. Pages are counted by `ChromiumPage.holdView`, the one place a page's view is set (not a `didSet`, which Swift skips inside an initializer, so a popup adopted by `init(adopting:)` would never be counted while its close is), through every path: made, adopted, closed, closed by the site; a count that would go below 0 is logged and ignored. One timer and a count, no rule of its own to check by harness.
  - **The hidden switch** (the one place it is documented). `chromiumCDPIdleSeconds` in Varnick's defaults, written by the user for a hand check and never by Varnick, sets the idle time in seconds, clamped to 1 s to 30 minutes, and the check ends by deleting it. It is a defaults key because the `VARNICK_*` switches (`VARNICK_LOG_RESIZE`) reach a Varnick only where `scripts/restart.sh` copies them into the launchd job's plist, which it does for the database path and `VARNICK_LOG_RESIZE` alone; a new one would change that script. Every text that states the time (`pane_read`'s, the tool descriptions, the reply of `pane_open`) says the real value (`cdpIdleText`).
  - **The port at a restart.** CDP asks for the port it last served, so an address a session saved works again, and takes one the system chooses when that is taken. Each serve has a new browser GUID; the page's target id stays the same, so a client reconnects to the page's own address.
  - **Why this and not the option's other ways.** The option's own rule was "if C doesn't show the panes' pages, B"; a spike on 2026-11-13 (its notes are kept locally) showed that way C, zebkit's Playwright-style token endpoint, cannot reach a view the host made, only views and contexts of its own, so B was built, with James shown this and saying to keep going. Verified in the spike on the real engine: CDP isn't served until `zebkit_cdp_listen` is called; `zebkit_cdp_stop` closes the port, and a connected client gets `Inspector.detached` and a close with code 1006; listening again works repeatedly in one engine run, on a new system-chosen port or on the earlier one when asked for by number; the page's target id stayed the same across restarts. zebkit.h has no hook that tells the host when a client connects or disconnects (checked in 0.4.0's headers), so Varnick can't tell a driving session from an idle one: **a session that is still driving when the idle time ends is cut off, and keeps CDP only by reading again**, which `pane_read`'s text and the tool descriptions say.
  - **What this does not solve.** While it is served there is still no authentication, and listen is TCP only (a numeric IP, no Unix socket), so any local process can use it then; the window is the session's reading plus the idle time instead of Varnick's whole run. A possible end is way D, `zebkit_automation_call` inside Varnick behind tools that know the caller, with no port; it is not decided or built; `zebkit_automation_call` is used only for the copy of WebKit's logins (below), with no tool surface (option 02's CDP section).
- **Which engine a page gets** (amended 2026-11-13, option 02 of `two-browser-panes`, step 5; the Chromium tile is gone). A page pane is drawn by Chromium when the framework is beside Varnick (or, from step 8, inside it), Settings › Experimental › Pages in Chromium is on (`pagesInChromium`, on when never set) and the engine hasn't failed to start in this process; otherwise by WebKit. That is `PageEngine.choose`, a pure function of those facts and of what step 6 hasn't moved yet (Packages/VarnickPeer, every case held by `make check-page`), asked by `ClaudeSession` when its pane is made: a pane keeps its engine until it closes, so the switch changes only panes made after it, and a Chromium page already open stays (the engine with it) until Varnick restarts. **The engine is chosen again at each restore**, from the address the pane was left at, so a page's engine can change across a restart when its address crosses between local and public (a Chromium page left at a localhost sign-in callback comes back in WebKit).
  - **What stays in WebKit until step 6** (the one list; the Settings row, the guide, the glossary and where-it-breaks point here): a custom app's page (Scratch is one), a page of another machine's tab (`record.host`, with `proxy`, `proxyNote`, `staysOnHost` and `applyHostProxy` as they were), and a page at a local address, since the load-failure card (`showLoadError`: the waiting text and the retries) is WebKit's alone. They are the first three cases of `PageEngine.choose`, and step 6 removes them there and builds the card for Chromium. This is a deliberate, temporary departure from step 5 as the option states it (`pane_open`'s `page` opens in Chromium where it can run), decided with the user's lead of the work: until step 6 a session's `pane_open page` at a local address gets a WebKit page it can't drive, while a Chromium pane the user types the same address into has no waiting card (Chromium's own error page shows, and Reload tries again).
  - **Saved state.** No new field. A record's `chromium` mark (from the Chromium tile and old `pane_open`) is decoded and means nothing: the pane gets an engine by the rule, `ClaudeSession` clears the mark and it is never saved again. A build before this one reading a file saved after shows those pages in WebKit. The switch is one UserDefaults key.
  - **The engine can't run.** The facts are read when the pane is made, so a pane made before a start that fails (it asked for the engine and waited) has no page: it says so and that Reload opens it in WebKit, which it does for good (`ClaudeSession.fallBackToWebKit`). A pane made after the failure is WebKit from the start. A framework that is missing is the same as a failed start.
  - **The address follows the page's own history changes.** zebkit's load events report new documents only, and its navigation events leave "renderer-only same-document changes" out (hooks.h), so a single-page site's route change reaches Varnick through neither. `ChromiumPage.checkAddress` reads `zebkit_view_get_url` once a second while the page exists (skipped inside a pump, whose wait runs timers) and acts on a change only to an http or https address, so a load under way or the engine's error page never replaces the address. **Untried:** `zebkit_automation_on_event` (automation.h) delivers "Frame.navigated" per view, which may report same-document navigations; if it does, a handler on it replaces the poll. **Unverified:** that the engine's URL follows `history.pushState` (Chromium's own does, from memory); the hand check is a single-page site's route change.
  - **Fullscreen is denied** (`zebkit_view_set_fullscreen_policy`, set where a page's hooks are connected, popups included; hooks.h allows it by default). WebKit's element fullscreen was off, so a video's fullscreen button did nothing; what Chromium's would do inside the panel is unknown and can't be tried without a run. Decided to match today; to be revisited after a hand check.
  - **Light and dark** follow the system through the startup setting `appearance.follow`, which the Chromium tile never set (its pages were always light).
  - **`pane_open`.** `page` is the kind that opens a Browser pane, in Chromium where it can run, and so is `find_open` beside. `chromium` is no kind of its own; a session started before this change that still sends it gets a `page` (`OpenedPaneKind.init(named:)`), and the schema no longer lists it. Opening a page in a tab another machine controls works as any page does (the tile and `chromium` refused it): the pane on this Mac is Chromium and has a page only while this Mac shows it. `pane_read` of a page in WebKit says it can't be driven and why (`ClaudeSession.webKitNote`).
  - **Not built here, left to later steps:** apps, Scratch, proxied pages and the failure card (6), Resources' row and the screen reader (7), the framework in `Varnick.app` (8), deleting WebKit's page path (9).
- **WebKit's logins are carried into Chromium, once and confirmed** (amended 2026-11-13, option 02 of `two-browser-panes`, step 4; the option's recommendation, which James was shown as the default and said to keep going on). At an engine start on a Mac where the copy isn't done, every cookie of WebKit's default store, HttpOnly ones included, is given to Chromium's profile (`ChromiumLogins`; the rules are `CookieCarry` in `Packages/VarnickPeer`, `make check-cookies`). Local storage and IndexedDB don't move, so a site that keeps its login there asks again. WebKit's store is left as it is, on disk. Copying the user's Chrome logins is not part of this.
  - **Route: in-process, no port.** `zebkit_automation_call(NULL, "BrowserContext.cookies" | "BrowserContext.addCookies", ...)` runs Playwright's command inside the engine; CDP is not served for the copy, so the on-demand rule above is untouched and nothing listens. This is the first use of `zebkit_automation_call`, and it is used for this copy only: way D (tools of Varnick's own that drive pages through it) is still not decided or built. What `automation.h` says: its text names a NULL view only for `Browser.newContext`, and says contexts a client makes are its own; it does not say which context a NULL view's `BrowserContext.*` command reaches. The only evidence is the spike of 2026-11-13 (notes kept locally; its output was read, nothing re-run): `BrowserContext.pages` with a NULL view answered with the host's own view's page (`["p1"]`), so a NULL view reaches the context host views live in, which `API.md` says is the profile's (`zebkit_context_new()` contexts have cookies "of their own", and in-memory contexts get no disk cookies). Its `BrowserContext.cookies` answer, `[]`, proves nothing: that profile held no cookies. `addCookies` was never run. That the copy lands in the persistent profile and survives a restart is inferred, not seen, which is why the copy is confirmed at a later start (below). The CDP fallback, if the hand check shows the copy doesn't persist: `ChromiumEngine.serveCDP` for the moment of the copy, `Storage.setCookies` on the browser target with the same entries (the shape the Chrome import prototype used successfully on 2026-11-11), then `stopCDP` at once; it is not built.
  - **Mapping** (`CookieCarry.entry`): name, value, path, secure and HttpOnly as WebKit has them; the domain lowercased, with its leading dot kept (a leading dot is a domain cookie, none is host-only, which is how Playwright's `domain` reads it, from its documentation and not seen here); Lax and Strict kept; an expiry as whole Unix seconds. A cookie with no policy gets `None` when it is Secure and none otherwise: `HTTPCookie` can't tell WebKit's `None` from unset and WebKit sends both cross-site, while Chromium reads unset as Lax and would stop sending the cookie with a cross-site top-level POST (a single sign-on's return); Chromium refuses `None` without Secure. A **session cookie stays a session cookie** (no expiry): it lives until Varnick quits, as in any browser, and is never made to last longer than it did, so it carries a login through that run only. Cookies that have expired and ones with no domain are left out.
  - **Which wins.** Chromium's cookies are read after WebKit's answer is in, and a WebKit cookie whose name, domain (as written, so a host-only and a domain cookie of one host are two) and path Chromium holds is never given, whatever its value or expiry: the copy is of an older store, and a page that loaded during the hold may have set a newer one. If what Chromium holds can't be read, nothing is copied.
  - **When.** The read of WebKit's store (`WKHTTPCookieStore.getAllCookies`, the main actor's completion; Apple's page doesn't say no web view is needed, its example uses the data store alone) starts when the engine starts and overlaps it. The engine's start then holds the pages: a page asking for the engine while the copy is under way waits (it shows "starting"), so none loads before the cookies are in, for at most 3 s (`ChromiumLogins` holds them). Past 3 s the pages load and the copy goes on, still leaving alone any cookie Chromium has by then; a page that loaded first doesn't send the copied cookies until its next request. The engine calls are made once the pump under way has returned (`ChromiumPump.afterPump`), and the engine's answers are handled in the callback. Unmeasured: how long WebKit's read takes on a Mac that has made no WebKit page in the process.
  - **Confirmed at a later start by a check cookie, never set on the run that copies.** Chromium's cookie store batches its writes to disk (at 512 pending or every 30 s, from its source; unconfirmed for zebkit 0.4.0, which commits them in order if it matches), a restart by SIGTERM skips `ChromiumEngine.shutdown`, and a call that landed outside the persistent context would never be noticed. So when the copy gives Chromium any persistent cookie it ends the batch with **Varnick's own check cookie** (`CookieCarry.sentinel`): name `varnick-carry-check`, host-only on `varnick-carry.invalid` (a reserved name that can't be a real site), path `/`, not Secure, no SameSite, 180 days (inside Chromium's cap). It is written last, so finding it at the next start means everything before it reached the profile, whatever the user has done to their own cookies since. A copy that carried only session cookies, or nothing, has no check cookie and is done at once, since nothing could be lost. A record is kept in a file in Chromium's profile folder (`varnick-logins-carry.json`, mode 0600): the number of starts that copied, how many cookies Chromium took and whether the check cookie is in. The next start reads Chromium's cookies: the check cookie there, the copy is **confirmed** and done, and the check cookie is deleted (given again with an expiry in the past, which deletes it; the read after says whether it went, and it expires in 180 days if not, which the log says); it absent, it is copied again, and **its absence is the only reason to retry**, so a user who logged out of the only carried site in Chromium before the confirming start is not logged back in. Whether the engine takes that cookie is unverified. So the read-back right after the copy checks it: when the check cookie isn't there, the record says so, the log line says "the carried cookies stand in for it" (counts only), and for that copy the record holds the persistent carried cookies as salted digests (the first 12 bytes of a SHA-256 over a salt kept in the file, name, domain and path, with each expiry), and the next start confirms when at least one of those still unexpired is there; it retries only when none is, which for a user who logged out of every carried site brings the logins back once more, up to the bound. With the check cookie accepted the record holds no digests. A Varnick cookie on a made-up host is therefore in the profile between the copy and its confirmation.
  - **The bound.** A copy is made at a start only while fewer than 3 copies have been made: the first three starts that find it unconfirmed. A copy made at the third start is judged at the fourth, which finds the check cookie missing and **gives up** (log line saying so, mark set, record deleted), so the copy runs at most 3 times and the last check is at the 4th start. The mark is set also when: nothing was left to give (WebKit's cookies all already in Chromium, or expired), or what Chromium took has no persistent cookie. It is never set on an **empty WebKit read**: nothing shows `getAllCookies` returns the persisted store before any web view exists in the process (unverified on macOS), and a false empty would lose every login. An empty read counts as a copy, so a Mac that truly has no WebKit cookies stops at its 3rd engine start (the 3rd read is the last). If the record can't be written the copy ends at once, with the check cookie removed (it would otherwise run at every start and bring back what the user removed). A read-back that fails right after a copy leaves no record and the copy is tried again at the next start.
  - **Failure.** The store or Chromium's cookies can't be read, or Chromium takes none of what it is given: nothing is marked, and the next start tries again (a read of Chromium's cookies that fails each start costs one call a start and copies nothing; one that took none counts toward the 3). One batch call gives every cookie; if it fails, each cookie is given alone, so one that Chromium refuses leaves out only itself (counted). The log has one line of counts a start; never a name, a value, a domain or a site, and the engine's error text is logged only for the read of Chromium's cookies, which names none.
  - **Unverified:** that `BrowserContext.*` with a NULL view works before any view exists (the spike called it after one was made; if not, every start logs that it couldn't read Chromium's cookies); that `addCookies` writes the persistent profile and survives a restart; that the engine accepts the check cookie, deletes it when given an expiry in the past, and that Chromium commits cookie writes in order; that a read with an empty `urls` returns every cookie once the jar has some; Chromium's reading of a dotless `domain` as host-only; that `getAllCookies` is complete before a WebKit page exists; whether macOS asks about the keychain when the cookies are first written after a rebuild.
- **Where the framework sits** (amended 2026-11-13, option 02 of `two-browser-panes`, step 8). Beside the binary in a checkout: `make build` fetches the release, pinned by SHA-256 like zmx and Bun, into `.build/release`. In `Varnick.app/Contents/Frameworks` in the app: `make app` copies the one `make build` signed and signs the copy again (`ResourceFolder.Place.frameworks`, `ChromiumEngine.frameworkURL`; nowhere else is looked at). What zebkit 0.4.0 says, read from its package and source copy, not tried: the engine finds itself with `dladdr` on `zebkit_main` (`LibraryDirectory`), takes its helper at `Helpers/Zebkit Helper.app` in that framework version (`HelperPath`), and sets Chromium's framework bundle path to that folder (`SetUpBundle`); the helper is a 33 KB stub whose one rpath, `@executable_path/../../../../../../..`, goes up to the folder that holds the framework the helper is in and loads `@rpath/Zebkit.framework/Versions/A/Zebkit`. The host's own place enters nowhere, and there are no settings for a framework or helper path (API.md: "every child process is `zebkit-helper` (`Zebkit Helper.app`), beside the library, whatever the application's executable is"). **Unexplained:** the prototype of 2026-11-11 recorded that the helpers crash at start when the host executable is anywhere but beside the framework, with no cause kept; the source says otherwise, no agent may run the engine, and so whether the bundle's layout starts the helpers is the hand check of step 8, not a fact. If it crashes there, the way out is a zebkit release or a patch, not a layout trick: Contents/Frameworks is where Apple's signing rules put nested frameworks, and a framework in Contents/MacOS next to the executable is not signable as nested code (inferred from those rules, not tried).
- **Signed with Varnick's identity, everything with the hardened runtime** (amended 2026-11-13, step 8). The hardened runtime's library validation refuses the package's ad-hoc framework, so the build signs the helper and then the framework with the same identity; Varnick, the helper and the framework then share a team, which library validation accepts (checked locally on the signed bundle, not run). Notarization wants the hardened runtime on every executable, so both carry it, signed inside out and never `--deep` (it would put the helper's entitlements on the library). The helper, which runs the renderers, carries `Zebkit.entitlements`: `com.apple.security.cs.allow-jit` only, for V8's JIT memory, which is what Chrome's own renderer helper asks for (from memory, not checked here); zebkit ships one helper for every process role (renderer, GPU, network), so the one file covers all of them, and none of Chrome's other entitlements (unsigned executable memory; no library validation, which only its plugin helper has) is asked for until a failure shows one is needed. Varnick's own entitlements are unchanged: the engine's browser process is Varnick, and a checkout's Varnick has run it under the hardened runtime with the microphone entitlement alone. **`make build` signs the same way** (the identity and no secure timestamp, as for zmx), so a checkout's restart runs the hardened helper and is the test of the entitlement before any release; before this amendment the helper had no hardened runtime, and the framework in place is re-signed once, by clone and rename, at the first build after. `make app` signs the copy in the bundle with the secure timestamp. **Verified locally on the signed bundle:** `codesign --verify --deep --strict`, the flags and entitlements of every part, one team across them. **Not verified:** that Apple's notary service accepts it (nothing has been submitted), and that a helper under the hardened runtime with this one entitlement runs a page.

## Considered Options

- **Linking the framework:** passed over. Varnick would fail to start without it, and every launch would map it.
- **Off-screen views drawn by Varnick:** passed over for now. `attach_native` puts the page in the pane as a subview, with the system's own input, and needs no event forwarding.

## Consequences

- **A session can read and act in every logged-in Chromium page.** One endpoint serves every page in Chromium as a target, so a read of any one lets the session list and drive them all, in every tab and project, until the idle time ends ([privacy and security](../privacy-and-security.md#pages-in-chromium) says it to the user). It goes to Anthropic with the session, as a terminal's screen does. `docs/privacy-and-security.md` and where-it-breaks ("What the tools do not promise") say so.
- **CDP has no password.** Any process on this Mac can drive the profile while CDP is served, which is from a session's read until the idle time after the last one (above), as with Chrome's `--remote-debugging-port`.
- **Accepted gaps, until the later steps of option 02:** (the framework is in `Varnick.app` as of step 8, signed for notarization, and not yet run or notarized there; see "Where the framework sits") apps, Scratch, proxied pages and local addresses are WebKit's; the helpers aren't counted in Resources. (Popups, downloads, dialogs and the context menu are answered by Varnick as of 2026-11-13, and the switch and the engine rule are step 5's.)

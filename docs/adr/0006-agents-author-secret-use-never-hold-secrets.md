# The agent authors code that uses secrets; it never holds one

A Secrets Store the agent can read is just a config file with extra steps. The agent instead writes code that *names* a secret, and the host resolves that name to a value when it runs the code — so `process.env.STRIPE_KEY` appears in the Userspace the agent builds while no secret value ever enters the sandbox.

## Consequences

- **Egress substitution was considered and rejected for local use.** Anthropic's Managed Agents give the sandbox an opaque placeholder and swap in the real value at the network boundary, which works because they own the egress proxy. Locally that means building and maintaining a proxy, and any client that validates credential format before making a request breaks on the placeholder.
- **The built application runs outside the sandbox, and that is what makes this work.** The agent is confined; the code it produces is not. Secrets are available to the running application and never to the process that wrote it.
- **Secrets and credentials are separate paths.** A credential authenticates the agent itself and is injected by Tauri's main process ([ADR-0003](./0003-containment-wraps-the-process-tree.md)); a secret is used by code the agent writes. Conflating them puts an agent credential where Userspace code can read it.
- **The binding is non-enumerable, which is what makes the claim structural rather than remembered.** Resolution defines each name on `process.env` as a non-enumerable accessor for the duration of one Userspace module's evaluation. `process.env.STRIPE_KEY` reads it, because reading it is naming it; `Object.keys`, spread, `JSON.stringify`, `util.inspect` and a child process handed the environment all come up empty. That last one is the load-bearing case: `agentEnvironment` builds what Claude Code is spawned with by walking `Object.entries`, so it cannot see a resolved secret rather than having to remember to skip one. This is the same move as `Secret` in `src-tauri/src/credential.rs`, where "the value cannot cross" is a property of the type because there is no `Serialize` to cross with.
- **A failure raised while the value is in hand is redacted where the sentence is built.** A client that rejects a request quotes what it rejected, and the loader turns that into the failed Surface's message, which the transcript then carries. So `importSurface` redacts through the resolution rather than trusting every caller downstream to.
- **The names ride the control channel, not the spawn environment, because the list changes while the agent runs.** The agent can only name a secret it knows exists, and the names are in a keychain under `$HOME` that the Sandbox denies it. Two carriers were available. The spawn environment is simpler and the credential already travels that way, and — names not being secret — it would have weakened nothing; it is rejected because it can only ever say what was true at launch, and `bun run secret add` runs in another process, minutes later. The Agent SDK settles it rather than leaving it a preference: `appendSystemPrompt` belongs to the `initialize` control request and is fixed for the life of a session, so a system prompt fed from the environment could carry a snapshot and could never carry a list that changes. What can change per Turn is a `UserPromptSubmit` hook's `additionalContext`, so the agent host holds the last list it was told and composes the brief there, and `src-tauri/src/bridge.rs` asks the runtime for the names immediately before every Turn — the same answer ticket 06 reached for the mirror, which re-reads the store before every save rather than trusting the snapshot taken at start-up. The cost is one round-trip to the runtime per Turn, and it is deliberately unchecked: an unnameable secret makes a Turn a poorer answer, never a failed one.
- **Only names cross, and that is a property of the parse rather than a rule the callers keep.** `read-secret-names` is answered from `SecretsStore.names()`, which cannot yield a value — `secretValues()` is the single member that does and nothing on this path calls it. `control_line_for` in `src-tauri/src/agent.rs` and `parseControlRequest` in `packages/harness/src/turn.ts` both rebuild the request out of `kind` and `names`, so a line carrying values alongside is a line whose values were never read. Neither `read-secret-names` nor `describe-secrets` is on `route_of`, so the renderer can neither ask what a developer's keys are called nor tell the confined agent that a secret exists which does not.
- **Resolution needs a host process, so a Surface rendered in the window cannot use a secret.** The renderer is a webview with no `process.env`, and the only route for a value to reach it is the bridge, across which no secret value travels in either direction — a dev server bound past localhost would otherwise hand out every key the developer owns. What follows is that the code *using* a secret and the Surface *showing* the result are not necessarily the same code, and varnick does not yet have a place to run the first. See ticket 12's Comments.

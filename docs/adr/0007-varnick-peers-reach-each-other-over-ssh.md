# Varnicks on different Macs are peers over SSH, and the host's Varnick runs each session

A session runs on one Mac, its host, and stays there. Varnick on each Mac pairs with the Varnicks on the others as peers, and reaches them over SSH with the user's own keys. A peer's SSH command runs Varnick's own binary in a relay mode, through a link at a fixed path in the host's Application Support folder; the relay hands the request, one base64 JSON argument, to the running Varnick over a Unix socket only the user can open, and prints its reply. The host's own Varnick starts each session, from its own GUI login the way a local pane starts today, and keeps a pane for every session it runs. Which Mac is in control of a session, the one whose keyboard reaches it, is a zmx label (`varnick-control=<peer id>`), so it survives either Varnick restarting; another Mac takes control by relabelling, detaching the clients and attaching. We chose this over SSH straight to the host's zmx because Claude then starts the same way on every Mac, and because the user wants peers that know about each other, not SSH hosts. The problem and its options are in `docs/problems/sessions-tied-to-one-mac/`; this records option 01.

## Considered Options

- **SSH straight to the host's zmx (option 02)**: not chosen. It is smaller, with no socket in the app, and works while the host's Launchy is down, but claude would run from an SSH login that lacks a GUI session's Keychain login and environment (a session started over SSH showed "Claude API" rather than the subscription login). The host's Launchy would learn of its sessions late, so ADR 0004's launch sweep would need an exception, and the two Launchys would read each other's files. It is closer to a list of SSH hosts than to peers.
- **A control endpoint behind `tailscale serve` (option 03)**: not chosen. It pushes changes instead of polling and makes cheap calls, but it adds a second door beside SSH, which the user chose, with weaker authentication (anyone on the tailnet reaches the port, so Launchy would need a pairing secret of its own), it changes Tailscale's own persistent serve settings on each Mac, and it puts a listener with port clashes in Launchy.
- **A live view on the Mac not in control (option 04)**: not chosen for now. It builds on this option: a second zmx client that never sends keys. Its costs are the leader's size applying to the viewer, one stray byte taking control, twice the traffic and an ordered takeover. The frozen screen comes first, and nothing here prevents adding it. The live screen took it up in ADR 0008, with a reader that never sends the socket input, Init or a size.

## Consequences

- No listening port (amended by ADR 0011's one door for the user's own devices, and by [ADR 0035](0035-remote-web-and-app-panes-go-through-a-port-proxy-in-each-hosts-phone-page-server.md)'s port proxy). SSH is the only way in from another Mac, and the socket is owner-only on the Mac itself, like the user's existing browser terminal, where Tailscale is the only door. A Mac that isn't in the peer list is never contacted, except by Find Macs and Add, which the user starts. The Phone page is a second door, for the user's own devices: see ADR 0011.
- A second runtime role for Varnick's binary: `Varnick --peer <base64 request>`, run before the app starts like `--search` and `--rerank-eval`, and a socket in the running app. Both Macs must agree on a request format; every request and reply carries a protocol version, and a different version answers with an error that the peer's row shows and that blocks every other request to it.
- Varnick's calls over SSH all go through one runner: no prompts (`BatchMode`), a host key accepted on first contact and refused if it changes, the user's `SSH_AUTH_SOCK`, and one connection per peer kept open by a background `ssh` master with its control socket under Application Support. The runner never runs on the main actor and never waits for a process on a run loop. Without the shared connection every call is slower and nothing else changes.
- The host keeps a pane for every session it runs, so "kill the zmx sessions no pane owns" still holds on every Mac and ADR 0004 stands as written, with one exception: the sweep spares a session whose `varnick-control` label names a paired peer, in case its pane here was closed while that Mac still types into it. Closing the card on the host asks first and then ends the session, so the pane isn't lost by accident. A session started from a peer shows on its host as a background tab.
- The host's Varnick must be running to start a session there. Taking over, attaching and reading status work through the relay's fallback to saved state and zmx while it restarts, and an attached session doesn't depend on it at all.
- A peer must have Keep sessions running on (ADR 0004) to host sessions, since a peer attaches through zmx.
- A peer's prompts are copied to the other Mac for Recent and search, between paired Macs only, and never reach a reranker. This changed the rule in `docs/agents/where-it-breaks.md` (Search store) that a session's prompts stay on this Mac, which now says they stay on the paired Macs.
- Pairing is mutual but removal isn't: a hello carries how to reach the sender, so the receiving Varnick lists it back, marked as added by it; removing a peer on one Mac leaves the other Mac's list alone. Only the hello that Add sends asks the receiver to pair, so nothing that runs by itself brings back a removed Mac. A Mac that finds itself removed from a peer's list shows that on the peer's row and doesn't ask again.
- Every request but `hello` names the Mac asking and is answered only to a Mac the receiver lists (since protocol version 6): they reveal or change what runs there, or hold the user's prompts. A hello is open so Macs can pair. The requests and what each does are in the option and in `docs/agents/where-it-breaks.md`. ADR 0013 adds two requests a listed Mac may ask, `upgrade` and `restart`, which are read before the version check.
- A session's conversation follows /clear and /resume on the host, which the Mac in control learns by polling `status`. A session that ended is never started again by itself: the host restarts only a pane it restored, and resuming one on purpose (Recent, search) is a separate request. The rules are in `docs/agents/where-it-breaks.md` (Peers).
- Closing a pane in control ends the session only if its origin names the Mac closing it, and otherwise releases it to the host, which keeps running it (protocol version 7). The origin is a zmx label written as the session is created for a peer, and a saved field on the host's record; the decision is the host's, which knows it. The mechanics are in `docs/agents/where-it-breaks.md` (Peers). Opening a peer's open session from the session list or from Recent or search shows its frozen screen with Take over rather than taking control, so nothing moves control but the user's Take over (or starting or resuming a session there).
- A host with no app amends "the host's Varnick runs each session": see ADR 0009, where a headless host's relay starts them itself.

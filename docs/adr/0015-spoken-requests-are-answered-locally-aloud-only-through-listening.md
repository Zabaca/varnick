# Spoken requests are answered locally, aloud only, through Listening

While Listening is on, a mic phrase that starts "Hey Varnick" is a spoken request. Varnick's own three steps answer it: Text generation picks the source and the search words, Varnick runs the panel's ranking apart from the panel, and Text generation writes a one- or two-sentence answer that Varnick speaks in the Voice setting (the system voice unless picked otherwise). The wake phrase is matched on the final text of the mic transcript Listening already produces, so nothing listens while Listening is off. The answer is only heard: the panel doesn't come forward, nothing is selected, nothing opens or starts. Text generation runs wherever Settings › Models says (ADR 0012, ADR 0014), so the request and the rows it reads stay on this Mac or go to the user's own server on the tailnet, and nowhere else. The problem and its options are in `docs/problems/listening-never-answers/`; this records option 01.

## Considered Options

- **A local model calling the sources as tools (option 02)**, **Claude calling them (option 03)** and **a local router that hands work to a Claude session (option 04)**: not built. A fixed three-step flow keeps a 2 B model on rails, needs no tool-call format, and sends nothing to a cloud model, which no Launchy feature does today. They stay proposed.
- **A wake listener of its own (option 05)**: not built. It would keep the mic open without Listening. It is the fallback if wake accuracy on the transcript is poor (a hand check).
- **Showing the answer in the panel and opening it with ↩**: left for later. The user chose speech only, so a misheard request costs a sound and a sentence and never disturbs the app in front.

## Consequences

- **Varnick must never hear itself.** The system audio tap excludes Varnick's own process. Mic results whose audio began while Varnick spoke, plus a short tail, are neither transcribed nor checked for the wake phrase (`SpeechSpans`). The speech is rendered by the system synthesizer (amended by ADR 0033: or streamed from ElevenLabs) and played by Varnick's own audio engine, so it always comes from this process; the span is opened before the first sound and closed after the last (amended by ADR 0036: each line has a span of its own, and none is open between lines, while Varnick waits for the writer or the web). Anything that moves the speech out of the process breaks the tap's exclusion, and a long answer, a slow device or a late final all depend on the span.
- **The panel's ranking is shared.** A spoken request calls the panel's keyword and meaning passes and the same fusion, and sets nothing the panel shows. (Amended by ADR 0017: `RelevanceSearch` holds them, and the relevance filter now runs too.)
- **Answers only from what a row holds** (title, site or folder, date, description or prompts), never a page's text or Claude's replies, and never the address.
- **Waking is unmeasured.** The match tolerates the mishearings of "Launchy" that start "launch", "lunch" or "lanch" and misses the rest, and the mic also hears speakers. Latency is estimated at 2.5 to 3.5 s warm. Both are hand checks.
- Text generation gains a second consumer that the user waits on, so it uses the interactive rule of `ModelServerState.place` (a server not known to have failed, else this Mac's model) where the background rule was the one titles used (titles are gone, ADR 0012). With a server chosen, the request and the rows' text go to it, as session prompts do for Search embeddings.
- The answer is written to the transcript as a `[varnick]` line (transcripts written before the rename keep `[launchy]`). This was a default, not the user's choice, and is one call to remove.
- Amended by ADR 0016: the decide step asks TypeSafe's Jev when the relevance filter is on TypeSafe with a key saved, so the request text can leave this Mac. The rows, the answer and the other steps stay as written here.
- Amended by ADR 0017: the relevance filter runs on a spoken request wherever Settings › Search says, through `RelevanceSearch` (which replaces `searchApart`), so with the filter on TypeSafe the search words and the first 20 pages' title, site and description go to TypeSafe. The answer names up to three results when the request asks for several.
- Amended by ADR 0019: with Point at the screen on, a spoken request about something on the screen is also answered with an **Arrow** drawn at it. Nothing is opened, clicked or focused, as before.
- Amended by ADR 0033: with an ElevenLabs voice chosen and a key saved, the speech is streamed from ElevenLabs and played by the same engine, so the sound still comes from this process and the span still covers it; the installed voice is the fallback and speaks everything while no ElevenLabs voice is chosen. The answer's text then leaves this Mac.
- Amended by ADR 0029: with Text generation on Claude Code (the default for a new install), the request and the rows it reads go to Anthropic under the user's own account to write the answer. "On this Mac or … the user's own server … and nowhere else" now holds for the other two choices only.
- Amended by ADR 0036: a spoken request searches all three sources together and is answered from the rows Jev keeps, or, with Answer from the web on, from the web through the user's own Claude Code. "Answered locally" holds only for what the rows can answer; the clock is answered from this Mac's clock.
- Amended by ADR 0042: With Voice session on (Settings › Experimental), the voice session answers a spoken request in place of Varnick's own steps. It is still only spoken, still only through Listening, and still opens nothing on its own.

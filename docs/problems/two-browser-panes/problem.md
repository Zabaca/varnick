---
title: Two browsers, and the one a session can drive is a prototype
description: Varnick shows web pages in two pane kinds. The Browser pane (WebKit) is where every page, custom app, Scratch page and page proxied from another machine opens, and a session can't read or drive it. The Chromium pane can be driven over CDP, but it sits beside the Browser pane as a prototype with a tile of its own. The first one needs a restart, it isn't in the installed app, it has no off switch, and its CDP port is open to any process on the Mac.
impact: The user picks between two browsers for every page, and the one sessions can act in is the one fewer pages use. Every page behaviour (titles, failures, retries, popups, dialogs) has to be built twice or is missing from one of them. A session asked to act in the page the user sees can do it only in a Chromium pane the user opened by its own tile, after a restart, from a checkout build. If page panes simply moved to Chromium as it stands, the user's real logins would sit behind a CDP port that any local process can use.
severity: mid
evidence: James's decision of 2026-11-12, "make this the browser now vs having browser and chromium", covering pages proxied from another host, Scratch and custom apps; rendered Markdown in a file pane stays on WebKit. ADR 0048 (the Chromium pane, its engine, pump and CDP endpoint). The prototype's follow-ups, kept locally with the chromium-pane scratch notes (no switch, no hand check of keys, mouse, tab hiding, overlays, focus or restore; popups, downloads, the context menu and alert() untested; the framework not in Varnick.app). A standalone harness the user ran on 2026-11-12 started the engine from the application's sendEvent with no restart, while a start from a main-queue block crashed; not yet tried inside Varnick, nor while a menu, sheet or drag runs its own loop. The framework is 143 MB on disk; an idle engine and its helpers cost about 200 MB (ADR 0048).
status: open
---

A pane whose saved record has an address is a web pane. Today it gets a WebKit view unless the record is marked Chromium, which only the split picker's Chromium tile does. Custom apps, Scratch (a catalog custom app), `pane_open`'s `page`, `find_open` beside a session and a page of another machine's tab are all WebKit. The Chromium pane runs zebkit 0.4.0 (Chromium 157 as a library), one engine per process, started only at launch on a Mac that has opened one before, with CDP served on 127.0.0.1 from that start until quit.

The engine can't be started inside a run of the main run loop: it traps (ADR 0048). That is why the first Chromium pane on a Mac asks for a restart. It can't be stopped and started again in one process either, so once any Chromium page has shown, its 200 MB stays until Varnick quits.

## What the Browser pane does today, and what zebkit 0.4.0 has for it

Read from the code and from the 0.4.0 package's headers (`zebkit.h`, `hooks.h`, `page.h`, `automation.h`, `window.h`) on 2026-11-12. "Inferred" and "unverified" mark what was not run or read.

| What | The Browser pane today (WebKit) | zebkit 0.4.0 |
|---|---|---|
| The page itself | A web view per pane, no background before the first paint, Inspect Element on; WebKit's default persistent store, shared by every page and app pane | A view made at the pane's size and attached as a subview of the pane's own view (the prototype does this); one profile in Varnick's support folder for every pane |
| Title | Observed, and it names the tab | `view_on_title` (the prototype uses it) |
| Address | Observed, same-document changes (history push, `#`) included; saved, and shown in the address bar | `view_on_load`'s committed event, for new documents only. For same-document changes nothing in the C API; Playwright's `Frame.navigated` through `automation_on_event`, or CDP's `Page.navigatedWithinDocument` (both unverified here) |
| A load that fails | A card in the page with the reason. A local address says it is waiting for the server and tries again every 1.5 s; a page through another Mac's port proxy gives the host's reason and tries every 3 s, and at once when the host lists the address again; a finished load clears the failure; a cancelled load is ignored | `view_on_load`'s failed event (failed or stopped, with the address, no reason); `view_on_navigation`'s failure phase carries `netError`. No call loads HTML: the card would be the pane's own view over the page |
| Reload | The address bar's button and ⌘R; the saved address when the view shows nothing or an error card; after an app's server exited, the app runs again | `view_reload`, `view_load_url` |
| Back and forward | No button or key; WebKit's own context menu (unverified that it offers them) | `view_go_back`, `view_go_forward`; no "can go back"; the engine's default context menu has Back and Forward |
| Find in the page | None | Nothing (script through `view_evaluate` at most) |
| Zoom | None: ⌘+ and ⌘− size terminals and files only | Nothing in the C API; pinch zoom may be Chromium's own (unverified) |
| Inspect Element | Right-click › Inspect Element, and Safari's Develop menu | Nothing in the C API. No DevTools front end was found in the framework's resources; Chrome's own DevTools can attach to a CDP target while CDP is served (unverified with zebkit) |
| Downloads | None: no download handling, so a link to a file fails the load, and at a local address the retry would repeat it (inferred) | `view_on_download`: asked per file, saved at a path the app gives, or cancelled, with progress. Without it files go silently into a folder inside the profile. Nothing says the engine marks a download with macOS's quarantine (unverified) |
| New windows (`target=_blank`, `window.open`) | Dropped: no UI delegate | `view_on_new_window` (the address only), or `view_on_window_open` (a view linked to its opener, as a "Sign in with Google" popup needs). With neither, zebkit opens a window of its own outside the panel, the prototype's accepted gap |
| `alert`, `confirm`, `prompt`, "Leave this page?" | Answered silently (no UI delegate): alert returns, confirm is false, prompt is null, the page is left (inferred from WebKit's defaults) | `view_on_dialog` and `view_dialog_respond`, or a per-view policy. By default the system's alert, whose modal loop would run inside a pump (untested, ADR 0048) |
| Context menu | WebKit's own, with Inspect Element | The engine's default menu (Back, Forward, Reload; Cut, Copy, Paste in a field; links; images), shown during a pump (untested); or `view_on_context_menu` with `view_context_menu_show` to show it from Varnick |
| Light and dark | Follows the system (WebKit's default, inferred) | Only with the startup setting `appearance.follow`; light otherwise |
| Focus | Focus makes the view first responder; a click on the page focuses its pane through the panel's mouse monitor, which knows web views by kind and leaves out a file pane's | `view_focus` (it makes the page first responder in the pane, ADR 0048); the monitor already knows the Chromium pane's view |
| Keys | The panel's key monitor takes Varnick's shortcuts before the page; ⌘C, ⌘V and ⌘A reach the page through the Edit menu | The same monitor. That Chromium's view answers the Edit menu and input methods is unverified (hand check owed by ADR 0048's follow-ups) |
| Tab switches, moves, overlays | The view moves between containers with its pane; the strip's lists, the split picker and the drag veil draw above it | The page moves with the pane's view (ADR 0048); overlays above it are a hand check owed |
| Resources | Each pane's page process, by WebKit's private process id; WebKit's shared processes by macOS's responsible process | No process id in the C API. The helpers are Varnick's children, so they count in Varnick's total under no pane (step 7 gives them one row, "Chromium's helpers") |
| Reading the screen (a spoken request with Varnick's own panel in front) | WebKit's page is in Varnick's accessibility tree | Whether Chromium's page tree shows inside Varnick is unverified (Chrome turns it on from its own application class, which Varnick doesn't use; from memory). The fallback for an empty page tree, which reads the page's area as text, is keyed on Chrome's bundle id, so Varnick's panel never gets it |
| `pane_read` | Kind and title only | The address, the CDP endpoint and the pane's target (the prototype) |
| `pane_open` `page`, `find_open` beside | A Browser pane | The same path; nothing new needed |
| Custom apps and Scratch | The app's localhost page, the waiting retry while its server starts, the server's output when it exits, Reload running it again | As failures and reload above |
| A page of another machine's tab | A card until the host lists a proxied address, then the page at that address (https, the peer's own tailnet name); a page that has loaded stays whatever the listing says next | Load and reload only: these rules are Varnick's |
| Restore | The address is saved and loads at the next start; an app reruns on its saved port | Saved records already carry a `chromium` mark; nothing new needed |
| Other machines | A Mac host lists its page panes as web with their address, and the viewer shows them in its own browser; the headless host has no browser and lists no page | Unchanged: each viewer's own engine |
| The phone | Frames the host's proxied address in the phone's own browser | Unaffected |
| Driving it | Nothing | `cdp_listen(address, port)`: only the bind address and the port are chosen, nothing limits who connects, `cdp_stop` ends it. `automation_listen` is the one endpoint with a credential (its address holds a random token, and a request with an Origin header is refused), and it speaks Playwright's protocol, not CDP. `automation_call` drives a page inside the engine, with no port |
| Starting | (none) | Only outside any run of the main run loop. Varnick starts it at launch today |
